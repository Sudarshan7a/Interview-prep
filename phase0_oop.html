Concept 01 of 08

Encapsulation

Hiding internal state. Controlling access. Preventing invalid data. The simplest pillar to understand but the most misexplained in interviews.
must knowAsked at every product company
01What it is + Why it exists

Encapsulation means: bundle data (fields) and the methods that operate on that data together inside a class, and restrict direct access to the data from outside.

Without encapsulation, any code anywhere in your program can modify your object's state directly. This causes bugs that are nearly impossible to trace. Imagine a bank account object where anyone can do account.balance = -999999 — no validation, no guard, just a direct assignment.

Encapsulation fixes this: make the field private, then expose controlled getters and setters that validate before modifying. Now the class is the only one who changes its own data.

Real analogy: An ATM machine. You can deposit and withdraw (controlled methods). You cannot reach inside and grab cash directly (private state). The machine validates every operation before allowing it.
02Java implementation
Java
JavaScript
Java — private fields + controlled access
public class BankAccount {
    // private = ONLY this class can access these fields
    // External code cannot do: account.balance = -9999
    private double balance;
    private String owner;
    private static int transactionCount = 0;

    // Constructor — the only way to create an account
    public BankAccount(String owner, double initialBalance) {
        if (initialBalance < 0)
            throw new IllegalArgumentException("Initial balance cannot be negative");
        this.owner = owner;
        this.balance = initialBalance;
    }

    // Getter — read-only access. No setter for balance.
    // Why no setter? Because balance MUST change through validated operations only.
    public double getBalance() { return balance; }
    public String getOwner()  { return owner; }

    // Controlled mutation — validates BEFORE changing state
    public void deposit(double amount) {
        if (amount <= 0)
            throw new IllegalArgumentException("Deposit amount must be positive");
        balance += amount;
        transactionCount++;
    }

    public void withdraw(double amount) {
        if (amount <= 0)
            throw new IllegalArgumentException("Withdrawal amount must be positive");
        if (amount > balance)
            throw new IllegalStateException("Insufficient funds");
        balance -= amount;
        transactionCount++;
    }
}

// Usage — external code HAS to go through the methods
BankAccount acc = new BankAccount("Ravi", 1000.0);
acc.deposit(500);    // ✓ valid
acc.withdraw(200); // ✓ valid
// acc.balance = -9999;  → COMPILE ERROR: balance is private

    return {
        getBalance: () => balance,
        deposit:    (amt) => { balance += amt; },

            balance -= amt;

Interview Q&A — Encapsulation
What is encapsulation? Why do we need it? ▼
Strong answer (what interviewers want to hear) Encapsulation is the bundling of data and the methods that operate on that data within a single unit (class), and restricting direct access to the internal state. We need it to prevent invalid state — if any external code could directly modify an object's fields, you lose control over the object's validity. For example, in a banking system, allowing account.balance = -999 directly would break the business constraint that balances can't go negative. By making balance private and exposing only deposit() and withdraw(), the class guarantees that its state is always valid, no matter who uses it. Likely follow-up: "What access modifiers does Java have?" private (class only), default/package (same package), protected (same package + subclasses), public (everywhere). The most restrictive you can use while still working is best practice.
What's the difference between encapsulation and abstraction? ▼
Strong answer Encapsulation is the mechanism of hiding internal data — it's HOW you protect state using access modifiers. Abstraction is hiding complex implementation and exposing only relevant behavior — it's WHAT the object shows to the outside world. They work together: encapsulation implements abstraction. An ATM machine abstracts the complex cash dispensing process (you just press "withdraw") and encapsulates the internal mechanisms (you can't directly access the cash). In Java, encapsulation = private fields with getters/setters. Abstraction = interfaces and abstract classes that define WHAT operations exist without specifying HOW they work.
Can you have encapsulation in JavaScript? It doesn't have private keywords. ▼
Strong answer JavaScript now has native private fields using the # prefix (ES2022). class Person { #name; } — the #name field is truly private and throws a SyntaxError if accessed from outside. Before ES2022, closures were used: variables declared inside a factory function are private because they're in the function's scope, but the returned object only exposes the methods you choose to expose. The closure approach still works and is used in older codebases. TypeScript adds compile-time private and readonly keywords, though these become public at runtime in the JavaScript output.

Encapsulation — 60-second revision

  • Bundle data + methods in one class. Make data private. Expose only controlled methods.
  • Java: private fields + public getters/setters. Setter validates before assigning.
  • JS modern: # prefix for private fields. JS old: closure pattern.
  • Encapsulation = HOW you protect data. Abstraction = WHAT you expose. Not the same.
  • Why: prevents invalid state. Only the class itself can change its own data.
Concept 02 of 08

Abstraction

Hiding complexity. Exposing only what users need. The most practically important pillar — every interface and abstract class you've ever used is abstraction.
must knowAbstract class vs Interface is asked constantly
01What it is

Abstraction means showing only the essential features of an object and hiding the underlying complexity. Users of your class know WHAT it can do, not HOW it does it.

In Java, abstraction is achieved through two mechanisms: Abstract classes (partial abstraction — some implementation allowed) and Interfaces (full abstraction — pure contract, no implementation in Java 7 and earlier).

Real analogy: A TV remote. You press "Volume Up" — you don't know how the IR signal works, how the TV's audio processor interprets it, or how the speaker increases output. The remote's interface is abstracted. You deal with buttons, not circuits.
02Abstract class vs Interface — the most asked OOP question
Java
JavaScript
Java — Abstract class vs Interface
// ── ABSTRACT CLASS: partial abstraction ──
// Use when: IS-A relationship + shared implementation code
// Can have: constructors, instance variables, concrete + abstract methods
// Restriction: a class can EXTEND only ONE abstract class

abstract class PaymentProcessor {
    protected String currency = "INR";  // shared state for all processors
    protected double processingFee;

    public PaymentProcessor(double fee) {
        this.processingFee = fee;
    }

    // Abstract: MUST be implemented by subclass. No body.
    public abstract void processPayment(double amount);
    public abstract String getPaymentMethod();

    // Concrete: shared behavior — subclasses inherit this for free
    public void logTransaction(double amount) {
        System.out.println("Processing " + amount + " " + currency
            + " via " + getPaymentMethod());
    }

    public double calculateFee(double amount) {
        return amount * processingFee / 100;
    }
}

// ── INTERFACE: pure contract ──
// Use when: CAN-DO capability across UNRELATED classes
// In Java 7: no implementation. In Java 8+: default methods allowed
// A class can IMPLEMENT MULTIPLE interfaces (solves multiple inheritance)

interface Refundable {
    void refund(double amount);   // implicitly public abstract
    boolean isRefundable();

    // Java 8+: default method — optional to override
    default String getRefundPolicy() { return "Standard 7-day refund policy"; }
}

interface Auditable {
    void audit(String action);
}

// Class can extend ONE abstract class but implement MANY interfaces
class UPIProcessor extends PaymentProcessor
                    implements Refundable, Auditable {

    public UPIProcessor() { super(0.5); }  // 0.5% fee

    @Override
    public void processPayment(double amount) {
        logTransaction(amount);   // inherited from abstract class
        // UPI-specific logic: VPA validation, NPCI API call, etc.
    }

    @Override public String getPaymentMethod() { return "UPI"; }
    @Override public void   refund(double a)    { /* UPI refund */ }
    @Override public boolean  isRefundable()   { return true; }
    @Override public void   audit(String a)  { /* audit log */ }
}

04Why Java doesn't allow multiple class inheritance (Diamond Problem)
Diamond Problem
The diamond problem — why Java restricts to single inheritance
// HYPOTHETICAL — Java does NOT allow this
class A {
    void greet() { System.out.println("Hello from A"); }
}
class B extends A {
    void greet() { System.out.println("Hello from B"); }
}
class C extends A {
    void greet() { System.out.println("Hello from C"); }
}
// class D extends B, C {}  → WHICH greet() does D inherit? B's or C's?
// → This ambiguity is the diamond problem
// → Java prevents this by disallowing multiple class inheritance

// SOLUTION: Java allows implementing multiple INTERFACES
// If two interfaces have the same default method, you MUST override in the class
interface IA { default void greet() { System.out.println("IA"); } }
interface IB { default void greet() { System.out.println("IB"); } }

class MyClass implements IA, IB {
    @Override
    public void greet() {
        // Must explicitly choose or create new implementation
        IA.super.greet();  // Can call specific interface's default
    }
}
// Java forces you to resolve the ambiguity → diamond problem solved
Interview Q&A — Abstraction
When would you use an abstract class over an interface? ▼
Strong answer I'd use an abstract class when classes share common implementation code and have an IS-A relationship — for example, an Animal abstract class where eat() and sleep() are concrete (shared) and speak() is abstract (each animal speaks differently). I'd use an interface when I want to define a capability that unrelated classes might share — for example, both a Bird and an Airplane can implement a Flyable interface, even though they're completely unrelated in the class hierarchy. The key rule: abstract class for shared behavior and IS-A, interface for shared contract and CAN-DO. Follow-up: "Can an abstract class implement an interface?" Yes. An abstract class can implement an interface without implementing all its methods — the concrete subclass is responsible for implementing them. This is actually a common pattern.
Can you instantiate an abstract class? ▼
Strong answer No, you cannot directly instantiate an abstract class — new Animal() is a compile error. However, you CAN instantiate it via an anonymous class: Animal a = new Animal() { public void speak() { ... } } — this creates a nameless subclass inline that implements all abstract methods. This is commonly used in Java for event listeners and callbacks, especially in older Android code. The abstract class reference variable (Animal a) can hold a subclass instance, which is normal polymorphism.
What changed with interfaces in Java 8? Why? ▼
Strong answer Java 8 added default methods and static methods to interfaces. Before Java 8, interfaces were pure contracts — no implementation allowed. The problem: if you add a new method to an existing interface, ALL implementing classes break (they must implement the new method). Java 8's default methods solve this by providing a default implementation that existing classes inherit without breaking. The classic example is the Iterable interface — adding forEach() as a default method let all existing collections get it for free without every custom collection implementation needing to add it. Java 9 added private methods to interfaces, allowing default methods to share private helper logic.

Abstraction — 60-second revision

  • Hide complexity, show only what users need. Abstract class or Interface in Java.
  • Abstract class: has constructors, state, concrete + abstract methods. Single inheritance only.
  • Interface: pure contract. No state (only constants). Multiple implementation allowed.
  • Use abstract class for IS-A + shared code. Use interface for CAN-DO capabilities.
  • Diamond problem: two parents define same method → ambiguity. Java solves by disallowing multiple class inheritance. Interfaces solve it by forcing override.
  • Java 8 default methods: backward compatibility — add new methods without breaking existing implementations.

Child class reuses parent class code. The super keyword. Constructor chaining. Why Java has single inheritance. JS prototype chain under class syntax.
must knowsuper keyword and constructor chaining are tested
01What it is + Key rules

Inheritance allows a child class to inherit fields and methods from a parent class, enabling code reuse and modeling IS-A relationships.

Rules: Java uses extends for single inheritance only (one parent class). JavaScript uses class Child extends Parent which is syntactic sugar over the prototype chain. The super keyword refers to the parent — super() calls the parent constructor, super.method() calls a parent method.

Critical rule in both Java and JS: If a child class has a constructor, it MUST call super() before accessing this. In JavaScript, failing to call super() throws a ReferenceError. In Java, if you don't write a super() call, Java silently inserts super() (no-arg) — if parent has no no-arg constructor, it's a compile error.
Java
JavaScript
Java — extends, super, override, protected
class Employee {
    protected String name;    // protected = visible to subclasses
    protected double baseSalary;

    public Employee(String name, double salary) {
        this.name = name;
        this.baseSalary = salary;
    }

    public double calculatePay() {
        return baseSalary;
    }

    public String getInfo() {
        return name + " earns ₹" + calculatePay();
    }
}

class Manager extends Employee {
    private double bonus;
    private String[] reportees;

    public Manager(String name, double salary, double bonus) {
        super(name, salary);  // MUST be FIRST line — calls Employee constructor
        this.bonus = bonus;
    }

    // @Override tells Java (and humans) this replaces parent's method
    // Without @Override: still overrides but no compile-time safety check
    @Override
    public double calculatePay() {
        return super.calculatePay() + bonus;  // extend parent, don't replace
    }

    // New method not in Employee — adds to Manager's interface
    public void conductReview(Employee emp) {
        System.out.println(name + " reviewing " + emp.name);
    }
}

class Contractor extends Employee {
    private double hourlyRate;
    private int hoursWorked;

    public Contractor(String name, double hourlyRate, int hours) {
        super(name, 0);   // contractors have no fixed base salary
        this.hourlyRate = hourlyRate;
        this.hoursWorked = hours;
    }

    @Override
    public double calculatePay() {
        return hourlyRate * hoursWorked;  // completely different calculation
    }
}

// Runtime polymorphism — Java decides at runtime which calculatePay() to call
Employee[] team = {
    new Employee("Dev", 60000),
    new Manager("Priya", 80000, 20000),
    new Contractor("Ravi", 500, 160)

for (Employee e : team) {

Interview Q&A — Inheritance
What is constructor chaining? What happens when you don't call super()? ▼
Strong answer Constructor chaining means calling one constructor from another. In inheritance, when a child class constructor calls super(), it chains to the parent constructor. In Java: if you don't explicitly write super(), the compiler implicitly inserts a no-arg super() call at the start. If the parent has no no-arg constructor — compile error. In JavaScript: if a child class has a constructor, it MUST call super() before any reference to this — otherwise ReferenceError at runtime. The reason is that in JS, the parent constructor is responsible for creating the this object, so you need it to run first.
Can a constructor be inherited? Can it be overridden? ▼
Strong answer No, constructors are NOT inherited. This is a subtle but important point. A child class does not automatically get the parent's constructors — it must define its own. However, it can CALL the parent's constructor using super(). Constructors cannot be overridden because they're not instance methods — they belong to the class, not polymorphically resolved on instances. You can have a method with the same name as the parent's constructor in a child class, but it's just a regular method (no constructor semantics). The child class always needs its own constructor chain.
What is the difference between method overriding and method hiding? ▼
Strong answer Overriding: instance methods. When a child class provides a new implementation for an inherited instance method, and the reference is the parent type — the child's version is called at runtime (dynamic dispatch). Employee e = new Manager(); e.calculatePay(); calls Manager's version. Hiding: static methods. If a child class defines a static method with the same signature as the parent's static method, it hides (doesn't override) it. Employee.staticMethod() calls Employee's. Manager.staticMethod() calls Manager's. The reference type determines which static method is called — no dynamic dispatch. This distinction matters because @Override on a static method is a compile error.

Inheritance — 60-second revision

  • extends = single parent class. A class can extend only ONE class (diamond problem prevention).
  • super() = call parent constructor. MUST be first line. Java auto-inserts no-arg super() if missing.
  • super.method() = call parent's version of a method from within overriding child method.
  • protected = visible to same package + subclasses. private = NOT inherited (invisible to subclass).
  • JS: class syntax = sugar over prototype chain. Manager.prototype.__proto__ === Employee.prototype.
  • Constructors are NOT inherited. Cannot be overridden. Static methods are hidden, not overridden.
Concept 04 of 08

Polymorphism

One interface, many behaviors. Compile-time (overloading) and runtime (overriding). Dynamic dispatch. Why JS has no overloading.
must knowCompile-time vs runtime distinction is always asked
01Two types — understand both

Polymorphism = "many forms." Same method call can execute different code depending on context. There are two completely different mechanisms:

Compile-time polymorphism (Static/Early binding): Method overloading. Same method name, different parameter lists. Java resolves which version to call at compile time based on the argument types.

Runtime polymorphism (Dynamic dispatch/Late binding): Method overriding. Child class redefines parent's method. Java resolves which version to call at runtime based on the actual object type.

Java
JavaScript
Java — overloading + overriding + dynamic dispatch
// ── COMPILE-TIME POLYMORPHISM: Method Overloading ──
class Calculator {
    // Same name, different PARAMETER LISTS. Compiler picks the right one.
    public int    add(int a, int b)            { return a + b; }
    public double add(double a, double b)    { return a + b; }
    public int    add(int a, int b, int c)   { return a + b + c; }
    public String add(String a, String b)   { return a + b; }
    // Return type alone does NOT make overloading. Parameters must differ.
}
// Compiler resolves at COMPILE TIME based on argument types
Calculator calc = new Calculator();
calc.add(1, 2);         // → add(int, int)
calc.add(1.0, 2.0);   // → add(double, double)
calc.add("Hi", "!"); // → add(String, String)

// ── RUNTIME POLYMORPHISM: Method Overriding + Dynamic Dispatch ──
class Shape {
    public double area()        { return 0; }
    public String describe()   { return "Shape with area: " + area(); }
}

class Circle extends Shape {
    private double radius;
    Circle(double r) { this.radius = r; }
    @Override
    public double area() { return Math.PI * radius * radius; }
}

class Rectangle extends Shape {
    private double w, h;
    Rectangle(double w, double h) { this.w = w; this.h = h; }
    @Override
    public double area() { return w * h; }
}

// The MAGIC of runtime polymorphism:
Shape[] shapes = { new Circle(5), new Rectangle(4, 6), new Shape() };
for (Shape s : shapes) {
    System.out.println(s.describe());
    // s.area() — reference type is 'Shape' but ACTUAL type determines which runs:
    // Circle    → Circle.area()    (78.54)
    // Rectangle → Rectangle.area() (24.0)
    // Shape     → Shape.area()     (0.0)
    // Even inside Shape.describe(), 'this.area()' calls the overridden version!
}
// This is DYNAMIC DISPATCH: Java looks at actual object type at RUNTIME
// The reference type (Shape) doesn't matter for instance method resolution
JavaScript — overriding yes, overloading no
// JS does NOT have method overloading
// If you define the same name twice, second definition REPLACES the first
function greet(name)         { console.log("Hello, " + name); }
function greet(name, greeting) { console.log(greeting + ", " + name); }
greet("Ravi");  // → "undefined, Ravi" — second definition wins!

// JS workaround for overloading: check arguments inside the function
function add(...args) {
    if (args.every(a => typeof a === "number"))
        return args.reduce((a, b) => a + b, 0);
    if (args.every(a => typeof a === "string"))
        return args.join("");
    throw new Error("Invalid arguments");
}

// Overriding works perfectly — same as Java's runtime polymorphism
class Shape     { area() { return 0; } }
class Circle    extends Shape { constructor(r) { super(); this.r = r; } area() { return Math.PI * this.r ** 2; } }
class Rectangle extends Shape { constructor(w,h) { super(); this.w=w; this.h=h; } area() { return this.w * this.h; } }

const shapes = [new Circle(5), new Rectangle(4, 6)];
shapes.forEach(s => console.log(s.area()));
// Same runtime polymorphism — JS checks actual object's prototype chain

Interview Q&A — Polymorphism
What is the difference between method overloading and method overriding? Which is compile-time and which is runtime? ▼
Strong answer Overloading (compile-time polymorphism): Same method name, different parameter lists within the same class. The Java compiler decides which version to call based on argument types at compile time — no runtime decision needed. JavaScript does NOT support overloading; the second definition replaces the first. Overriding (runtime polymorphism): Child class redefines parent's method with the same signature. Java decides which version to call at runtime based on the actual object type — this is called dynamic dispatch. Even through a parent-type reference, the child's overriding method runs. @Override annotation tells the compiler to verify you're actually overriding something (prevents typos in method names).
What is dynamic dispatch / dynamic binding? ▼
Strong answer Dynamic dispatch (also called dynamic binding or late binding) is the mechanism where Java determines at runtime — not compile time — which overriding method implementation to call, based on the actual type of the object, not the type of the reference. Example: Shape s = new Circle(); — the reference type is Shape, but s.area() calls Circle's area() because the actual object is a Circle. Java maintains a virtual method table (vtable) for each class mapping method signatures to implementations. When you call an overridable method, Java looks up the vtable of the actual object. This enables writing generic code that works on parent types but gets the right behavior for each subtype. Follow-up: "Does dynamic dispatch work for static methods?" No. Static methods are resolved at compile time based on the reference type, not the actual object type. This is called static binding.
Can you override a method and reduce its visibility? Example: parent is public, can child make it private? ▼
Strong answer No — this would violate the Liskov Substitution Principle. If a parent class method is public, any code that has a parent reference expects to call that public method. If a child class overrode it as private, calling it through a parent reference would fail — breaking the contract. Java enforces this: you cannot reduce visibility when overriding. Parent is public → child can be public (same). Parent is protected → child can be protected or public (same or wider). You can WIDEN access (protected → public) but never NARROW it (public → protected or private = compile error).

Polymorphism — 60-second revision

  • Overloading: same name, different params, resolved at COMPILE TIME. Java only. Return type alone doesn't distinguish.
  • Overriding: child redefines parent method, resolved at RUNTIME via dynamic dispatch. Both Java and JS.
  • Dynamic dispatch: Java checks ACTUAL object type at runtime, not reference type. Circle through Shape reference → Circle's method.
  • Cannot override: final, static, or private methods. Static methods are hidden, not overridden.
  • Cannot narrow visibility when overriding. Can widen (protected → public). Cannot narrow (public → private).
  • JS: no overloading. Second definition replaces first. Simulate via arguments check inside function.

The this Keyword in JS

The most common JavaScript trap. 4 rules. Arrow functions. bind/call/apply. React event handler gotcha. Java's this is simple — JavaScript's is not.
must knowAsked at every JS/full stack interview
01Java's this — simple

In Java, this always refers to the current object instance. Period. No ambiguity. It's lexically bound — Java looks at the class you're in and that's the object. You use it to: disambiguate when a parameter has the same name as a field, call another constructor from a constructor (this(args)), or pass the current object as an argument.

02JavaScript's this — 4 rules, and they can conflict

JavaScript's this is determined at call time (when the function is invoked), not at definition time (where the function is written). This is the source of most JS bugs.

JavaScript — all 4 rules
The 4 rules for 'this' in JavaScript
// ── RULE 1: Global context ──
function whoAmI() { console.log(this); }
whoAmI();
// Browser (non-strict): this = window object
// Browser (strict mode) or Node.js: this = undefined
// 'use strict' at top of file enforces strict mode

// ── RULE 2: Method call — object before the dot ──
const user = {
    name: "Ravi",
    greet() {
        console.log("Hello, I am " + this.name);
    }
};
user.greet();       // → "Hello, I am Ravi"  (this = user, object before dot)

// THE CLASSIC BUG: detach the method — lose 'this'
const greetFn = user.greet;  // no longer called as user.greet
greetFn();                    // → "Hello, I am undefined" — this = global/undefined
// WHY: greetFn() has nothing before the dot — falls back to global context

// ── RULE 3: new keyword — this = newly created object ──
function Person(name, age) {

    this.age  = age;
}
const p = new Person("Priya", 25);
// 'new' does 4 things: 1) creates empty object, 2) sets its proto,
// 3) runs Person with this = new object, 4) returns the object

// ── RULE 4: Explicit binding — call, apply, bind ──
function introduce() {
    console.log("I am " + this.name + " from " + this.city);
}
const person1 = { name: "Ravi",  city: "Bangalore" };
const person2 = { name: "Priya", city: "Mumbai"    };

// .call(thisArg, arg1, arg2, ...) — call immediately with explicit this
introduce.call(person1);   // → "I am Ravi from Bangalore"
introduce.call(person2);   // → "I am Priya from Mumbai"

// .apply(thisArg, [args]) — like call but arguments as array
function greetWith(greeting, punctuation) {
    console.log(greeting + " " + this.name + punctuation);
}
greetWith.apply(person1, ["Hello", "!"]);  // → "Hello Ravi!"

// .bind(thisArg) — returns NEW function with this permanently bound
const boundGreet = user.greet.bind(user);
boundGreet();  // → "Hello, I am Ravi" — always! even if detached

// ── ARROW FUNCTIONS: no own 'this' — lexically inherited ──
const timer = {
    name: "countdown",

    start_BROKEN() {
        setTimeout(function() {
            console.log(this.name);  // undefined — regular function has own 'this'
        }, 100);
    },

    start_FIXED() {
        setTimeout(() => {
            console.log(this.name);  // "countdown" — arrow inherits 'this' from start_FIXED
        }, 100);
    }
};
// Arrow functions DON'T have their own 'this'
// They capture 'this' from the enclosing scope at DEFINITION time — not call time
// This is WHY React functional component event handlers work:
// const handleClick = () => { /* 'this' not needed — we use closures */ }

// ── REACT CLASS COMPONENT GOTCHA ──
class Counter extends React.Component {

        super(props);
        this.state = { count: 0 };

        this.increment = this.increment.bind(this);
    }

    increment() { this.setState(s => ({ count: s.count + 1 })); }
    // ↑ Without binding, onClick={this.increment} detaches the method
    // → 'this' inside increment becomes undefined when button is clicked

    // FIX 2: arrow class field (no binding needed)
    incrementArrow = () => { this.setState(s => ({ count: s.count + 1 })); }
    // Arrow class fields are defined in the constructor, so 'this' is lexically bound
}
Interview Q&A — this keyword
What does 'this' refer to in JavaScript? How is it different from Java? ▼
Strong answer In Java, this always refers to the current object instance — simple, predictable, determined at definition time. In JavaScript, this is dynamic — determined by HOW a function is called, not where it's defined. The 4 rules: (1) Global context → window or undefined (strict mode). (2) Method call → object before the dot. (3) new → newly created object. (4) call/apply/bind → explicitly provided value. Arrow functions are the exception — they don't have their own this and inherit from the enclosing scope lexically.
What's the difference between call, apply, and bind? ▼
Strong answer All three explicitly set this for a function. call: invokes the function immediately, passes arguments individually: fn.call(obj, arg1, arg2). apply: invokes immediately, passes arguments as an array: fn.apply(obj, [arg1, arg2]). bind: does NOT invoke immediately — returns a NEW function with this permanently bound to the specified value: const boundFn = fn.bind(obj). You call boundFn() later. Bind is used for event handlers and callbacks where you want to pre-set the context.
Why do arrow functions fix the 'this' problem in React class components? ▼
Strong answer In React class components, when you pass a method as an event handler — onClick={this.handleClick} — the method gets detached from the component instance. When the button is clicked, handleClick() is called as a plain function (no object before dot), so this is undefined in strict mode. Arrow class fields solve this because they're defined in the constructor scope — handleClick = () => {...} — the arrow function captures this lexically at definition time (when the constructor runs), so it permanently refers to the component instance regardless of how it's called later. This is why functional components with hooks are preferred — there's no this at all.

this keyword — 60-second revision

  • Java: this = current object, always. Simple.
  • JS: this = determined by call site, not definition. 4 rules.
  • Rule 1: Global call → window (browser) / undefined (strict). Rule 2: Method call → object before dot.
  • Rule 3: new → the newly created object. Rule 4: call/apply/bind → explicitly provided value.
  • Arrow functions: NO own this. Inherits from enclosing scope lexically (at definition time).
  • React class: bind in constructor OR use arrow class fields. OR just use functional components with hooks.
  • bind() returns new function. call/apply() invoke immediately. call = args separately, apply = args as array.

JavaScript Prototype Chain

How JS inheritance actually works under the hood. Class syntax is sugar over this. Property lookup walks the chain. instanceof checks the chain.
must know for JS interviewsProves you understand JS deeply, not just surface
01How the chain works

Every JavaScript object has an internal [[Prototype]] link (accessible via Object.getPrototypeOf(obj) or the non-standard obj.__proto__). When you access a property that doesn't exist on an object, JavaScript automatically walks up this chain looking for it.

The class syntax introduced in ES6 is syntactic sugar — it compiles to the exact same prototype-based mechanism that existed before classes. Understanding prototypes helps you understand why classes work the way they do, how instanceof works, and how to debug inheritance issues.

JavaScript — prototype chain
Prototype chain — what class syntax actually does
// ── PART 1: Pre-class prototype pattern (still used, need to understand) ──
function Animal(name) {
    this.name = name;       // instance property
}
// Methods go on the prototype — SHARED across all instances (memory efficient)
Animal.prototype.speak = function() {
    console.log(this.name + " makes a sound");
};

function Dog(name, breed) {
    Animal.call(this, name);  // call parent constructor with this object
    this.breed = breed;
}
// Set up prototype chain: Dog → Animal → Object
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog;  // fix constructor reference
Dog.prototype.bark = function() { console.log("Woof!"); };

const d = new Dog("Bruno", "Labrador");

// Property lookup — walks the chain:
d.name;     // on d itself (instance property) → found immediately
d.breed;    // on d itself → found
d.bark;     // NOT on d → check Dog.prototype → found!
d.speak;    // NOT on d → NOT on Dog.prototype → check Animal.prototype → found!
d.toString; // not found all the way up → check Object.prototype → found!
d.missing;  // not anywhere → returns undefined (end of chain: null)

// Chain visualization:
// d → Dog.prototype → Animal.prototype → Object.prototype → null

// ── PART 2: Class syntax — compiles to the SAME prototype setup ──
class Animal2 {
    constructor(name) { this.name = name; }
    speak() { console.log(this.name + " makes a sound"); }
    // speak goes to Animal2.prototype — not on each instance
}
class Dog2 extends Animal2 {
    constructor(name, breed) { super(name); this.breed = breed; }
    bark() { console.log("Woof!"); }
}

// Proof that class syntax = prototype chain:
console.log(Dog2.prototype.__proto__ === Animal2.prototype);  // true
console.log(Object.getPrototypeOf(Dog2) === Animal2);         // true (static inheritance)

// instanceof walks the prototype chain:
const d2 = new Dog2("Rex", "Poodle");
d2 instanceof Dog2;     // true — Dog2.prototype is in d2's chain
d2 instanceof Animal2;  // true — Animal2.prototype is in d2's chain
d2 instanceof Object;   // true — Object.prototype is at the end of every chain

// ── KEY INSIGHT: instance methods are on the prototype, not the instance ──
const a = new Dog2("A", "Lab");
const b = new Dog2("B", "Pug");
a.bark === b.bark;  // true — same function reference! Both share Dog2.prototype.bark
a.name === b.name;  // false — own properties, each instance has its own copy
Interview Q&A — Prototype Chain
How does JavaScript's prototype chain work? What is `class` syntax really? ▼
Strong answer Every JavaScript object has an internal link ([[Prototype]]) to another object. When you access a property, JS first checks the object itself, then its prototype, then that prototype's prototype, continuing until null. class syntax is syntactic sugar over this prototype mechanism — it doesn't add a new inheritance system. When you write class Dog extends Animal, JavaScript sets Dog.prototype.__proto__ = Animal.prototype. Methods defined in a class go on the prototype (shared by all instances, memory efficient). Properties set with this.x in the constructor go on the instance (each instance has its own copy).
What does instanceof check? ▼
Strong answer a instanceof B walks a's prototype chain and returns true if B.prototype is found anywhere in that chain. It does NOT check if a was constructed by B directly — it checks the prototype chain, which means it returns true for parent classes too. dog instanceof Animal is true because Animal.prototype is in the chain. Edge cases: if someone replaces the prototype after construction, instanceof can give unexpected results. It also doesn't work across iframe boundaries (different global contexts have different Object.prototypes).

Prototype Chain — 60-second revision

  • Every object has [[Prototype]] link. Property lookup walks the chain until found or null.
  • class syntax = syntactic sugar over prototype chain. Same mechanism, cleaner syntax.
  • class Foo extends Bar → Foo.prototype.__proto__ = Bar.prototype.
  • Methods on prototype = shared by all instances. this.x in constructor = own property per instance.
  • instanceof walks the prototype chain. Returns true for parent classes too.
  • Object.prototype is at the top of every chain. Has: toString, hasOwnProperty, valueOf.

SOLID Principles

5 principles for writing maintainable OOP code. Know one real example per principle. Interviewers test understanding, not definition memorization.

All 5 Principles
SOLID — what each one fixes + real example
// ── S: Single Responsibility Principle ──
// A class should have ONE reason to change.
// VIOLATION: UserService does too many things
class UserService_BAD {
    void createUser(User u)  { /* save to DB */ }
    void sendWelcomeEmail()   { /* email logic here — wrong! */ }
    void generateUserReport() { /* report logic here — wrong! */ }
}
// FIXED: separate concerns
class UserService   { void createUser(User u)  { } }
class EmailService  { void sendWelcomeEmail(User u) { } }
class ReportService { void generateReport(User u) { } }
// Now if email logic changes → only EmailService changes. DB logic unchanged.

// ── O: Open/Closed Principle ──
// Open for EXTENSION, closed for MODIFICATION.
// Adding new behavior by adding new code, not changing existing code.
interface Discount { double apply(double price); }
class NoDiscount       implements Discount { public double apply(double p) { return p; } }
class TenPercentOff    implements Discount { public double apply(double p) { return p * 0.9; } }
// New discount type: create new class. Don't touch existing discount classes.
class FlatRs500Off     implements Discount { public double apply(double p) { return p - 500; } }

// ── L: Liskov Substitution Principle ──
// Subclasses must be replaceable for their parent without breaking behavior.
// VIOLATION: Square extends Rectangle but breaks setWidth contract
class Rectangle {
    protected int width, height;
    void setWidth(int w)  { width = w; }   // width and height independent
    void setHeight(int h) { height = h; }
    int area() { return width * height; }
}
class Square_VIOLATION extends Rectangle {
    void setWidth(int w)  { width = height = w; } // breaks Rectangle's contract!
    void setHeight(int h) { width = height = h; } // setWidth → changes height too?!
}
// Code expecting Rectangle: rect.setWidth(4); rect.setHeight(5); → area=20
// With Square: area = 25 (both become 5). Contract broken. LSP violated.
// Fix: don't force IS-A. Square and Rectangle should be siblings, not parent/child.

// ── I: Interface Segregation Principle ──
// Don't force classes to implement methods they don't use.
// VIOLATION: Fat interface
interface Machine_BAD {
    void print(); void scan(); void fax();
}
// OldPrinter must implement scan() and fax() even though it has neither
// FIXED: split into focused interfaces
interface Printable { void print(); }
interface Scannable  { void scan(); }
interface Faxable    { void fax(); }
// OldPrinter implements only Printable. MultiFunctionDevice implements all three.

// ── D: Dependency Inversion Principle ──
// High-level modules should not depend on low-level modules.
// Both should depend on abstractions (interfaces).
// VIOLATION: UserService directly depends on concrete MySQL implementation
class UserService_BAD2 {
    private MySQLUserRepository repo = new MySQLUserRepository(); // concrete!
}
// FIXED: depend on interface
interface UserRepository { User findById(int id); void save(User u); }
class UserService_GOOD {
    private final UserRepository repo;    // depends on abstraction
    public UserService_GOOD(UserRepository repo) { this.repo = repo; }
    // Inject MySQL in production, InMemory for tests — no code change needed
    // This is exactly what Spring Boot's @Autowired does!
}
Interview Q&A — SOLID
Can you explain SOLID and give a real example for any two principles? ▼
Strong answer — focus on S and D (most relevant to full stack) S (Single Responsibility): A UserService should only handle user domain logic. Email sending belongs in an EmailService. If the email provider changes, only EmailService changes — UserService is untouched. In my Node.js project, I have separate authService, userService, and emailService for exactly this reason. D (Dependency Inversion): High-level modules (UserService) should depend on abstractions (UserRepository interface), not concrete implementations (MySQLUserRepository). Makes unit testing easy: inject a MockUserRepository in tests, the real MySQL one in production.

SOLID — 60-second revision

  • S: One class, one responsibility. Email sending ≠ User management. One reason to change.
  • O: Open for extension (new class), closed for modification (don't edit existing). Add discount types, don't edit discount calculator.
  • L: Subclass must work wherever parent is expected. Square breaking Rectangle's contract = violation.
  • I: Don't force classes to implement unused methods. Split fat interfaces into focused ones.
  • D: Depend on interfaces, not concretions. Spring's @Autowired implements this. Enables unit testing.

    private Config_UNSAFE() {}              // private constructor

// ── OBSERVER: Notify subscribers when state changes ──
// Use case: Event listeners, pub/sub systems, MVC model notifying views
interface OrderObserver { void onOrderUpdate(String status); }

class Order {

    private String status = "PENDING";

    public void addObserver(OrderObserver o) { observers.add(o); }
    public void updateStatus(String newStatus) {
        status = newStatus;
        observers.forEach(o -> o.onOrderUpdate(status));  // notify all
    }
}

class EventEmitter {
    #events = {};

    on(event, listener) {
        if (!this.#events[event]) this.#events[event] = [];
        this.#events[event].push(listener);
        return this;  // enable chaining: emitter.on('a', fn).on('b', fn2)
    }

    emit(event, data) {
        (this.#events[event] || []).forEach(fn => fn(data));
        return this;
    }

    off(event, listener) {
        this.#events[event] = (this.#events[event] || [])
            .filter(fn => fn !== listener);
    }
}

Interview Q&A — Design Patterns
Explain the Singleton pattern. Why is the basic implementation not thread-safe in Java? ▼
Strong answer Singleton ensures only one instance of a class exists globally. The private constructor prevents external instantiation. The static getInstance() method returns the single instance. The basic lazy implementation (if (instance == null) create) is not thread-safe because two threads can simultaneously pass the null check before either creates the instance — both then create separate instances, violating the singleton guarantee. Solutions: (1) synchronized on the whole method — safe but locks on every call (slow); (2) double-checked locking with volatile — faster, only locks on first creation; (3) enum singleton — best, JVM guarantees enum instances are created once and thread-safely. In JavaScript, modules are automatically singletons due to module caching.
Where does the Observer pattern appear in your projects? ▼
Strong answer — connect to your actual work The Observer pattern is everywhere in frontend and backend work. In my CollabDocs project, Socket.io uses Observer — when a user edits, the server emits to all subscribers in the room (document observers). In Node.js, EventEmitter is the Observer pattern — my Express server uses it for request handling. In React, the component re-render mechanism is Observer — useState triggers an update notification to React, which re-renders the component (observer). In Java/Spring, ApplicationEventPublisher is the official Observer implementation — services can publish events and listeners react without direct coupling. The pattern decouples the source of change from the things that need to respond to it.

Design Patterns — 60-second revision

  • Singleton: one instance globally. Java: enum (thread-safe). Classic if-null: NOT thread-safe. JS: modules are automatic singletons.
  • Observer: subject notifies multiple observers on state change. Decouples producer from consumers. Node EventEmitter, addEventListener, Socket.io events all use this.
  • Factory: create objects without knowing exact class. Client asks factory, factory decides which concrete class. PaymentFactory.create("UPI") returns the right implementation.

1. What are the 4 pillars of OOP? Explain each in one sentence. ▼
AnswerEncapsulation: bundle data and methods, restrict direct access to internal state. Abstraction: hide complexity, expose only relevant interface (abstract classes, interfaces). 2. What is the difference between abstract class and interface in Java? When use which? ▼
AnswerAbstract class: can have constructors, state, concrete + abstract methods. Single inheritance only. Use for IS-A + shared code. Interface: pure contract (Java 7), default methods (Java 8). No state. Multiple implementation. Use for CAN-DO capabilities across unrelated classes. Key: if you need shared implementation → abstract class. If you need a contract multiple unrelated classes satisfy → interface.
3. Can a class extend multiple classes in Java? Can it implement multiple interfaces? Why the difference? ▼
AnswerA class can extend only ONE class (diamond problem — ambiguity when two parents have the same method). A class CAN implement multiple interfaces. Java 8 partially reintroduces the diamond problem with default methods — resolved by forcing the implementing class to override the conflicting method. class Dog extends Animal implements Runnable, Serializable is valid.
4. What is method overriding? What are the rules? ▼
AnswerChild class provides new implementation for an inherited instance method with the same signature. Rules: same name and parameters; return type can be covariant (subtype); cannot reduce visibility (public → protected = error); cannot override final, static, or private methods; checked exceptions can't be broader than parent's declared exceptions. @Override annotation verifies you're overriding, not accidentally creating a new method.
5. What is dynamic dispatch? Give an example. ▼
AnswerDynamic dispatch is Java's mechanism of resolving which overriding method to call at runtime based on the actual object type, not the reference type. Example: Shape s = new Circle(); s.area(); — reference type is Shape, but Java calls Circle's area() because the actual object is a Circle. This is how polymorphism works in practice. Java maintains a vtable per class for this. Note: static methods use static binding — reference type decides, not actual type.
6. What is the diamond problem? How does Java solve it? ▼
AnswerThe diamond problem: if class D extends B and C, and B and C both override the same method from A, D has ambiguous inheritance — which version does it get? Java prevents this by allowing only single class inheritance. With interfaces (Java 8 default methods), the problem can occur — solved by forcing the implementing class to explicitly override the conflicting method, choosing which interface's implementation to call or providing its own.
7. What does the 'this' keyword mean in Java vs JavaScript? ▼
AnswerJava: always the current object instance. Lexically bound. Predictable. Used to disambiguate fields from parameters, call other constructors. JavaScript: determined at call time, not definition time. Four rules: (1) global call → window/undefined, (2) method call → object before dot, (3) new → new object, (4) explicit binding via call/apply/bind. Arrow functions are special — no own this, lexically inherit from enclosing scope.
8. Why are arrow functions different from regular functions regarding 'this'? ▼
AnswerRegular functions have their own this, determined at call time. Arrow functions don't have their own this — they inherit this from the enclosing lexical scope at definition time. This makes them predictable in callbacks. Classic problem: setTimeout(function() { this.count++ }, 1000) — this is window, not the object. With arrow: setTimeout(() => { this.count++ }, 1000) — this is whatever it was in the surrounding code. This is why React functional components with hooks are cleaner — no this at all.

10. What is the Singleton pattern? Why is the basic implementation not thread-safe? ▼
AnswerSingleton ensures one instance globally. The classic if(instance==null) create is not thread-safe because two threads can both pass the null check simultaneously before either creates the instance. Best Java solution: enum singleton (JVM guarantees thread-safe enum creation). JavaScript: modules are singletons by default due to require/import caching — no synchronization needed since JS is single-threaded.
11. What is SOLID? Explain S and D with a real example. ▼
AnswerS (Single Responsibility): UserService handles only user logic. Email sending → EmailService. If the email provider changes, only EmailService changes. O: add new behavior by creating new code, not editing existing. L: subclasses must be substitutable for parents without breaking behavior. I: don't force classes to implement unused methods. D (Dependency Inversion): depend on interfaces, not concretions. Spring's @Autowired injects the implementation at runtime. Your service depends on UserRepository (interface), not MySQLUserRepository (concrete) — enables testing with mocks.
12. Can you instantiate an abstract class? ▼
AnswerNo, directly — new AbstractClass() is a compile error. However, you can instantiate it via an anonymous subclass: AbstractClass a = new AbstractClass() { public void method() {...} }. This creates a nameless subclass inline that implements all abstract methods. Commonly used for event listeners in Java. The abstract class reference variable can hold any subclass instance — this is standard polymorphism.
13. What is constructor chaining? What happens if you don't call super() in Java vs JavaScript? ▼
AnswerConstructor chaining = calling one constructor from another, forming a chain to the root. Java: if you don't write super(), the compiler inserts a no-arg super() automatically. If parent has no no-arg constructor → compile error. JavaScript: if a child class has a constructor, not calling super() before using this → ReferenceError at runtime. This is because in JS, the parent constructor creates the this object — without it, this doesn't exist yet.
14. What is the Observer pattern? Where does it appear in your projects? ▼
AnswerObserver: a subject maintains a list of observers and notifies all when state changes. Decouples producers from consumers. In my CollabDocs project: Socket.io uses Observer — when a document changes, the server emits to all subscribed clients. In React: useState triggers re-render (component is observer of state). In Node.js: EventEmitter is Observer — button.addEventListener in browser, server.on('request') in Node. In Spring: ApplicationEventPublisher. The pattern enables one-to-many change notification without tight coupling.
15. What is encapsulation? How does JavaScript implement it? ▼
AnswerEncapsulation: bundle data and methods together, restrict direct external access. Java: private fields + public getters/setters with validation. JavaScript: (1) ES2022 # prefix for truly private fields — class Foo { #secret; } — #secret throws SyntaxError if accessed externally. (2) Closure pattern (older): factory function returns object exposing only selected methods; variables inside the function are private by scope. TypeScript adds compile-time private keyword (becomes public in generated JS).
16. What is covariant return type in method overriding? ▼
AnswerWhen overriding a method, the return type in the child class can be a subtype of the parent's return type. Example: parent declares Animal getAnimal(). Child can override with Dog getAnimal() because Dog IS-A Animal. The caller using a parent reference still gets a valid Animal (actually a Dog). This is called covariant return type. It's valid overriding in Java. Useful for builder patterns and factory methods in subclasses.
17. What is the Liskov Substitution Principle? Give a violation example. ▼
AnswerLSP: Any code using a parent class must work correctly with a subclass without knowing the difference. Classic violation: Square extends Rectangle. Rectangle's contract says setWidth() and setHeight() are independent. Square overrides them to keep sides equal — calling setWidth(4) on a Square also changes height. Code expecting Rectangle behavior is broken. Fix: don't force IS-A when the subtype can't honor the parent's contract. Square and Rectangle should both implement a Shape interface, not have a parent-child relationship.
18. What is the difference between method overloading and method overriding? Which is compile-time? ▼
AnswerOverloading (compile-time): same name, different parameters, resolved at compile time. Java only. Overriding (runtime): child redefines parent's instance method with same signature, resolved at runtime via dynamic dispatch. Key differences: overloading in same class, overriding in different classes (parent/child). Overloading = compile-time polymorphism. Overriding = runtime polymorphism. @Override annotates overriding, not overloading. JS has no overloading.
19. Can you override a private method? A static method? A final method? ▼
AnswerPrivate methods: Cannot be overridden — they're not inherited. If you write the same signature in a child class, it's a new independent method, not an override. Static methods: Cannot be overridden — they're hidden. Declaring the same static method in a child creates a separate method. @Override on a static method = compile error. Static binding uses reference type, not actual type. Final methods: Cannot be overridden by design — compile error. Final signals "this implementation is complete, don't change it."
20. Why would you use composition over inheritance? ▼
Answer"Favor composition over inheritance" — GoF Design Patterns principle. Inheritance creates tight coupling: child class knows about parent's internals. If parent changes, child breaks. Composition: a class has a reference to another class and delegates to it. More flexible — you can swap implementations at runtime. Example: instead of class LoggingUserService extends UserService (breaks if UserService changes), do class LoggingUserService { private UserService service; /* delegate + add logging */ }. Composition enables the Decorator pattern. Inheritance is appropriate for genuine IS-A relationships with stable base classes — not just code reuse.
