Operating Systems

✓
Process vs Thread
Memory model, isolation, when to use which, Chrome and Node.js examples
must
Exactly what to learn
  • Process: own memory space (code, stack, heap, data). Isolated. Heavy to create. Crash doesn't affect others.
  • Thread: shares process heap and data. Own stack + registers only. Lightweight. Crash kills whole process.
  • How Chrome uses this: each tab = separate process (isolation). Within tab = multiple threads (rendering, JS, network)
  • How Node.js uses this: single process, single main thread (event loop), libuv thread pool for I/O
  • IPC (Inter-Process Communication): how processes talk — pipes, sockets, shared memory. Threads just use shared memory directly (simpler but risky)

Concurrency vs Parallelism
The difference, why Node.js is concurrent not parallel, event loop basics
must · Node.js core concept
Exactly what to learn
  • Concurrency: multiple tasks in progress at same time, taking turns on 1 CPU (time-slicing). Illusion of simultaneity.
  • Parallelism: multiple tasks running at exact same time on multiple CPU cores. Truly simultaneous.
  • Node.js is concurrent (single thread, event loop) but NOT parallel by default
  • The event loop: single thread handles callbacks. I/O handed to libuv thread pool. Thread never sits idle waiting.
  • When Node.js breaks: CPU-heavy work (image processing, video encoding) BLOCKS the event loop. All requests wait.
  • Fix for CPU-heavy: worker_threads module or separate microservice

Race Conditions, Mutex, Semaphore
What they are, difference between mutex and semaphore, when each is used
must
Exactly what to learn
  • Race condition: 2+ threads read-modify-write same variable without coordination. count++ is 3 operations — not atomic.
  • Mutex: binary lock (locked/unlocked). Only thread that locked it can unlock it (ownership). Used for critical sections — one thread at a time.
  • Semaphore: counter. Any thread can signal. Used for resource pools (allow max 10 DB connections simultaneously).
  • Binary semaphore vs mutex: similar but mutex has ownership, semaphore doesn't
  • Java: synchronized keyword = mutex. Semaphore class for semaphores.
  • JS: mostly immune to CPU race conditions (single thread) but async logic can still have logical races

Deadlock — 4 Conditions + Prevention
Coffman conditions, how deadlock happens, how to prevent with lock ordering
must
Exactly what to learn
  • What a deadlock looks like: Thread A holds lock 1, waits for lock 2. Thread B holds lock 2, waits for lock 1. Stuck.
  • 4 Coffman conditions (all must hold): Mutual exclusion, Hold and wait, No preemption, Circular wait
  • Prevention: break any one condition. Easiest in practice: break circular wait by always acquiring locks in same fixed order
  • How databases handle it: detect deadlock, timeout one transaction, rollback it, retry
  • Real example: bank transaction deadlock (two accounts, two transactions, opposite lock order)

Stack vs Heap Memory
What lives where, who manages what, memory leaks in Java and JavaScript
must
Exactly what to learn
  • Stack: local variables, function call frames, fixed size, auto-freed when function returns, very fast
  • Heap: objects created with new, dynamic size, managed by GC (Java) or manually (C)
  • In JS: primitives on stack, objects and closures on heap
  • Stack overflow: too many nested function calls (infinite recursion)
  • Java GC: generational — Young Gen (most objects die young, fast minor GC), Old Gen (long-lived, slow major GC)
  • Memory leaks in Java: static collections that grow forever, unclosed streams/connections
  • Memory leaks in JS/React: forgotten setInterval, setState after unmount, event listeners not removed — fix with useEffect cleanup

CPU Scheduling Algorithms
FCFS, SJF, Round Robin, Priority — concept and trade-offs only
high value
Exactly what to learn — concept level only, no calculations needed
  • FCFS: first come first served. Simple. Problem: convoy effect (long process blocks short ones)
  • SJF: shortest job first. Optimal average wait time. Problem: starvation of long processes
  • Round Robin: each gets a time quantum, then goes to back of queue. Fair, good for interactive systems
  • Priority Scheduling: highest priority runs first. Problem: starvation. Fix: aging (increase priority over time)
  • Preemptive vs Non-preemptive: can OS interrupt a running process or must it wait for it to finish?

Blocking vs Non-Blocking I/O
How Node.js achieves concurrency with libuv, when non-blocking breaks
must for full stack
Exactly what to learn
  • Blocking I/O: thread calls OS for file/network I/O, waits idle until done. 1000 requests = 1000 threads sitting idle.
  • Non-blocking I/O: register callback, move on, OS notifies when I/O ready. Single thread handles many requests.
  • Node.js: single event loop thread. I/O handed to libuv thread pool (4 threads by default). Callback queued when done.
  • Why non-blocking is fast: thread is never idle — always processing next callback
  • Where it breaks: CPU-heavy work (encryption, image resize) blocks the event loop. Fix: worker_threads
  • Proof you can show: console.log(1); setTimeout(()=>console.log(2),0); console.log(3) outputs 1,3,2

Virtual Memory + Paging
Concept only — why virtual memory exists, what paging does
good to know
Exactly what to learn — concept only, no deep math
  • Virtual memory: each process thinks it has its own large contiguous memory. OS manages mapping to real physical RAM.
  • Why: allows running more programs than physical RAM. Processes are isolated — can't access each other's memory.
  • Paging: divides virtual memory into fixed-size pages, maps to physical page frames. Page table does the mapping.
  • Page fault: accessing a page not in RAM — OS loads it from disk (swap). Slow.
  • This is why: "Out of memory" errors, why too many processes slow down the system (constant swapping)

✓
Keys — Primary, Foreign, Candidate, Composite, Surrogate
What each one is, when to use surrogate vs natural keys
must
Exactly what to learn
  • Primary key: unique identifier for a row, NOT NULL, one per table
  • Foreign key: references primary key of another table, enforces referential integrity
  • Candidate key: any column that could be a primary key (unique + not null). Email AND phone are both candidate keys for users.
  • Composite key: primary key made of 2+ columns. Example: (student_id, course_id) in Enrollment table
  • Surrogate key: artificial auto-increment ID. Never from real data. Preferred because natural keys (email) can change.
  • Why surrogate keys over natural: phone numbers can change, emails can change, Aadhaar numbers have privacy issues

Normalization — 1NF, 2NF, 3NF
Step-by-step normalization of a messy table. Denormalization trade-off.
must · normalise a table cold
Exactly what to learn
  • 1NF: each cell must have one atomic value. No arrays, no comma-separated lists in a cell. Each row must be unique.
  • 2NF: 1NF + no partial dependency. Every non-key column must depend on the WHOLE primary key (matters when composite key exists)
  • 3NF: 2NF + no transitive dependency. Non-key column depending on another non-key column → move to separate table
  • Update anomaly: if Ravi changes city, you update 10 rows. Normalization fixes this — update 1 row.
  • Denormalization: intentionally break normalization for read performance. Analytics/reporting DBs do this.
  • When to denormalize: reads >> writes, joins are too slow at scale, pre-computing aggregates

ACID Properties
All 4 properties explained with payment example — not just acronym definitions
must · explain with payment example
Exactly what to learn
  • Atomicity: all operations in a transaction succeed or all are rolled back. UPI: debit A AND credit B. If credit fails → debit rolls back.
  • Consistency: DB moves from one valid state to another. Constraints never violated. Total money before = total after.
  • Isolation: concurrent transactions don't see each other's intermediate state. T1 deducting, T2 reading balance → T2 sees before or after, never during.
  • Durability: committed transactions survive crashes. Written to disk via WAL (Write-Ahead Log). Even if server dies immediately after COMMIT.
  • How each is implemented: Atomicity=UNDO log, Consistency=constraints, Isolation=locking/MVCC, Durability=WAL/redo log

Transaction Isolation Levels
4 levels, 3 problems they prevent, which is MySQL/PostgreSQL default
must
Exactly what to learn
  • Dirty read: reading uncommitted data from another transaction that might roll back
  • Non-repeatable read: same query returns different result because another committed transaction updated the row
  • Phantom read: same query returns different rows because another committed transaction inserted/deleted rows
  • Read Uncommitted: all 3 problems possible. Avoid.
  • Read Committed: no dirty reads. PostgreSQL default.
  • Repeatable Read: no dirty or non-repeatable reads. MySQL InnoDB default.
  • Serializable: fully isolated, no anomalies. Slowest — use for financial transactions.
  • Higher isolation = safer but slower (more locking, less concurrency)

Database Indexing
B-Tree structure, clustered vs non-clustered, when to index and when not to
must · very practical
Exactly what to learn
  • Without index: full table scan O(n). With index: B-Tree binary search O(log n). 10M rows = 23 comparisons vs 10M.
  • B-Tree index: balanced tree, leaf nodes point to actual rows. Most common index structure.
  • Clustered index: rows physically sorted by index key. One per table (primary key in InnoDB). Like a dictionary.
  • Non-clustered index: separate structure, leaf nodes have pointers. Multiple per table. Two lookups: index + row.
  • When to index: columns in WHERE, JOIN ON, ORDER BY. High cardinality (email, id).
  • When NOT to index: small tables (full scan is fine), low cardinality (gender: M/F — index useless), frequently updated columns
  • Trade-off: index speeds reads, slows writes (every INSERT/UPDATE must also update the index)
  • Composite index column order matters: (last_name, first_name) helps queries filtering by last_name but not first_name alone

SQL vs NoSQL + CAP Theorem
When to use each, real trade-offs, what CAP means for distributed systems
must
Exactly what to learn
  • SQL: rigid schema, ACID, complex joins, vertical scaling, strong consistency. Use for: payments, user auth, orders.
  • NoSQL: flexible schema, horizontal scaling, eventual consistency. Types: Document (MongoDB), Key-Value (Redis), Column (Cassandra), Graph (Neo4j)
  • When NoSQL: schema evolves (product catalog with different attributes per category), massive scale (billions of writes), eventual consistency OK
  • CAP Theorem: distributed system can only guarantee 2 of 3: Consistency (every read = latest write), Availability (always gets a response), Partition Tolerance (works despite network failure)
  • Since network partitions always happen in distributed systems: choose C+P or A+P
  • MongoDB: CP. Cassandra: AP. Traditional SQL: CA (no partition tolerance — single node)

Optimistic vs Pessimistic Locking
When to use each, real-world use cases, how Spring Boot handles it
good to know
Exactly what to learn

  • Spring Boot: @Version annotation on entity field = optimistic locking automatic
  • Real example: Zepto ordering last item in stock — pessimistic locking prevents overselling

TCP vs UDP — Three-Way Handshake
Reliability, ordering, use cases, when UDP is better than TCP
must
Exactly what to learn
  • TCP: reliable, ordered, connection-based. Handshake: SYN → SYN-ACK → ACK. Retransmits lost packets. Use for: HTTP, email, file transfer.
  • UDP: unreliable, connectionless, no handshake. Faster. Use for: video streaming, gaming, DNS, VoIP.
  • Why UDP for real-time: a late correct packet is worse than a missed one. Video call — don't retransmit 2-second-old frame.
  • TCP connection overhead: handshake takes time. HTTPS adds TLS handshake on top.
  • HTTP/1.1, HTTP/2, HTTP/3 — what each improved (multiplexing, header compression, QUIC on UDP)

HTTP Methods + Status Codes
GET/POST/PUT/PATCH/DELETE, idempotency, every status code category
must · daily use
Exactly what to learn

  • 401 vs 403: most asked gotcha. 401 = "who are you?" 403 = "I know who you are but no."

HTTPS + TLS Handshake
Why HTTPS, how TLS works, symmetric vs asymmetric encryption, Certificate Authorities
must
Exactly what to learn
  • HTTPS = HTTP + TLS. Without it: anyone on same network reads your data (MITM attack).
  • TLS handshake: client hello → server sends certificate → client verifies with CA → key exchange (asymmetric) → symmetric session key established → data encrypted with symmetric key
  • Why asymmetric (RSA) to exchange, symmetric (AES) for data: RSA is 1000x slower than AES
  • Certificate Authority (CA): trusted third party (Let's Encrypt, DigiCert) that signs server certificates, proving "this is really google.com"
  • Without CA: anyone could make a certificate for google.com → MITM attacks easy

CORS — What It Is and How to Fix It
Same-origin policy, preflight requests, configuring Express correctly
must · you'll hit this daily
Exactly what to learn

  • Simple requests: GET/POST with basic headers → browser adds Origin header → server responds with Access-Control-Allow-Origin
  • Preflight: before PUT/DELETE/custom headers → browser sends OPTIONS first → server must respond with allowed methods/headers → then actual request

WebSocket vs HTTP Long Polling
Full-duplex connection, when to use WebSocket, Socket.io basics
must · used in your CollabDocs project
Exactly what to learn
  • HTTP: request-response, client always initiates. Server can't push data.
  • Polling: client asks server every N seconds "any updates?" Wasteful.
  • Long polling: client sends request, server holds it open until there's data. Better but still wasteful.
  • WebSocket: persistent full-duplex connection. Server can push anytime. Starts as HTTP then upgrades via Upgrade header → 101 Switching Protocols.
  • Use WebSocket for: live chat, order tracking (Swiggy), collaborative editing (Google Docs), live sports, gaming
  • Socket.io: library that wraps WebSocket + fallbacks. io.on('connection'), socket.emit(), socket.broadcast.emit()

Cookie vs LocalStorage vs SessionStorage
Security implications, where to store JWT, XSS vs CSRF trade-offs
must · auth security
Exactly what to learn
  • Cookie: sent with every request automatically. HttpOnly = JS can't read it (XSS protection). Secure = HTTPS only. SameSite = CSRF protection.
  • LocalStorage: never auto-sent. Accessible via JS. Survives page close. 5-10MB.
  • SessionStorage: same as LocalStorage but cleared when tab closes.
  • JWT in LocalStorage: easy but XSS attack can steal it (localStorage.getItem('token') from injected script)
  • JWT in HttpOnly Cookie: JS cannot read it → immune to XSS token theft. Vulnerable to CSRF → mitigate with SameSite=Strict
  • Best practice: short-lived access token (15 min) in memory (JS variable), long-lived refresh token in HttpOnly cookie

interface vs type — real differences
Declaration merging, extension, when to prefer each

GROUP BY, HAVING, Aggregate Functions

Exactly what to learn

  • COUNT(*) vs COUNT(column): COUNT(*) counts all rows including NULLs. COUNT(column) counts non-NULL values in that column.

Most asked SQL concept in interviews. Know all types and when to use each.
must · most asked
Exactly what to learn
