Object-Oriented Programming

You know OOP syntax. Phase 0 goal is to understand it deeply enough to explain every concept in Java AND JavaScript with real examples — because interviewers ask follow-ups.

Java + JavaScript both 4–5 days Very high interview frequency
Topics to cover — check off as you go
The 4 Pillars
✓
Encapsulation — private fields, getters/setters, why it matters must

Encapsulation = hiding internal state. In Java: private fields + public getters/setters. In JS: closures or #privateField syntax. Interviewers ask: "What's the difference between encapsulation and abstraction?" — encapsulation is HOW (restrict access), abstraction is WHAT (hide complexity).

✓
Abstraction — abstract classes vs interfaces, when to use each must

Abstraction hides complexity, exposes only essentials. In Java: abstract class (partial implementation) vs interface (contract only). Key Q: "Can you extend multiple abstract classes?" No. "Multiple interfaces?" Yes. JS uses duck typing — no native abstract keyword.

✓
Inheritance — super keyword, method overriding, constructor chaining must

Java uses extends. JS uses class A extends B (syntactic sugar over prototypes). Key: super() must be called first in child constructor. Interviewers ask about the diamond problem — Java avoids with interfaces, Python handles via MRO.

✓
Polymorphism — compile-time (overloading) vs runtime (overriding) must

Compile-time: method overloading (same name, different params) — resolved at compile time. Runtime: method overriding (child replaces parent method) — resolved at runtime via dynamic dispatch. JS has no overloading natively (functions just use the last definition).

Classes & Objects deep
✓
Constructors — default, parameterized, copy constructor (Java) must

Java has default constructor (compiler adds if none defined), parameterized, and copy constructor. JS constructors use constructor() inside class. Key: Java constructors are not inherited; JS classes call super() to access parent constructor.

✓
Static vs instance — static fields, static methods, when to use must
✓
this keyword — how it works in Java vs JavaScript (critical diff) must

Java this always refers to current object. JS this depends on call context — in a function it's the caller, in arrow functions it's lexically inherited. Classic interview trap: passing a JS method as a callback loses this — solve with .bind() or arrow function.

✓
JS Prototype chain — how inheritance actually works under the hood must

Every JS object has a __proto__ reference. Property lookup walks up the prototype chain. class syntax is sugar over prototype-based inheritance. Key: Object.create(), prototype property, Object.getPrototypeOf(). Interviewers at product companies ask this — it shows you understand JS deeply.

Interview Q&A — OOP (click to reveal answers)
What is the difference between abstraction and encapsulation? ▼
Encapsulation is about restricting direct access to internal data (HOW you protect data). Abstraction is about hiding complex implementation and showing only relevant details (WHAT the object does). Example: A car — you press the accelerator (abstraction, you don't see the engine), but the engine internals are private (encapsulation).
Can you have multiple inheritance in Java? How does Java handle the diamond problem? ▼
Java does not support multiple class inheritance (no extends A, B) to avoid the diamond problem — ambiguity when two parents define the same method. Java solves this with interfaces: a class can implement multiple interfaces. If two interfaces have the same default method, the implementing class must override it to resolve the conflict.
Why is 'this' in JavaScript unpredictable? Give an example. ▼
In JS, this is determined by how a function is called, not where it's defined. const greet = obj.greet; greet() — here this is undefined (strict) or window, not obj. Fix: greet.bind(obj) or use an arrow function (arrow functions inherit this from enclosing scope lexically).
What is the Singleton pattern and why is it not thread-safe by default in Java? ▼
Singleton ensures only one instance of a class exists. The classic lazy implementation with if (instance == null) instance = new Singleton() is not thread-safe — two threads can simultaneously pass the null check and create two instances. Fix: use synchronized keyword, double-checked locking, or an enum (thread-safe by design in Java).
What is method overloading vs overriding? Which is compile-time and which is runtime? ▼
Overloading: same method name, different parameters — resolved at compile time (static polymorphism). Overriding: child class redefines parent's method with same signature — resolved at runtime via dynamic dispatch (runtime polymorphism). Java checks the actual object type at runtime to call the right override.

Operating Systems

Don't go deep like GATE. Cover concepts to interview depth — enough to explain with examples and answer follow-ups. No kernel internals needed.

Theory only — no coding 4–5 days High frequency at product companies
Topics checklist
Process & Thread fundamentals
✓
Process vs Thread — definition, memory model, use casesmust

Process: independent execution unit, own memory space (code, stack, heap, data). Thread: lightweight, shares memory with parent process. Process creation is heavy (fork); thread creation is cheap. Key interview Q: "Why use threads over processes?" — lower overhead, faster communication (shared memory). Risk: race conditions.

✓
Process states — new, ready, running, waiting, terminatedmust
✓
Context switching — what it is, why it's expensivemust

When OS switches CPU from one process to another — saves current process state (PCB), loads next process state. Expensive because: CPU cache flush, TLB flush, register save/restore. Too many threads = too much context switching = slower performance. This is why Node.js's single thread + event loop is efficient for I/O.

✓
Multithreading — concurrency vs parallelism (critical concept)must

Concurrency: multiple tasks make progress by time-slicing (illusion of simultaneity). Parallelism: multiple tasks run at exactly the same time on multiple cores. Node.js is concurrent (single thread, event loop) but not parallel. Java can do both. Interview gold: "Node.js is single-threaded — so how does it handle concurrent requests?"

CPU Scheduling
✓
FCFS, SJF, Round Robin, Priority Scheduling — concept + trade-offsmust
✓
Starvation and aging — why lower priority processes starvegood
Synchronization & Deadlocks
✓
Race condition — what it is, how it happens, examplemust

When outcome depends on timing of threads — two threads read-modify-write the same variable without synchronization. Classic: counter++ is not atomic (read, add, write — 3 ops). Interviewers relate this to JS: "Is JS immune to race conditions?" — mostly yes for CPU ops (single thread), but async operations can still cause logical race conditions.

✓
Mutex vs Semaphore — difference, when to use eachmust

Mutex: binary lock (0 or 1), only the thread that locked it can unlock it. Used for mutual exclusion. Semaphore: counter (can be >1), any thread can signal. Used for controlling access to a resource pool (e.g., database connection pool of 10). Key: mutex is a special case of semaphore (binary semaphore) but with ownership.

✓
Deadlock — 4 conditions (Coffman), prevention, detectionmust

4 conditions (all must hold): Mutual exclusion, Hold and wait, No preemption, Circular wait. Prevention: break any one condition. Detection: resource allocation graph. Example: Thread A holds DB lock, waits for file lock. Thread B holds file lock, waits for DB lock. → deadlock.

Memory Management
✓
Stack vs Heap memory — what lives where, who manages whatmust

Stack: function calls, local variables, fixed size, LIFO, managed by compiler, very fast. Heap: dynamic allocation (new in Java, malloc in C), variable size, managed by GC (Java) or manually (C). In JS: primitives on stack, objects on heap. Stack overflow = too many function calls (infinite recursion).

✓
Virtual memory — paging, why it existsgood
✓
Garbage Collection — how JVM GC works (mark and sweep, generational)must

JVM GC: Mark (find reachable objects from GC roots), Sweep (free unmarked). Generational: Young Gen (most objects die young, minor GC is fast), Old Gen (survivors, major GC is slow), PermGen/Metaspace (class metadata). For JS: V8 uses similar generational GC. Interview Q: "What causes memory leaks in Java/JavaScript?"

✓
Memory leak — what causes it in Java and JavaScriptmust

Java: unclosed streams, static collections holding references, listeners not removed. JS: closures holding DOM references, global variables, forgotten timers/intervals, detached DOM nodes still referenced in JS. Interviewers at React-heavy companies ask: "How can a React component cause a memory leak?" — setState after unmount, forgotten useEffect cleanup.

File Systems & I/O
✓
Blocking vs non-blocking I/O — how Node.js uses thismust

Blocking: thread waits until I/O completes (traditional Java servlet model). Non-blocking: thread initiates I/O and moves on, gets notified via callback/event when done. Node.js uses libuv — async non-blocking I/O + event loop. This is why Node.js handles 10k concurrent connections efficiently with a single thread — threads aren't sitting idle waiting for I/O.

Interview Q&A — OS
What is the difference between process and thread? When would you prefer one over the other? ▼
A process is an independent execution unit with its own memory space (code, stack, heap, data). A thread is a lightweight unit within a process that shares the same memory. Use multiple processes when isolation matters (crashes don't affect others, like Chrome tabs). Use threads when you need shared memory and fast communication (e.g., a web server handling requests — one thread per request shares the same app state).
What are the 4 conditions for deadlock? How do you prevent it? ▼
The 4 Coffman conditions (all must hold simultaneously): 1. Mutual exclusion — resources can't be shared. 2. Hold and wait — process holds a resource while waiting for another. 3. No preemption — resources can't be taken away. 4. Circular wait — chain of processes each waiting for the next. Prevention: break any one condition — e.g., always acquire locks in the same order (prevents circular wait).
Node.js is single-threaded. How can it handle thousands of concurrent requests? ▼
Node.js uses an event loop with non-blocking I/O via libuv. When a request comes in and needs I/O (database, file, network), Node doesn't block the thread — it registers a callback and moves on to the next request. When the I/O completes, the callback is queued in the event loop. So the single thread is never sitting idle — it's always processing. This is efficient for I/O-bound tasks but bad for CPU-heavy tasks (which block the event loop).
What is the difference between mutex and semaphore? ▼
A mutex (mutual exclusion lock) is binary (locked/unlocked) and has ownership — only the thread that locked it can unlock it. Used for protecting a critical section. A semaphore is a counter — multiple threads can hold it up to the count limit. Used for resource pool management (e.g., limit database connections to 10). A binary semaphore is similar to mutex but without ownership — any thread can signal it.

DBMS — Database Management Systems

Most asked subject in Bangalore product company interviews after DSA. Every backend question eventually touches DBMS. Don't skip normalization or ACID.

Theory + some SQL 5–6 days Very high interview frequency
Topics checklist
Database fundamentals
✓
DBMS vs RDBMS — difference, examples of eachmust
✓
Keys — primary, foreign, candidate, composite, surrogatemust

Primary key: unique identifier, not null. Foreign key: references primary key of another table (referential integrity). Candidate key: any column that could be a primary key. Composite key: primary key made of 2+ columns. Surrogate: artificial key (auto-increment ID). Interview Q: "Why use surrogate keys instead of natural keys?" — natural keys can change (email), surrogate keys don't.

Fix: move customer details to a Customer table. Interviewers ask: "When would you denormalize?" — when read performance matters more than write consistency (analytics, reporting).

Transactions & ACID — critical
✓
ACID properties — Atomicity, Consistency, Isolation, Durabilitymust

Atomicity: all or nothing (bank transfer debit + credit both succeed or both fail). Consistency: DB moves from one valid state to another (balance can't be negative). Isolation: concurrent transactions don't interfere. Durability: committed transactions survive crashes (written to disk). Real example: UPI payment — if debit succeeds but credit fails, atomicity rolls back the debit.

✓
Transaction isolation levels — read uncommitted to serializablemust

4 levels (ascending isolation): Read Uncommitted (dirty reads possible) → Read Committed (no dirty reads, phantom reads possible) → Repeatable Read (no dirty/non-repeatable, phantom possible) → Serializable (fully isolated, slowest). MySQL InnoDB default: Repeatable Read. PostgreSQL default: Read Committed. Higher isolation = less concurrency = slower performance.

✓
Dirty read, non-repeatable read, phantom read — what each meansmust
✓
Optimistic vs Pessimistic locking — use casesgood
Indexing — very practical
✓
What is an index — B-Tree structure, how it speeds up readsmust

Index = separate data structure (usually B-Tree) that maps column values to row locations. Read: instead of full table scan O(n), index gives O(log n). Write penalty: every INSERT/UPDATE/DELETE must also update the index. When to index: columns used in WHERE, JOIN ON, ORDER BY. When not to: small tables, frequently updated columns.

✓
Clustered vs non-clustered indexmust

Clustered: rows are physically sorted by the index key (primary key in InnoDB). Only one per table. Non-clustered: separate structure pointing to rows. Multiple allowed. Analogy: Clustered = dictionary (words in alphabetical order). Non-clustered = book index (points to page numbers, book itself is unordered).

✓
Composite index — column order matters, prefix rulegood
✓
SQL vs NoSQL — when to use each, CAP theorem basicsmust

SQL: structured schema, ACID, joins, vertical scaling. Good for: financial data, user accounts, anything needing consistency. NoSQL: flexible schema, horizontal scaling, eventual consistency. Good for: user activity logs, product catalogs, real-time analytics, MongoDB for JSON data. CAP theorem: can only guarantee 2 of 3 (Consistency, Availability, Partition tolerance). SQL = CP, MongoDB = AP by default.

Interview Q&A — DBMS
Explain ACID properties with a real-world example. ▼
Using a PhonePe transfer of ₹500: Atomicity — debit from A and credit to B must both happen, or neither happens. Consistency — total money before and after must be equal; balance can't go negative. Isolation — if A and B are both transferring simultaneously, they shouldn't interfere. Durability — once the "Transfer Successful" screen appears, the transaction is written to disk even if the server crashes immediately after.
What is the difference between clustered and non-clustered index? ▼
A clustered index physically sorts the table rows by the index key — the data IS the index. Only one allowed per table (usually the primary key). Like a dictionary — words are in alphabetical order. A non-clustered index is a separate structure with pointers to the actual rows — the data is not reordered. Like a book's index at the back — tells you what page to go to. Non-clustered reads require two lookups: index + data page.
When would you use NoSQL over SQL? Give a real product example. ▼
Use NoSQL when: (1) schema is flexible/evolving (product catalog with different attributes per category), (2) you need horizontal scaling across many servers, (3) eventual consistency is acceptable. Example: Swiggy's restaurant menu catalog — every restaurant has different data structures, schema changes frequently, and consistency doesn't need to be immediate. MongoDB fits well. But for Swiggy's financial transactions (payments, refunds) — SQL with ACID is required because consistency is non-negotiable.
Explain 1NF, 2NF, and 3NF. Why do we normalize? ▼
1NF: Each column has atomic values (no arrays in a cell), each row is unique. 2NF: 1NF + every non-key attribute depends on the whole primary key (no partial dependency). 3NF: 2NF + no transitive dependencies (non-key attributes only depend on the primary key). We normalize to: eliminate data redundancy, prevent update anomalies (update one row's city, forget others), and maintain data integrity. Trade-off: more joins = slower reads, so data warehouses denormalize for performance.

Computer Networks

As a full stack developer, this is directly tied to your daily work. HTTP, REST, TCP, DNS — you use these without realizing it. Understand them deeply enough to explain what happens when a user clicks a button in your app.

Directly applies to full stack work 3–4 days High frequency for backend/full stack roles
Topics checklist
Network layers
✓
OSI model — 7 layers, what happens at eachgood

Physical → Data Link → Network → Transport → Session → Presentation → Application. For interviews, focus on: Layer 3 (IP addressing, routing), Layer 4 (TCP/UDP), Layer 7 (HTTP, DNS). Mnemonic: "Please Do Not Throw Sausage Pizza Away." Interviewers rarely ask all 7 — they ask which layer HTTP is on (7) and TCP (4).

✓
TCP vs UDP — reliability, use cases, three-way handshakemust

TCP: reliable, ordered, connection-oriented (handshake: SYN → SYN-ACK → ACK). Use for: HTTP, emails, file transfers. UDP: unreliable, connectionless, faster. Use for: video streaming, DNS, gaming, VoIP (a few lost packets are acceptable, retransmission would be too slow). Three-way handshake ensures both sides are ready before data flows.

✓
IP addressing — IPv4 vs IPv6, public vs private, subnetting basicsgood
HTTP — very important for full stack
✓
HTTP methods — GET, POST, PUT, PATCH, DELETE + when to use eachmust

GET: fetch (idempotent, no body). POST: create (not idempotent). PUT: replace entire resource (idempotent). PATCH: partial update (not always idempotent). DELETE: remove (idempotent). Interview trap: "Is POST idempotent?" — No, calling POST twice can create 2 resources. "Is PUT?" — Yes, calling PUT twice with same body has same result.

✓
HTTP status codes — 1xx, 2xx, 3xx, 4xx, 5xx with key examplesmust

200 OK, 201 Created, 204 No Content. 301 Moved Permanently, 304 Not Modified. 400 Bad Request, 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but no permission), 404 Not Found, 409 Conflict, 422 Unprocessable Entity. 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout. Know the difference between 401 vs 403 — asked frequently.

✓
HTTP/1.1 vs HTTP/2 vs HTTP/3 — key improvementsgood
✓
HTTPS — TLS handshake, symmetric vs asymmetric encryptionmust

HTTPS = HTTP + TLS. TLS handshake: client hello → server sends certificate → client verifies cert with CA → key exchange (asymmetric to share a symmetric key) → symmetric encryption for the session. Why not always asymmetric? — too slow. Key concept: asymmetric (RSA) to exchange keys, then symmetric (AES) for speed. Certificate Authority (CA) proves the server is who it claims to be.

✓
Headers — Content-Type, Authorization, CORS, Cache-Controlmust
Key protocols & concepts
✓
DNS — how it works, resolution chain, cachingmust

DNS resolves domain names to IP addresses. Resolution chain: Browser cache → OS cache → Router → Recursive resolver (ISP) → Root nameserver → TLD nameserver (.com) → Authoritative nameserver → returns IP. TTL controls caching. Interview Q: "What happens when you type google.com in the browser?" — DNS → TCP connection → HTTP request → response rendering.

✓
WebSocket — vs HTTP, use cases, how handshake worksmust

HTTP is request-response (client always initiates). WebSocket is full-duplex persistent connection — server can push data anytime. Starts as HTTP, upgrades via Upgrade header. Use cases: live chat, real-time notifications (Swiggy order tracking), collaborative tools (Google Docs), live sports scores. Your CollabDocs project uses this — know it well.

✓
REST vs GraphQL — trade-offs, when to use eachgood
✓
CORS — what it is, why it exists, how to fix it in Expressmust

CORS (Cross-Origin Resource Sharing): browser security policy — JS can only make requests to same origin by default. Preflight: browser sends OPTIONS request first to check if cross-origin is allowed. Fix in Express: app.use(cors()) or configure allowed origins. Important: CORS is a browser enforcement — Postman and curl are not affected (they're not browsers).

✓
Cookie vs LocalStorage vs SessionStorage — security implicationsmust

Cookie: sent with every request automatically, can be HttpOnly (no JS access → CSRF safe), Secure (HTTPS only). LocalStorage: persists after browser close, accessible via JS (XSS risk). SessionStorage: cleared on tab close. For JWT storage: HttpOnly cookie (safest, prevents XSS theft) vs LocalStorage (convenient but XSS risk). This is asked in every auth-related interview.

Interview Q&A — Networks
What happens when you type a URL in the browser and press Enter? ▼
1. Browser checks cache. 2. DNS resolution: browser cache → OS cache → ISP resolver → root/TLD/authoritative nameserver → IP returned. 3. TCP connection established (3-way handshake). 4. TLS handshake if HTTPS. 5. Browser sends HTTP GET request. 6. Server processes, queries DB, returns HTML. 7. Browser parses HTML, discovers CSS/JS/images, fires more requests. 8. Critical rendering path: DOM + CSSOM → render tree → layout → paint → composite.
What is CORS and why does it exist? How do you fix it in Node.js? ▼
CORS (Cross-Origin Resource Sharing) is a browser security policy that prevents JS on one origin (domain/port) from making requests to a different origin without permission. It exists to prevent malicious sites from stealing data from authenticated sessions on other sites (CSRF-like attacks). Fix in Express: install the cors package and app.use(cors({ origin: 'http://yourdomain.com' })). Preflight: for non-simple requests, browser sends an OPTIONS request first — the server must respond with correct CORS headers.
JWT vs session cookies — which is better and when? ▼
Session cookies: server stores session state, cookie holds only a session ID. Stateful — works for monoliths but hard to scale across servers without shared session store. JWT: stateless — all data is in the token, server needs no storage. Better for: microservices, multiple servers, mobile apps. Downside: can't be revoked easily (until expiry). Best practice: short-lived access token (15 min) + long-lived refresh token in HttpOnly cookie. Store JWT in HttpOnly cookie to prevent XSS, not localStorage.

TypeScript

You know JavaScript well. TypeScript is 80% of the same thing with a type system on top. Don't overthink it. The goal is to be able to write TypeScript React + Node.js confidently. You'll learn the rest on the job.

Practical coding 5–6 days Expected at good product companies
Topics checklist — learn by doing, not just reading
Core types
✓
Primitive types — string, number, boolean, null, undefined, any, unknown, never, voidmust

Key distinctions: any bypasses type checking (avoid!). unknown is safer — you must narrow the type before using it. never = a function that never returns (throws or infinite loop). void = function returns nothing. undefined vs null in TypeScript — both exist, configure with strictNullChecks.

✓
Type inference — when TS infers types, when to annotate explicitlymust
✓
Arrays, tuples, enums — syntax and use casesmust
✓
Union types (A | B) and intersection types (A & B)must

Union: value can be one of multiple types — string | number. Intersection: value must satisfy all types — User & Admin. Literal types: 'GET' | 'POST' | 'PUT'. Discriminated union: union with a common kind or type field used to narrow — very clean for state machines and API response shapes.

Type definitions
✓
interface vs type — differences, when to prefer eachmust

Both define object shapes. interface: can be extended (extends), merged (declaration merging — two interface User blocks merge). type: can represent any type (unions, primitives, tuples), cannot be merged. Rule of thumb: use interface for objects and classes, use type for complex types (unions, intersections, mapped types). Interviewers ask this — have a clear answer.

✓

Generics make components reusable with different types. function identity<T>(arg: T): T — works for any type. Constrained generics: <T extends object>. Real use: useState<User | null>(null) in React. Interview Q&A — TypeScript
What is the difference between 'interface' and 'type' in TypeScript? ▼
Both define shapes, but: interface supports declaration merging (two declarations with the same name automatically merge) and extension via extends. type can represent any type — unions, intersections, primitives, tuples — and is more flexible. Use interface for object shapes and public APIs (since merging is useful for library augmentation). Use type for complex composed types. In practice, either works for most cases — consistency matters more than choosing perfectly.
What are generics and why are they useful? Give a real example. ▼
Generics allow you to write reusable code that works with multiple types while maintaining type safety. Without generics, you'd use any (losing type checking) or duplicate code for each type. Real example: type ApiResponse<T> = { data: T; error: string | null; loading: boolean }. Now ApiResponse<User> gives a user, ApiResponse<Order[]> gives an order list — fully typed, no duplication. Another: function getFirst<T>(arr: T[]): T | undefined — works for any array type.
What is the difference between 'any' and 'unknown'? ▼
any: completely opts out of type checking. You can do anything with it — call methods, access properties. Dangerous because TypeScript won't catch errors. unknown: type-safe alternative. You cannot use an unknown value without first narrowing it (using typeof, instanceof, or a type guard). Use unknown for API responses or external data — it forces you to validate before using, which is safer.

Interview Q&A — SQL
What is the difference between WHERE and HAVING? ▼
WHERE filters rows before aggregation — it operates on individual rows. HAVING filters groups after aggregation — it operates on the results of GROUP BY. You cannot use aggregate functions (COUNT, SUM, AVG) in WHERE. Example: SELECT dept, COUNT(*) FROM employees GROUP BY dept HAVING COUNT(*) > 5 — this finds departments with more than 5 employees. If you tried WHERE COUNT(*) > 5, you'd get an error.
Find the 2nd highest salary from an Employee table. ▼
Using window function (best): SELECT salary FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) as rnk FROM Employee) t WHERE rnk = 2. Using subquery: SELECT MAX(salary) FROM Employee WHERE salary < (SELECT MAX(salary) FROM Employee). The window function approach works for any Nth salary by changing the WHERE condition, while the subquery only works for 2nd highest easily.
What is the difference between DELETE, TRUNCATE, and DROP? ▼
DELETE: removes specific rows (with WHERE clause), can be rolled back, fires triggers, logs each row deletion (slow for large tables). TRUNCATE: removes all rows, minimal logging (fast), cannot be rolled back in most DBs, resets auto-increment, doesn't fire row-level triggers. DROP: removes the entire table (structure + data + indexes + constraints). You can't SELECT from a dropped table. DELETE is DML, TRUNCATE is DDL in most databases.
Explain INNER JOIN vs LEFT JOIN with a real example. ▼
Using Orders and Customers tables: INNER JOIN returns only customers who have placed orders (rows with matches in both tables). LEFT JOIN returns all customers — those with orders show the order data, those without orders show NULL in the order columns. Use case: INNER when you only care about matched data (active users with purchases). LEFT when you need all entities regardless of relation (all users, including those who never ordered — to find inactive users).
