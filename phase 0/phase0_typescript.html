Concept 01 of 08

Why TypeScript? What Problem It Solves

TypeScript is not just "JavaScript with types." It changes how you design code, catch bugs, and document intent. Know the real arguments for why companies adopt it.
must know"Why TypeScript?" is the first question in every TS interview
01The real problem TypeScript solves

JavaScript is dynamically typed — types are determined at runtime. This means you can pass the wrong type to a function, access a property that doesn't exist, or call something that isn't a function — and JavaScript won't tell you until the code actually runs (and your user sees a crash). 

// JavaScript — these all silently fail at runtime
function getUser(id) {
    return db.users[id];  // returns undefined if id doesn't exist
}

const user = getUser(999);
console.log(user.name);   // TypeError: Cannot read property 'name' of undefined
// This crashes in production. TypeScript would catch it at compile time.

function add(a, b) { return a + b; }
add("5", 3);  // → "53" (string concatenation!) instead of 8
// TypeScript would flag this as a type error immediately

TypeScript is a static type checker — it checks types at compile time, before code runs. The TypeScript compiler catches type errors and refuses to compile until you fix them. You ship less broken code.

02What TypeScript actually is

TypeScript is a superset of JavaScript — every valid JavaScript file is a valid TypeScript file. TypeScript adds type annotations, which are stripped during compilation. The output is plain JavaScript that runs anywhere JavaScript runs.

BenefitReal impact
Compile-time errorsCatch "cannot read property of undefined" before deployment. Not in production at 2 AM.
Autocomplete / IntelliSenseYour IDE knows the shape of every object. Type user. and see all available fields. Massive productivity boost.
Self-documenting codeFunction signatures tell you what goes in and what comes out. No need to read the implementation.
Safe refactoringRename a field — TypeScript shows every place that needs updating. Refactor with confidence.
Better team collaborationAPI contracts are explicit. "What does this function accept?" is answered by the type, not a comment that might be wrong.
TypeScript does NOT: Make JavaScript faster at runtime. Run in the browser (TS compiles to JS first). Guarantee runtime safety (you can still get runtime errors — TS only checks what it knows at compile time). Eliminate all bugs. It's a powerful tool, not a silver bullet.

Why TypeScript — 30-second revision

  • TypeScript: static type checker. Catches errors at compile time, not at runtime in production.
  • Superset of JavaScript: every JS file is valid TS. Types are stripped at compile time — output is plain JS.
  • Benefits: IDE autocomplete, safe refactoring, self-documenting, fewer runtime crashes, better team collaboration.
  • Does NOT make JS faster. Does NOT eliminate all runtime errors. Does NOT run in browser directly.

Basic Types + Type Annotations

Primitive types, arrays, objects, union types, literal types, optional properties. The building blocks. Know when to annotate explicitly vs let TypeScript infer.
must knowFoundation — everything else builds on this
01Primitive and core types
// ── PRIMITIVE TYPES ──────────────────────────────────────────
let name:    string  = "Ravi";
let age:     number  = 25;
let active:  boolean = true;
let nothing: null    = null;
let missing: undefined = undefined;
let id:      symbol  = Symbol('id');
let big:     bigint  = 9007199254740991n;

// TYPE INFERENCE: TypeScript is smart — you don't always need to annotate
let city = "Bangalore";  // TypeScript INFERS: string
let count = 0;           // TypeScript INFERS: number
// Rule: annotate when TypeScript can't infer, or when the annotation adds clarity

// ── ARRAYS ───────────────────────────────────────────────────
const names:  string[]     = ["Ravi", "Priya"];
const ids:    number[]     = [1, 2, 3];
const mixed:  (string | number)[] = ["a", 1, "b"];
const users:  Array<string> = ["Ravi"];   // equivalent to string[]

// ── OBJECT TYPE ──────────────────────────────────────────────
let user: {
    id:      number;
    name:    string;
    email?:  string;    // '?' means optional — may be undefined
    readonly joinedAt: Date;  // readonly: cannot reassign after creation
} = {
    id: 1,
    name: "Ravi",
    joinedAt: new Date()
};
// user.joinedAt = new Date() → Error: Cannot assign to 'joinedAt' (readonly)

// ── UNION TYPES: OR ──────────────────────────────────────────
type ID = string | number;     // can be either
type Status = "pending" | "active" | "inactive";  // literal union (enum-like)

function setStatus(status: Status) { }
setStatus("active");    // ✓
setStatus("deleted");   // ✗ Error: "deleted" is not assignable to Status

// ── TUPLE: fixed-length, known types at each position ────────
const point: [number, number] = [12.9, 77.5];   // [lat, lng]
const entry: [string, number] = ["score", 95];
// point[2] → Error: Tuple type '[number, number]' has no element at index 2

// ── any vs unknown vs never ──────────────────────────────────
let dangerous: any;         // escapes type system — AVOID in production
dangerous = "hello";
dangerous.anything();      // no error — TypeScript looks away

let safe: unknown;          // safer alternative to any
safe = "hello";
// safe.toUpperCase() → Error! Must narrow first:
if (typeof safe === "string") safe.toUpperCase();  // ✓ after narrowing

function throwError(msg: string): never {
    throw new Error(msg);  // never returns — return type is 'never'
}

Interview Q&A — Basic Types
What is the difference between `any`, `unknown`, and `never`? ▼
Strong answerany: escapes the type system entirely. You can do anything with an any variable — call it, access properties, assign anything. TypeScript effectively turns off for that value. Dangerous: using any removes the entire point of TypeScript. unknown: the safe alternative to any. You can assign anything TO it, but you can't DO anything with it until you narrow its type first (typeof check, instanceof, type guard). Forces you to validate before use. Use for: API responses, external input, JSON.parse result. never: represents a type that never occurs. A function that always throws or has an infinite loop has return type never. Useful in exhaustive checks — if TypeScript says a value is never, you've handled all cases.
What is a union type? What is a literal type? ▼
Strong answerUnion type: A | B — a value can be of type A or type B. Example: string | number — the value is either a string or a number. To use the value, you must narrow it first (check which type it actually is). Literal type: a type that's a specific VALUE rather than a general type. "pending" | "active" | "completed" — the value must be exactly one of these three strings, not any arbitrary string. Like a string-based enum. Literal unions are great for status fields, action types, configuration options. TypeScript will catch typos at compile time: setStatus("pendng") → type error, "pendng" is not assignable to "pending" | "active" | "completed".

Basic Types — 60-second revision

  • Primitives: string, number, boolean, null, undefined, symbol, bigint.
  • Arrays: string[] or Array<string>. Tuple: [string, number] — fixed length, known types per position.
  • Optional property: name? — may be string or undefined. Readonly: cannot reassign after initialization.
  • Union: A | B — can be either. Literal union: "pending" | "active" — specific values only.
  • any: escape hatch — avoid. unknown: safe any — must narrow before use. never: unreachable code, always-throw functions.
  • Inference: TS infers from initialization. Annotate: function params (required), return types (good practice), empty arrays.

Interface vs Type Alias

The most asked TypeScript question in interviews. They look similar but have real differences. Know when to choose which — and which one your DevTracker project should use.
must knowAsked in almost every TypeScript interview
01Interface — for objects and classes
// Interface: defines the shape of an object or class contract
interface User {
    id:        number;
    name:      string;
    email:     string;
    role?:     "admin" | "user";
    readonly createdAt: Date;
}

// Interfaces EXTEND other interfaces (IS-A relationship)
interface AdminUser extends User {
    permissions: string[];
    canDelete:   boolean;
}

// DECLARATION MERGING: you can re-open an interface to add fields
interface User {
    lastLogin?: Date;   // merged with the original User interface
}
// Now User has: id, name, email, role, createdAt, lastLogin
// This is how TypeScript extends library types (e.g., Express Request)

// Interface for a class (class contract)
interface Repository<T> {
    findById(id: number): Promise<T | null>;
    save(entity: T): Promise<T>;
    delete(id: number): Promise<void>;
}

class UserRepository implements Repository<User> {
    async findById(id: number): Promise<User | null> { return null; }
    async save(user: User): Promise<User> { return user; }
    async delete(id: number): Promise<void> { }
}
02Type Alias — for everything else
// Type alias: a name for ANY type expression

// Can alias primitives (interfaces can't)
type UserID = number;
type Email  = string;

// Can create union types (interfaces can't)
type Status = "pending" | "active" | "cancelled";
type ID     = string | number;

// Can create intersection types (like extends but for types)
type AdminUser = User & { permissions: string[] };

// Can alias tuples, functions, mapped types
type Point    = [number, number];
type Callback = (error: Error | null, result?: string) => void;

// Type alias objects work almost like interfaces
type User = {
    id:   number;
    name: string;
};

// But: type aliases cannot be re-opened (no declaration merging)
type User = { email: string; };   // ERROR: Duplicate identifier 'User'

The practical rule (used in real teams): Use interface for object shapes that represent a domain concept (User, Order, Product) — especially if they might be extended. Use type for unions, utility types, and complex type compositions. In your DevTracker project: interface User, interface Job — but type Status = "applied" | "interview" | "rejected".
Interview Q&A — Interface vs Type
What is the difference between interface and type in TypeScript? ▼
Strong answerBoth can define object shapes, and for object types they're largely interchangeable. Key differences: (1) Declaration merging: interfaces can be re-opened and extended across multiple declarations — TypeScript merges them. Type aliases cannot. This is how you augment library types (e.g., adding fields to Express's Request). (2) What they can describe: type aliases can describe unions (string | number), tuples, primitives, and mapped types — interfaces can only describe object shapes and function signatures. (3) Extends vs &: interface uses extends for inheritance, type uses & for intersection. (4) Error messages: interfaces show their name in errors; type aliases expand their definition (can be verbose). Use interface for domain objects (User, Product), type for unions and complex compositions.
What is declaration merging? Give a practical use case. ▼
Strong answerDeclaration merging: if you define an interface with the same name twice, TypeScript merges the two declarations into one. The merged interface has all properties from both declarations. Practical use case: extending Express's Request type. Express defines Request in its types. When you add JWT auth middleware, you want to attach the decoded user to the request: declare global { namespace Express { interface Request { user?: JWTPayload } } } — now req.user is available with proper typing everywhere in your routes. This is only possible because interfaces support declaration merging. You can't do this with a type alias — that's why Express used interface for Request.

Interface vs Type — 60-second revision

  • interface: object shapes, class contracts, declaration merging (re-open to add fields).
  • type: unions, intersections, primitives, tuples, mapped types, anything complex.
  • Key difference: interface supports declaration merging. type does not — redefining is an error.
  • Declaration merging: re-open interface in multiple declarations → TS merges. Used to extend library types (Express Request).
  • extends vs &: interface extends Interface. type A = B & C.
  • Rule: interface for domain objects. type for unions and utility compositions.
Concept 04 of 08

Generics

Write code that works with any type without losing type safety. The most powerful TypeScript feature — and the most misunderstood by freshers. Learn to read, write, and constrain generics.
must knowGenerics are asked in every mid-to-senior TS interview
01The problem generics solve

Without generics, you'd write separate functions for each type, or use any and lose type safety. Generics let you write a function ONCE that works with any type, while still knowing exactly what type is used at each call site. 

// WITHOUT generics — either duplicate code or use 'any'
function getFirstString(arr: string[]): string { return arr[0]; }
function getFirstNumber(arr: number[]): number { return arr[0]; }
// Duplicate code. If you add User[], Order[], etc., keep adding functions.

// WITH generics — one function, any type, full type safety
function getFirst<T>(arr: T[]): T {
    return arr[0];
}
// T is a TYPE PARAMETER — placeholder that TypeScript fills in at each call site

const name:   string = getFirst(["Ravi", "Priya"]);  // T = string
const score:  number = getFirst([95, 87, 92]);       // T = number
const active: boolean = getFirst([true, false]);      // T = boolean
// TypeScript infers T from the argument — no need to write getFirst<string>(...)
02Generic functions — real-world patterns
// ── Pattern 1: API Response wrapper ──────────────────────────
interface ApiResponse<T> {
    data:    T;
    status:  number;
    message: string;
}

// TypeScript knows the exact shape of data in each case
type UserResponse  = ApiResponse<User>;      // data: User
type OrderResponse = ApiResponse<Order>;     // data: Order
type ListResponse  = ApiResponse<User[]>;   // data: User[]

// ── Pattern 2: Generic fetch function ────────────────────────
async function fetchData<T>(url: string): Promise<T> {
    const res  = await fetch(url);
    const json = await res.json();
    return json as T;  // type assertion — we trust the API shape
}

// Caller specifies what they expect back
const user  = await fetchData<User>('/api/users/1');
const users = await fetchData<User[]>('/api/users');
// user.name ✓ — TS knows user is User. user.invalid → compile error.

// ── Pattern 3: Generic React useState typing ─────────────────
const [user, setUser] = useState<User | null>(null);
const [jobs, setJobs] = useState<Job[]>([]);
// TypeScript knows setUser only accepts User | null, not arbitrary objects
03Generic constraints — restrict what T can be
// Without constraints, T can be ANYTHING — even number, which has no .name
function printName<T>(obj: T) {
    console.log(obj.name);  // Error: Property 'name' does not exist on type 'T'
}

// WITH constraint: T must be an object that has at least a name property
function printName<T extends { name: string }>(obj: T) {
    console.log(obj.name);  // ✓ — TS guarantees T has name
}

printName({ name: "Ravi", age: 25 });  // ✓ — has name
printName(42);                         // ✗ — number has no name property

// Useful constraint: keyof — ensures K is a valid key of T
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key];
}

const user = { id: 1, name: "Ravi", email: "r@g.com" };
const name = getProperty(user, "name");   // ✓ returns string
const id   = getProperty(user, "id");     // ✓ returns number
getProperty(user, "phone");              // ✗ Error: "phone" not in User
04Generic interfaces and classes
// Generic class — Stack data structure with type safety
class Stack<T> {
    private items: T[] = [];

    push(item: T): void  { this.items.push(item); }
    pop():         T | undefined { return this.items.pop(); }
    peek():        T | undefined { return this.items[this.items.length - 1]; }
    isEmpty():     boolean       { return this.items.length === 0; }
}

const numStack = new Stack<number>();
numStack.push(42);
numStack.push("hello");  // ✗ Error: Argument of type 'string' is not assignable to 'number'

const userStack = new Stack<User>();
const topUser = userStack.peek();  // type: User | undefined ✓
Interview Q&A — Generics
What are generics? Why use them instead of `any`? ▼
Strong answerGenerics are type parameters that let you write functions, classes, and interfaces that work with any type while preserving type information. The key difference from any: any abandons type safety — once you assign any, TypeScript no longer knows or checks the type. Generics preserve the type relationship. Example: function identity<T>(arg: T): T { return arg; } — if you call it with a string, TypeScript knows the return is also a string. With any, the return would be any — you'd lose autocomplete and type checking on the result. Real use case: ApiResponse<T> — a wrapper where data is typed to whatever T is. All callers get the exact type they passed, not any.
What is a generic constraint? Give an example. ▼
Strong answerA generic constraint restricts what types can be passed as the type parameter. Using T extends SomeType, TypeScript ensures T has at least the properties of SomeType. Example: function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] — K must be a valid key of T. This prevents accessing invalid properties: getProperty(user, "phone") is a compile error if user doesn't have a phone field. Another example: function merge<T extends object, U extends object>(a: T, b: U): T & U — T and U must both be objects (not primitives), enforcing that you can only merge object types. Constraints give you the power of generics while still knowing something about T's shape.

Generics — 60-second revision

  • Generics: type parameters (<T>) that let you write reusable code while preserving type info.
  • vs any: generics preserve the type relationship. any throws it away.
  • Inference: TS infers T from arguments — you usually don't need to write <string> explicitly.
  • Constraints: T extends SomeType — restrict what T can be. T extends keyof U — T must be a key of U.
  • Common patterns: ApiResponse<T> wrapper, fetchData<T>() for typed fetch, useState<T> in React.
  • Generic class: Stack<T>. push(item: T), pop(): T | undefined. Type-safe for any element type.
Concept 05 of 08

Type Narrowing + Type Guards

When you have a union type, TypeScript needs to know which specific type it is before you use type-specific operations. Narrowing is how you prove the type to TypeScript.
must knowNarrowing explains why your TS code sometimes doesn't compile
01Type narrowing techniques
// ── typeof narrowing ─────────────────────────────────────────
function printId(id: string | number) {
    if (typeof id === "string") {
        // In this block, TS knows id is string
        console.log(id.toUpperCase());  // ✓ string method
    } else {
        // In this block, TS knows id is number
        console.log(id.toFixed(2));     // ✓ number method
    }
}

// ── instanceof narrowing ─────────────────────────────────────
function handleError(error: Error | string) {
    if (error instanceof Error) {
        console.log(error.message);  // ✓ Error has .message
    } else {
        console.log(error.toUpperCase());  // ✓ string in else branch
    }
}

// ── in operator narrowing ────────────────────────────────────
interface Cat { meow(): void; }
interface Dog { bark(): void; }

function makeSound(animal: Cat | Dog) {
    if ("meow" in animal) {
        animal.meow();  // ✓ TS knows it's a Cat
    } else {
        animal.bark();  // ✓ TS knows it's a Dog
    }
}

// ── Discriminated unions — the cleanest pattern ───────────────
interface LoadingState { kind: "loading"; }
interface SuccessState { kind: "success"; data: User; }
interface ErrorState   { kind: "error";   message: string; }

type AppState = LoadingState | SuccessState | ErrorState;

function render(state: AppState) {
    switch (state.kind) {  // 'kind' is the discriminant
        case "loading": return "Loading...";
        case "success": return state.data.name;    // TS knows data exists
        case "error":   return state.message;       // TS knows message exists
    }
}

// ── Custom type guard function ────────────────────────────────
function isUser(obj: unknown): obj is User {
    return (
        typeof obj === "object" &&
        obj !== null &&
        "id" in obj &&
        "name" in obj
    );
}

function processData(data: unknown) {
    if (isUser(data)) {
        console.log(data.name);  // ✓ TS knows data is User after the guard
    }
}
02Exhaustive checks with never
// If you add a new variant to AppState, the default branch catches it
function render(state: AppState) {
    switch (state.kind) {
        case "loading": return "...";
        case "success": return state.data.name;
        case "error":   return state.message;
        default:
            // state is 'never' here — all cases handled
            const exhaustiveCheck: never = state;
            throw new Error(`Unhandled state: ${exhaustiveCheck}`);
    }
}
// If you add 'interface ReloadingState { kind: "reloading" }' to AppState
// TypeScript immediately shows an error on the never assignment
// Compile error forces you to handle the new case. Zero runtime surprises.
Interview Q&A — Narrowing
What is type narrowing? What are the different ways to do it? ▼
Strong answerType narrowing is the process of refining a wider union type to a more specific type within a conditional block. TypeScript tracks these checks and narrows the type accordingly. Methods: (1) typeof — for primitives: if (typeof x === "string"). (2) instanceof — for class instances: if (error instanceof Error). (3) in — for property existence: if ("meow" in animal). (4) Discriminated unions — check a shared literal field: switch (state.kind). (5) Custom type guards — function with return type obj is Type. (6) Truthiness — if (value) narrows out null/undefined. Discriminated unions are the cleanest pattern for complex state — each variant has a unique literal "tag" field, and the switch on that tag narrows perfectly.
What is a discriminated union? Give a React example. ▼
Strong answerA discriminated union is a union of types where each member has a shared property with a unique literal value — the discriminant. TypeScript uses this property to narrow to the correct type. React example: modeling async state: type State = { status: "idle" } | { status: "loading" } | { status: "success"; data: User } | { status: "error"; message: string }. In your component: switch (state.status). In the "success" case, TypeScript knows state.data exists. In the "error" case, state.message exists. If you add a new status later, TypeScript will show a compile error if you haven't handled it (with the exhaustive check pattern). This eliminates entire classes of runtime bugs like accessing state.data when you're in an error state.

Narrowing — 60-second revision

  • Narrowing: refine union type → specific type inside a conditional block.
  • typeof: for primitives. instanceof: for class instances. in: for property existence.
  • Discriminated union: shared tag field with literal values. switch on tag → TS narrows to each variant.
  • Custom type guard: function returns `obj is Type` — tells TS the type after the check.
  • Exhaustive check with never: default case assigns to never → compile error if new union member not handled.

Utility Types

TypeScript ships 20+ built-in utility types. Know the essential 8 cold — Partial, Required, Readonly, Pick, Omit, Record, ReturnType, Parameters. You use these daily.
must knowInterviewers test if you know TS beyond basic types
01The 8 essential utility types
Partial<T>
Makes all properties optional
Use for update DTOs — not all fields required on update.
Required<T>
Makes all properties required
Opposite of Partial. Removes all optional marks.
Readonly<T>
All properties become readonly
Use for immutable config objects. Prevents accidental mutation.
Pick<T, K>
Select a subset of keys from T
Create a type with only the fields you need. Pick<User, "id" | "name">
Omit<T, K>
Remove keys K from T
Omit<User, "password"> — safe to send to client. Opposite of Pick.
Record<K, V>
Object with keys K, values V
Record<string, number> = { [key: string]: number }. Typed dictionaries.
ReturnType<F>
Extract function's return type
ReturnType<typeof getUser> — type your result from an existing function.
Parameters<F>
Extract function's params as tuple
Parameters<typeof fetchData> — get the arg types of any function.
02Using utility types — real DevTracker examples
interface User {
    id:        number;
    name:      string;
    email:     string;
    password:  string;   // sensitive — never send to frontend
    createdAt: Date;
}

// ── Omit: safe public-facing type ───────────────────────────
type PublicUser = Omit<User, "password">;
// PublicUser: { id, name, email, createdAt } — no password
// Express route returns PublicUser — TypeScript ensures password never leaks

// ── Partial: update DTO ──────────────────────────────────────
type UpdateUserDTO = Partial<Omit<User, "id" | "createdAt">>;
// All of User's fields (minus id and createdAt) become optional
// PATCH /users/1 body can have name?, email?, password? — all optional

// ── Pick: projection ─────────────────────────────────────────
type UserPreview = Pick<User, "id" | "name">;
// For dropdown lists — only need id and name, not full user object

// ── Record: typed dictionaries ───────────────────────────────
type StatusCounts = Record<"applied" | "interview" | "rejected" | "offer", number>;
const counts: StatusCounts = { applied: 5, interview: 2, rejected: 1, offer: 0 };
// TypeScript ensures all 4 status keys are present and values are numbers

// ── ReturnType: extract from existing function ────────────────
async function getUser(id: number) {
    return { id, name: "Ravi", email: "r@g.com" };
}
type GetUserResult = Awaited<ReturnType<typeof getUser>>;
// GetUserResult = { id: number; name: string; email: string }
// Now you can type other code that receives this function's return value

// ── NonNullable: remove null/undefined ────────────────────────
type MaybeUser = User | null | undefined;
type DefiniteUser = NonNullable<MaybeUser>;  // = User (null and undefined removed)
Interview Q&A — Utility Types
What is the difference between Pick and Omit? Give a real use case for each. ▼
Strong answerPick<T, K>: creates a new type by selecting only the specified keys from T. Use when you want a small subset of a large type. Real use: dropdown list needs only id and name from User — Pick<User, "id" | "name">. Prevents accidentally sending unnecessary data. Omit<T, K>: creates a type with all keys of T EXCEPT the specified ones. Use when most fields are needed but a few must be excluded. Real use: Omit<User, "password"> — safe public type to send to the frontend. The password field is structurally absent from the type — TypeScript guarantees you can't accidentally include it. Rule: use Pick when you're keeping a few fields. Use Omit when you're removing a few fields from a large type.
How do you create an update DTO type where all fields are optional? ▼
Strong answerUse Partial<T>. For a PATCH endpoint where any subset of fields can be updated: type UpdateUserDTO = Partial<Omit<User, "id" | "createdAt">> — first Omit the immutable fields (id and createdAt shouldn't be changeable via an update), then wrap with Partial to make all remaining fields optional. The result: a type where name, email, password are all optional — the client can send just { name: "New Name" } and TypeScript validates it. Combine with runtime validation (Zod) for the actual data check, but Partial handles the compile-time type contract cleanly.

Utility Types — 60-second revision

  • Partial<T>: all optional. Use for update DTOs (PATCH body).
  • Required<T>: all required. Opposite of Partial.
  • Readonly<T>: all readonly. Immutable configs.
  • Pick<T, K>: keep only K keys. Use for small projections (id + name only).
  • Omit<T, K>: remove K keys. Use to exclude sensitive fields (password).
  • Record<K, V>: typed dictionary. Record<Status, number> = typed count object.
  • ReturnType<typeof fn>: extract return type. Awaited<ReturnType<...>> for async functions.
  • NonNullable<T>: remove null and undefined from type.

Interview Q&A — Express Typing
How do you add a `user` property to Express's Request object? Why do you need this? ▼
Strong answerExpress's Request type doesn't include a user property — that's set by your auth middleware. Without extending the type, accessing req.user would give a TypeScript error. Solution: declaration merging. Create a types/express.d.ts file and re-open Express's namespace: declare global { namespace Express { interface Request { user?: JWTPayload } } }. Since Express uses interface for Request (not type alias), TypeScript merges this declaration with the existing one. Now req.user is typed as JWTPayload | undefined everywhere in your app. This is why we use interfaces for library types — their declarative merging allows exactly this extension pattern. TypeScript ensures you only access .userId, .email, .role on req.user — no typos, no accessing non-existent properties.
How do you type the request body and params in an Express route? ▼
Strong answerExpress's Request is generic: Request<Params, ResBody, ReqBody, QueryString>. To type them: define interfaces for each and pass as type arguments. Example: req: Request<{ id: string }, {}, UpdateJobBody>. Note that URL params are always strings even if you typed them as number — you must convert: Number(req.params.id). For the body: if you have Zod validation middleware that parses and validates before your handler runs, the validated data is on req.body with the correct type. If you use the generic approach, TypeScript knows the shape at compile time but runtime validation (Zod) is still required since TypeScript can't validate incoming HTTP data. Combine both: type-level for autocomplete, Zod for runtime.

Express Typing — 60-second revision

  • Route handler: Request<Params, ResBody, ReqBody, Query>. All type params are generic.
  • URL params: always string in type. Convert with Number() for numeric IDs.
  • Extend Request: declare global namespace Express interface Request { user?: JWTPayload }. Requires declaration merging → use interface not type.
  • Service layer: use Omit and Partial for Create/Update input types. Return Promise<Job | null> for find operations.
  • Error handler: type as ErrorRequestHandler (4-argument middleware signature). instanceof AppError for custom errors.

All TypeScript Interview Questions

20 questions. Answer out loud without looking first. Interviewers connect every TS answer back to your actual project — be ready for "how did you use this in DevTracker?"
Complete TypeScript Q&A bank — 20 questions
1. What is TypeScript? Why would you choose it over JavaScript? ▼
AnswerTypeScript is a statically-typed superset of JavaScript that compiles to plain JS. Benefits: (1) Compile-time error detection — catch "cannot read property of undefined" before runtime. (2) IDE autocomplete and IntelliSense — type a dot and see all valid methods/fields. (3) Self-documenting code — function signatures are explicit contracts. (4) Safe refactoring — rename a field and TypeScript shows every affected location. Use JS for quick scripts, small projects, prototypes. Use TypeScript for any project with multiple files, a team, or production expectations. My DevTracker project uses TypeScript throughout — the no-any rule caught several API shape mismatches during development.
2. What is the difference between interface and type alias? When use which? ▼
AnswerBoth can define object shapes. Key differences: declaration merging (interface can be re-opened and merged; type alias cannot), and expressiveness (type can describe unions, primitives, tuples; interface can only describe objects). Use interface for domain objects (User, Job, Order) that might need extending or that implement classes. Use type for unions ("pending" | "active"), intersections (A & B), aliases for complex types, utility type results. Practical rule: if in doubt and it's an object shape, use interface. If it's a union or complex composition, use type.
3. What are generics? Why use them instead of `any`? ▼
AnswerGenerics are type parameters that allow writing reusable code that works with multiple types while preserving type information. Unlike any (which discards type info and disables checking), generics maintain the type relationship: if you call fetchData<User>(), TypeScript knows the return is User, not any — you get autocomplete on the result. Use cases: ApiResponse<T> wrapper, generic Stack<T> class, fetchData<T>() function. Type parameters can be constrained with extends: T extends object ensures T is not a primitive. T extends keyof U ensures T is a valid key of U.
4. What is the difference between `any` and `unknown`? ▼
Answerany: escapes the type system entirely. You can call methods, access properties, do anything — TypeScript looks away. Contagious — code receiving an any value also becomes untyped. unknown: the safe version of any. You can assign anything TO it, but you cannot DO anything with it without first narrowing its type (typeof, instanceof, custom type guard). Forces you to validate before use. Use unknown for: API responses (json: unknown), catch blocks (error: unknown), function parameters that accept arbitrary input. Example: JSON.parse returns any — wrap the result in a Zod schema to convert from any to your specific type safely.
5. What is type narrowing? What is a discriminated union? ▼
AnswerType narrowing: refining a union type to a specific type within a conditional block. Methods: typeof (primitives), instanceof (class instances), in (property check), switch on discriminant. Discriminated union: a union where each member has a shared literal "tag" field. switch (state.kind) narrows to the specific variant — in the "success" case, TypeScript knows data exists; in "error" case, message exists. If a new variant is added and not handled, exhaustive check (assigning to never) shows a compile error. This eliminates runtime errors from accessing properties on the wrong union variant. Used in React for modeling async state: { status: "loading" } | { status: "success"; data: User } | { status: "error"; message: string }.
6. What is `Partial`? When do you use it? ▼
AnswerPartial<T> creates a new type where all properties of T become optional (may be undefined). Use case: update DTOs for PATCH endpoints. For PATCH /users/:id, the client sends only the fields they want to change — you shouldn't require all fields. type UpdateUserDTO = Partial<Omit<User, "id" | "createdAt">> — omit immutable fields, then make everything else optional. TypeScript then validates that any provided fields are the correct type, and allows any subset to be present. Commonly combined with Omit to first remove fields that should never be updatable, then Partial for the rest.
7. What is the difference between `Pick` and `Omit`? ▼
AnswerPick<T, K>: select only the specified keys from T. Use when you need a small subset. Omit<T, K>: remove specified keys from T. Use when you want most fields except a few. Example: Pick<User, "id" | "name"> for a dropdown list — only those two fields. Omit<User, "password"> for API responses — all fields except the sensitive one. Rule: Pick when you're keeping a few fields (small output). Omit when you're removing a few fields from a large type (small exclusion). Both create new types without modifying the original — original User is unchanged.
8. What does `readonly` do? What is the difference between readonly and const? ▼
Answerconst: prevents reassigning the VARIABLE (the binding). The object it points to can still be mutated: const user = { name: "Ravi" }; user.name = "Priya"; // valid! readonly: prevents reassigning a PROPERTY on an object. interface Config { readonly apiUrl: string } — config.apiUrl = "..." → compile error. To make all properties readonly: Readonly<T> utility type. Note: both are compile-time only — there's no runtime enforcement. Object.freeze() adds runtime immutability. In React: props should effectively be readonly (don't mutate props). TypeScript doesn't enforce this but it's a convention. Use readonly for configuration objects, DTOs that should not be modified after creation.
9. How do you type a React component's props and children? ▼
AnswerDefine a Props interface, destructure in the function parameters. For children: use React.ReactNode (most permissive — accepts string, number, JSX, arrays, null). Use React.ReactElement if you only want JSX elements. Event handlers: React.ChangeEvent<HTMLInputElement>, React.FormEvent<HTMLFormElement>, React.MouseEvent<HTMLButtonElement>. Optional props: add ? to the interface field. Default values: use destructuring defaults function Component({ isLoading = false }: Props). Avoid React.FC (deprecated-ish in React 18) — use plain function instead. useState: useState<User | null>(null), useState<Job[]>([]). For hooks with complex return types, explicitly annotate the return type to prevent inference surprises.
10. What is `ReturnType` and when do you use it? ▼
AnswerReturnType<typeof fn> extracts the return type of a function as a type. Use when: you want to type something based on an existing function's return but don't want to repeat the type definition. Example: async function getUser() { return { id: 1, name: "Ravi" } }. type UserResult = Awaited<ReturnType<typeof getUser>> — extracts the resolved type. Now if you change what getUser returns, UserResult automatically updates. Practical: if your service functions return DB models, use ReturnType to type the controller layer without duplicating types. Awaited<> is needed to unwrap Promise — ReturnType of an async function is Promise<T>; Awaited removes the Promise wrapper.
11. What is `Record`? Give a real use case. ▼
AnswerRecord<K, V> creates an object type with keys of type K and values of type V. Equivalent to { [key in K]: V }. Use case: when you need a typed dictionary or map. Example: Record<"pending" | "active" | "rejected", number> — a typed status count object where all four status keys must be present and values are numbers. TypeScript will error if you access a key that's not in the union. Another use: Record<string, User> — a user cache indexed by string ID. Prefer Record<UserID, User> where UserID = string for documentation. Record is cleaner than { [key: string]: V } because Record with a literal union type is exhaustive — you must provide all keys.
12. How do you extend Express's Request type to add a `user` field? ▼
AnswerUse declaration merging. Create a file types/express.d.ts. Re-open the Express namespace: declare global { namespace Express { interface Request { user?: JWTPayload } } }. This works because Express defines Request as an interface (not type alias), so it supports merging. TypeScript automatically includes this declaration in the project. Your auth middleware sets req.user after JWT verification. All route handlers now have req.user typed as JWTPayload | undefined — autocomplete works, accessing invalid fields is a compile error. Note: include this types file in tsconfig.json's include array, or TypeScript might not pick it up.
13. What is a type guard? How do you write a custom one? ▼
AnswerA type guard is a function that narrows a type at the point where it's called. The key is the return type annotation: obj is SomeType. When this function returns true, TypeScript narrows the type of obj to SomeType in the if-block. Example: function isUser(obj: unknown): obj is User { return typeof obj === "object" && obj !== null && "id" in obj && "name" in obj }. After calling if (isUser(data)) { ... }, TypeScript knows data is User inside the block. Use for: validating API responses (unknown → specific type), narrowing union members, type-safe runtime checks. The function must actually implement the check correctly — TypeScript trusts your assertion and won't verify it. Use Zod schemas for robust runtime validation.
14. What is the non-null assertion operator `!`? When should you use it? ▼
AnswerThe non-null assertion operator (!) tells TypeScript "I know this value is not null or undefined, trust me." It strips null and undefined from the type. Example: req.user!.userId — you know the auth middleware set req.user, but TypeScript sees it as optional. Use sparingly and only when you're certain the value exists at that point in code. Never use it to suppress TypeScript errors you don't understand — that defeats the purpose of TypeScript. Better alternatives: optional chaining (req.user?.userId), explicit null check (if (!req.user) throw...), or restructure code so the value is guaranteed non-null. Appropriate uses: after verified existence (if (!ref.current) return; ... ref.current.focus()), or environment variables that are guaranteed to exist (process.env.JWT_SECRET!).
15. What is the `keyof` operator? Give an example. ▼
Answerkeyof T produces a union of all keys of type T. Example: keyof User = "id" | "name" | "email" | "createdAt". Use cases: (1) Function that accesses a property by name: function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] — ensures key is actually a key of T, and the return type is T[K] (the type of that specific property). (2) Mapped types: { [K in keyof User]: string } — creates a new type with the same keys but all string values. (3) Validating property names at compile time: instead of passing "name" as a raw string (typo-prone), pass it as a keyof User literal — TypeScript catches typos. Combine with typeof: keyof typeof someObject — gets keys from a runtime object's inferred type.
16. What is optional chaining `?.` and nullish coalescing `??`? ▼
AnswerOptional chaining (?. ): safely access nested properties that might be null/undefined. user?.address?.city — if user is null, returns undefined instead of throwing. Short-circuits the entire chain on first null/undefined. Also works for methods: user?.getFullName(), and array indexing: users?.[0]. Nullish coalescing (??): provide a default value only for null/undefined (not for other falsy values like 0, "", false). user?.name ?? "Anonymous" — if name is null or undefined, returns "Anonymous"; if name is "" (empty string), returns "" (unlike || which would also return "Anonymous" for empty string). Use ?? instead of || when 0 or "" are valid values. Both are TypeScript-aware — TS narrows the type correctly after ?..
17. What is `as const`? When is it useful? ▼
Answeras const tells TypeScript to infer the narrowest possible literal type and make everything readonly. Without as const: const status = "active" — TS infers string (widened). const config = { port: 3000 } — TS infers { port: number }. With as const: const status = "active" as const — TS infers literal type "active". const config = { port: 3000 } as const — TS infers { readonly port: 3000 } (literal 3000, not number). Use cases: (1) Const arrays that you want to use as union types: const statuses = ["applied", "interview", "rejected"] as const; type Status = typeof statuses[number] — creates "applied" | "interview" | "rejected". (2) Config objects where exact values matter. (3) Preventing widening when you need exact literal types.
18. What is the `infer` keyword? Where is it used? ▼
Answerinfer is used inside conditional types to capture and name a type that TypeScript infers at that position. Most common built-in use: ReturnType is implemented as: type ReturnType<T> = T extends (...args: any) => infer R ? R : never — "if T is a function, infer what it returns as R, and use R as the result type." Example of custom use: type ArrayElement<T> = T extends Array<infer E> ? E : never — extracts the element type from an array. ArrayElement<string[]> = string. ArrayElement<User[]> = User. You likely won't write conditional types with infer as a fresher, but you use their results constantly (ReturnType, Awaited, Parameters are all built using infer). Understanding it shows TypeScript depth.
19. How do you handle `catch` block errors in TypeScript? ▼
AnswerIn TypeScript's strict mode, the error in a catch block is typed as unknown (in older versions: any). You cannot directly access .message or .stack without narrowing. Best practice: check instanceof Error first: if (error instanceof Error) { console.log(error.message) } else { console.log(String(error)) }. Or create a helper: function getErrorMessage(error: unknown): string { if (error instanceof Error) return error.message; return String(error); }. Why unknown and not Error? In JavaScript, you can throw anything — throw "a string", throw 42, throw { code: 500 }. TypeScript correctly types catch errors as unknown because any value might be thrown. This is a TypeScript improvement over JavaScript's implicit any on caught errors.
