When to use Stack vs Queue:

Stack (LIFO): the most recently seen element is most relevant. Bracket matching (last opened = first closed). Undo/redo. DFS. Evaluating expressions. Building results where you process backwards. Signal word: "most recent", "last", "undo", "nested", "LIFO"

Queue (FIFO): process elements in the order they arrived. BFS (level-order traversal). Processing tasks in order. Sliding window with deque. Signal word: "level by level", "shortest path", "first seen", "BFS", "FIFO"
Section 02

6 Core Patterns

The monotonic stack (Pattern 4) is the most important — it unlocks an entire class of interview problems that look impossible but have O(n) solutions.
Pattern 01
Bracket Matching
Push open brackets. When seeing a close bracket, check/pop the top. If it doesn't match, invalid. Stack empty at end = valid. Classic LIFO necessity.
Valid Parentheses · Longest Valid Parentheses · Minimum Add to Make Parentheses Valid
Pattern 02
Stack for Expression Evaluation
Evaluate math expressions with operators and parentheses. Two stacks: one for numbers, one for operators. Or use a single stack with RPN (Reverse Polish Notation).
Basic Calculator · Evaluate Reverse Polish Notation · Basic Calculator II
Pattern 03
Stack Simulation
Simulate a process where you undo/redo recent actions. Remove adjacent duplicates. Decode strings. Stack naturally tracks "most recent" state for reversal.
Remove All Adjacent Duplicates · Decode String · Backspace String Compare
Pattern 04 ⭐
Monotonic Stack
Stack maintains elements in monotonically increasing or decreasing order. Pop when invariant is broken. At pop time, the popped element's "next greater/smaller" is the current element. O(n) — each element pushed and popped once.
Next Greater Element · Daily Temperatures · Largest Rectangle in Histogram · Trapping Rain Water
Pattern 05
BFS with Queue
Level-order traversal of trees and graphs. Enqueue root/start. Process level by level. Queue ensures you process all nodes at depth d before depth d+1.
Binary Tree Level Order · Rotting Oranges · Word Ladder · Number of Islands (BFS)
Pattern 06
Monotonic Deque
Deque maintains window maximum/minimum. Front holds max index. Evict indices outside window from front. Evict smaller values from back when new element added.
Sliding Window Maximum · Constrained Subsequence Sum
Section 03

Interview Framework

What to say before coding — especially for the monotonic stack which needs the most explanation.
1
Identify: LIFO or FIFO?
Is the most recently seen element the relevant one? (LIFO → Stack). Or do you need to process in arrival order? (FIFO → Queue). For "next greater element" — when you find a greater element, the stack holds everything waiting for a greater element. LIFO because the most recently pushed element might also be resolved by this new element.
"This is a 'next greater element' problem — LIFO ordering. I'll maintain a stack of elements waiting to find their next greater. When I see a new element larger than the stack top, I resolve the top element's answer."
2
For Monotonic Stack: state the invariant clearly
The most important step. Before coding: "My stack maintains elements in decreasing order (for next greater element). When a new element is larger than the top, I pop — at that moment, the popped element's next greater is the current element." The invariant tells you when to pop and what that pop means.
"Invariant: stack contains indices in decreasing order of their values. When nums[i] > nums[stack.top()], I pop — the popped index's next greater element is at index i. I continue popping as long as the invariant is violated."
3
Decide: store values or indices?
If you only need the values, push values. If you need positions (to compute distances, ranges, or for result arrays), push indices and access values via nums[index]. Monotonic stack problems almost always push indices — you need to know WHERE the element is, not just what it is.
"I'll store indices, not values, in the stack. That way when I pop an index, I know both its value (nums[idx]) and its position — useful for computing distances like in Daily Temperatures."
4
Trace through a small example before coding
For [2,1,2,4,3] — next greater element: push index 0 (val 2). Push index 1 (val 1 < 2, keep). Push index 2 (val 2, not > 1? Pop 1, answer[1]=2. Val 2 = stack top's value 2, not strictly greater so just push). Push index 3 (val 4 > 2, pop index 2, answer[2]=4. Pop index 0, answer[0]=4. Stack empty, push 3). This trace reveals the algorithm before coding.
"Let me trace through [2,1,2,4,3] to verify my logic before I code it. i=0: push 0. i=1: 1 < 2, push 1. i=2: 2 > 1, pop idx 1 — answer[1]=2. Stack top is idx 0 with val 2, not < 2, push 2. Continue..."
5
Handle leftovers in the stack after the loop
After iterating through all elements, the stack may still have indices/elements. These are elements that never found a next greater/smaller element. For "next greater element": their answer is -1. For histogram area: their right boundary is the array's right edge. Always check what the leftover elements mean for the specific problem.
"After the loop, anything remaining in the stack never found a next greater element. Their answer is -1. I'll initialize the result array to -1 so I don't need to explicitly handle these — they're already correct."
Monotonic Stack — the two flavors and when to use each:

Increasing stack (next smaller): Pop when current element is SMALLER than top. At pop time: current element is the "next smaller element" for the popped index. Stack: values are increasing from bottom to top.

Decreasing stack (next greater): Pop when current element is GREATER than top. At pop time: current element is the "next greater element" for the popped index. Stack: values are decreasing from bottom to top.

Memory trick: the stack maintains the ORDER of what you're looking for. If looking for next GREATER → decreasing stack (pop smaller, keep larger waiting). If looking for next SMALLER → increasing stack (pop larger, keep smaller waiting).

The 5 Templates

Memorize these. The monotonic stack template (T3) is the most important — apply it to any "next greater/smaller" variant.
JavaScriptTemplate 1 — Bracket Matching
function isValid(s) {
    const stack = [];
    const match = { ')':'(', '}':'{', ']':'[' };

    for (const ch of s) {
        if ('([{'.includes(ch)) {
            stack.push(ch);
        } else {
            if (stack.pop() !== match[ch]) return false;
        }
    }
    return stack.length === 0;
}
JavaScriptTemplate 2 — Stack Simulation (Remove Adjacent Duplicates)
function removeDuplicates(s) {
    const stack = [];

    for (const ch of s) {
        if (stack.length > 0 && stack[stack.length - 1] === ch) {
            stack.pop();  // duplicate — cancel each other out
        } else {
            stack.push(ch);
        }
    }
    return stack.join('');
}
// Generalizes to: remove k adjacent duplicates, remove any pattern
// The stack holds "candidates" — pop when condition met, push otherwise
JavaScriptTemplate 3 — Monotonic Stack (Next Greater Element)
function nextGreaterElement(nums) {
    const n = nums.length;
    const result = new Array(n).fill(-1); // default: no greater element found
    const stack = [];  // stores INDICES (not values)

    for (let i = 0; i < n; i++) {
        // While stack has elements AND current > stack top's value
        // → current element is the "next greater" for the top element
        while (stack.length > 0 && nums[i] > nums[stack[stack.length - 1]]) {
            const idx = stack.pop();
            result[idx] = nums[i]; // nums[i] is the next greater for idx
        }
        stack.push(i); // push current index — waiting for its next greater
    }
    // Remaining indices in stack have no next greater → result[idx] = -1 (default)
    return result;
}
// What changes per problem:
// Next SMALLER:  while (nums[i] < nums[stack.top])  → pop, result[idx] = nums[i]
// Previous GREATER: pop on push, not on current element comparison
// Circular array: iterate 2n, use i % n for index
JavaScriptTemplate 4 — BFS with Queue
function bfs(root) {
    if (!root) return [];
    const queue = [root];
    const result = [];

    while (queue.length > 0) {
        const levelSize = queue.length; // number of nodes at this level
        const level = [];

        for (let i = 0; i < levelSize; i++) {
            const node = queue.shift(); // dequeue (use index for O(1))
            level.push(node.val);

            if (node.left)  queue.push(node.left);
            if (node.right) queue.push(node.right);
        }

        result.push(level);
    }
    return result; // array of arrays, one per level
}
// levelSize snapshot is KEY — captures size before adding children
// Without levelSize, you can't distinguish levels
JavaScriptTemplate 5 — Monotonic Deque (Sliding Window Maximum)
function maxSlidingWindow(nums, k) {
    const deque = [];  // stores INDICES, front = max index
    const result = [];

    for (let i = 0; i < nums.length; i++) {
        // Remove indices outside current window from front
        while (deque.length > 0 && deque[0] < i - k + 1) {
            deque.shift();
        }

        // Remove indices from back whose values are ≤ nums[i]
        // They can never be the max while nums[i] is in the window
        while (deque.length > 0 && nums[deque[deque.length - 1]] <= nums[i]) {
            deque.pop();
        }

        deque.push(i); // add current index to back

        // Window of size k formed: front of deque is the max index
        if (i >= k - 1) {
            result.push(nums[deque[0]]);
        }
    }
    return result;
}
// Each index enters deque once, exits once → O(n) total

Problem 01 of 05Medium
Min Stack (Design)
LeetCode #155 · leetcode.com/problems/min-stack
1
Problem: Design a stack that supports push, pop, top, and getMin — all O(1). getMin must return the minimum element currently in the stack.
2
Why it's hard: When you pop the minimum element, the new minimum could be anything previously in the stack. You can't just track a single min variable — it's invalidated by pops.
3
Key insight — two stacks: Maintain a second "minStack" in parallel. When pushing to main stack: also push to minStack if the value is ≤ current min (i.e., minStack.top). When popping: if popped value equals minStack.top, also pop from minStack. The minStack.top is always the current minimum.
4
Alternative — store pairs: Each node in the stack stores (value, minAtThisPoint). When you push, minAtThisPoint = min(value, previous minAtThisPoint). When you pop, the new min is automatically restored from the remaining top's minAtThisPoint. O(n) space but a single stack.
Interviewer
Design a stack with O(1) push, pop, top, and getMin.
You
The challenge is getMin after pops. Tracking a single min variable breaks when you pop the current minimum — you'd need to rescan the stack which is O(n). I need O(1) min retrieval at every state.
You
Solution: two stacks. Main stack for values. A minStack that tracks minimums. When pushing X: push to main. If X ≤ minStack.top (or minStack is empty), also push X to minStack. When popping: pop from main. If popped value equals minStack.top, pop from minStack too. getMin returns minStack.top — always the current minimum.
Interviewer
What if we push [5,3,3,7,3]? Walk through the minStack.
You
Push 5: main=[5], minStack=[5]. Push 3: 3≤5, main=[5,3], minStack=[5,3]. Push 3: 3≤3, main=[5,3,3], minStack=[5,3,3]. Push 7: 7>3, main=[5,3,3,7], minStack=[5,3,3] (unchanged). Push 3: 3≤3, main=[5,3,3,7,3], minStack=[5,3,3,3]. Pop 3: equals minStack top 3, minStack=[5,3,3], getMin=3. ✓
JavaScriptMin Stack — two stacks approach
class MinStack {
    constructor() {
        this.stack    = [];
        this.minStack = []; // tracks minimums at each state
    }

    push(val) {
        this.stack.push(val);
        // Push to minStack if it's empty OR val ≤ current min
        const minLen = this.minStack.length;
        if (minLen === 0 || val <= this.minStack[minLen - 1]) {
            this.minStack.push(val);
        }
    }

    pop() {
        const popped = this.stack.pop();
        // If we're popping the current minimum, update minStack
        if (popped === this.minStack[this.minStack.length - 1]) {
            this.minStack.pop();
        }
    }

    top() {
        return this.stack[this.stack.length - 1];
    }

    getMin() {
        return this.minStack[this.minStack.length - 1];
    }
}

// Alternative: store pairs [val, minSoFar] in one stack
// push(val): min = Math.min(val, stack.top?.min ?? Infinity)
// stack.push([val, min])
// getMin(): stack.top[1]
Time: O(1) all operations Space: O(n) — minStack can have up to n entries
  • Duplicate minimums: Push [3,3,3] — minStack=[3,3,3]. Pop: each 3 removal also pops from minStack. After all 3 pops, minStack is empty. Correct — no elements left.
  • Why ≤ not < for minStack push: If we use strict <, we'd only push the first occurrence of the minimum. When we pop it, the minStack loses the minimum entirely — but there are still copies of that value in the main stack. Using ≤ pushes each minimum occurrence, so one pop from minStack corresponds to one pop from the main stack.
  • The pairs approach (alternative): Store [value, currentMin] at each node. When pushing val: currentMin = Math.min(val, top?.currentMin ?? Infinity). When calling getMin: return top[1]. One stack, same O(1) all operations, O(n) space. Slightly more space per entry.
Problem 02 of 05Medium
Daily Temperatures
LeetCode #739 · leetcode.com/problems/daily-temperatures
1
Problem: Given daily temperatures array, return array where result[i] = number of days to wait for a warmer temperature. If none, result[i] = 0.
2
Brute force: For each day i, scan forward until a warmer day is found. O(n²). Too slow for large inputs.
3
Monotonic decreasing stack: Stack holds indices whose next warmer day hasn't been found yet. Process each day: while the stack has indices with temperatures less than today's → pop those indices, their answer is i - poppedIndex. Push current index. Stack holds elements in decreasing temperature order.
4
Why this is O(n): Each index is pushed exactly once and popped exactly once. Total operations = 2n = O(n). Not O(n²) even though there's a while loop inside the for loop.
Interviewer
How many days until a warmer temperature? If none, 0.
You
Brute force: for each day, scan forward — O(n²). I can do O(n) with a monotonic decreasing stack. I'll store indices of days waiting for a warmer day. When I see a temperature warmer than the stack top, those days now have their answer: current index minus stored index.
You
Invariant: stack holds indices in decreasing order of their temperatures — no day in the stack has found a warmer day yet. When temps[i] > temps[stack.top], pop — that day's wait = i - popped. Continue popping while stack isn't empty and current is warmer.
Interviewer
Trace through [73,74,75,71,69,72,76,73].
You
i=0: push 0 (73). i=1: 74>73, pop 0, result[0]=1-0=1, push 1. i=2: 75>74, pop 1, result[1]=1, push 2. i=3: 71<75, push 3. i=4: 69<71, push 4. i=5: 72>69 pop 4, result[4]=5-4=1. 72>71 pop 3, result[3]=5-3=2. 72<75, push 5. i=6: 76>72 pop 5, result[5]=1. 76>75 pop 2, result[2]=6-2=4. Stack empty, push 6. i=7: 73<76, push 7. End: indices 6,7 have result 0.
JavaScriptDaily Temperatures — Monotonic Decreasing Stack O(n)
function dailyTemperatures(temps) {
    const n = temps.length;
    const result = new Array(n).fill(0); // default: 0 (no warmer day)
    const stack = [];  // stores INDICES — not temperatures

    for (let i = 0; i < n; i++) {
        // While stack has indices whose temps are LESS than today's
        while (stack.length > 0 && temps[i] > temps[stack[stack.length - 1]]) {
            const idx = stack.pop();
            result[idx] = i - idx; // days to wait = current day - stored day
        }
        stack.push(i); // today is waiting for a warmer day
    }

    // Remaining indices in stack: no warmer day found → result = 0 (default)
    return result;
}
Time: O(n) — each index pushed once, popped once Space: O(n) — stack can hold up to n indices
  • Decreasing temperatures [5,4,3,2,1]: All indices pushed, none popped during loop. All result[i] = 0. Stack = [0,1,2,3,4] after loop. Return all 0s. Correct.
  • Increasing temperatures [1,2,3,4,5]: Every element pops all previous. result = [1,1,1,1,0]. Stack always has 1 element. Correct.
  • All same [4,4,4,4]: No element is strictly greater, nothing pops. All 0s. Correct.
  • Why store indices not temperatures: We need i - idx (days difference) for the answer. If we stored temperatures, we'd lose the position information. Storing indices lets us access both the temperature (temps[idx]) and the position (idx) when we pop.
Problem 03 of 05Medium
Evaluate Reverse Polish Notation
LeetCode #150 · leetcode.com/problems/evaluate-reverse-polish-notation
1
Problem: Evaluate an expression in Reverse Polish Notation (postfix). Operators come after their operands. ["2","1","+","3","*"] = (2+1)*3 = 9.
2
Why RPN is stack-friendly: When you see a number, push it. When you see an operator, pop two numbers, apply the operator, push the result. The stack handles operand ordering naturally — the two most recently seen numbers are always the operands for the next operator.
3
Order matters for subtraction/division: The first popped value is the RIGHT operand, the second popped is the LEFT. So: b = stack.pop(), a = stack.pop(), result = a OP b. NOT b OP a.
4
Integer truncation: Division should truncate toward zero. Use Math.trunc(a/b) or parseInt(a/b). In JS, -7/2 = -3.5. Math.trunc(-3.5) = -3 (truncate toward zero). Math.floor(-3.5) = -4 (floor toward negative infinity). The problem requires truncate toward zero.
Interviewer
Evaluate an expression in Reverse Polish Notation.
You
RPN is designed for stack evaluation. Numbers push onto the stack. Operators pop two operands, apply the operation, push the result. At the end, the stack has exactly one element — the answer.
You
Key detail: when popping for binary operators, the first pop is the RIGHT operand, second pop is the LEFT. So b = pop(), a = pop(), then a OP b. Getting this backwards breaks subtraction and division.
Interviewer
What about integer division rounding?
You
Division should truncate toward zero, not floor. In JavaScript: -7 / 2 = -3.5. Math.trunc(-3.5) = -3. Math.floor(-3.5) = -4. I'll use Math.trunc to truncate toward zero as the problem requires. This difference only matters for negative operands.
JavaScriptEvaluate RPN — O(n)
function evalRPN(tokens) {
    const stack = [];
    const ops = new Set(['+', '-', '*', '/']);

    for (const token of tokens) {
        if (!ops.has(token)) {
            stack.push(Number(token)); // it's a number — push
        } else {
            const b = stack.pop(); // RIGHT operand (popped first)
            const a = stack.pop(); // LEFT operand (popped second)

            switch (token) {
                case '+': stack.push(a + b); break;
                case '-': stack.push(a - b); break;
                case '*': stack.push(a * b); break;
                case '/': stack.push(Math.trunc(a / b)); break; // truncate toward 0
            }
        }
    }

    return stack[0]; // exactly one element remains
}
Time: O(n) — one pass through tokens Space: O(n) — stack holds operands
  • Single number ["42"]: Push 42. Loop ends. Return stack[0] = 42. Correct.
  • Subtraction order ["5","3","-"]: Push 5, push 3. See '-': b=3, a=5. Push 5-3=2. Return 2. Correct (not 3-5=-2).
  • Division truncation ["7","2","/"]: 7/2 = 3.5, Math.trunc = 3. ["-7","2","/"]: -3.5, Math.trunc = -3 (not Math.floor which gives -4).
  • Negative number tokens ["-3"]: Number("-3") = -3. Works correctly.
  • The problem guarantee: Input is always a valid RPN expression. Stack will always have exactly two elements when an operator is seen. No need to check stack underflow.
Problem 04 of 05Hard
Largest Rectangle in Histogram
LeetCode #84 · leetcode.com/problems/largest-rectangle-in-histogram
1
Problem: Given bar heights, find the largest rectangle that fits in the histogram. The rectangle must use full bar heights (can't cut a bar).
2
Key insight: For each bar, the largest rectangle where this bar is the HEIGHT bottleneck spans from the first bar to the left that's shorter, to the first bar to the right that's shorter. These boundaries are exactly what a monotonic increasing stack gives us.
3
Monotonic increasing stack: Stack holds indices of bars in increasing height order. When a bar shorter than the stack top is seen, pop — the popped bar is the height of a rectangle. Its right boundary is the current bar (shorter bar found). Its left boundary is the new stack top (next shorter bar to the left). Width = right - left - 1.
4
Sentinel trick: Add a 0 at the end of the heights array (a virtual bar of height 0). This ensures all bars are popped from the stack when we reach the end — so we don't need a separate pass to process remaining stack elements.
Interviewer
Find the largest rectangle in a histogram.
You
For each bar, I want to know: how far left and right can I extend a rectangle of this bar's height? The rectangle is bounded by the first shorter bar on each side. This is a classic monotonic stack problem — the stack naturally gives me the "nearest shorter bar" on both sides.
You
I maintain a monotonic increasing stack of indices. When I encounter a bar shorter than the stack top, I pop — that bar's rectangle area = popped height × (right boundary - left boundary - 1). Right boundary is the current index. Left boundary is the new stack top (the next shorter bar to the left).
Interviewer
What about bars never popped before the loop ends?
You
I add a 0-height sentinel bar at the end. Since 0 is shorter than every bar, it triggers popping of all remaining bars. This avoids a separate post-loop processing step. Elegant and clean.
JavaScriptLargest Rectangle in Histogram — Monotonic Stack O(n)
function largestRectangleArea(heights) {
    // Sentinel: add 0 at end to flush remaining stack elements
    heights.push(0);
    const stack = []; // monotonic increasing — stores indices
    let maxArea = 0;

    for (let i = 0; i < heights.length; i++) {
        // Pop while current height < stack top height
        while (stack.length > 0 && heights[i] < heights[stack[stack.length - 1]]) {
            const height = heights[stack.pop()]; // height of rectangle
            const width  = stack.length === 0
                ? i                               // no left boundary → extends to start
                : i - stack[stack.length - 1] - 1; // right - left - 1
            maxArea = Math.max(maxArea, height * width);
        }
        stack.push(i);
    }

    heights.pop(); // restore original array
    return maxArea;
}

// Trace [2,1,5,6,2,3] + sentinel 0:
// i=0: push 0 (h=2). i=1: h=1 < h[0]=2. Pop 0: width=1 (stack empty), area=2. Push 1.
// i=2: push 2. i=3: push 3. i=4: h=2 < h[3]=6. Pop 3: width=4-2-1=1, area=6.
// h=2 < h[2]=5. Pop 2: width=4-1-1=2, area=10. h[1]=1 not < 2, push 4.
// i=5: push 5. i=6 (sentinel 0): pop 5: width=6-4-1=1, area=3.
// Pop 4: width=6-1-1=4, area=2*4=8. Pop 1: width=6 (empty), area=1*6=6. Max=10. ✓
Time: O(n) — each bar pushed and popped once Space: O(n) — stack holds at most n indices
  • Single bar [5]: With sentinel: [5,0]. Push 0 (h=5). i=1, h=0 < 5: pop, height=5, width=1 (empty stack). area=5. Return 5. Correct.
  • All same height [3,3,3]: With sentinel [3,3,3,0]. Stack grows to [0,1,2]. At sentinel: pop 2, width=3-1-1=1, area=3. Pop 1, width=3-0-1=2, area=6. Pop 0, width=3 (empty), area=9. Return 9. Correct — the largest rectangle uses all 3 bars.
  • Width when stack is empty: If stack is empty after popping, the popped bar's rectangle extends all the way to the left edge (index 0). Width = i (current index). This is why the empty stack check uses i, not i - (-1) - 1.
  • Connection to Trapping Rain Water: Both use monotonic stack but in different ways. Rain water: boundaries are set by taller bars, water fills inward. Histogram: rectangles extend outward from each bar until a shorter bar stops them. Same structure, different invariant.

1
Problem: Return level-order traversal of a binary tree as an array of arrays — each inner array contains all values at that depth level.
2
BFS with queue: Enqueue the root. Process nodes level by level. The key trick: snapshot the queue size before processing each level — that tells you how many nodes are at the current level vs next level's children.
3

4

JavaScriptLevel Order Traversal — BFS with queue O(n)
function levelOrder(root) {
    if (!root) return [];

    const queue = [root];
    const result = [];

    while (queue.length > 0) {
        const levelSize = queue.length; // snapshot: nodes at this level
        const level = [];

        for (let i = 0; i < levelSize; i++) {
            const node = queue.shift(); // dequeue
            level.push(node.val);

            // Enqueue children (they belong to the NEXT level)
            if (node.left)  queue.push(node.left);
            if (node.right) queue.push(node.right);
        }

        result.push(level);
    }

    return result;
}

// Variations using the same template:
// Right side view: take last element of each level
// Level averages: compute average of each level array
// Zigzag: alternate left→right and right→left for each level
// Max depth: count number of levels (result.length)
Time: O(n) — visit each node once Space: O(n) — queue holds up to n/2 nodes (bottom level)
  • Empty tree (root=null): Guard returns [] immediately.
  • Single node: queue=[root], levelSize=1, process root, no children. result=[[root.val]]. Return [[val]].
  • Using shift() vs index pointer: queue.shift() is O(n) in JS (shifts all elements). For large trees, use let front=0; const node = queue[front++] instead. For interview problems with small inputs, shift() is fine and cleaner.
  • Variations from the same template: Right side view (last element per level), binary tree level averages (average per level), zigzag traversal (alternate direction), maximum depth (count levels). All use identical BFS structure — just change what you do with each level array.

15 Interview Questions

Answer out loud first. The monotonic stack questions are the most important — practice explaining the invariant clearly.
CoreWhat is a monotonic stack? When do you use it?▼
A monotonic stack maintains elements in monotonically increasing or decreasing order. When a new element violates the invariant (e.g., a larger element enters a decreasing stack), we pop elements until the invariant is restored — and at each pop, we've found the answer for the popped element. Use it when the problem involves: "next greater/smaller element," "previous greater/smaller element," histogram area calculations, or temperature waiting days. The key property: each element enters and exits the stack exactly once → O(n) total despite the nested while loop inside the for loop. Recognition signal: "for each element, find the nearest element that's larger/smaller" → monotonic stack.
CoreExplain the monotonic stack invariant for "next greater element."▼
Invariant: the stack holds indices of elements in DECREASING order of their values. These are elements that have NOT yet found their "next greater element." When processing element at index i: while the stack is not empty AND nums[i] > nums[stack.top] → the current element is the "next greater" for the top. Pop the top, set result[top] = nums[i]. Continue popping while the condition holds. Push index i (it's now waiting for its next greater). After the full loop: remaining elements in the stack have no next greater → their result is -1. Why decreasing: if the stack were NOT decreasing (i.e., we had a smaller element below a larger one), the larger one would have already "resolved" the smaller one. The only way elements survive in the stack is if everything above them is larger (decreasing order).
InterviewWhy is monotonic stack O(n) when there's a while loop inside a for loop?▼
Amortized analysis. Each element is pushed onto the stack exactly once (when processed in the outer for loop). Each element is popped from the stack at most once. Total push operations = n. Total pop operations ≤ n. Total work = O(2n) = O(n). Even though the while loop might run multiple iterations for a single i, across the entire algorithm, the total number of iterations of the while loop across all values of i is bounded by n (since each element is popped at most once). This is the same argument as for Two Pointers: individual loop bodies might do multiple steps, but the aggregate across all iterations is linear. The nested loop doesn't automatically mean O(n²) — it depends on the total number of operations.
InterviewHow do you implement a queue using two stacks?▼
LeetCode #232. Use two stacks: "inStack" for enqueue, "outStack" for dequeue. Enqueue: always push to inStack. Dequeue: if outStack is empty, pop all elements from inStack and push to outStack (reversing order — LIFO becomes FIFO). Return outStack.pop(). Peek: same as dequeue but return top without removing. Why it works: elements in inStack are in reverse order. Moving them all to outStack reverses them again → original order → FIFO. Amortized complexity: each element is pushed to inStack once, moved to outStack once, popped from outStack once → 3 operations per element → O(1) amortized. Worst case single operation: O(n) (when outStack needs refilling). This is a common system design + DSA question — interviewers ask it to test understanding of amortized analysis.
TrapWhat is the difference between a monotonic stack and a monotonic deque?▼
Monotonic stack: only one end (top). Used for "next greater/smaller" type problems where you process linearly and pop when invariant violated. Monotonic deque: double-ended queue. Front holds the maximum/minimum index for the current window. Back is where new elements are added (with eviction of dominated elements). Key difference: the deque needs to remove expired indices from the FRONT (outside the sliding window) AND remove dominated elements from the BACK. A stack can only remove from one end. Deque is used when: the question has a fixed-size sliding window and you need max/min of the window at each position (Sliding Window Maximum). The deque maintains: indices in the window in monotonically decreasing value order. Front = max of current window. Time: O(n) — each index enters and exits deque once.
CoreWhat is the levelSize snapshot trick in BFS? Why is it necessary?▼
In BFS level-order traversal, we process nodes level by level. The queue holds nodes to visit. Problem: as we process nodes at level d, we enqueue their children (level d+1). Without a snapshot, we'd process children of the current level in the same iteration — losing track of level boundaries. The snapshot: before processing a level, record levelSize = queue.length. Then iterate exactly levelSize times (processing all current-level nodes). Any nodes enqueued during this iteration are level d+1 and will be counted in the NEXT outer while iteration. Without it: single flat array of all values in BFS order. With it: nested array where each inner array is one level. Critical for: level-order traversal, right side view (take last of each snapshot), level averages, min/max per level, zigzag traversal.
InterviewHow do you solve "Largest Rectangle in Histogram"? Explain the invariant.▼
Use a monotonic increasing stack. Invariant: stack holds indices of bars in increasing height order. When a bar shorter than the stack top is seen: the top bar's maximum rectangle is bounded on the right by the current shorter bar, and on the left by the new stack top (next shorter bar to the left). Width = right_index - left_index - 1. Area = popped_height × width. Keep popping while the invariant is violated. Add a sentinel bar of height 0 at the end — this triggers all remaining bars to be popped and their areas computed, without a separate post-loop. Time: O(n) — each bar pushed and popped once. Key insight: for each bar as the "minimum height" (bottleneck), its maximum width is determined by the nearest shorter bar on each side — exactly what the stack gives us.
DesignHow does Min Stack achieve O(1) getMin after pops?▼
Naive approach: track a single min variable. Problem: when you pop the current min, what's the new min? You'd have to scan the whole stack — O(n). Two solutions: (1) Parallel minStack: push to minStack only when the new value is ≤ current min. Pop from minStack only when the popped main stack value equals the minStack top. getMin = minStack.top. O(1) all operations. (2) Store pairs (value, minAtThisPoint): each node stores the minimum value in the entire stack AT THE TIME it was pushed. getMin = top.minAtThisPoint. When popping, the new min is automatically the new top's minAtThisPoint. O(1) all operations. Both use O(n) space. The parallel stack approach is more space-efficient in practice (minStack only grows when a new minimum is found). The pairs approach uses exactly n entries.
InterviewWhat is multi-source BFS? Give an example.▼
Multi-source BFS: instead of starting BFS from a single source, start from MULTIPLE sources simultaneously. Enqueue all sources at distance 0. BFS naturally processes all "distance 1" nodes before "distance 2" — same as single-source but with multiple starting points. Example: Rotting Oranges (#994). All initially rotten oranges are sources (distance 0). Fresh oranges adjacent to rotten ones get "infected" at distance 1, etc. Without multi-source: you'd need to run BFS from each rotten orange separately and take the minimum — O(rotten × fresh) in the worst case. With multi-source: one BFS run, O(grid_size). Example 2: 0/1 Matrix (#542) — distance from each cell to nearest 0. All 0 cells are sources. 1 cells get their BFS distance from the nearest source.
TrapWhat's the order of operands when popping from a stack for binary operations?▼
When you push numbers onto a stack and then pop two for a binary operation: the FIRST popped value is the RIGHT operand, the SECOND popped is the LEFT operand. This matters for non-commutative operations (subtraction, division). Example: expression "5 3 -" in RPN. Push 5, push 3. See '-': b = pop() = 3 (right), a = pop() = 5 (left). Result = a - b = 5 - 3 = 2. If you did b - a = 3 - 5 = -2 — wrong! Memory aid: push order is left-to-right. Stack is LIFO — last pushed is first popped. So the most recently pushed (rightmost operand) pops first. Always: first pop = right operand, second pop = left operand. Also applies to the histogram problem: width = right_boundary - left_boundary - 1. Stack stores in correct order.
InterviewHow do you detect the "next greater element" for a circular array?▼
LeetCode #503. The circular array means each element's "next greater" can come from either after it or before it (wrapping around). Technique: iterate 2n times instead of n times. Use index i % n for the actual array access. This simulates the circular property — after reaching the end, we wrap back to the start. In the second pass (n to 2n-1), we only push elements to the stack if they haven't been resolved in the first pass (or we can just always try to resolve — elements already resolved just re-push their answer, which doesn't matter since we won't pop them again). Cleaner implementation: for the second pass (i >= n), don't push to the stack — only pop. Elements still in the stack after 2n iterations truly have no next greater element. Initialize result to -1, only update when resolved.
CoreStack vs Queue — when does each data structure fit the problem?▼
Stack (LIFO) fits when: The most recently seen element is the most relevant. Problems involving "most recent," "last opened must close first" (brackets), "undo" semantics, DFS traversal, evaluating expressions with operator precedence, building results backwards. Signal: nesting, reversal, "most recent match." Queue (FIFO) fits when: Processing elements in the order they arrived matters. Level-by-level processing, shortest path in unweighted graphs (BFS), scheduling tasks in order. Signal: "level by level," "shortest," "process in arrival order." Neither is always better: DFS (stack) finds A path. BFS (queue) finds the SHORTEST path (in unweighted graphs). Choose based on problem requirement — don't default to one.
InterviewHow do you handle the "Decode String" problem?▼
LeetCode #394. Input like "3[a2[bc]]" → "abcbcabcbc". Use a stack (or two stacks: one for strings, one for numbers). Process character by character: digit → build the number (could be multi-digit). '[' → push (current_string, current_number) to stack, reset both. letter → append to current string. ']' → pop (prev_string, repeat_count), current_string = prev_string + current_string.repeat(repeat_count). Walk through "3[a2[bc]]": encounter '3': num=3. '[': push ("",3), reset. 'a': current="a". '2': num=2. '[': push ("a",2), reset. 'b','c': current="bc". ']': pop ("a",2), current = "a"+"bc".repeat(2) = "abcbc". ']': pop ("",3), current = ""+"abcbc".repeat(3) = "abcbcabcbc". Return "abcbcabcbc".
TrapWhat's wrong with using `queue.shift()` for BFS? How do you fix it?▼
Array.shift() in JavaScript is O(n) — it removes the first element and shifts all remaining elements one position left. For BFS with n nodes where each is shifted once: O(n²) total. For small n (interview problem sizes), this is acceptable. For large n or performance-critical code: use an index pointer instead. let front = 0; const node = queue[front++]. This is O(1) — just advance the pointer, don't shift the array. The array grows but doesn't shrink — memory is not freed until the array is garbage collected. For very large BFS problems, a proper circular buffer deque is optimal. In interviews: mention the O(n) cost of shift() and that you'd use an index pointer for large inputs. Then code with shift() for clarity — most interviewers accept this trade-off.
InterviewHow would you find the minimum number of operations to reach target in a problem using BFS?▼
Classic BFS shortest path pattern. BFS guarantees minimum steps in an unweighted graph because it explores nodes level by level — all "1-step" nodes before "2-step" nodes. Template: enqueue start state, mark visited (to avoid cycles), track distance. Process level by level (using levelSize snapshot). When you reach the target, the current level number = minimum steps. Example: Word Ladder — each word transformation is one step. Enqueue start word, explore all words reachable in 1 transformation (change 1 letter), find those in the word list, enqueue them marked visited. Continue until "end" word is found. The level when we reach end = minimum transformations. Key: mark states as visited BEFORE or WHEN enqueuing (not when dequeuing) — otherwise you may enqueue the same state multiple times, causing exponential blowup.
