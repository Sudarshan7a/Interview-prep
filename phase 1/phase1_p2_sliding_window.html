Section 01

The Core Idea

A window is a contiguous subarray or substring defined by two pointers: left (L) and right (R). The window slides by moving R right to expand and L right to shrink.

Many problems ask about contiguous subarrays or substrings — "find the longest/shortest/maximum/minimum subarray that satisfies some condition." The brute force checks every possible subarray: O(n²) or worse. Sliding Window avoids this by maintaining a window that never needs to restart from scratch.

The sliding window insight: Instead of checking every subarray independently, maintain a window [L, R]. Expand R to include more elements. When the window violates the condition, shrink from L. Neither pointer ever moves backward — each pointer traverses at most n positions, giving O(n) total.

Use Sliding Window when:

✓ Problem involves a contiguous subarray or substring
✓ Keywords: "longest", "shortest", "maximum", "minimum" + "subarray/substring"
✓ Problem has a condition on what's inside the window (sum ≤ k, at most k distinct chars, no repeats)
✓ You need to avoid re-computing the same overlapping subarray from scratch
✓ Fixed window size k given explicitly
Don't use Sliding Window when:

✗ Elements in the subarray don't need to be contiguous → Subsequence, not subarray → DP or Two Pointers
✗ The window condition requires looking at all previous subarrays, not just the current window → Prefix sum + HashMap
✗ Problem is about pairs or sorted data → Two Pointers
✗ "Count subarrays where sum equals k exactly" — a shrinking window won't work cleanly → Prefix sum + HashMap (#560)

The critical mental model — when to expand vs shrink:

Section 02

The 3 Sliding Window Variants

Recognize the variant from the problem statement — the template you use changes accordingly.
Variant A
Fixed Size Window
Window size k is given. Slide the window by adding right element and removing left element. No need to shrink — just slide. Track max/min of window metric.
Maximum Average Subarray I, Contains Duplicate II (within k), Sliding Window Maximum
Variant B
Variable Window — Find Longest
Expand R. When condition violated → shrink from L until valid. Track max window size seen. Condition on what's INSIDE window (at most k distinct, no repeats, sum ≤ target).
Longest Substring Without Repeating, Longest Subarray with Sum ≤ K, Fruit Into Baskets
Variant C
Variable Window — Find Shortest
Expand R until condition met (valid window found). Then shrink L while still valid — find minimum. Record shortest. Condition on SATISFYING something (sum ≥ target, contains all chars).
Minimum Window Substring, Minimum Size Subarray Sum, Smallest Subarray Covering All
Longest vs Shortest — the direction reversal:

Longest: expand R eagerly, shrink L when violated. Max = widest valid window.
Shortest: expand R until valid, then shrink L while still valid. Min = narrowest valid window.

The code structure is almost identical — only what triggers shrinking changes, and whether you record size before or after shrinking.
Section 03

Interview Framework for Sliding Window

What to say at each stage. Sliding Window has nuances — state the variant, the condition, and the data structure you'll use inside the window.
1
Identify: is it a subarray/substring problem with a condition?
Listen for: "longest/shortest/maximum subarray where..." — the "where" is the window condition. Also check: are we looking for contiguous elements? If non-contiguous, it's a subsequence problem (different pattern). Confirm the problem is about a contiguous range before committing to Sliding Window.
"This is asking for the longest contiguous subarray where [condition]. That's a sliding window problem — the window maintains the condition as it slides."
2
Identify the variant and what data structure tracks the window state
Fixed k → Variant A. Finding longest → Variant B. Finding shortest → Variant C. Then: what do you track inside the window? Sum → running total. Distinct characters → Map/frequency count. Presence of duplicates → Set. This tracking structure is key — name it before coding.
"It's a variable window finding the longest. I'll use a HashMap to track character frequencies inside the window. When distinct character count exceeds k, I shrink from the left."
3
State the expand condition and shrink condition explicitly
Before coding: say what makes the window expand (always: R moves right), what makes it invalid (the condition is violated), and what you do when invalid (move L right until valid). This is the algorithm in plain English — say it before touching code.
"Window expands by adding s[R] to the frequency map. If the number of distinct chars exceeds 2, shrink: remove s[L] from map, delete if count reaches 0, move L right. Record max window size whenever window is valid."
4
Code while narrating — especially the shrink loop
The expand step is usually one line. The shrink is a while loop — narrate what it's doing: "This inner while loop shrinks the window from the left until the condition is satisfied again. L moves right, we remove the element leaving the window." Explain why it's still O(n) — L never moves backward.
"The inner while loop shrinks from L... L only ever moves right — so total L movements across all iterations is at most n. That's why the overall algorithm is O(n) despite the nested loops."
5
Trace one full expand-shrink cycle + state complexity
Walk through 2–3 steps of the example. Show one expansion, one shrink, and the result recording. State O(n) time (both L and R traverse at most n positions). State the space: O(k) for fixed distinct elements, O(n) worst case for unbounded maps.
"Time: O(n) — R advances n times, L advances at most n times, total 2n operations. Space: O(k) where k is the number of distinct characters in the window — bounded by the alphabet size, so O(26) = O(1) for lowercase letters."
The most common Sliding Window mistakes in interviews:

✗ Shrinking with if instead of while — one shrink might not be enough to restore validity
✗ Not updating the window tracking structure when shrinking (forgetting to decrement/delete from map)
✗ Recording the max INSIDE the shrink loop instead of AFTER — captures invalid window sizes
✗ Off-by-one: window size = R - L + 1, not R - L
✗ Using Sliding Window for "sum equals k exactly" (not ≤ k) — that needs Prefix Sum + HashMap
Section 04

The 3 Templates

Memorize these. The only part that changes per problem is the condition check and what you track.
JavaScriptTemplate A — Fixed Window Size k
function fixedWindow(arr, k) {
    // Build initial window of size k
    let windowVal = 0;
    for (let i = 0; i < k; i++) windowVal += arr[i];

    let best = windowVal;

    // Slide: remove left element, add right element
    for (let R = k; R < arr.length; R++) {
        windowVal += arr[R];          // add incoming right
        windowVal -= arr[R - k];      // remove outgoing left
        best = Math.max(best, windowVal);
    }

    return best;
}
// What changes: windowVal computation (sum, count, etc.), what "best" means
JavaScriptTemplate B — Variable Window, Find LONGEST (at most k distinct)
function longestWindow(s, k) {
    const freq = new Map(); // track what's inside window
    let L = 0, maxLen = 0;

    for (let R = 0; R < s.length; R++) {
        // 1. Expand: add s[R] into the window
        freq.set(s[R], (freq.get(s[R]) || 0) + 1);

        // 2. Shrink: while window is INVALID, move L right
        while (freq.size > k) {             // condition: too many distinct chars
            const leftChar = s[L];
            freq.set(leftChar, freq.get(leftChar) - 1);
            if (freq.get(leftChar) === 0) freq.delete(leftChar);
            L++;
        }

        // 3. Record: window is now valid — update max
        maxLen = Math.max(maxLen, R - L + 1); // R - L + 1 = window size
    }

    return maxLen;
}
// What changes: what you add/remove from freq, the invalid condition, what you record
JavaScriptTemplate C — Variable Window, Find SHORTEST (sum ≥ target)
function shortestWindow(arr, target) {
    let L = 0, sum = 0;
    let minLen = Infinity;

    for (let R = 0; R < arr.length; R++) {
        // 1. Expand: add arr[R] into window
        sum += arr[R];

        // 2. Shrink while VALID: record minimum, then shrink
        while (sum >= target) {            // condition: window is valid (sum met)
            minLen = Math.min(minLen, R - L + 1);
            sum -= arr[L];                  // remove left element
            L++;                            // shrink from left
        }
        // Note: record INSIDE the shrink loop (while valid)
    }

    return minLen === Infinity ? 0 : minLen;
}
// Key difference from Template B:
// B shrinks while INVALID, records AFTER shrinking
// C shrinks while VALID, records BEFORE removing L
The shrink-while-valid vs shrink-while-invalid distinction:

Template B (find longest): shrink while invalid → restore the window → record max size. Goal: keep window as big as possible.
Template C (find shortest): shrink while valid → record minimum → keep shrinking until invalid. Goal: find smallest window that still satisfies condition.

Problem 01 of 05Easy
Best Time to Buy and Sell Stock
LeetCode #121 · leetcode.com/problems/best-time-to-buy-and-sell-stock
1
Problem: Find the maximum profit from buying on one day and selling on a later day. If no profit possible, return 0.
2
Brute force: Try every pair (buy day, sell day) where buy < sell. O(n²). Too slow.
3
Sliding Window insight: The left pointer tracks the minimum price seen so far (buy day). The right pointer scans ahead (sell day). If prices[R] < prices[L], we found a cheaper buy day — move L to R. Otherwise, compute profit and update max.
4
Why this is sliding window: The window [L, R] represents a potential buy-sell pair. We only move L when we find a cheaper price (the window shrinks to a better left boundary). We never look backward — O(n).
5
Alternative framing: Track minPrice as you scan. At each R, compute prices[R] - minPrice. Update minPrice = min(minPrice, prices[R]). This is equivalent but cleaner to code.
Interviewer
Find the maximum profit from buying and selling once.
You
Can I buy and sell on the same day? And I must buy before selling?
Interviewer
Must buy before sell. Same day counts as 0 profit.
You
Brute force: check every pair — O(n²). But I can do O(n). As I scan forward, I track the minimum price seen so far. At each day, profit is today's price minus that minimum. I update the minimum if today's price is lower.
You
This is a sliding window — left pointer holds the cheapest buy day seen so far. If today's price is cheaper, I reset the buy day to today. Otherwise, I check if today's profit beats the maximum.
Interviewer
What if prices always decrease?
You
Every profit calculation would be negative or zero. I initialize maxProfit to 0 — the "do nothing" case. If no trade is profitable, we return 0.
JavaScriptBest Time to Buy and Sell — O(n)
function maxProfit(prices) {
    let minPrice = Infinity;
    let maxProfit = 0;    // 0 = no trade (guaranteed minimum)

    for (const price of prices) {
        // Update minimum buy price seen so far
        minPrice = Math.min(minPrice, price);

        // Compute profit if selling today at best possible buy price
        maxProfit = Math.max(maxProfit, price - minPrice);
    }

    return maxProfit;
}

// Two-pointer framing (equivalent, shows sliding window explicitly):
function maxProfitTP(prices) {
    let L = 0, R = 1, maxProfit = 0;

    while (R < prices.length) {
        if (prices[R] > prices[L]) {
            maxProfit = Math.max(maxProfit, prices[R] - prices[L]);
        } else {
            L = R;  // found cheaper buy price — reset window
        }
        R++;
    }

    return maxProfit;
}
Time: O(n) — single pass Space: O(1)
  • Prices always increasing [1,2,3,4,5]: minPrice stays 1. Max profit = 5-1=4. Correct.
  • Prices always decreasing [5,4,3,2,1]: Every profit is negative. maxProfit stays 0. Return 0. Correct.
  • Single price [7]: No second day to sell. maxProfit stays 0. Return 0. Correct.
  • Two prices [2,4]: min=2. profit=4-2=2. maxProfit=2. Return 2.
  • Why initialize maxProfit to 0, not -Infinity: Problem says return 0 if no profit possible. 0 is the "no trade" baseline, not a real profit computation.
Problem 02 of 05Medium
Longest Substring Without Repeating Characters
LeetCode #3 · leetcode.com/problems/longest-substring-without-repeating-characters
1
Problem: Find length of longest substring without repeating characters.
2
Window condition: Window is valid when it contains NO duplicate characters. Violation: adding s[R] creates a duplicate.
3
Tracking: Use a Set (we only need existence, not count) OR a Map storing last seen index (for the jump optimization). Set is simpler; Map allows jumping L directly to the duplicate's position + 1.
4
Set approach: Expand R. If s[R] is in Set → remove s[L] from Set, L++. Repeat until s[R] not in Set. Add s[R] to Set. Record window size.
5
Map approach (optimization): Store each char's last seen index. When duplicate found at R, jump L directly to max(L, lastSeen[s[R]] + 1). The max(L, ...) is crucial — ensures L never moves backward.
Interviewer
Find the longest substring without repeating characters.
You
This is a classic sliding window — variable size, finding the longest. The window condition is: no duplicate characters inside. I'll use a Set to track what's in the window.
You
R expands right. When s[R] is already in the Set — duplicate found, window is invalid. Shrink from L: remove s[L] from Set, advance L. Keep shrinking until s[R] is no longer in the Set. Then add s[R] and record window size R - L + 1.
Interviewer
Can you make it faster?
You
Yes — use a Map storing the last index of each character. When we find s[R] at a previous position, instead of shrinking L one step at a time, jump L directly to lastSeen[s[R]] + 1. We skip the entire prefix. Still O(n) total, but fewer iterations in practice. Need to take max of current L and the jump position — can't let L go backward.
JavaScriptLongest Substring No Repeats — Set approach (simpler)
function lengthOfLongestSubstring(s) {
    const seen = new Set();
    let L = 0, maxLen = 0;

    for (let R = 0; R < s.length; R++) {
        // Shrink while duplicate exists in window
        while (seen.has(s[R])) {
            seen.delete(s[L]);  // remove from window
            L++;                 // shrink from left
        }

        seen.add(s[R]);                         // add new char
        maxLen = Math.max(maxLen, R - L + 1); // record max
    }

    return maxLen;
}

// Optimized: Map stores last index, jump L instead of stepping
function lengthOfLongestSubstringFast(s) {
    const lastSeen = new Map();
    let L = 0, maxLen = 0;

    for (let R = 0; R < s.length; R++) {
        if (lastSeen.has(s[R])) {
            // Jump L to just after the previous occurrence
            // But never move L backward (use max)
            L = Math.max(L, lastSeen.get(s[R]) + 1);
        }
        lastSeen.set(s[R], R); // update last seen index
        maxLen = Math.max(maxLen, R - L + 1);
    }

    return maxLen;
}
Time: O(n) — each char added/removed from Set at most once Space: O(min(n, alphabet)) — Set bounded by unique chars
  • All unique "abcde": Window grows to full length. maxLen = n. Return n.
  • All same "aaaa": Every R triggers shrink. Window always size 1. maxLen = 1.
  • Empty string: Loop doesn't run. maxLen = 0. Return 0.
  • Single char "a": R=0, no duplicate, add to Set, maxLen=1. Return 1.
  • The max(L, ...) in Map approach: Critical. "dvdf" — 'd' first at 0, then at 2. At R=2: lastSeen['d']=0. L = max(1, 0+1) = 1. Correct — L was already at 1 (from 'v'). Without max: L would jump back to 1 (fine here), but in other cases L could jump backward which would include characters already removed from window.

Minimum Size Subarray Sum
LeetCode #209 · leetcode.com/problems/minimum-size-subarray-sum
1
Problem: Find the minimum length contiguous subarray with sum ≥ target. Return 0 if impossible.
2
Variant C — Find Shortest: Expand until condition met (sum ≥ target). Then shrink while still valid — record minimum length each time before shrinking. Stop shrinking when condition breaks.
3
Why shrink while valid (not while invalid): We want the SHORTEST window that satisfies sum ≥ target. Once valid, try to make it smaller. Keep shrinking from L — each shrink might still leave a valid window. Record minimum each time. Stop when shrinking would break the condition.
4
All positive numbers assumption: Works because adding elements increases sum, removing decreases. With negative numbers, this approach breaks — use prefix sum + deque for that variant.

Yes, all positive integers.
You
All positive means adding elements increases sum, removing decreases it — sliding window works. This is the "find shortest" variant: expand R until sum ≥ target, then shrink from L while still valid, recording minimum each step.

JavaScriptMinimum Size Subarray Sum — O(n)
function minSubArrayLen(target, nums) {
    let L = 0, sum = 0;
    let minLen = Infinity;

    for (let R = 0; R < nums.length; R++) {
        sum += nums[R]; // expand: add right element

        // Shrink WHILE VALID: record min, then remove left
        while (sum >= target) {
            minLen = Math.min(minLen, R - L + 1); // record before shrinking
            sum -= nums[L]; // remove left element
            L++;            // shrink window
        }
    }

    return minLen === Infinity ? 0 : minLen;
}
Time: O(n) — L and R each traverse at most n positions Space: O(1)
  • Single element equals target [5], target=5: R=0, sum=5. While: minLen=1, sum=0, L=1. Loop ends. Return 1.
  • No valid subarray [1,2,3], target=10: Sum never reaches 10. minLen stays Infinity. Return 0.
  • Entire array is valid: minLen records the full array length at some point. Correct.
  • Negative numbers don't work here: If array had [-1, 5, 3], removing -1 from left would INCREASE sum — the while loop logic breaks. Use binary search + prefix sums for that case (O(n log n)).
  • Why record BEFORE removing L: At the point of recording, the window [L, R] is valid. After sum -= nums[L], the window might no longer be valid — so record first.
Problem 04 of 05Medium
Longest Repeating Character Replacement
LeetCode #424 · leetcode.com/problems/longest-repeating-character-replacement
1
Problem: You can replace at most k characters in a substring. Find the longest substring where all characters can be made the same with at most k replacements.
2
Key insight: In a window of size windowSize, if the most frequent character appears maxFreq times, we need windowSize - maxFreq replacements to make all characters the same. Window is valid when windowSize - maxFreq ≤ k.
3
Window condition: (R - L + 1) - maxFreq > k → invalid. Shrink from L: remove s[L] from frequency map, L++.
4
The maxFreq shortcut: We don't decrement maxFreq when shrinking. This is valid because we only care about finding a LONGER valid window — if maxFreq doesn't increase, we never find a longer window. The window size stays the same while invalid (L and R both move). We only grow when maxFreq increases.
5
This is Variant B (find longest): Expand R. If invalid (replacements needed > k), shrink L by 1. Record max window size only when valid. Unlike other B problems, we use if not while for shrinking here — because we only ever shrink by 1 at a time (window only shrinks when invalid, then R moves forward next iteration, maintaining the window size).
Interviewer
At most k replacements. Find longest substring where all chars can be made the same.
You
The key insight: if I have a window of size W where the most frequent character appears maxFreq times, I need W - maxFreq replacements to make all characters the same. The window is valid when W - maxFreq ≤ k.
You
So I'll maintain a frequency map for the window. At each R, update the frequency and recalculate maxFreq. If (window size - maxFreq) exceeds k — window is invalid, shrink L by 1.
Interviewer
Why do you use if instead of while for shrinking here?
You
We want the LONGEST window — we never need to shrink by more than 1 because we're looking for maximum. The window only grows when maxFreq increases enough to justify a larger window. When invalid, we shrink by exactly 1 to maintain the same window size, then R grows again. We track the maximum as R-L+1, which only increases when the window truly grows.
JavaScriptLongest Repeating Character Replacement — O(n)
function characterReplacement(s, k) {
    const freq = {};
    let L = 0, maxFreq = 0, maxLen = 0;

    for (let R = 0; R < s.length; R++) {
        // Expand: add s[R], update frequency and maxFreq
        freq[s[R]] = (freq[s[R]] || 0) + 1;
        maxFreq = Math.max(maxFreq, freq[s[R]]);

        // Check: replacements needed = window size - most frequent count
        const windowSize = R - L + 1;
        if (windowSize - maxFreq > k) {
            // Invalid: shrink by exactly 1 from left
            freq[s[L]]--;
            L++;
            // Note: we DON'T update maxFreq here — it's a valid optimization
            // maxFreq can only stay same or increase, never decrease usefully
        }

        // Record max — window is either valid or just shrunk by 1 (same size)
        maxLen = Math.max(maxLen, R - L + 1);
    }

    return maxLen;
}
Time: O(n) — R advances n times, L advances at most n times Space: O(26) = O(1) — frequency for 26 letters
  • "AABABBA", k=1: AABAB has 3 A's, 2 B's, size 5. maxFreq=3. Replacements=2 > k=1. Shrink. ABAB size 4, 2A 2B. Replacements=2 > 1. Shrink. BAB size 3, 1A 2B. Replacements=1 ≤ 1. Valid! maxLen=4 was recorded earlier. Answer = 4.
  • k=0: Must find longest run of same character. windowSize - maxFreq = number of non-dominant chars. Must be 0 → window size = maxFreq. Valid windows are all same char.
  • Why not update maxFreq on shrink: When maxFreq doesn't decrease, we might think the window is valid when it isn't — but that's OK. We're looking for LONGEST, and we already recorded the maximum. If the window is technically invalid, R-L+1 won't be larger than maxLen anyway.
  • k ≥ window size: Always valid (replace everything). maxLen = s.length.
Problem 05 of 05Medium
Permutation in String
LeetCode #567 · leetcode.com/problems/permutation-in-string
1
Problem: Return true if s2 contains a permutation of s1 as a substring.
2
Key insight: A permutation of s1 is a window of s2 with the exact same character frequencies as s1. Fixed window size = s1.length.
3
Template A (Fixed Window): Build frequency map for s1. Slide a window of size s1.length over s2. At each position, check if window's frequency matches s1's frequency. If yes, return true.
4
Efficient frequency comparison: Instead of comparing two Maps per window (O(26) per slide), track a matches counter — number of characters with matching frequency. When matches = 26, the window is a permutation.
5
matches counter logic: When adding character c to window: if windowFreq[c] becomes equal to s1Freq[c] → matches++. If it was equal before (now exceeds) → matches--. Symmetric when removing c from left. If matches === 26 → all chars match → permutation found.
Interviewer
Does s2 contain a permutation of s1?
You
A permutation of s1 has the exact same character frequencies as s1. So I'm looking for a substring of s2 with length s1.length that has identical char frequencies to s1. Fixed window size — Template A.
You
Build frequency map for s1. Slide window of size s1.length over s2. Naively, compare maps per window — O(26) per slide, O(26n) total. I can optimize with a matches counter.
Interviewer
Explain the matches counter.
You
I track how many of the 26 characters have matching counts between s1's map and the current window. When a char's window count becomes equal to s1's count, matches++. When it was equal and now differs, matches--. If matches = 26 — all characters match — found a permutation. This makes each slide O(1) instead of O(26).
JavaScriptPermutation in String — O(n) with matches counter
function checkInclusion(s1, s2) {
    if (s1.length > s2.length) return false;

    const s1Freq = new Array(26).fill(0);
    const winFreq = new Array(26).fill(0);
    const a = 'a'.charCodeAt(0);

    for (const ch of s1) s1Freq[ch.charCodeAt(0) - a]++;

    let matches = 0;
    // Count how many chars already match (with s1 freq 0 — all 26 start matched?)
    // Since winFreq is all 0 and some s1Freq might be 0: initially matches counts 0-freq chars
    for (let i = 0; i < 26; i++) if (s1Freq[i] === 0) matches++;

    const update = (idx, delta) => {
        if (winFreq[idx] === s1Freq[idx]) matches--;  // was matching, now won't be
        winFreq[idx] += delta;
        if (winFreq[idx] === s1Freq[idx]) matches++;  // now matches
    };

    // Build initial window of size s1.length
    for (let i = 0; i < s1.length; i++) update(s2.charCodeAt(i) - a, 1);
    if (matches === 26) return true;

    // Slide window
    for (let R = s1.length; R < s2.length; R++) {
        update(s2.charCodeAt(R) - a, 1);                    // add right
        update(s2.charCodeAt(R - s1.length) - a, -1);       // remove left
        if (matches === 26) return true;
    }

    return false;
}
Time: O(n) — O(26) setup + O(n) sliding Space: O(26) = O(1) — two fixed-size arrays
  • s1 longer than s2: Guard at top returns false immediately.
  • s1 = s2: Exactly one window — the whole s2. If same chars, return true.
  • s1 has repeated chars "aab": s1Freq['a']=2, s1Freq['b']=1. Window must also have exactly 2 a's and 1 b. matches counter handles this correctly.
  • Why start matches at count of s1Freq[i] === 0: Characters not in s1 (freq 0) should be considered "matched" when window freq is also 0. Pre-counting these avoids false negatives.
  • Simpler version: Just compare Maps per slide — O(26n). Still acceptable in interviews. The matches counter is an optimization worth mentioning but not always required.

Section 07

15 Interview Questions

Answer out loud before expanding. Focus on the conceptual answers — interviewers test understanding, not memorization.
CoreWhat is a sliding window? How does it achieve O(n) instead of O(n²)?▼
A sliding window is a contiguous subarray defined by two pointers L and R. Instead of re-computing each subarray from scratch (O(n) per subarray × O(n) subarrays = O(n²)), the window maintains a running state as it moves: when R advances, add the new element to the window state; when L advances, remove the leaving element. Each pointer moves at most n times (L only moves right, R only moves right). Total operations: at most 2n = O(n). The key property: the window state can be updated incrementally in O(1) — sum (add/subtract), frequency (increment/decrement), set (add/remove). If updating state is O(1), the overall algorithm is O(n).
VSWhat's the difference between Sliding Window and Two Pointers?▼
Both use two pointers. The distinction: Sliding Window — maintains a window with a specific invariant (condition on what's INSIDE the window). The window is a contiguous range [L, R] that expands and shrinks to maintain the condition. Focus is on the window's content. Works on arrays and strings. Two Pointers — pointers compare elements or count things, not necessarily maintaining a window invariant. Often moves based on comparison of elements at L and R (opposite ends), or one pointer follows the other (fast/slow). Works well on sorted arrays. Overlap: some problems can be solved with either. The window condition test: "Is there a constraint on what's inside the range [L, R]?" If yes → Sliding Window. "Are you comparing/combining elements at two specific positions?" → Two Pointers.
TrapWhy use `while` for shrinking instead of `if`?▼
When the window becomes invalid, one shrink might not be enough to restore validity. Example: longest substring without repeats, window "abcdca", R adds 'a'. Now there are two 'a's. Shrinking once: remove s[L]='a', L++. Now window is "bcdca" — still has two 'a's! Need to keep shrinking until the duplicate is gone. Using if would only shrink once and leave an invalid window. Use while when one invalid event might require multiple shrinks. Exception: Longest Repeating Character Replacement uses if because we deliberately only want to shrink by 1 to maintain window size parity (we're finding the longest, and one shrink keeps the window the same size while R advances).
CoreWhat is the window size formula? What's a common off-by-one error?▼
Window size = R - L + 1. The +1 is because both L and R are inclusive. Example: L=2, R=5. Elements at indices 2, 3, 4, 5 = 4 elements. 5 - 2 = 3 (wrong). 5 - 2 + 1 = 4 (correct). Common off-by-one: returning R - L instead of R - L + 1. For fixed window sliding, the outgoing element is at index R - k (not R - k + 1): when window reaches [R-k+1, R], the element leaving is at R-k. Example: k=3, R=3. Window is [1,2,3]. Element leaving is arr[R-k] = arr[0]. arr[R-k+1] = arr[1] would be the wrong element.
InterviewHow do you identify that a problem needs a sliding window vs prefix sum + HashMap?▼
The distinguishing question: Is the condition ≤/≥ (inequality) or = (equality)? Inequality (≤, ≥, at most, at least): Sliding Window. When sum exceeds k, shrinking the window predictably decreases sum. The window can restore validity by shrinking. Equality (exactly k): Prefix Sum + HashMap. Example: subarray sum = k exactly (#560). If sum becomes k+1 and you remove an element (sum might go to k or to k-2 or anything). The window can't reliably "restore" exact equality by shrinking. The trick for equality: "at most k" - "at most k-1" = "exactly k". Some problems use this trick to apply sliding window to equality problems. If the problem says "at most", "no more than", "at least", "minimum/maximum" — Sliding Window. If "exactly" or "equal to" — Prefix Sum + HashMap or the subtraction trick.
InterviewExplain the key insight for Longest Repeating Character Replacement.▼
In any window, to make all characters the same, you keep the most frequent character and replace everything else. Replacements needed = window size - max frequency of any single character. Window is valid when: (window size - maxFreq) ≤ k. The insight that makes it O(n): we track maxFreq but don't update it when shrinking. When L advances, we remove a character and the actual maxFreq might decrease — but we don't recalculate it. This is fine because: we only care about finding a LONGER valid window. If maxFreq decreases, the window can't be valid at the same size — so R-L stays constant (window doesn't grow). We only grow the window when we find a character with higher frequency than maxFreq (maxFreq increases). This means we only ever find windows of increasing size — exactly what we want for "find longest".
CoreWhat data structures do you use inside sliding windows? When to use each?▼
Running sum/count: Simple integer. Use when window condition involves sum (sum ≥ target, sum ≤ k). O(1) add/remove. HashMap/frequency array: When condition involves character/element frequency (at most k distinct, permutation match). O(1) add/remove, O(1) lookup. Use Map for any type, plain object/array for characters. Set: When condition is "no duplicates". O(1) add/remove/check. Simpler than Map when you don't need counts. Monotonic Deque: When you need min or max of the window efficiently (Sliding Window Maximum #239). O(1) amortized per operation. Elements in deque are always in sorted order (monotone). Sorted structure (TreeMap in Java): When you need sorted access to window elements. O(log n) add/remove but supports range queries. In JS: not built-in, simulate with sorted array or skip list.
TrapWhat's the "at most K" subtraction trick for "exactly K" problems?▼
Problem: count subarrays with exactly k distinct integers (#992). Sliding Window works for "at most k" but not "exactly k" (equality). The trick: subarrays with exactly k distinct = subarrays with at most k distinct - subarrays with at most k-1 distinct. Write a helper atMost(k) that counts subarrays with at most k distinct integers using Sliding Window. Answer = atMost(k) - atMost(k-1). Why it works: atMost(k) counts all subarrays with 1, 2, ..., or k distinct. atMost(k-1) counts those with 1, 2, ..., or k-1 distinct. The difference = subarrays with exactly k distinct. This trick converts many "exactly k" problems into two "at most k" sliding window calls. Look for it when you see "exactly k" with a counting constraint on unique elements.
InterviewHow do you solve Minimum Window Substring? (LeetCode #76)▼
Find smallest window in s that contains all characters of t. Variant C (find shortest). Build frequency map for t. Use a `need` counter = number of distinct characters in t that still need to be satisfied. Expand R: add s[R] to window map. If s[R]'s window count now equals t's count → need--. Shrink while need === 0 (window is valid): record current window size (candidate for minimum). Remove s[L] from window map. If s[L]'s count drops below t's needed count → need++. L++. When need > 0, stop shrinking, continue expanding. Time: O(n + m) where n = s.length, m = t.length. Space: O(n + m). Edge cases: if t has repeated chars (t="aa"), the window must have at least 2 a's. The frequency count handles this correctly.
CoreWhy is it O(n) even though there's a nested while loop?▼
The nested while loop shrinks from L. L can only move right. L starts at 0 and can reach at most n. Across ALL iterations of the outer for loop, the total number of L movements is at most n. Not n per outer iteration — n total across all outer iterations. Think of it as a "charge": each element is added to the window once (when R reaches it) and removed from the window at most once (when L passes it). Total adds = n. Total removes ≤ n. Total operations = 2n = O(n). This amortized analysis is the standard explanation for why any sliding window with inner shrink loop is still O(n). Same reasoning applies to Two Pointer O(n) analysis. Important: this requires that L never moves backward — which is guaranteed by the structure of sliding window.
InterviewWhen does a fixed window need a monotonic deque instead of a simple aggregate?▼
When you need the MAXIMUM or MINIMUM of the window — not just sum or count. Sliding Window Maximum (#239): find max of each window of size k. Naive: re-scan window each slide → O(nk). With deque: maintain a deque of indices in decreasing order of their values. When R advances: pop from back while arr[back] ≤ arr[R] (smaller values can never be the maximum while R is in the window). Push R. The front of the deque is always the index of the current window maximum. When L advances past the front index, pop front. Each element pushed and popped at most once → O(n) total. The deque is monotonic (decreasing) — front is always the max. This is the standard O(n) solution for range maximum queries with a sliding window.
TrapWhat goes wrong if you record the result inside the shrink loop for "find longest"?▼
For find-longest (Variant B), you record AFTER the shrink loop (once window is valid). If you record INSIDE the shrink loop: the window might be invalid at that point (shrink loop runs while invalid). You'd be recording invalid window sizes as candidates for the maximum. Example: find longest subarray with at most 2 distinct chars. Window = "aabbc" (3 distinct, invalid). Shrink loop runs. Inside: record R-L+1 for "aabb" size 4. But window is still invalid (3 distinct). Continue shrink: "abbc" still 3. Shrink: "bbc" = 2 distinct. Valid. Exit loop. Now if you'd recorded inside, you'd have recorded the invalid window. Correct: record AFTER the while loop exits — at that point, L has been advanced until the window is valid again.
InterviewHow do you count ALL valid subarrays, not just the longest?▼
When the window [L, R] is valid, count += R - L + 1. Why: all subarrays ending at R with left boundaries from L to R are valid. That's R - L + 1 subarrays: [L..R], [L+1..R], ..., [R..R]. When you slide R to the next position, L either stays (still valid) or moves right (shrink). In both cases, the count for the new R position includes R - L + 1 new valid subarrays. This counting trick is used in: Number of Subarrays with at most k distinct (#904), Subarray Product Less Than K (#713), and similar counting problems. Key: this works for "at most" conditions where all shorter subarrays ending at R are also valid. For "exactly k," use the subtraction trick.
VSSliding Window vs Prefix Sum — which for "subarray sum = k exactly"?▼
Subarray sum = k exactly (#560): use Prefix Sum + HashMap. When sum increases to k+2 and you shrink, you might get k+1, k, or k-1 depending on what element you remove — unpredictable. Can't reliably "seek" equality by shrinking. Sliding Window for sum = k only works if all values are positive AND you can shrink predictably (positive means removing always decreases). If values can be 0 or negative → Prefix Sum + HashMap always works. When prefix[j] - prefix[i] = k, or equivalently prefix[i] = prefix[j] - k, use a HashMap: for each prefix sum, check if (prefix - k) exists in map. O(n) time and space. Sliding Window for sum ≥ k or sum ≤ k (with all positives) → O(n) time, O(1) space. When in doubt: sum constraints with equality → Prefix Sum. Sum constraints with inequality and all positives → Sliding Window.
InterviewWhat's the template difference between "find longest" and "find shortest"?▼
Find longest (Variant B): Expand R (always). If window becomes INVALID: shrink L until VALID again. Record max window size AFTER shrink loop. The shrink loop runs while the window violates the condition. Find shortest (Variant C): Expand R until window becomes VALID. Once VALID: record current window size (candidate for minimum). Shrink L while STILL VALID (record each time). Stop shrinking when window becomes invalid again. The critical difference: in B, you shrink while INVALID and record AFTER. In C, you shrink while VALID and record BEFORE each shrink. This reversal is because B wants the biggest valid window (stop as soon as valid after shrinking) and C wants the smallest valid window (keep shrinking while you can). Code check: where is maxLen = Math.max(...) or minLen = Math.min(...) relative to the shrink loop? After = find longest. Inside (before shrinking) = find shortest.
