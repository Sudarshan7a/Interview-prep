Section 01

The Core Idea — Halving the Search Space

Binary search works on any sorted (or monotonic) space. Each comparison eliminates half the remaining candidates. O(log n) — 1 billion elements in 30 comparisons.

Binary search halves the search space at each step. Start with the full range [lo, hi]. Pick the middle element. If it's the answer, done. If the answer is to the left, set hi = mid - 1. If to the right, set lo = mid + 1. Repeat until the space collapses.

The real power of Binary Search: You don't need an actual sorted array. You need a monotonic decision function — any function where the answer is "No, No, No, Yes, Yes, Yes" (or the reverse). Binary search finds the boundary between No and Yes in O(log n). This is why it applies to problems far beyond "search in sorted array."
JavaScriptClassic Binary Search — find exact target
function binarySearch(nums, target) {
    let lo = 0, hi = nums.length - 1;

    while (lo <= hi) {                          // ≤ not <
        const mid = lo + Math.floor((hi - lo) / 2); // avoids overflow

        if (nums[mid] === target) {
            return mid;          // exact match found
        } else if (nums[mid] < target) {
            lo = mid + 1;        // target is to the right
        } else {
            hi = mid - 1;        // target is to the left
        }
    }

    return -1; // not found
}

// Why lo + (hi - lo) / 2 instead of (lo + hi) / 2:
// If lo and hi are both large, lo + hi can overflow a 32-bit integer.
// In JS, numbers are 64-bit floats so this rarely matters,
// but the habit is important for Java/C++ interviews.
The 3 classic binary search bugs — memorize and avoid:

✗ lo < hi instead of lo <= hi → misses the last element when lo === hi
✗ mid = (lo + hi) / 2 → integer overflow (use lo + Math.floor((hi-lo)/2))
✗ lo = mid or hi = mid without +1/-1 → infinite loop when lo === hi

The template with lo <= hi, lo = mid+1, hi = mid-1 is the safest. Use it for all basic binary search. The lower/upper bound variants have different rules — covered in templates.

Binary Search on Answer — the advanced pattern explained:

The most powerful binary search variant. Instead of searching in an array, you search in the space of possible answers. The key insight: if a solution with answer X is feasible, then any answer Y > X is also feasible (or vice versa). This monotonic property means binary search applies.

How to recognize "Binary Search on Answer":

✓ Problem asks for minimum/maximum value satisfying some condition
✓ You can write a canDo(X) function that returns true/false
✓ The condition is monotonic: if canDo(X) is true, canDo(X+1) is also true (or false for all smaller X)
✓ Problem involves "minimize the maximum" or "maximize the minimum"

Template: binary search on X in [lo, hi]. At each mid: if canDo(mid) → record answer, try smaller (hi = mid). Else try larger (lo = mid + 1).
Section 03

Interview Framework

The 5 questions to answer before writing any binary search code.
1
What is the search space?
Is it indices in an array? A range of values (like eating speed or ship capacity)? A range of days? Clearly defining the search space sets lo and hi. For arrays: lo=0, hi=n-1 or lo=0, hi=n. For answer space: lo=minimum_possible_answer, hi=maximum_possible_answer.
"The search space is the range of possible eating speeds — from 1 banana per hour (minimum) to max(piles) bananas per hour (worst case: eat the largest pile in one hour). I'll binary search within this range."
2
What is the condition (feasibility function)?
Define exactly what makes a mid value "valid" or "feasible." For sorted array: nums[mid] === target. For Koko: canFinish(speed) = sum of ceil(pile/speed) for each pile ≤ h hours. The feasibility function is the core logic — everything else is scaffolding.
"My feasibility function: given a speed k, can Koko finish all bananas in h hours? Check: for each pile, it takes ceil(pile/k) hours. If total hours ≤ h, feasible. This is O(n) per check."
3
Which boundary are you finding? (exact, lower, upper)
Exact: target exists exactly. Lower bound: first position where condition switches to true. Upper bound: last position where condition is true. This determines whether you use lo ≤ hi (exact) or lo < hi with careful hi/lo updates (bounds). State this explicitly before coding.
"I'm looking for the minimum feasible speed — the first X where canFinish(X) is true. So I'm finding the lower bound. I'll use lo < hi, and when mid is feasible, I try smaller: hi = mid. When not feasible, lo = mid+1."
4
What does lo represent after the loop?
For lo < hi template: when the loop ends, lo === hi. This single value is your answer. Understand WHY: the loop invariant maintains that the answer is always in [lo, hi]. The loop shrinks this interval until lo === hi. For the lo ≤ hi template: if loop ends without returning, return -1 (not found).
"After the loop, lo === hi. At this point, lo is the minimum speed where canFinish is true — the invariant guarantees this. I return lo."
5
Verify: trace through a small example, state complexity
Binary search complexity: O(log n) iterations × O(cost of feasibility check). For arrays: O(log n) total. For "binary search on answer": O(log(hi-lo) × n) if check is O(n). Always state both the log factor AND the check cost. Common mistake: stating only log n.
"Time: O(n log m) where n is the number of piles and m is max(piles). Log m iterations of binary search, each checking all n piles. Space: O(1)."
Section 04

The 4 Templates

Learn T1 first (exact). T2 and T3 for bounds. T4 for "binary search on answer" — the interview favourite.
JavaScriptTemplate 1 — Exact Search (three-way check)
function exactSearch(nums, target) {
    let lo = 0, hi = nums.length - 1;

    while (lo <= hi) {   // ≤ because lo === hi is still a valid position to check
        const mid = lo + Math.floor((hi - lo) / 2);

        if      (nums[mid] === target) return mid;    // found
        else if (nums[mid] <  target) lo = mid + 1;  // target right
        else                          hi = mid - 1;  // target left
    }
    return -1; // not found
}
JavaScriptTemplate 2 — Lower Bound (first position where condition is true)
// Find: smallest index where nums[i] >= target
// Or: first bad version, first true in [false,false,true,true,true]
function lowerBound(nums, target) {
    let lo = 0, hi = nums.length; // hi = n (not n-1) to handle "insert at end"

    while (lo < hi) {   // strict < — loop exits when lo === hi
        const mid = lo + Math.floor((hi - lo) / 2);

        if (nums[mid] >= target) {
            hi = mid;    // mid could be the answer — don't exclude it
        } else {
            lo = mid + 1; // mid is definitely NOT the answer
        }
    }

    return lo; // lo === hi: the first position where nums[i] >= target
}
// Invariant: answer is always in [lo, hi]
// When loop ends, lo === hi is the exact answer
JavaScriptTemplate 3 — Upper Bound (last position where condition is true)
// Find: largest index where nums[i] <= target
function upperBound(nums, target) {
    let lo = 0, hi = nums.length - 1;

    while (lo < hi) {
        // CEILING division — avoids infinite loop when lo = hi - 1
        const mid = lo + Math.ceil((hi - lo) / 2);

        if (nums[mid] <= target) {
            lo = mid;    // mid could be the answer — don't exclude it
        } else {
            hi = mid - 1; // mid is definitely NOT the answer
        }
    }

    return lo; // last position where nums[i] <= target
}
// Why ceiling? When lo and hi are adjacent (lo = hi-1):
// Floor: mid = lo → lo = mid = lo → infinite loop
// Ceiling: mid = hi → if valid: lo = hi → loop ends
JavaScriptTemplate 4 — Binary Search on Answer (Koko Eating Bananas pattern)
function binarySearchOnAnswer(piles, h) {
    // Search space: [lo, hi] = [min_possible_answer, max_possible_answer]
    let lo = 1;                     // minimum speed: 1
    let hi = Math.max(...piles);    // maximum speed: largest pile

    while (lo < hi) {
        const mid = lo + Math.floor((hi - lo) / 2);

        if (canFinish(piles, mid, h)) {
            hi = mid;     // mid works — try smaller (find MINIMUM)
        } else {
            lo = mid + 1; // mid too slow — need larger speed
        }
    }

    return lo; // minimum speed that works
}

function canFinish(piles, speed, h) {
    let hours = 0;
    for (const pile of piles) {
        hours += Math.ceil(pile / speed);
    }
    return hours <= h;
}
// Pattern: find MINIMUM → when feasible: hi = mid (try smaller)
// Pattern: find MAXIMUM → when feasible: lo = mid (try larger), ceiling mid

Problem 01 of 05Easy
Binary Search
LeetCode #704 · leetcode.com/problems/binary-search
1
Problem: Given a sorted array and target, return the index of target or -1 if not found. O(log n) required.
2
Template 1 (exact search): lo=0, hi=n-1. While lo ≤ hi: compute mid. Three-way check: equal (return mid), less (lo=mid+1), greater (hi=mid-1). Return -1 if loop exits.
3
Why lo ≤ hi: When lo equals hi, there's exactly one element left to check. We must check it. If we used lo < hi, we'd exit the loop without checking this last element.
4
Why mid = lo + (hi-lo)/2: Prevents integer overflow. In languages with fixed-size integers (Java, C++), (lo+hi) can overflow if both are near Integer.MAX_VALUE. In JS this is safe due to 64-bit floats, but the habit matters for Java interviews.
Interviewer
Implement binary search on a sorted array. Must be O(log n).
You
Three pointers: lo at index 0, hi at the last index. At each step, compute mid as lo plus floor of (hi minus lo) divided by 2 — this form prevents overflow. Compare nums[mid] to target: if equal, return mid. If target is to the right, lo = mid+1. If to the left, hi = mid-1. Loop condition is lo ≤ hi — when they're equal, we still have one element to check.
Interviewer
Why lo ≤ hi and not lo < hi?
You
When lo equals hi, there's exactly one element left to check — we haven't determined if it's the target yet. With lo < hi, we'd exit the loop and miss it. With lo ≤ hi, we check it. If it's the target, return mid. If not, lo = mid+1 (or hi = mid-1) makes lo > hi and the loop exits naturally, returning -1.
Interviewer
What if the array has duplicates and you want the first occurrence?
You
Switch to the lower bound template. When nums[mid] === target, instead of returning immediately, set hi = mid — keep searching left for an earlier occurrence. When the loop ends (lo === hi), that's the first occurrence. This is Template 2.
JavaScriptBinary Search — Template 1
function search(nums, target) {
    let lo = 0, hi = nums.length - 1;

    while (lo <= hi) {
        const mid = lo + Math.floor((hi - lo) / 2);

        if      (nums[mid] === target) return mid;
        else if (nums[mid] <  target) lo = mid + 1;
        else                          hi = mid - 1;
    }

    return -1;
}
Time: O(log n) — halve search space each step Space: O(1) — just three variables
  • Empty array: lo=0, hi=-1. lo > hi immediately. Return -1. Correct.
  • Single element: lo=hi=0. Check nums[0]. If target, return 0. Else lo=1>hi=0, return -1.
  • Target not in array: Loop exits with lo > hi. Return -1.
  • Target at lo or hi: At some point mid will equal the boundary index. Found normally.
  • All same elements: [5,5,5,5], target=5. First mid hits a 5, return that mid. If target=3: lo moves right each time since nums[mid]=5>3... wait, 5 > 3 so hi = mid-1. Loop exits. Return -1.
Problem 02 of 05Easy
First Bad Version
LeetCode #278 · leetcode.com/problems/first-bad-version
1
Problem: Given n versions 1..n. Some version was corrupted and everything after is also bad. Find the first bad version using a provided isBadVersion(v) API.
2
Pattern: [Good, Good, Good, Bad, Bad, Bad] — classic lower bound. Find the first position where isBadVersion(v) is true. Template 2.
3
When mid is bad: hi = mid (mid could be the first bad — don't exclude it). When mid is good: lo = mid+1 (mid is definitely not the first bad). Loop exits when lo === hi = first bad version.
4
Minimize API calls: Each isBadVersion call costs. Binary search calls it O(log n) times — optimal. A linear scan would call it n times in the worst case.
Interviewer
Find the first bad version. You have an isBadVersion API.
You
The versions are [Good...Good, Bad...Bad] — the first bad splits the array into a monotone pattern. This is lower bound binary search. I want the first position where isBadVersion is true.
You
lo=1, hi=n. Loop while lo < hi. If isBadVersion(mid) is true — this could be the first bad — set hi=mid (don't exclude mid). If false — mid is good — set lo=mid+1. When the loop exits, lo equals hi equals the first bad version.
Interviewer
Why lo < hi instead of lo ≤ hi here?
You
Because I want the loop to exit when lo === hi — that single remaining value IS the answer. If I used lo ≤ hi, I'd need a separate "return" inside the loop when mid is bad and lo===hi, or handle the exit case differently. The lo < hi template exits naturally when the interval collapses to one element.
JavaScriptFirst Bad Version — Lower Bound (Template 2)
var solution = function(isBadVersion) {
    return function(n) {
        let lo = 1, hi = n;

        while (lo < hi) {   // strict < — exits when lo === hi (the answer)
            const mid = lo + Math.floor((hi - lo) / 2);

            if (isBadVersion(mid)) {
                hi = mid;      // mid could be first bad — keep it in range
            } else {
                lo = mid + 1; // mid is good — first bad must be after
            }
        }

        return lo; // lo === hi: the first bad version
    };
};
Time: O(log n) — log n API calls Space: O(1)
  • Version 1 is bad: lo=1, hi=n. mid=n/2. isBadVersion(mid)=true. hi=mid. Eventually hi shrinks to 1. lo===hi===1. Return 1.
  • Version n is the only bad: isBadVersion always false until n. lo keeps moving right. Eventually lo=n, hi=n. Loop exits. Return n.
  • Why hi starts at n (not n-1): The first bad version could be at position n. If we start hi=n-1, we'd never check the last version. Using hi=n includes it in the search space.
  • Invariant: The first bad version is always in [lo, hi]. lo only moves past definite goods. hi only moves to potential bads. When lo===hi, that must be the first bad.
Problem 03 of 05Medium
Koko Eating Bananas
LeetCode #875 · leetcode.com/problems/koko-eating-bananas
1
Problem: Koko can eat k bananas per hour. She must finish all piles in h hours. Find the minimum k. Piles are arrays of banana counts.
2
Binary Search on Answer: The answer k is somewhere in [1, max(piles)]. For any k, we can check if it's feasible in O(n). The feasibility is monotonic: if k works, k+1 also works. Find the minimum k that works.
3
Feasibility check: For each pile, Koko needs ceil(pile/k) hours. Total hours = sum of ceil(pile/k). If total ≤ h → feasible. O(n) per check.
4
Why max(piles) as hi: At speed max(piles), Koko finishes each pile in exactly 1 hour. Total hours = number of piles ≤ h (guaranteed). So max(piles) is always feasible — it's a valid upper bound.
5
Template 4: lo=1, hi=max(piles). When canFinish(mid): hi=mid (try smaller, find minimum). When !canFinish(mid): lo=mid+1 (need faster). Return lo after loop.
Interviewer
Find the minimum eating speed for Koko to finish all bananas in h hours.
You
The possible eating speeds range from 1 to max(piles). For any speed k, I can check feasibility in O(n): does sum of ceil(pile/k) for all piles ≤ h hours? The feasibility is monotonic — faster is always feasible if slower is. This is binary search on the answer space.
You
Lo=1, hi=max(piles). Binary search: if canFinish(mid) → hi=mid (mid works, look for something smaller). Else → lo=mid+1 (too slow). At the end, lo is the minimum feasible speed.
Interviewer
What's the time complexity?
You
O(n log m) where n is number of piles and m is max(piles). Log m iterations of binary search, each running the O(n) feasibility check. Space O(1).
Interviewer
Why not just try speeds from 1 to max(piles) linearly?
You
That would be O(m × n) — m up to 10^9, n up to 10^4, total 10^13 operations. Way too slow. Binary search reduces to O(log m × n) — about 30 × 10^4 = 300,000 operations. That's the power of binary search on answer space.
JavaScriptKoko Eating Bananas — Binary Search on Answer
function minEatingSpeed(piles, h) {
    let lo = 1;
    let hi = Math.max(...piles);

    while (lo < hi) {
        const mid = lo + Math.floor((hi - lo) / 2);

        if (canFinish(piles, mid, h)) {
            hi = mid;      // works at mid → try smaller
        } else {
            lo = mid + 1; // too slow → need faster
        }
    }

    return lo; // minimum feasible speed
}

function canFinish(piles, speed, h) {
    let totalHours = 0;
    for (const pile of piles) {
        totalHours += Math.ceil(pile / speed); // hours for this pile
    }
    return totalHours <= h;
}
Time: O(n log m) — n = piles, m = max(piles) Space: O(1)
  • Single pile [10], h=1: lo=1, hi=10. Binary search finds k=10 (must eat 10 in 1 hour). Return 10.
  • h ≥ total bananas: Speed of 1 always works. lo never moves from 1. Return 1.
  • h = number of piles: Must eat each pile in exactly 1 hour. Minimum speed = max(piles).
  • Integer ceiling in JS: Math.ceil(pile/speed). Alternative: Math.floor((pile + speed - 1) / speed) — integer-only ceiling without floating point. Both work in JS.
  • Why max(piles) is a valid upper bound: At speed max(piles), each pile takes exactly 1 hour. Total = n piles ≤ h (problem guarantees a solution exists). So hi is always a valid answer — binary search will find something ≤ hi.
Problem 04 of 05Medium
Search in Rotated Sorted Array
LeetCode #33 · leetcode.com/problems/search-in-rotated-sorted-array
1
Problem: A sorted array was rotated at some unknown pivot. Find the target. Array has no duplicates. O(log n) required.
2
Key insight: Even after rotation, one of the two halves [lo, mid] or [mid, hi] is always sorted. Determine which half is sorted, then check if target is in that sorted half. If yes, search there. If no, search the other half.
3
Which half is sorted: If nums[lo] ≤ nums[mid] → left half [lo, mid] is sorted (no rotation in this half). Else → right half [mid, hi] is sorted.
4
Is target in the sorted half: If left half is sorted and nums[lo] ≤ target < nums[mid] → target must be in left half → hi = mid-1. Else → go right → lo = mid+1. Mirror logic for right half.
Interviewer
Search in a rotated sorted array. O(log n) required.
You
A rotated sorted array has one key property: at any mid point, at least one of the two halves is fully sorted. I determine which half is sorted, then check if the target falls in that sorted range. If yes, search there. If no, search the other half.
You
If nums[lo] ≤ nums[mid], the left half is sorted. If target is in [nums[lo], nums[mid]) — go left. Otherwise go right. Mirror for the right half: if nums[mid] ≤ nums[hi], the right is sorted. Target in (nums[mid], nums[hi]] — go right. Otherwise go left.
Interviewer
What if there are duplicates?
You
Duplicates break the "which half is sorted" check. If nums[lo] === nums[mid], we can't tell which side is sorted. We'd need to skip duplicates: lo++ and hi-- when nums[lo] === nums[mid] === nums[hi]. This degrades to O(n) in the worst case but remains O(log n) on average. That's LeetCode #81 — Search in Rotated Array II.
JavaScriptSearch in Rotated Sorted Array — O(log n)
function search(nums, target) {
    let lo = 0, hi = nums.length - 1;

    while (lo <= hi) {
        const mid = lo + Math.floor((hi - lo) / 2);

        if (nums[mid] === target) return mid;

        // Determine which half is sorted
        if (nums[lo] <= nums[mid]) {
            // Left half [lo, mid] is sorted
            if (nums[lo] <= target && target < nums[mid]) {
                hi = mid - 1; // target in sorted left half
            } else {
                lo = mid + 1; // target in right half
            }
        } else {
            // Right half [mid, hi] is sorted
            if (nums[mid] < target && target <= nums[hi]) {
                lo = mid + 1; // target in sorted right half
            } else {
                hi = mid - 1; // target in left half
            }
        }
    }

    return -1;
}
Time: O(log n) — binary search guaranteed Space: O(1)
  • Not rotated [1,2,3,4,5]: nums[lo]=1 ≤ nums[mid] always. Always enters left branch. Standard binary search.
  • Rotation at index 1 [6,1,2,3,4,5]: lo=0, mid=2. nums[0]=6 > nums[2]=2. Right half [2..5] is sorted. Target 1 not in (2,5]. Go left. hi=1. lo=0, hi=1, mid=0. nums[0]=6=target? No. nums[lo]=6 > nums[mid]=6... wait, they're equal → left sorted. Target 1 not in [6,6). Go right. lo=1. nums[1]=1=target. Return 1.
  • Target not present: Loop exits with lo > hi. Return -1.
  • Why nums[lo] ≤ nums[mid] (not <): The ≤ handles the case when lo === mid (single element — always "sorted"). Strict < would miss this case.
Problem 05 of 05Medium
Find Minimum in Rotated Sorted Array
LeetCode #153 · leetcode.com/problems/find-minimum-in-rotated-sorted-array
1
Problem: Find the minimum element in a rotated sorted array. Array has no duplicates. The minimum is the pivot point — where the array "restarts" from a smaller value.
2
Key insight: Compare nums[mid] to nums[hi]. If nums[mid] > nums[hi] → the minimum is in the right half (the rotation is in the right half). If nums[mid] ≤ nums[hi] → the minimum is in the left half (or at mid itself).
3
Why compare to nums[hi] not nums[lo]: If not rotated, nums[lo] < nums[mid] — doesn't tell us where the minimum is. But nums[mid] vs nums[hi] tells us: if nums[mid] > nums[hi], the big-to-small "jump" (the pivot) must be to the right of mid.
4
Template 2 variant: lo < hi. When nums[mid] > nums[hi]: lo = mid+1 (minimum is to the right). Else: hi = mid (minimum could be at mid). Return nums[lo] after the loop.
Interviewer
Find the minimum in a rotated sorted array.
You
The minimum is the rotation point — where the value "resets" to a smaller value. I binary search by comparing nums[mid] to nums[hi]. If nums[mid] > nums[hi], the rotation point (minimum) is in the right half — lo = mid+1. Otherwise the minimum is at mid or to the left — hi = mid. Loop exits when lo === hi = index of minimum.
Interviewer
Why nums[hi] and not nums[lo]?
You
If we compare to nums[lo]: if nums[lo] < nums[mid], the left half is sorted — but we don't know if the minimum is in the right half or left half without more info. Comparing to nums[hi] is cleaner: if nums[mid] > nums[hi], there's a "drop" somewhere to the right of mid — the minimum must be there. This uniquely determines which half contains the minimum.
Interviewer
What if the array isn't rotated?
You
nums[mid] will always be ≤ nums[hi] (since the array is sorted ascending). So hi keeps shrinking toward lo. Eventually lo === hi === 0, which is the minimum (first element). Correct for non-rotated arrays.
JavaScriptFind Minimum in Rotated Array — O(log n)
function findMin(nums) {
    let lo = 0, hi = nums.length - 1;

    while (lo < hi) {
        const mid = lo + Math.floor((hi - lo) / 2);

        if (nums[mid] > nums[hi]) {
            // Mid is in the "high" part — minimum is to the right
            lo = mid + 1;
        } else {
            // Mid could be the minimum or minimum is to the left
            hi = mid;
        }
    }

    return nums[lo]; // lo === hi: index of minimum element
}

// Trace [4,5,6,7,0,1,2]:
// lo=0, hi=6, mid=3, nums[3]=7 > nums[6]=2 → lo=4
// lo=4, hi=6, mid=5, nums[5]=1 ≤ nums[6]=2 → hi=5
// lo=4, hi=5, mid=4, nums[4]=0 ≤ nums[5]=1 → hi=4
// lo=4=hi: return nums[4]=0 ✓
Time: O(log n) Space: O(1)
  • Not rotated [1,2,3,4,5]: nums[mid] ≤ nums[hi] always. hi shrinks to 0. Return nums[0]=1. Correct.
  • Rotated by 1 [2,3,4,5,1]: hi=4. Minimum is at index 4. Binary search converges there.
  • Single element [1]: lo=hi=0. Loop doesn't run. Return nums[0]=1. Correct.
  • Two elements [2,1]: lo=0, hi=1, mid=0. nums[0]=2 > nums[1]=1. lo=1. lo===hi=1. Return nums[1]=1. Correct.
  • Two elements [1,2]: mid=0. nums[0]=1 ≤ nums[1]=2. hi=0. lo===hi=0. Return nums[0]=1. Correct.

15 Interview Questions

Answer out loud. Binary search is deceptively tricky — the off-by-one errors and template choices are what interviews test.
TrapWhat are the 3 most common binary search bugs? How do you avoid each?▼
Bug 1 — Wrong loop condition: Using lo < hi when you should use lo ≤ hi (or vice versa). Fix: exact search uses lo ≤ hi (must check when lo===hi). Bound-finding uses lo < hi (exit when interval collapses to one element). Bug 2 — Integer overflow in mid calculation: (lo + hi) / 2 can overflow. Fix: always use lo + Math.floor((hi - lo) / 2). Bug 3 — Infinite loop from wrong boundary update: Using lo = mid (without +1) or hi = mid (without -1) in the wrong template. Fix: for lo < hi template: when moving lo, always use lo = mid+1 (mid is excluded). When moving hi, use hi = mid (mid is included as potential answer). For upper bound template: use ceiling mid to avoid infinite loop when lo = hi-1.
CoreWhat is "Binary Search on the Answer Space"? Give an example.▼
Instead of searching in an array, you search in the range of possible answers. The key: define a feasibility function canDo(X) that returns true/false. The condition must be monotonic: if canDo(X) is true, canDo(X+1) is also true (for minimum-finding problems). Binary search finds the exact boundary. Example — Koko Eating Bananas: "What's the minimum eating speed?" Binary search on speed from 1 to max(piles). For each speed, check if she can finish in h hours. The feasibility switches from false to true at exactly one speed — find that boundary. Time: O(log(answer_range) × check_cost). Recognition: problem asks "find minimum/maximum X such that condition holds," and you can write a O(n) or O(n log n) feasibility check.
InterviewExplain the lower bound template. What does lo represent after the loop?▼
Lower bound: find the first (leftmost) position where a condition becomes true. Template: lo=0, hi=n. Loop while lo < hi. Mid = lo + floor((hi-lo)/2). If condition(mid) is true: hi = mid (mid could be the answer, don't exclude it). If false: lo = mid+1 (mid is definitely not the answer, exclude it). After the loop, lo === hi. This single value is the leftmost position where the condition is true. Why it works: the invariant "the answer is always in [lo, hi]" is maintained throughout. lo only moves past definite non-answers. hi only moves to potential answers. When the interval collapses to one element, that must be the answer. Use for: first occurrence of value in sorted array, first bad version, search insert position, first position satisfying some monotonic condition.
TrapWhy does the upper bound template need ceiling mid instead of floor mid?▼
Upper bound: find the LAST position where condition is true. When condition(mid) is true: lo = mid (mid could be the answer, keep it). When false: hi = mid-1. The problem: if lo = hi-1 and we use floor mid: mid = lo+floor((hi-lo)/2) = lo+0 = lo. Then lo = mid = lo — lo doesn't move. Infinite loop! Fix: use ceiling mid when moving lo = mid (not lo = mid+1). Ceiling: mid = lo + ceil((hi-lo)/2). When lo=hi-1: mid=lo+1=hi. If condition(hi)=true: lo=hi → loop exits. If false: hi=mid-1=lo → loop exits. Both cases terminate. Memorize: lower bound uses floor mid (lo = mid+1 always moves). Upper bound uses ceiling mid (lo = mid must still make progress).
InterviewHow do you search in a rotated sorted array? What's the key insight?▼
Key insight: even after rotation, at every midpoint, at least one half is fully sorted. Determine which half is sorted: if nums[lo] ≤ nums[mid], the left half [lo, mid] is sorted. Otherwise the right half [mid, hi] is sorted. Then check if target falls in the sorted half's range. If yes, binary search there (half is sorted — normal comparison works). If no, search the other half. This eliminates half the array each step → O(log n). The ≤ in nums[lo] ≤ nums[mid] handles lo===mid (single element — trivially sorted). Code: while(lo≤hi), compute mid, check sorted half, check target range, eliminate half. Return -1 if not found. For duplicates (LC#81): if nums[lo]===nums[mid], can't determine which half is sorted — increment lo (sacrifice one element, O(n) worst case).
InterviewHow do you implement Sqrt(x) using binary search?▼
Find the largest integer k where k² ≤ x. This is upper bound binary search on integers 0..x. lo=0, hi=x (or hi=min(x,46340) for 32-bit optimization since 46340²≈2^31). Loop while lo < hi: ceiling mid (to avoid infinite loop). If mid*mid ≤ x: lo=mid (could be answer). Else: hi=mid-1 (too large). Return lo. Note: mid*mid can overflow 32-bit integers for large x. Use BigInt or compare mid ≤ x/mid (integer division) instead. Alternative brute force: increment from 0 until k*k > x, return k-1. O(sqrt(x)) — acceptable for small inputs. Binary search is O(log x) — much better. The answer space [0, x] has x+1 elements, log₂ of which is about 15-30 bits — very fast.
CoreWhat's the time complexity of binary search? Why O(log n)?▼
Each iteration, the search space is halved. Starting with n elements: after 1 step → n/2. After 2 steps → n/4. After k steps → n/2^k. We stop when 1 element remains: n/2^k = 1 → k = log₂(n). So: O(log n) iterations. For 1 billion elements: log₂(10^9) ≈ 30. Binary search finds any element in 30 comparisons — regardless of n. For "Binary Search on Answer": iterations = log₂(hi - lo). If the answer space is [1, 10^9]: log₂(10^9) ≈ 30 iterations. Each feasibility check is O(n). Total: O(n log(10^9)) = O(30n). Space: O(1) — just the lo, hi, mid variables. No recursion stack (iterative). Recursive binary search has O(log n) stack space.
InterviewHow do you search in a 2D matrix where each row is sorted? (#74 and #240)▼
#74 (rows sorted, first element of each row > last of previous): The entire matrix is effectively one sorted array. Treat it as such: lo=0, hi=m*n-1. mid maps to row=floor(mid/n), col=mid%n. Standard binary search. O(log(m*n)) = O(log m + log n). #240 (rows sorted, columns sorted — but no row≥row guarantee): Different approach: start at top-right corner. If matrix[row][col] == target: found. If > target: move left (col--). If < target: move down (row++). Each step eliminates a row or column. O(m+n). Why not binary search #240: the 2D structure doesn't reduce to a 1D sorted sequence. The top-right elimination approach exploits both sorted dimensions. Know both problems and their different approaches — interviewers use them to test if you understand WHY binary search works, not just the mechanics.
AdvancedHow would you binary search on a real-valued (non-integer) answer?▼
When the answer is a real number (floating point), use a fixed number of iterations instead of lo < hi: run 100 iterations of binary search (or until hi - lo < 1e-9). Each iteration: mid = (lo + hi) / 2.0. Floating point mid has no integer division issues. If feasible: hi = mid. Else: lo = mid. After 100 iterations, lo ≈ hi with precision 2^(-100) ≈ 10^-30. For problems requiring 1e-6 precision: about 60 iterations suffice. Example: Minimize Max Distance to Gas Station — binary search on the maximum gap (real number). The feasibility check counts how many stations to add to keep all gaps ≤ mid. This pattern is cleaner than trying to handle floating point with ≤ comparisons.
InterviewWhat is the "Capacity to Ship Packages" problem? Why is it binary search?▼
LeetCode #1011. Ship packages (with weights) within D days. Find minimum ship capacity. Binary search on the answer (capacity): lo = max(weights) (minimum: can ship the heaviest), hi = sum(weights) (maximum: ship everything in 1 day). Feasibility: can we ship all within D days at this capacity? Simulate: greedily pack packages into each day until adding the next would exceed capacity, then start a new day. If days needed ≤ D → feasible. Why binary search: capacity range is monotonic — if capacity C works, C+1 also works. Find the minimum C where feasible → lower bound binary search on [max, sum]. This is a classic "binary search on answer" that appears at PhonePe/Swiggy level interviews. The pattern: minimize a resource (capacity, speed, days) → binary search + greedy feasibility check.
TrapWhat goes wrong with binary search when the array has duplicates?▼
Classic binary search: if you want ANY occurrence, works fine. But for "first occurrence" or "last occurrence" of a target in an array with duplicates: must use lower/upper bound templates. For "first occurrence": when nums[mid]===target, don't return immediately — set hi=mid and continue searching left. For "last occurrence": when nums[mid]===target, set lo=mid and continue right (with ceiling mid to avoid infinite loop). For rotated sorted array with duplicates (#81): when nums[lo]===nums[mid]===nums[hi], can't determine which half is sorted. Must skip: lo++, hi--. This degrades to O(n) worst case (all same elements). Always clarify with the interviewer: "Are there duplicates? Do you want first/last/any occurrence?" This affects both the template choice and worst-case complexity.
InterviewExplain "Find First and Last Position" (#34). Why two binary searches?▼
LeetCode #34. Find the first and last index of target in a sorted array with duplicates. Solution: two separate binary searches. First binary search: lower bound — first index where nums[i] >= target. Check if nums[lo] === target. If yes, lo is the first position. Second binary search: upper bound — last index where nums[i] <= target. Check if nums[lo] === target. If yes, lo is the last position. Return [first, last] or [-1,-1] if target not found. Why two searches: a single binary search can find any occurrence of target, but finding both boundaries requires knowing how far left and right the duplicates extend — that's two separate monotonic problems. Time: O(log n) per search, O(log n) total. Never use O(n) linear scan to extend outward from a found position — that would be O(n) total in the worst case.
AdvancedHow does "Split Array Largest Sum" use binary search? (#410)▼
LeetCode #410 (Hard). Split array into k subarrays to minimize the maximum subarray sum. Binary search on the answer (the maximum sum): lo = max(nums) (minimum: each number must be in its own subarray), hi = sum(nums) (maximum: all in one subarray). Feasibility: given maximum allowed sum X, can we split the array into at most k subarrays each summing ≤ X? Greedy check: scan left to right, greedily add to current subarray until adding next would exceed X — start a new subarray. Count subarrays needed. If count ≤ k → feasible. Binary search finds minimum X where feasible. Time: O(n log(sum)). This problem also has a DP solution O(n²k) but binary search is O(n log(sum)) — much better for large inputs. The "minimize maximum" framing is the signal for this BS+greedy pattern.
InterviewHow do you find the peak element in an array? Why binary search works on unsorted data?▼
LeetCode #162. A peak element is one that's strictly greater than its neighbors. Binary search works even though the array isn't globally sorted because of a local monotonicity: at any mid, if nums[mid] < nums[mid+1], then a peak exists to the right (nums[mid+1] might be the peak, or there's a larger element further right — but by the "left boundary = -infinity" rule, a peak must exist). If nums[mid] > nums[mid+1], a peak exists to the left (or at mid). Algorithm: lo=0, hi=n-1, lo<hi. Compare nums[mid] to nums[mid+1]. If nums[mid] < nums[mid+1]: lo=mid+1 (go right). Else: hi=mid (go left). Return nums[lo] after loop. O(log n). The key: we don't need a global sorted property — the local slope (rising or falling) tells us which direction to search.
CoreWhen does binary search NOT apply? What's the pre-condition?▼
Binary search requires a monotonic property: the answer space must be divided into exactly two regions (No/Yes, or smaller/larger) with a single boundary. If the answer space is not monotonic — e.g., "find any element satisfying a condition where the condition doesn't have a clean boundary" — binary search won't work. Examples where it fails: finding the maximum of a general function (might have multiple peaks — need ternary search or different approach). Finding a specific element in an unsorted array (no monotonic structure — need linear scan or hash). "Is this number prime" (no monotonic property with respect to the number itself). Examples where it applies more broadly than expected: sorted matrices (with the right starting point), "feasibility" problems with monotonic feasibility, decision problems with monotonic answer space. The key question: "If I increase the answer by 1, does feasibility only go from false→true (or true→false)?" If yes, binary search.
