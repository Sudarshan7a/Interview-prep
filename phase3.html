"CollabDocs is a real-time collaborative document editor — think Google Docs in miniature. The interesting engineering: I used Socket.io for WebSocket connections. "ShopFlow is a RESTful order management API built with Spring Boot and PostgreSQL. System Design Basics

Freshers get asked system design too — simpler versions, but still asked. "Design a URL shortener", "design a notification system", "design a rate limiter." Learn the framework first, then 3 specific designs, then the 6 building blocks that appear in every system.

The framework — use for every system design question
Step 1 · 5 min
Requirements
Functional (what it does) + Non-functional (scale, latency, consistency). Ask: how many users? reads/writes ratio? data size?
Step 2 · 5 min
High-Level Design
Draw the boxes: clients, load balancer, app servers, database, cache. Don't over-engineer yet.
Step 3 · 10 min
Deep Dive
Pick 1–2 components to go deep. DB schema, algorithm, caching strategy, API design. Interviewer guides this.
Step 4 · 5 min
Scale + Trade-offs
How does this handle 10x traffic? What breaks first? What are the trade-offs in your design choices?
💡 For freshers: don't try to design Netflix
Interviewers at CRED/Razorpay/BrowserStack asking freshers for system design expect you to: know the building blocks (caching, load balancing, database types), apply them sensibly, and discuss trade-offs. They don't expect you to design Cassandra from scratch. Show structured thinking, not encyclopedic knowledge.
Design 1 — URL Shortener (most common fresher question)
Design a URL shortener like bit.ly ▼
Requirements
  • Functional: Given a long URL, return a short URL. Given a short URL, redirect to long URL.
  • Non-functional: 100M URLs, reads >> writes (100:1 ratio), low latency (<100ms redirect), high availability
DB Schema
  • urls table: id (PK), short_code (VARCHAR 7, unique index), long_url (TEXT), user_id (FK), created_at, expiry_at, click_count
  • Index on short_code for O(1) lookup
Key design decisions to discuss
  • Short code generation: Base62 encode a counter (0-9, a-z, A-Z = 62 chars). 7 characters = 62^7 = 3.5 trillion URLs. Alternative: random hash (MD5, take first 7 chars) — risk of collision.
  • Redirect type: 301 (permanent, browser caches — fewer server hits but can't track clicks) vs 302 (temporary, browser always hits server — can track clicks). Use 302 for analytics.
  • Caching: Redis cache for hot URLs (reads are 100x writes). Cache short_code → long_url mapping. Cache eviction: LRU. TTL: 24 hours.
  • Scaling: Read replicas for DB (most traffic is reads). Multiple app server instances behind load balancer. Redis cluster for cache.
  • Custom slugs: Users can request custom short code (e.g., bit.ly/my-product-launch). Check availability, store as any other URL.
Architecture diagram to draw: Client → Load Balancer → App Server (multiple) → [Redis Cache → PostgreSQL DB]. Write flow: App Server → DB (generate ID, base62 encode, store). Read flow: App Server → Redis (hit?) → if miss → DB → 302 redirect.
Design 2 — Notification System
Design a notification system (like Swiggy order updates) ▼
Requirements
  • Channels: Push notification (mobile), SMS, email. User can set preferences.
  • Scale: 10M notifications/day. Some are time-sensitive (order updates), some are not (promotional).
  • Reliability: Notifications must be delivered at least once. Retry on failure.
Key components
  • Notification Service: Validates, routes to correct channel, enqueues
  • Message Queue: Kafka or RabbitMQ. Decouple sender from delivery workers.
  • Workers: Separate workers for push/SMS/email. Each reads from queue, calls 3rd party API.
  • 3rd party APIs: FCM (Firebase) for push, Twilio for SMS, SendGrid for email
  • Message queue (why): Order service publishes event → Notification service consumes. Decoupled, handles traffic spikes, retries on failure automatically.
  • Priority queue: High-priority (order delivered) vs low-priority (promotional). Separate queues, workers process high-priority first.
  • User preferences: Store in DB (user_id, channel, enabled). Check before sending — don't SMS a user who opted out.
  • Retry logic: Dead letter queue for failed notifications. Retry 3 times with exponential backoff. Alert on repeated failures.
  • Rate limiting: Don't send more than X notifications per user per day (spam prevention). Redis counter per user per day.
Design 3 — Rate Limiter
Design a rate limiter for an API ▼
  • What it does: Limit requests per user/IP to N per time window. Return 429 when exceeded.
  • Fixed window: Count requests per minute. Resets at minute boundary. Problem: burst at window boundary (100 at :59, 100 at :00 = 200 in 2 seconds).
  • Sliding window log: Store timestamp of each request. Count within last 60 seconds. Accurate but memory-heavy (store all timestamps).
  • Sliding window counter: Track current window count + fraction of previous window count. Approximate but memory-efficient. Most production choice.
  • Token bucket: Bucket holds N tokens. Each request consumes 1 token. Tokens refill at fixed rate. Allows bursting up to bucket capacity.
  • Redis implementation: For distributed rate limiting (across multiple servers): INCR key → if 1 (first request) set EXPIRE. If count exceeds limit → 429. Atomic operations.
Redis rate limiter — sliding window counter 
async function isRateLimited(userId, limit = 100, windowMs = 60000) {
    const key = `rate:${userId}:${Math.floor(Date.now() / windowMs)}`;
    const count = await redis.incr(key);
    if (count === 1) await redis.expire(key, windowMs / 1000);
    return count > limit;  // true = rate limited → return 429
}
// INCR is atomic — no race condition in distributed environment
// Key includes time window — auto-expires, no cleanup needed
6 building blocks — know all of these
⚖️
Load Balancer
Distributes traffic across multiple app servers. Round-robin, least-connections, or consistent hashing. Enables horizontal scaling. Health checks remove failed servers.
⚡
Caching (Redis)
Store frequently read data in memory (microseconds) instead of DB (milliseconds). Cache-aside pattern: check cache → if miss → read DB → write to cache. Eviction: LRU. TTL prevents stale data.
🌐
CDN
Content Delivery Network: serve static assets (images, JS, CSS) from edge servers close to users. Reduces latency from 200ms to 10ms for static content. CloudFront, Cloudflare.
📨
Message Queue
Decouple services: producer publishes, consumer processes asynchronously. Handles traffic spikes (queue absorbs burst). Retry on failure. Kafka for high-throughput, RabbitMQ for simpler use cases.
🗄️
Database Sharding
Split data across multiple DB instances (shards). Each shard holds a subset of data. Horizontal scaling for writes. Routing: hash of user_id → shard. Downside: cross-shard queries are expensive.
📖
Read Replicas
Primary DB handles writes. Replica DBs replicate data and serve reads. Most apps are read-heavy (10:1 ratio). Replicas scale reads without touching the primary. Small replication lag (eventual consistency for reads).

Docker — Containerize Everything

Docker packages your app and all its dependencies into a container that runs identically everywhere. "Works on my machine" stops being an excuse. Every project you build should have a Dockerfile. Interviewers at good companies expect this.

What to learn — in order
✓
Docker basics — images, containers, volumes, networks
What Docker solves, core concepts, essential CLI commands
must · understand before Dockerfile
Exactly what to learn
  • Image: blueprint/template. Built from Dockerfile. Immutable. Like a class definition.
  • Container: running instance of an image. Like an object from a class. Isolated process with own filesystem.
  • Volume: persistent storage outside container lifecycle. Data survives container restarts. Used for DB data.
  • Network: containers on same Docker network communicate by container name (not localhost).
  • Key commands: docker build -t name ., docker run -p 3000:3000 name, docker ps, docker stop id, docker exec -it id sh, docker logs id
  • -p 8080:3000: host port 8080 maps to container port 3000. Access via localhost:8080.
  • -e NODE_ENV=production: pass environment variables to container. Never hardcode secrets in Dockerfile.

Interview questions on Docker
  • "What is Docker and why use it?" Containerization: packages app + dependencies + runtime into isolated unit. Runs identically in dev, staging, production. Eliminates environment differences.
  • "What's the difference between an image and a container?" Image = static blueprint (like a class). Container = running instance (like an object). Multiple containers can run from same image.
  • "What is multi-stage build and why use it?" Build in one image (has compiler/build tools), copy artifacts to a smaller runtime image. Result: much smaller production image (800MB → 100MB).
  • "How does docker-compose networking work?" Services on the same compose network communicate by service name (not localhost). Backend connects to MongoDB at mongo:27017 where "mongo" is the service name.

NGINX config — reverse proxy + WebSocket support 
server {
    listen 80;
    server_name your-domain.com;  # or EC2 public IP

    location / {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;     # WebSocket support
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_cache_bypass $http_upgrade;
    }
}
# Enable config:
# sudo ln -s /etc/nginx/sites-available/collabdocs /etc/nginx/sites-enabled/
# sudo nginx -t && sudo systemctl reload nginx
What to know for interviews about this setup
  • Why NGINX in front of Node? NGINX handles SSL termination, serves static files (10x faster than Node), can act as load balancer, and is battle-tested for production traffic.
  • WebSocket in NGINX: the Upgrade and Connection headers tell NGINX to proxy the WebSocket protocol upgrade, not just HTTP.
  • Security group (firewall): EC2 security group controls which ports are open to the internet. Only 22 (SSH), 80 (HTTP), 443 (HTTPS) should be public. All other ports blocked.
  • HTTPS: use Let's Encrypt (certbot) for free SSL certificate. sudo certbot --nginx -d your-domain.com. Auto-renews every 90 days.
