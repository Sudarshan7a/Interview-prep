Keys in RDBMS

Primary, Foreign, Candidate, Composite, Surrogate. Every interview starts here. Know the difference between surrogate and natural keys — it's a design question.
must knowFoundation for everything else
01All key types with real examples
Key TypeDefinitionReal ExampleConstraint
Primary Key Uniquely identifies each row. Never null. user_id in Users table UNIQUE + NOT NULL. One per table.
Foreign Key References primary key of another table. Enforces referential integrity. orders.user_id references users.user_id Must match an existing PK or be NULL. Prevents orphan records.
Candidate Key Any column(s) that COULD be the primary key — unique + not null. Both email AND phone uniquely identify a user. Both are candidate keys. UNIQUE + NOT NULL. One chosen as PK, others remain as unique constraints.
Composite Key A primary key made of TWO or MORE columns. (student_id, course_id) in Enrollment table — neither alone is unique, but together they are. Combination must be UNIQUE + NOT NULL.
Surrogate Key Artificial, system-generated key — not from real business data. Auto-increment ID. id SERIAL PRIMARY KEY — just a number, means nothing in the real world. Auto-generated. Never changes. Not visible to users.
Natural Key Key derived from real-world data that naturally identifies the entity. email address, phone number, Aadhaar number, ISBN, PAN card number Already meaningful. Problem: can change (email changes, phone changes).
02Surrogate vs Natural Key — the design question

This is a real design decision you'll make on every project and potentially be asked about in interviews.

Surrogate Key (id = 12345)Natural Key (email = "ravi@gmail.com")
StabilityNever changes — just a numberCan change (person changes email)
PrivacySafe to expose in URLsExposing email in URL is a privacy issue
PerformanceInteger join — fast B-tree lookupString join — slower, larger index
Business meaningNone — purely technicalMeaningful to business domain
When to preferAlmost always (production standard)When natural key is truly stable and required externally (ISBN, country code)
Interview question: "Why use surrogate keys instead of email as primary key?" — Email can change. If email is the PK, changing it requires updating every foreign key reference in every related table (orders, sessions, logs). With a surrogate key, you update email in one place (users table) and nothing else changes. Also: integer JOINs are faster than string JOINs.
03Referential Integrity — why foreign keys matter

Referential integrity means you can't have an orphan record — a row that references something that doesn't exist. Foreign key constraints enforce this at the database level. 

-- Referential integrity in action
CREATE TABLE users (
    id    SERIAL PRIMARY KEY,
    name  VARCHAR(100) NOT NULL
);

CREATE TABLE orders (
    id      SERIAL PRIMARY KEY,
    user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    amount  DECIMAL(10,2)
);

-- INSERT INTO orders (user_id, amount) VALUES (9999, 500);
-- → ERROR: insert or update on table "orders" violates foreign key constraint
-- → user_id=9999 doesn't exist in users table

-- ON DELETE CASCADE: if user is deleted, all their orders are deleted too
-- ON DELETE SET NULL: if user deleted, order's user_id becomes NULL
-- ON DELETE RESTRICT (default): cannot delete user if they have orders
Interview Q&A — Keys
What is the difference between primary key and unique key? ▼
Strong answerBoth enforce uniqueness — no two rows can have the same value. The differences: (1) A table can have only ONE primary key but MULTIPLE unique keys. (2) A primary key column cannot be NULL; a unique key column CAN be NULL (one NULL is allowed, since NULL ≠ NULL in SQL). (3) The primary key is the main identifier for the table — foreign keys in other tables reference it. Unique keys are additional uniqueness constraints (e.g., users table might have PK on id and UNIQUE on email — both enforced, but id is what other tables reference).
When would you use a composite primary key vs a surrogate key? ▼
Strong answerUse a composite key when the table represents a many-to-many relationship — e.g., Enrollment(student_id, course_id) where each student-course pair is unique and meaningful. The composite of both columns IS the identity. Use a surrogate key when: the entity needs its own identity beyond relationships, you want simple integer foreign key references from other tables, or the combination of natural columns would be verbose as a PK. In practice, even junction tables often get a surrogate PK for simplicity in applications and ORM frameworks like Hibernate/JPA that expect single-column PKs.

Keys — 60-second revision

  • Primary Key: UNIQUE + NOT NULL. One per table. Main identifier.
  • Foreign Key: references another table's PK. Enforces referential integrity. Prevents orphan records.
  • Candidate Key: any column that COULD be PK (unique + not null). Multiple can exist — one chosen as PK.
  • Composite Key: PK made of 2+ columns. Used in junction tables (student_id + course_id).
  • Surrogate Key: auto-increment integer. Stable, fast, safe. Production standard.
  • Natural Key: from real data (email, phone). Problem: can change, privacy risk.
  • Referential integrity: FK enforces "referenced row must exist." ON DELETE CASCADE/RESTRICT/SET NULL.

Normalization — 1NF, 2NF, 3NF

Step-by-step normalization of a real messy table. This is the concept most freshers can define but can't apply. You need to apply it cold in an interview.
must knowNormalize a table from scratch — asked at CRED, PhonePe level
01Why normalize? The problems it solves.

Normalization eliminates data redundancy (same data stored multiple places) and prevents update anomalies.

AnomalyWhat happensExample
Update anomalyUpdating one fact requires changing multiple rows. Miss one → inconsistent data.Ravi moves cities. Must update every order row that has "Ravi, Bangalore". Miss one → some orders show old city.
Insert anomalyCan't insert data without unrelated data being present.Can't add a new product category without having a product in it.
Delete anomalyDeleting one fact accidentally deletes unrelated data.Delete the last order from a customer → lose the customer's contact info too.

  │ OrderID  │ Customer │ CustomerCity  │ Products                 │ Prices         │
  ├──────────┼──────────┼───────────────┼──────────────────────────┼────────────────┤
  │ 1        │ Ravi     │ Bangalore     │ Phone, Charger, Case     │ 999, 199, 49   │

031NF — First Normal Form
1NF Rule: Each column must have atomic (single) values. No repeating groups. Each row must be unique.

Problem in our table: The Products column contains multiple values ("Phone, Charger, Case"). This is not atomic — one cell has multiple items. Fix: split into separate rows.

  AFTER 1NF: Split multi-valued columns into separate rows
  ┌──────────┬──────────┬───────────────┬─────────────┬────────┐
  │ OrderID  │ Customer │ CustomerCity  │ Product     │ Price  │
  ├──────────┼──────────┼───────────────┼─────────────┼────────┤
  │ 1        │ Ravi     │ Bangalore     │ Phone       │ 999    │
  │ 1        │ Ravi     │ Bangalore     │ Charger     │ 199    │
  │ 1        │ Ravi     │ Bangalore     │ Case        │ 49     │

  │ 3        │ Ravi     │ Bangalore     │ Headphones  │ 1299   │
  └──────────┴──────────┴───────────────┴─────────────┴────────┘

  Primary Key must be composite: (OrderID, Product)
  — neither alone uniquely identifies a row.

  Still has problems: Ravi/Bangalore still repeated 3 times. Update anomaly still exists.
042NF — Second Normal Form
2NF Rule: Must be in 1NF + No partial dependency. Every non-key column must depend on the WHOLE primary key, not just part of it.

What is a partial dependency? In our table, the PK is (OrderID, Product). Customer and CustomerCity depend only on OrderID — not on Product. Knowing the Product doesn't tell you the Customer. This is a partial dependency — a non-key column depends on PART of the composite key.

Fix: Split into two tables. Move columns that depend on only part of the PK into their own table.

  AFTER 2NF: Split into two tables

  Orders table:           OrderItems table:
  ┌─────────┬──────────┬──────────────┐   ┌─────────┬─────────────┬────────┐
  │OrderID  │Customer  │CustomerCity  │   │OrderID  │Product      │Price   │
  │(PK)     │          │              │   │(FK)     │             │        │
  ├─────────┼──────────┼──────────────┤   ├─────────┼─────────────┼────────┤
  │ 1       │ Ravi     │ Bangalore    │   │ 1       │ Phone       │ 999    │

                                          │ 3       │ Headphones  │ 1299   │
                                          └─────────┴─────────────┴────────┘

  OrderItems PK: (OrderID, Product) — both needed to identify an item
  Price depends on which product is in which order → depends on FULL PK ✓

  Still has a problem: CustomerCity depends on Customer, not on OrderID.
  Customer Ravi appears in rows 1 and 3 → CustomerCity "Bangalore" is stored twice.
053NF — Third Normal Form
3NF Rule: Must be in 2NF + No transitive dependency. Non-key columns must depend ONLY on the primary key — not on other non-key columns.

What is a transitive dependency? In the Orders table: OrderID → Customer → CustomerCity. CustomerCity depends on Customer (a non-key column), not directly on OrderID. This is a transitive dependency — CustomerCity gets to OrderID only through Customer.

Fix: Move Customer data to its own table. Orders table just stores the customer's ID as a foreign key.

  AFTER 3NF: Three clean tables

  Customers table:      Orders table:          OrderItems table:
  ┌──────┬───────┬──────┐  ┌───────┬──────────┐     ┌───────┬─────────────┬────────┐

                           └───────┴──────────┘     └───────┴─────────────┴────────┘

  Now if Ravi moves: update ONE row in Customers. Done. ✓
  No redundancy. No update anomaly. No insert anomaly.

  Each non-key column depends ONLY on the primary key of its table:
  • Name, City depend on CustID ✓
  • CustomerID depends on OrdID ✓
  • Price depends on (OrdID, Product) ✓
06Denormalization — when to break the rules

Normalization is great for write-heavy, consistency-critical systems. But heavily normalized data requires many JOINs for reads — and JOINs are expensive at scale.

Normalized (3NF)Denormalized
Read performanceSlow (many JOINs)Fast (data pre-joined)
Write performanceFast (update one place)Slow (update multiple copies)
StorageMinimal (no redundancy)More (duplicate data)
Data consistencyGuaranteed (one source of truth)Risk of inconsistency
Use whenOLTP (transactions, e-commerce, banking)OLAP (analytics, reporting, data warehouses)
ExampleSwiggy orders DB, PhonePe transactionsAnalytics dashboard showing "total revenue by restaurant per day"
Interview Q&A — Normalization
Walk me through normalizing a table to 3NF. What is a transitive dependency? ▼
Strong answerStarting with Orders(OrderID, Customer, CustomerCity, Product, Price): 1NF: each cell one value — split multi-valued Products into separate rows. PK becomes (OrderID, Product). 2NF: no partial dependencies — Customer and CustomerCity depend only on OrderID, not on Product. Move them to an Orders table with PK=OrderID. OrderItems keeps (OrderID, Product, Price). 3NF: no transitive dependencies — CustomerCity depends on Customer (non-key), not OrderID. CustomerCity → Customer → OrderID is transitive. Fix: move Customer to its own Customers table with PK=CustomerID. Orders stores CustomerID as FK. Now: if Ravi moves, update ONE row in Customers. No anomalies. A transitive dependency is when A → B → C (C depends on B which depends on PK A, but C doesn't directly depend on A).
When would you intentionally denormalize a database? ▼
Strong answerWhen read performance matters more than write consistency — typically in analytics and reporting systems. Example: a dashboard showing "total revenue per restaurant per day" on Swiggy. Fully normalized, this requires JOINing orders, order_items, restaurants, and doing aggregations — expensive on billions of rows. Denormalized: pre-compute and store "daily_restaurant_revenue" with restaurant_name and revenue already combined. Reads are instant, but every order write must also update this summary. Trade-off: faster reads, more complex writes, risk of stale data. Data warehouses (Amazon Redshift, BigQuery) are built on denormalized star schemas for exactly this reason. OLTP systems (transactional) → normalize. OLAP systems (analytics) → denormalize.

Normalization — 60-second revision

  • Goal: eliminate redundancy, prevent update/insert/delete anomalies.
  • 1NF: atomic values (one value per cell), unique rows. No arrays in a column.
  • 2NF: 1NF + no partial dependency. Non-key columns depend on the WHOLE composite PK.
  • 3NF: 2NF + no transitive dependency. Non-key depends only on PK, not on other non-key columns.
  • Test for 3NF: "Does every non-key column directly and only depend on the primary key?"
  • Denormalize for OLAP/analytics (read performance). Keep normalized for OLTP (transaction integrity).

ACID Properties

Atomicity, Consistency, Isolation, Durability. Don't just memorize the acronym — understand each property with a real PhonePe payment example. Interviewers follow up with "what implements durability?" and "what is consistency really?"
must knowAsked at every product company, every round
01The scenario — PhonePe transfer of ₹500

Ravi sends ₹500 to Priya via PhonePe. This requires two operations: debit ₹500 from Ravi's account, credit ₹500 to Priya's account. ACID ensures this works correctly under all circumstances. 

BEGIN TRANSACTION;

UPDATE accounts SET balance = balance - 500 WHERE user_id = 'ravi';    -- debit Ravi
UPDATE accounts SET balance = balance + 500 WHERE user_id = 'priya';   -- credit Priya
INSERT INTO transaction_log (from_user, to_user, amount) VALUES ('ravi', 'priya', 500);

COMMIT;   -- or ROLLBACK if anything failed
02A — Atomicity: All or Nothing

Atomicity: All operations in a transaction either ALL succeed or ALL fail. There is no "partial success."

If the server crashes after debiting Ravi but before crediting Priya — Atomicity guarantees the debit is ROLLED BACK. Ravi doesn't lose ₹500. The transaction either completes fully or doesn't happen at all. 

  Scenario: Server crashes after DEBIT but before CREDIT

  Without Atomicity:        With Atomicity (ROLLBACK):
  Ravi:  -₹500  ← done     Ravi:  ₹0 change  ← rolled back
  Priya: no change          Priya: ₹0 change  ← never happened
  → ₹500 LOST              → Transaction as if it never occurred

  Implementation: UNDO log (write-ahead logging)
  Before changing data: write what the old value was to the log.
  If crash: read UNDO log → restore old values.
03C — Consistency: Valid State to Valid State

Consistency: A transaction takes the database from one valid state to another valid state. All constraints (NOT NULL, CHECK, FOREIGN KEY, business rules) are satisfied before AND after the transaction.

In our example: the constraint is balance >= 0 (can't have negative balance). If Ravi has ₹400 and tries to send ₹500 — the transaction violates the consistency constraint. The DB should reject it.

Also: total money in the system must be conserved. Before transaction: Ravi₹1000 + Priya₹500 = ₹1500. After transaction: Ravi₹500 + Priya₹1000 = ₹1500. The sum is consistent.

Common misconception: Consistency in ACID is about database constraints, not about distributed systems consistency (like in CAP theorem). In ACID, C means "constraints are not violated." In CAP, C means "all nodes see the same data." Different concepts, same letter.
04I — Isolation: Concurrent Transactions Don't See Each Other's Work

Isolation: concurrent transactions execute as if they were serial (one after another). Each transaction is unaware of other in-flight transactions.

Without isolation: while Transaction A is deducting from Ravi's account (but not yet committed), Transaction B might read Ravi's balance as already-deducted — seeing data that hasn't been committed yet (a "dirty read").

Implementation: locking (readers block writers or vice versa) or MVCC (Multi-Version Concurrency Control — each transaction sees a consistent snapshot of the data as of when the transaction started, without blocking other readers).

05D — Durability: Committed = Permanent

Durability: once a transaction is committed (COMMIT executed, success returned to user), the changes are permanent — even if the server crashes immediately after.

Once Ravi sees "Transfer Successful" on his PhonePe screen, that transaction has been committed. Even if the server dies at that exact moment, the data is safe.

Implementation: Write-Ahead Logging (WAL). Before applying any change to the actual data files, the change is first written to a persistent log on disk. On restart after a crash, the DB reads the WAL log and replays any committed transactions that weren't fully applied to data files. 

  WRITE-AHEAD LOGGING (WAL):
  ┌──────────────────────────────────────────────────────────┐
  │  Transaction commits:                                    │
  │  1. Write record to WAL log (on disk): "SET balance=500" │
  │  2. WAL log flushed (fsync) — data on physical disk      │
  │  3. Return "SUCCESS" to client                           │
  │  4. Apply change to actual data files (can be deferred)  │
  │                                                          │
  │  If crash between steps 3 and 4:                        │
  │  → On restart: WAL log shows committed transaction       │
  │  → DB replays it → data files updated → consistent       │
  └──────────────────────────────────────────────────────────┘
Interview Q&A — ACID
Explain ACID properties with a real payment example. ▼
Strong answer — the complete answerAtomicity: PhonePe transfer — debit Ravi AND credit Priya. If server crashes after debit: rollback. Ravi doesn't lose money. All-or-nothing. Implemented via UNDO log. Consistency: constraints never violated. Balance can't go negative. Total money before = total after. DB moves from one valid state to another. Isolation: two concurrent transfers don't see each other's uncommitted changes. Transaction B reading Ravi's balance doesn't see T1's partial debit. Implemented via locking or MVCC. Durability: once COMMIT returns success, the data is on disk permanently. Even if server dies 1ms after commit, data is safe. Implemented via WAL (Write-Ahead Log) — changes logged to disk before being confirmed.
What is the difference between Atomicity and Durability? Both seem to handle crashes. ▼
Strong answerThey handle different crash scenarios: Atomicity handles crashes that occur DURING a transaction (before commit). It ensures partial work is undone. "If I started and didn't finish, act like I never started." Durability handles crashes that occur AFTER a committed transaction. It ensures completed work survives. "If I finished and said so, the data must survive." Atomicity uses UNDO logs (to reverse partial work). Durability uses REDO logs / WAL (to replay committed work that hasn't hit the data files yet). Both use Write-Ahead Logging — the WAL log serves both purposes: undo for uncommitted, redo for committed.
NoSQL databases (like MongoDB) are often said to not be ACID. Is that still true? ▼
Strong answerThis was true of early NoSQL databases but is increasingly outdated. MongoDB supports ACID transactions at the single-document level since version 4.0 (2018) and multi-document ACID transactions since 4.0 (replica sets) and 4.2 (sharded clusters). Cassandra offers configurable consistency but is inherently eventual consistency — not ACID by default. Redis supports atomic operations on single keys and Lua scripts for multi-key atomicity but no full ACID transactions. The distinction now is less "SQL=ACID, NoSQL=not-ACID" and more about the default semantics and guarantees each system provides. For financial data requiring strict ACID guarantees, PostgreSQL/MySQL remain the standard choice. But saying "MongoDB is not ACID" is outdated for modern versions.

ACID — 60-second revision

  • Atomicity: all or nothing. Crash during transaction → rollback. UNDO log.
  • Consistency: constraints never violated. Valid state → valid state. Balance ≥ 0. Sum conserved.
  • Isolation: concurrent transactions don't see each other's uncommitted work. Locking or MVCC.
  • Durability: committed = permanent. Survives crashes. Write-Ahead Logging (WAL).
  • Atomicity vs Durability: Atomicity handles crash DURING transaction. Durability handles crash AFTER commit.
  • ACID ≠ ACID in CAP: Consistency in ACID = constraint satisfaction. Consistency in CAP = all nodes see same data.

Transaction Isolation Levels

Four levels, three problems they prevent. Which is MySQL default? Which is PostgreSQL default? This separates candidates who memorized ACID from those who actually understand it.
must knowInterviewers ask which level prevents which problem
01The three concurrency problems
ProblemWhat happensExample
Dirty Read T1 reads data that T2 has modified but NOT yet committed. T2 later rolls back — T1 read data that never existed. T2 debits Ravi's account to ₹500 (uncommitted). T1 reads ₹500. T2 rolls back — Ravi's balance is still ₹1000. T1 made a decision based on a value that never committed.
Non-Repeatable Read T1 reads a row. T2 updates that row and commits. T1 reads the SAME row again — gets different value. T1 reads Ravi's balance: ₹1000. T2 debits ₹500 and commits. T1 reads again: ₹500. Same query, different result within the same transaction.
Phantom Read T1 reads a SET of rows matching a condition. T2 inserts new rows matching that condition and commits. T1 re-queries — sees new "phantom" rows. T1 counts orders over ₹1000: 5 results. T2 inserts a new ₹5000 order and commits. T1 counts again: 6 results. The phantom row appeared.
02The four isolation levels
Isolation LevelDirty ReadNon-RepeatablePhantom ReadPerformanceDefault in
Read Uncommitted✗ Possible✗ Possible✗ PossibleFastest (no locking)Rarely used
Read Committed✓ Prevented✗ Possible✗ PossibleGoodPostgreSQL, Oracle
Repeatable Read✓ Prevented✓ Prevented✗ Possible*ModerateMySQL InnoDB
Serializable✓ Prevented✓ Prevented✓ PreventedSlowest (heavy locking)Financial transactions

* MySQL InnoDB's Repeatable Read actually prevents phantom reads through gap locks, but the SQL standard says Repeatable Read allows phantoms.

03How each level is implemented

Read Committed: Takes a read snapshot at the start of each statement. Each new query within a transaction sees the latest committed data. Dirty reads prevented (only committed data visible). But between two queries in the same transaction, other transactions can commit changes — non-repeatable reads possible.

Repeatable Read: Takes a snapshot at the start of the entire transaction. All reads within the transaction see the data as it was when the transaction began. Even if other transactions commit during this time, this transaction's reads are stable.

Serializable: Strongest. Transactions execute as if they were serial — one after another, no concurrent execution. Implemented with range locks or predicate locks. Prevents all anomalies. Slowest due to locking overhead.

Repeatable Read analogy: You take a photo of a spreadsheet at 10 AM. For the rest of the day, you only look at that photo — even as colleagues update the original spreadsheet. Your reads are "repeatable" — you always see 10 AM's data. The downside: you might miss important updates others have committed.
Interview Q&A — Isolation Levels
What is a dirty read? Which isolation level prevents it? ▼
Strong answerA dirty read is when Transaction T1 reads data that Transaction T2 has modified but NOT yet committed. If T2 later rolls back, T1 has read data that never officially existed. Example: T2 sets Ravi's balance to ₹500 (uncommitted). T1 reads ₹500 and approves a loan based on this. T2 rolls back — Ravi still has ₹1000. T1 approved a loan based on a ghost value. Prevention: READ COMMITTED isolation level and above. READ COMMITTED only shows committed data — T2's uncommitted change is invisible to T1. READ UNCOMMITTED allows dirty reads (essentially no isolation). In financial systems, READ COMMITTED is the minimum acceptable isolation level.
What is MVCC? How does it differ from locking? ▼
Strong answerMVCC (Multi-Version Concurrency Control): instead of locking rows when they're read, the DB maintains multiple versions of each row. Each transaction sees a consistent snapshot based on when it started. Readers never block writers, writers never block readers. PostgreSQL and MySQL InnoDB use MVCC. Traditional locking: when T1 reads a row, it acquires a shared lock. T2 trying to write that row must wait for T1's lock to release. Readers block writers, writers block readers. MVCC advantage: much higher read concurrency — no reader ever waits for a writer. MVCC disadvantage: must store multiple versions of rows (more storage) and periodically vacuum/clean up old versions (PostgreSQL VACUUM).

Isolation Levels — 60-second revision

  • Dirty Read: read uncommitted data that might be rolled back. Prevented by READ COMMITTED+.
  • Non-Repeatable Read: same row read twice in same transaction gives different values. Prevented by REPEATABLE READ+.
  • Phantom Read: same query returns different rows (new rows inserted by concurrent transaction). Prevented by SERIALIZABLE.
  • READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE. More isolation = less concurrency = slower.
  • PostgreSQL default: READ COMMITTED. MySQL InnoDB default: REPEATABLE READ.
  • MVCC: multiple row versions. Readers don't block writers. PostgreSQL + MySQL use it.

Database Indexing

B-Tree structure. Clustered vs non-clustered. When to add an index and when NOT to. The write penalty. EXPLAIN / EXPLAIN ANALYZE. Composite index prefix rule.
must know"Your query is slow — how do you fix it?" is always asked
01Why indexes exist — the problem they solve

Without an index, every query on a non-PK column does a full table scan — check every single row. On a 10 million row table, that's 10 million comparisons for every query. Catastrophically slow.

An index is a separate data structure that allows the DB to find rows in O(log n) instead of O(n). Like a book's index — instead of reading the whole book to find "REST API", you check the index for the page numbers.

02B-Tree — the internal structure
  B-Tree index on "email" column (simplified):

                      [M]
                    /     \
              [D–H]         [N–Z]
             /     \       /     \
           [D]   [E–H]  [N]   [O–Z]
                   ↓
               Leaf node: contains email value + pointer to actual row

  Key properties:
  • Balanced tree — all leaf nodes at same depth
  • Each lookup: O(log n) — about 23 comparisons for 10M rows
  • Range queries: O(log n + k) — find start, scan forward
  • Without index: O(n) = 10,000,000 comparisons for 10M rows

Dictionary analogy: Clustered index = dictionary — words ARE in alphabetical order. The book is the index. Non-clustered = book's index at the back — alphabetical list of topics with page numbers. The data (pages) are not sorted by topic.
04When to add an index — and when NOT to

05The write penalty — indexes slow writes

Every time you INSERT, UPDATE, or DELETE a row, every index on that table must also be updated. If you have 10 indexes on a table, every write operation must update 10 B-Trees. This is why over-indexing is a performance problem — too many indexes hurts write-heavy tables. 

-- Create an index
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_phone ON users(phone);
CREATE INDEX idx_users_city  ON users(city);

-- This INSERT must update ALL three indexes
INSERT INTO users (name, email, phone, city) VALUES ('Ravi', 'ravi@gmail.com', '9876543210', 'Bangalore');
-- → updates users table row + idx_users_email B-tree + idx_users_phone B-tree + idx_users_city B-tree

-- COMPOSITE INDEX: column order matters!
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);
-- Helps: WHERE user_id = 5 (leftmost prefix)
-- Helps: WHERE user_id = 5 AND created_at > '2024-01-01'
-- DOES NOT help: WHERE created_at > '2024-01-01' (not leftmost)

-- EXPLAIN to see if index is being used
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'ravi@gmail.com';
-- Without index: "Seq Scan" → full table scan → slow
-- With index:    "Index Scan" → B-tree lookup → fast
06When indexes aren't used — gotchas
-- GOTCHA 1: Leading wildcard — index on 'email' NOT used
SELECT * FROM users WHERE email LIKE '%gmail.com';  -- full scan!
SELECT * FROM users WHERE email LIKE 'ravi%';       -- index CAN be used

-- GOTCHA 2: Function on indexed column — index NOT used
SELECT * FROM users WHERE LOWER(email) = 'ravi@gmail.com'; -- full scan!
-- Fix: store emails lowercase always, OR create functional index
CREATE INDEX idx_lower_email ON users(LOWER(email));

-- GOTCHA 3: OR conditions — may prevent index use
SELECT * FROM users WHERE city = 'Bangalore' OR city = 'Mumbai';
-- May or may not use index. Better: WHERE city IN ('Bangalore', 'Mumbai')

-- GOTCHA 4: Composite index leftmost prefix rule
CREATE INDEX idx_abc ON t(a, b, c);
-- Works: WHERE a=1       (prefix a)
-- Works: WHERE a=1 AND b=2    (prefix a,b)
-- Works: WHERE a=1 AND b=2 AND c=3
-- FAILS: WHERE b=2       (skips a — not leftmost prefix)
-- FAILS: WHERE c=3       (skips a and b)
Interview Q&A — Indexing
Your query on a 10M row table is slow. How do you debug and fix it? ▼
Strong answerStep 1: Run EXPLAIN ANALYZE on the slow query — look for "Seq Scan" (full table scan, bad) vs "Index Scan" (uses index, good). Also look at the "actual time" and "rows" fields — where is most time being spent? Step 2: Check the WHERE clause — which column is the filter? Does an index exist on it? If not, CREATE INDEX. If yes, is it being used? Step 3: Check for index gotchas — LIKE with leading wildcard, function on the column, wrong column order in composite index. Step 4: Check cardinality — is the indexed column very low cardinality? (e.g., is_deleted = true/false — an index here is nearly useless, DB might prefer a seq scan anyway). Step 5: Consider composite index — if you always filter by user_id + created_at together, a composite index (user_id, created_at) is better than two separate indexes.
What is the difference between clustered and non-clustered index? ▼
Strong answerA clustered index physically sorts the data rows by the index key — the leaf nodes of the B-tree ARE the actual data rows. Only one allowed per table (data can only be sorted one way). In MySQL InnoDB, the primary key is always the clustered index. Fastest lookup — one step from index to data. A non-clustered index is a separate B-tree structure where leaf nodes contain the index key value plus a pointer back to the actual row. Multiple allowed per table. Lookup requires two steps: index → pointer → row data (unless covering index is used). Dictionary analogy: clustered = dictionary (words physically sorted alphabetically, book IS the index). Non-clustered = book's back-of-book index (separate list pointing to page numbers).

Indexing — 60-second revision

  • Without index: O(n) full scan. With index: O(log n) B-tree lookup. 10M rows = 23 comparisons.
  • Clustered: rows physically sorted by key. One per table. Fastest. MySQL InnoDB PK is clustered.
  • Non-clustered: separate B-tree with row pointers. Multiple per table. Two lookups needed.
  • Write penalty: every INSERT/UPDATE/DELETE must update all indexes on the table. Over-indexing hurts writes.
  • Add index on: WHERE columns, JOIN columns, ORDER BY columns, high-cardinality columns, FK columns.
  • Don't index: small tables, low-cardinality columns (boolean), frequently updated columns.
  • Composite index: leftmost prefix rule. (a,b,c) index helps WHERE a, WHERE a+b, WHERE a+b+c. Not WHERE b or WHERE c alone.
  • Indexes not used: LIKE '%text' (leading wildcard), LOWER(email)=... (function on column).

What is eventual consistency? When is it acceptable? ▼

CAP Theorem

Distributed systems can only guarantee 2 of 3: Consistency, Availability, Partition Tolerance. Network partitions always happen — so you really choose between C and A. Know where MongoDB, Cassandra, and PostgreSQL fall.
high valueAsked when discussing distributed systems and system design
01The three properties
PropertyWhat it meansReal scenario
C — Consistency Every read receives the most recent write (or an error). All nodes see the same data at the same time. After Ravi transfers ₹500, EVERY server in the cluster immediately shows the new balance. No stale reads possible.
A — Availability Every request receives a response (not necessarily the most recent data). The system never refuses to answer. Even during partial failures, the system responds — might return slightly stale data, but always responds.
P — Partition Tolerance The system continues operating even when some nodes can't communicate with others (network partition). The network cable between two data centers is cut. The system keeps working — doesn't go down.
02Why you MUST choose P — and then decide between C and A

Network partitions are an unavoidable reality in distributed systems. Network cables get cut, switches fail, AWS availability zones lose connectivity. You CANNOT say "I'll build a distributed system that never partitions" — it will happen. So Partition Tolerance is not a choice — it's a requirement.

Given that P is always chosen, the real choice is: when a network partition occurs, do you sacrifice Consistency (allow stale reads) or Availability (refuse requests until consistent)? 

  NETWORK PARTITION SCENARIO:
  Node A ←—✗—→ Node B   (network cut between them)

  A client writes to Node A: "balance = ₹500"
  Node A cannot replicate to Node B (partition!)

  Another client reads from Node B:
  
  CP system (Consistency + Partition Tolerance):
  → Node B refuses to answer (returns error)
  → "I can't guarantee I have the latest data. I won't serve stale data."
  → System is unavailable during partition
  → MongoDB (with majority write concern), HBase, Zookeeper

  AP system (Availability + Partition Tolerance):
  → Node B returns ₹1000 (old value, stale)
  → "I'll answer, but my data might be outdated."
  → System is available but inconsistent during partition
  → Cassandra, CouchDB, DynamoDB (by default)

  Traditional single-node SQL: CA (no partition tolerance)
  → Works perfectly when there's no distributed component
  → But you can't "distribute" an SQL DB without choosing C or A

The CAP theorem describes the theoretical limits — modern systems tune between them based on the importance of each operation.

Optimistic vs Pessimistic Locking

Two strategies for handling concurrent updates. Know when each applies. Spring Boot's @Version annotation implements optimistic locking automatically.
high valueConnects directly to your Spring Boot project
01Pessimistic Locking — assume conflict will happen

Pessimistic locking: lock the row as soon as you read it. Hold the lock until the transaction completes. No other transaction can read or write that row while you hold the lock.

Use when: contention is high — many concurrent transactions likely to modify the same data. Example: Zepto ordering the last item in stock. Multiple users simultaneously trying to buy it. Pessimistic locking prevents overselling. 

-- Pessimistic locking: SELECT FOR UPDATE
BEGIN;
SELECT * FROM products WHERE id = 42 FOR UPDATE;
-- ^ Acquires exclusive row lock. Other transactions trying SELECT FOR UPDATE on row 42 → BLOCK.

UPDATE products SET stock = stock - 1 WHERE id = 42;
COMMIT;  -- lock released here

-- Trade-off: high contention → many transactions waiting → throughput limited
-- Risk: if transaction takes long → deadlock possible
02Optimistic Locking — assume conflict is rare

Optimistic locking: no lock on read. Instead, add a version column. When you read a row, note the version. When you write, check that the version hasn't changed. If it has (someone else modified it) — conflict! Retry.

Use when: contention is low — conflicts are rare, most updates succeed without conflict. Example: user profile update. Very unlikely two users update the same profile simultaneously. 

-- Optimistic locking: version column
-- Schema: products table has a 'version' column

-- Step 1: Read, note the version
SELECT id, price, stock, version FROM products WHERE id = 42;
-- Returns: id=42, price=999, stock=5, version=3

-- Step 2: Update with version check
UPDATE products
SET stock = 4, version = version + 1
WHERE id = 42 AND version = 3;  -- ← condition on version

-- Check rows affected:
-- rows_affected = 1 → SUCCESS: version was still 3, nobody else modified it
-- rows_affected = 0 → CONFLICT: version changed (someone else updated first) → RETRY

-- Spring Boot JPA — @Version annotation handles this automatically
// @Entity
// public class Product {
//     @Id private Long id;
//     private int stock;
//     @Version  ← Spring JPA manages version automatically
//     private int version;
// }
// JPA automatically adds AND version=? to UPDATE queries
// Throws OptimisticLockException if conflict detected

Interview Q&A — Locking
When would you use optimistic vs pessimistic locking? ▼
Strong answerPessimistic locking: when conflicts are frequent and the cost of a conflict is high — like deducting inventory for Zepto's last item, or a bank transfer. SELECT FOR UPDATE ensures only one transaction processes the item at a time. Prevents overselling but reduces throughput (others wait). Optimistic locking: when conflicts are rare — like a user updating their profile settings. No lock on read means high throughput. The @Version check on write catches the occasional conflict, and the retry is usually fast. In Spring Boot: add @Version field to the entity. JPA automatically appends AND version=? to UPDATEs and throws OptimisticLockException if another transaction modified the row. Application code catches this and retries the operation. Trade-off: optimistic locking with high conflict rates causes retry storms — if conflicts are actually frequent, pessimistic is better despite lower throughput.

Locking — 60-second revision

  • Pessimistic: lock on read (SELECT FOR UPDATE). Hold till commit. Blocks others. High contention scenarios.
  • Optimistic: no lock on read. version column check on write. Retry on conflict. Low contention scenarios.
  • Spring Boot: @Version → JPA handles optimistic locking. @Lock(PESSIMISTIC_WRITE) → pessimistic.
  • Optimistic advantage: high read throughput — no blocking. Disadvantage: retry cost if conflicts are frequent.
  • Pessimistic advantage: guaranteed consistency, no retries. Disadvantage: deadlock risk, lower throughput.
Master Review

All DBMS Interview Questions

20 questions across all DBMS topics. Answer out loud without looking. If you stumble — re-study that concept section.
Complete DBMS Q&A bank — 20 questions
1. What is the difference between primary key and unique key? ▼
AnswerBoth enforce uniqueness. Differences: (1) One PK per table, multiple UNIQUE keys allowed. (2) PK cannot be NULL, UNIQUE key can have one NULL (since NULL ≠ NULL in SQL). (3) PK is the main identifier, referenced by foreign keys. UNIQUE ensures no duplicates on alternate columns (e.g., email, phone alongside the PK id).
2. Why use surrogate keys instead of natural keys? ▼
AnswerNatural keys (email, phone) can change — updating would require changing every FK reference in every related table. Integer surrogate key is stable, never changes. Also: integer JOINs are faster than string JOINs. Surrogate keys are smaller (4-8 bytes vs 100+ bytes for email). Privacy: exposing a surrogate ID in URLs is safe; exposing email in URLs is not.
3. Explain the three normal forms and the problems they solve. ▼
Answer1NF: atomic values — no arrays or lists in a column. Eliminates repeating groups. PK must uniquely identify each row. 2NF: 1NF + no partial dependency. In composite PK tables, every non-key column must depend on the WHOLE PK, not just part. Eliminates redundancy from columns depending on partial PK. 3NF: 2NF + no transitive dependency. Non-key columns must depend only on the PK, not on other non-key columns (A→B→C, fix by separating B and C). Each normal form eliminates a class of anomaly: update anomalies, insert anomalies, delete anomalies.
4. What is a transitive dependency? Give an example. ▼
AnswerA transitive dependency occurs when a non-key column depends on another non-key column rather than directly on the primary key. Example: Orders(OrderID, CustomerID, CustomerCity). CustomerCity → CustomerID → OrderID. CustomerCity depends on CustomerID (non-key), which depends on OrderID (PK). This is transitive: OrderID → CustomerID → CustomerCity. Fix: move Customer info to a separate Customers table. CustomerCity then depends directly on CustomerID (its own PK). 3NF eliminates transitive dependencies.
5. Explain ACID with a PhonePe payment example. ▼
AnswerAtomicity: debit Ravi + credit Priya — both or neither. Server crash after debit → UNDO log rolls back debit. Consistency: balance ≥ 0 constraint never violated, total money conserved. Isolation: concurrent transfers don't see each other's uncommitted changes — T2 doesn't see T1's intermediate debit. Implemented via MVCC or locking. Durability: once COMMIT returns success, data is on disk permanently via WAL. Even if server dies 1ms after commit, data survives.
6. What is a dirty read? A non-repeatable read? A phantom read? ▼
AnswerDirty read: T1 reads T2's uncommitted change. T2 rolls back → T1 read data that never existed. Non-repeatable read: T1 reads a row, T2 updates+commits it, T1 reads again — different value. Same query, different result. Phantom read: T1 queries a set of rows (WHERE price > 100), T2 inserts a new row matching the condition and commits, T1 re-queries — new row appears. Prevented by: Read Committed (dirty reads). Repeatable Read (+ non-repeatable). Serializable (+ phantoms).
7. What is the default isolation level in PostgreSQL? MySQL? ▼
AnswerPostgreSQL default: READ COMMITTED — no dirty reads, but non-repeatable and phantom reads possible. MySQL InnoDB default: REPEATABLE READ — no dirty or non-repeatable reads. MySQL InnoDB also prevents phantom reads via gap locks (technically stronger than the SQL standard's Repeatable Read). Serializable is the strongest level — prevents all anomalies but has the highest locking overhead. Most applications run fine with Read Committed or Repeatable Read.
8. What is database indexing? What data structure is used? ▼
AnswerIndexes allow O(log n) row lookup instead of O(n) full table scan. The data structure is a B-Tree (Balanced Tree). Leaf nodes contain the indexed column value and a pointer to the actual row (or for clustered indexes, the row itself). B-Tree properties: balanced (all leaf nodes at same depth), supports range queries (scan leaf nodes sequentially for BETWEEN, >, <). For 10M rows: full scan = 10M comparisons, B-tree = ~23 comparisons. Other index types: Hash (O(1) equality, no range queries), GiST/GIN (full-text search, PostGIS geometry).
9. What is the write penalty of indexes? ▼
AnswerEvery INSERT, UPDATE, or DELETE must update every index on the table. If a table has 10 indexes, every write operation updates 10 B-Trees — 10x write overhead. This is why over-indexing hurts write-heavy tables. Balance: index columns that are frequently queried (WHERE, JOIN, ORDER BY). Don't index: columns rarely used in queries, low-cardinality columns (boolean — index rarely helps), frequently updated columns (update overhead), small tables (full scan cheaper than index overhead + maintenance).
10. What is the composite index leftmost prefix rule? ▼
AnswerFor a composite index on (a, b, c): the index can be used for queries that filter on the leftmost columns in order. Helps: WHERE a=1 (prefix a), WHERE a=1 AND b=2 (prefix a,b), WHERE a=1 AND b=2 AND c=3. Does NOT help: WHERE b=2 (skips a), WHERE c=3 (skips a and b). Why: B-tree is sorted by (a, then b within same a, then c within same a+b). Skipping a means you can't use the sorted structure. Therefore, design composite indexes with the most selective or most commonly filtered column first.
11. What is the difference between clustered and non-clustered index? ▼
AnswerClustered: rows physically sorted by index key. Leaf nodes ARE the data rows. One per table. Fastest lookup — one step. MySQL InnoDB PK is always clustered. Non-clustered: separate B-tree, leaf nodes contain index key + row pointer. Multiple per table. Requires two lookups: index → row pointer → actual data. Dictionary analogy: clustered = words sorted alphabetically in the dictionary itself. Non-clustered = index at the back of a book (alphabetical list pointing to page numbers). PostgreSQL doesn't maintain clustered indexes automatically; it has CLUSTER command but is one-time.
12. When would you use MongoDB over PostgreSQL? ▼
AnswerMongoDB fits when: (1) Schema is flexible or frequently changing — product catalog where different products have different attributes. (2) Data is naturally hierarchical/nested — user profiles with embedded address, preferences, etc. (3) You're storing documents as-is (JSON from external API). (4) Schema evolution is frequent (startup phase, rapid iteration). PostgreSQL fits when: (1) ACID transactions required (financial, orders). (2) Complex queries with multiple JOINs. (3) Schema is stable and well-defined. (4) Data integrity constraints are important. Real answer: use both. Swiggy uses PostgreSQL for orders/payments, MongoDB for restaurant menus/content.
13. Explain the CAP theorem. Where does Cassandra fall? ▼
AnswerCAP: distributed system guarantees only 2 of 3. Consistency (all nodes see same data), Availability (always responds), Partition Tolerance (works despite network failures). Since partitions always happen, P is required — real choice is C or A during partition. Cassandra is AP: during a network partition, Cassandra will serve potentially stale data rather than refuse to respond. This makes sense for its use cases (activity logs, IoT data, social feeds) where slight staleness is acceptable but downtime is not. MongoDB is CP: during partition, MongoDB refuses reads that might be stale, preferring consistency — appropriate for data where accuracy matters more than availability.
14. What is optimistic locking? How does @Version work in Spring Boot? ▼
AnswerOptimistic locking assumes conflicts are rare — no lock on read. Instead, a version column is checked on write. Read a row (version=3), compute update, then: UPDATE ... WHERE id=42 AND version=3 SET version=4. If rows_affected=1: success. If rows_affected=0: another transaction modified the row first — throw exception, let application retry. Spring Boot: add @Version annotation to an entity field. JPA automatically appends AND version=? to all UPDATE SQL, increments the version in the SET clause, and throws OptimisticLockException if rows_affected=0. Perfect for low-contention scenarios like user profile updates.
15. What is MVCC? How does it improve concurrency? ▼
AnswerMVCC (Multi-Version Concurrency Control): the DB maintains multiple versions of each row, each with a timestamp or transaction ID. When a transaction reads, it sees the version of the data as of when its transaction started. Writers create new versions rather than overwriting. Readers never block writers; writers never block readers. This dramatically improves read concurrency vs traditional locking where readers and writers block each other. Used by: PostgreSQL (all versions), MySQL InnoDB (all versions), Oracle. Downside: requires periodic cleanup of old versions. PostgreSQL's VACUUM process removes dead row versions. Under heavy write load, VACUUM can't keep up → table bloat.
16. What is referential integrity? What does ON DELETE CASCADE do? ▼
AnswerReferential integrity ensures no orphan records — every FK value must reference an existing PK. If orders.user_id = 5 must exist in users.id = 5. ON DELETE CASCADE: when a user is deleted, all their orders are automatically deleted too. ON DELETE SET NULL: when user deleted, orders.user_id becomes NULL (order exists without a user). ON DELETE RESTRICT (default): prevents deleting a user if they have any orders — foreign key constraint violation. Choose based on business logic: CASCADE for dependent child records (user's sessions, logs). SET NULL when the reference is optional. RESTRICT when deletion shouldn't happen if children exist (protecting data integrity).
17. What is denormalization? When would you use it? ▼
AnswerDenormalization intentionally introduces redundancy to improve read performance. Instead of joining 5 tables for every analytics query, pre-compute and store the joined result. Example: instead of JOINing orders + order_items + restaurants to compute daily revenue, store daily_restaurant_revenue(date, restaurant_id, revenue) — updated by application on each order. Reads are instant, but writes must maintain the denormalized table. Use in OLAP/analytics systems where reads far outnumber writes and slight inconsistency windows are acceptable. Data warehouses (star schema, fact tables) are fully denormalized by design. OLTP systems (transactions) stay normalized for integrity.
18. What is a covering index? How does it help performance? ▼
AnswerA covering index is an index that contains all the columns a query needs — the DB can answer the query entirely from the index without accessing the actual table rows. Example: query SELECT email, name FROM users WHERE email = 'x'. If you create INDEX ON users(email, name), the index contains both email (for lookup) and name (for the SELECT). The DB never touches the users table — everything it needs is in the index. This eliminates the "key lookup" step (index → table) of non-clustered indexes, making the query much faster. Create covering indexes for your most performance-critical queries. Trade-off: larger indexes take more disk space and have higher write overhead.
19. What is the difference between WHERE and HAVING in SQL? ▼
AnswerWHERE filters rows BEFORE aggregation. HAVING filters groups AFTER aggregation. WHERE: operates on individual rows, cannot use aggregate functions (COUNT, SUM, AVG). HAVING: operates on grouped results, CAN use aggregate functions. Example: SELECT dept_id, COUNT(*) FROM employees WHERE salary > 30000 GROUP BY dept_id HAVING COUNT(*) > 5 — WHERE filters individual employees with salary > 30000 BEFORE grouping. HAVING then filters departments that have more than 5 such employees AFTER grouping. Trying WHERE COUNT(*) > 5 is a SQL error — aggregate in WHERE is invalid. Performance: WHERE reduces rows before grouping, so it's processed first and can use indexes. HAVING processes after the GROUP BY, on fewer rows.
20. What is a database transaction? How does ROLLBACK work? ▼
AnswerA transaction is a unit of work that executes atomically — all or nothing. Begin with BEGIN/START TRANSACTION. Execute SQL statements. End with COMMIT (make permanent) or ROLLBACK (undo all changes). ROLLBACK works via the UNDO log: before making any change to actual data, the DB writes what the old value was to the UNDO log. If ROLLBACK is called (or crash occurs before COMMIT), the DB reads the UNDO log and applies all the old values — reverting every change made in the transaction. SAVEPOINT allows partial rollback: ROLLBACK TO SAVEPOINT name undoes only changes after the savepoint, not the entire transaction. This is how nested transactions work in some databases.
