Concept 01 of 07

Process vs Thread

The most foundational OS concept. Everything else builds on understanding what a process is, what a thread is, and why the distinction matters for full stack work.
must knowConnects to Node.js, Spring Boot, every web server
01What is a Process?

A process is an independent running program. When you open Chrome, the OS creates a process for it. That process has its own isolated chunk of memory — no other program can read or write to it directly.

Every process gets its own: code segment (program instructions), data segment (global variables), heap (dynamic allocations), stack (function calls, local variables), and a PCB (Process Control Block — OS's metadata about this process: PID, state, register values, open files). 

  ┌──────────────────────────────────────────┐
  │              PROCESS MEMORY              │
  ├──────────────────────────────────────────┤
  │  Code (Text)  — program instructions     │  ← read-only
  ├──────────────────────────────────────────┤
  │  Data         — global + static vars      │
  ├──────────────────────────────────────────┤
  │  Heap  ↑ grows up                         │  ← new/malloc
  │         (dynamic allocation)             │
  │                                          │
  │  Stack ↓ grows down                        │  ← function calls
  │         (local vars, return addresses)   │
  └──────────────────────────────────────────┘

  Each process has its OWN copy of all of this.
  Process A CANNOT read process B's memory (isolation guarantee).
02What is a Thread?

A thread is a unit of execution within a process. A process can have many threads. They all share the same code, data, and heap — but each thread gets its own stack and registers.

Creating a thread is much cheaper than creating a process: no need to allocate separate memory space, no need to copy the program — just create a new stack and register set. Communication between threads is easy — they just read/write the shared heap. But this shared access creates the risk of race conditions. 

  ┌─────────────────────────────────────────────────────┐
  │                    ONE PROCESS                      │
  ├─────────────────────────────────────────────────────┤
  │  Code  │  Data  │         Heap                     │
  │       (shared by ALL threads in this process)      │
  ├─────────────────────────────────────────────────────┤
  │  Thread 1 Stack  │  Thread 2 Stack  │  Thread 3 Stack  │
  │  Thread 1 Regs  │  Thread 2 Regs  │  Thread 3 Regs  │
  │      (each thread has its own stack + registers)   │
  └─────────────────────────────────────────────────────┘

04Real-world examples you must know

Chrome browser: Each tab runs in a separate process. Why? If one tab crashes (e.g., bad JS), the other tabs survive. This is process isolation in action. Within each tab process, multiple threads handle: JavaScript execution (main thread), network requests, rendering, etc.

Node.js: Single process, single main thread (the event loop). No multi-threading by default. But Node uses libuv's thread pool (4 threads) for I/O operations internally. worker_threads module allows explicit multi-threading when needed.

Spring Boot / Java web server: By default (Tomcat), each HTTP request is handled by a thread from a thread pool. Threads share the application's heap (Spring beans, connection pools). This is why thread safety matters in Java web apps.

Node.js interview question connection: "Node.js is single-threaded. How does it handle concurrent requests?" — The answer is in the next section (Event Loop). For now: each request doesn't get its own thread. Node processes requests one at a time, but non-blocking I/O means the thread never waits — it registers callbacks and moves on.

Interview Q&A — Process vs Thread
What is the difference between a process and a thread? When would you use each? ▼
Strong answer A process is an independent execution unit with its own isolated memory space. A thread is a lightweight execution unit within a process that shares the heap and data segment but has its own stack. Use processes when isolation matters — browser tabs (one crash doesn't kill others), microservices (each service is a separate process). Use threads when you need shared state with low overhead — a Java web server where multiple request-handling threads share the same database connection pool and application objects. Threads are cheaper to create and switch between, but shared memory creates race condition risks. Follow-up: "What is a PCB?" Process Control Block — the OS's data structure for a process. Contains: PID, process state, program counter, CPU registers, memory map, list of open files, and scheduling info. When the OS context-switches to another process, it saves all this state so it can resume later.
What is context switching? Why is it expensive? ▼
Strong answer Context switching is when the OS pauses one running process/thread and starts another. The steps: save the current process's CPU registers and program counter into its PCB → update its state to READY → select next process → load that process's registers and program counter → update its state to RUNNING. It's expensive because: (1) saving and restoring registers takes time, (2) CPU caches (TLB, instruction cache) are invalidated — the new process's memory map is different, so cached memory lookups become misses. Too many threads = too many context switches = performance degradation. This is why Node.js's single-threaded model is efficient for I/O-bound work — no context switch overhead.
How does Chrome use processes? Why not threads? ▼
Strong answer Chrome runs each tab as a separate process (the "process-per-site" model). This gives complete isolation — if one tab runs malicious JavaScript that crashes, it only kills that tab's process. Other tabs' processes are unaffected. Security: processes can't access each other's memory, so a compromised tab can't steal data from another tab's memory. The cost: processes are heavier than threads (more memory, slower creation). Chrome accepts this cost for security and stability. Within each tab process, multiple threads handle different tasks: the main thread runs JavaScript, a separate thread handles network requests, the compositor thread handles rendering. Multi-process architecture is the foundation of microservices too — same isolation principle at a different scale.

Process vs Thread — 60-second revision

  • Process: own memory space (code, data, heap, stack). Isolated. Expensive. Crash doesn't affect others.
  • Thread: shares process heap + data. Own stack + registers only. Cheap. Shared memory = race conditions.
  • Context switch: save registers → load next process's registers. Expensive — cache invalidation.
  • Chrome: each tab = process (isolation + security). Within tab: multiple threads.
  • Node.js: single process, single main thread. libuv thread pool for I/O behind the scenes.
  • Java web server: thread pool — each request handled by a thread that shares the app's objects.
  • PCB: OS metadata per process — state, registers, memory map, open files.
Concept 02 of 07

Concurrency vs Parallelism

The most misunderstood pair in OS. Concurrency is NOT parallelism. Node.js is concurrent but not parallel. This concept directly answers the #1 Node.js interview question.
must knowThe Node.js question is asked everywhere
01Concurrency — the illusion of simultaneity

Concurrency means multiple tasks are making progress at the same time — but they may not literally run at the exact same instant. On a single CPU, the OS rapidly switches between tasks, giving each a small slice of time. This time-slicing creates the illusion that everything runs simultaneously.

Think of a chef cooking multiple dishes. They stir the soup, then check the oven, then chop vegetables, then stir again. Only one action at a time, but all dishes are progressing. That's concurrency.

02Parallelism — truly simultaneous

Parallelism means tasks literally run at the exact same instant on multiple CPU cores. Two threads on two different cores executing simultaneously — real parallelism.

Two chefs cooking two different dishes simultaneously in two kitchens. That's parallelism. 

  CONCURRENCY (single CPU, time-slicing):
  Time →  |--A--|--B--|--A--|--C--|--A--|--B--|
  CPU 1:  Task A  Task B  Task A  Task C  ...
  → Only one task runs at a time, but all make progress

  PARALLELISM (multiple CPUs):
  Time →  |--A--|--A--|--A--|
  CPU 1:  Task A (running)
  CPU 2:  Task B (running simultaneously)
  CPU 3:  Task C (running simultaneously)
  → Truly simultaneous execution
03Node.js — concurrent but not parallel (by default)

Node.js has a single JavaScript thread — the event loop. It cannot run two JS functions simultaneously. But it achieves high concurrency through non-blocking I/O: instead of waiting for a database query or file read (which would block the thread), Node registers a callback and immediately moves on to the next task. When the I/O completes, libuv queues the callback for execution. 

  Node.js event loop handling 3 concurrent requests:

  Request 1 arrives → start DB query (async) → move on immediately
  Request 2 arrives → start file read (async) → move on immediately
  Request 3 arrives → start API call (async) → move on immediately

  [libuv thread pool executes I/O in background]

  DB query done     → callback queued → event loop picks it up → send response 1
  File read done    → callback queued → event loop picks it up → send response 2
  API call done     → callback queued → event loop picks it up → send response 3

  The single thread is NEVER idle. It processes one callback at a time.
  This is concurrency without parallelism.
04When Node.js breaks — CPU-heavy work

Node's single-threaded model works only because I/O is non-blocking. CPU-heavy tasks (image processing, video encoding, complex encryption, sorting huge arrays) block the event loop — the single thread is busy doing computation, and no other requests can be handled. 

// BLOCKS the event loop — BAD for production Node
app.get('/resize', (req, res) => {
    const result = heavyImageProcessing(req.body.image);  // CPU intensive
    // While this runs: ALL other requests wait. Event loop is blocked.
    res.json(result);
});

// FIX 1: worker_threads (Node.js multi-threading)
const { Worker } = require('worker_threads');
app.get('/resize', (req, res) => {
    const worker = new Worker('./imageWorker.js', { workerData: req.body.image });
    worker.on('message', result => res.json(result));
    // Main event loop free to handle other requests while worker runs on separate thread
});

// FIX 2: separate microservice for CPU-heavy work
// Python/Go service handles image processing, Node just proxies to it
Interview gotcha: "Node.js is single-threaded so it can't handle concurrency." — WRONG. Node.js is single-threaded for JavaScript execution but achieves concurrency through non-blocking I/O and the event loop. It can handle thousands of concurrent I/O-bound requests efficiently. It's CPU-bound work that's problematic.
Interview Q&A — Concurrency vs Parallelism
Node.js is single-threaded. How does it handle thousands of concurrent requests? ▼
Strong answer — the most asked Node.js OS question Node.js uses a non-blocking I/O model with an event loop. When a request needs I/O (database query, file read, HTTP call to another service), instead of blocking the single thread and waiting, Node registers a callback with libuv and immediately moves to the next request. The actual I/O is handed to libuv's internal thread pool (4 threads by default). When the I/O completes, libuv queues the callback in the event loop. The main thread processes callbacks one at a time — it's never sitting idle. This is concurrency (not parallelism) — multiple tasks making progress via time-slicing and async I/O. It's extremely efficient for I/O-bound workloads. The problem: CPU-heavy work blocks the event loop — fix with worker_threads or a separate service. Follow-up: "Can you make Node.js parallel?" Yes: worker_threads module creates actual OS threads for CPU-heavy work. cluster module forks the Node process across CPU cores — each core runs an independent Node process, a load balancer distributes requests. Both approaches add real parallelism.
What is the difference between concurrency and parallelism? ▼
Strong answer Concurrency: multiple tasks are in progress at the same time but may not be executing simultaneously. They interleave on a single CPU via time-slicing — the OS gives each task a time quantum, rapidly switching between them. Creates the illusion of simultaneous progress. Parallelism: tasks literally execute at the exact same time on multiple CPU cores. Real simultaneity, not interleaving. Node.js is concurrent (single thread, event loop) but not parallel by default. Java can be both — a thread pool with 8 threads on an 8-core machine achieves true parallelism. You can have concurrency without parallelism (Node.js), but parallelism always implies some form of concurrency management.
What happens if you run a heavy synchronous loop in a Node.js request handler? ▼
Strong answer The event loop is blocked. While the loop runs, no other request callbacks can execute — all incoming requests pile up in the queue. Node.js cannot respond to anything until the synchronous computation finishes. This is a production incident — users see timeouts. Fix options: (1) worker_threads — offload CPU work to a separate thread; (2) setImmediate() or process.nextTick() to break up work into chunks and yield to the event loop periodically; (3) move CPU-intensive work to a separate service (Python, Go, Rust) and have Node proxy to it. This is why Node.js shines for I/O-heavy APIs and websocket servers, but is a poor choice for image processing or ML inference servers.

Concurrency vs Parallelism — 60-second revision

  • Concurrency: multiple tasks make progress by time-slicing on 1 CPU. Illusion of simultaneity.
  • Parallelism: multiple tasks execute literally simultaneously on multiple CPU cores.
  • Node.js: concurrent (not parallel by default). Single thread + event loop + non-blocking I/O.
  • Node event loop: register I/O callback → move on → libuv handles I/O → callback queued → event loop picks it up.
  • Node breaks on: CPU-heavy work (blocks event loop). Fix: worker_threads or separate service.
  • Java web server: parallel — thread pool on multiple cores. Each request handled by a thread.
Concept 03 of 07

CPU Scheduling

When multiple processes are ready to run, how does the OS decide who goes next? Know the trade-offs — not the calculations.
high valueTrade-offs matter more than Gantt charts
01Why scheduling matters

At any moment, many processes are in the READY state (waiting for CPU). The scheduler picks which one runs next. The goal: maximize CPU utilization, minimize waiting time, ensure fairness, and meet response time requirements. Different algorithms make different trade-offs.

Two types: Preemptive (OS can interrupt a running process and give CPU to another) vs Non-preemptive (process runs until it voluntarily gives up CPU or blocks). Modern OS schedulers are preemptive.

AlgorithmHow it worksProblemReal use
FCFS
(First Come First Served)		 Run in arrival order. Non-preemptive. Convoy effect: one long process blocks all short ones behind it. Simple batch systems. Never in interactive OS.
SJF
(Shortest Job First)		 Run shortest estimated job next. Minimizes average wait time. Starvation: long jobs may never run if short jobs keep arriving. Requires knowing burst time in advance. Batch systems where job length is known. Approximated in modern schedulers.
Round Robin Each process gets a time quantum (e.g., 10ms). After quantum expires, preempt and go to end of queue. Too small quantum = too many context switches. Too large = behaves like FCFS. Most real interactive OS. Fair. Good response time.
Priority Scheduling Highest priority runs first. Can be preemptive or not. Starvation: low priority processes may never run. Real-time systems. OS kernel processes. Fixed with aging (priority increases over time).
Multilevel Feedback Queue Multiple queues with different priorities and time quantums. Processes move between queues based on behavior. Complex to configure. Linux (CFS - Completely Fair Scheduler). macOS. Modern OS.
Round Robin analogy: A restaurant where each table gets 10 minutes of waiter attention in rotation. No table starves. If your order isn't taken in 10 minutes, waiter moves to next table and comes back. Fair and responsive.
Starvation vs Deadlock: Starvation = process keeps getting delayed indefinitely (still able to run, just never selected). Deadlock = process is permanently blocked waiting for a resource that will never come. Starvation fix: aging (increase priority over time). Deadlock fix: breaking one of the Coffman conditions.
Interview Q&A — Scheduling
What is the convoy effect in FCFS scheduling? ▼
Strong answer The convoy effect occurs when one long CPU-bound process holds up many shorter processes. Example: process A needs 200ms of CPU time. Processes B, C, D each need 2ms but arrive just after A. Under FCFS (non-preemptive), B, C, D wait 200ms before they can run, even though they could each complete in 2ms. The long process creates a "convoy" of waiting processes. Average waiting time is terrible. Round Robin solves this by preempting A after each time quantum and giving B, C, D a chance to run, dramatically reducing average wait time.
What is starvation? How does aging fix it? ▼
Strong answer Starvation occurs when a process is perpetually denied CPU time because higher-priority processes always arrive and preempt it. In priority scheduling, if high-priority processes keep arriving, a low-priority process may wait indefinitely — never starving technically (it's not blocked forever) but practically never running. Aging is the fix: the longer a process waits in the ready queue, the higher its priority becomes. Eventually its priority rises high enough that it gets CPU time. Most production OS schedulers (like Linux's CFS) use aging or similar mechanisms to ensure fairness and prevent starvation.

CPU Scheduling — 60-second revision

  • Preemptive: OS can interrupt. Non-preemptive: process runs till done or blocks.
  • FCFS: arrival order. Problem: convoy effect (long process blocks short ones).
  • SJF: shortest job first. Optimal average wait. Problem: starvation of long jobs.
  • Round Robin: time quantum per process. Fair. Good response time. Most real OS use this basis.
  • Priority: highest priority first. Problem: starvation. Fix: aging (priority increases over wait time).
  • Starvation: process never selected. Deadlock: process permanently blocked. Different problems.
Concept 04 of 07

Race Conditions, Mutex & Semaphore

When threads share memory, they can corrupt each other's data. Synchronization primitives prevent this. Mutex and semaphore are different — most freshers confuse them.
must knowMutex vs Semaphore is asked constantly
01Race Condition — what it is and why it happens

A race condition occurs when the outcome of a program depends on the unpredictable timing/ordering of thread execution. Two threads read-modify-write the same variable without coordination → wrong result.

The key insight: even simple operations like count++ are not atomic. They compile to three separate CPU instructions: READ the value, ADD 1, WRITE back. If two threads execute these three steps concurrently, they can interleave in ways that produce wrong results. 

  Initial value: count = 5

  Thread A               Thread B
  READ count = 5
                         READ count = 5    ← Both read 5 before either writes!
  ADD 1 → 6
  WRITE count = 6
                         ADD 1 → 6
                         WRITE count = 6   ← Overwrites A's result

  Final: count = 6  (Expected: count = 7)  ← RACE CONDITION
    
// Java — demonstrating race condition
class Counter {
    int count = 0;
    void increment() { count++; }  // NOT atomic — 3 CPU instructions
}

// Two threads each call increment() 1000 times
// Expected: count = 2000
// Actual: count = 1734 (random, depends on thread interleaving)

// FIX 1: synchronized — turns increment() into a critical section
synchronized void increment() { count++; }
// Only ONE thread can execute synchronized method at a time
// Other threads wait (blocked) at the method's lock

// FIX 2: AtomicInteger — lock-free, uses CPU-level compare-and-swap
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();  // truly atomic at hardware level
02Critical Section

A critical section is a piece of code that accesses shared resources (variables, files, data structures) and must not be executed by more than one thread at the same time. The goal of synchronization is to protect critical sections.

Requirements for a correct solution: Mutual Exclusion (only one thread in the critical section at a time), Progress (if no one is in the critical section, a waiting thread should eventually enter), Bounded Waiting (a thread should not wait forever to enter the critical section).

03Mutex — binary lock with ownership

A mutex (mutual exclusion lock) is a binary lock — it's either locked or unlocked. The key property: only the thread that locked it can unlock it. This is ownership.

When a thread tries to lock a mutex that's already locked, it blocks — it goes to WAITING state until the mutex is unlocked. Then it wakes up and acquires the lock. 

// Java — mutex via synchronized block (implicit mutex)
class SafeCounter {
    private final Object lock = new Object();  // the mutex object
    private int count = 0;

    void increment() {
        synchronized(lock) {     // acquire mutex — blocks if another thread holds it
            count++;              // critical section — only 1 thread here at a time
        }                         // release mutex automatically when block exits
    }
}

// Explicit mutex via ReentrantLock
ReentrantLock mutex = new ReentrantLock();
mutex.lock();                // acquire lock (blocks if held by another thread)
try {
    count++;                  // critical section
} finally {
    mutex.unlock();           // release lock — MUST be in finally to guarantee release
}
// Only the thread that called lock() can call unlock() — ownership
04Semaphore — counter, no ownership

A semaphore is a counter (not just binary). It can allow multiple threads to access a resource simultaneously, up to a defined limit. Two operations: wait() — decrement the counter, block if it reaches 0; signal() — increment the counter, wake a waiting thread.

Key difference from mutex: any thread can signal a semaphore, not just the one that waited. There's no ownership concept. 

  SEMAPHORE example: Database connection pool allows max 10 connections

  Initial semaphore count: 10

  Thread A: wait() → count = 9, gets a connection
  Thread B: wait() → count = 8, gets a connection
  Thread C: wait() → count = 7, gets a connection
  ... (10 threads each acquire a connection)

  Thread K (11th): wait() → count = 0, BLOCKS — waits for a connection to free up

  Thread A finishes: signal() → count = 1, Thread K unblocks, gets the connection

  BINARY SEMAPHORE (count starts at 1): similar to mutex, but WITHOUT ownership.
  Thread A can signal a semaphore that Thread B waited on — this is valid.
  Thread A cannot unlock a mutex that Thread B locked — this would be an error.

Analogy: Mutex = single-occupancy bathroom key. Only one person at a time. The person who took the key returns it. Semaphore = parking lot with 10 spaces. A counter shows available spaces. Any car can take a space (wait/decrement). Any car can free a space (signal/increment). You don't have to leave with your own ticket.
Is JavaScript affected by race conditions? — Mostly no for CPU operations, because JavaScript is single-threaded. Two JS functions cannot run simultaneously and corrupt shared variables. However, async operations can create logical race conditions. Example: two async functions both read a user's balance, both check if balance > 100, both decide to deduct — if the check and deduction aren't atomic at the DB level, you have a race condition. Fix: database transactions with proper isolation levels.
Interview Q&A — Synchronization
What is a race condition? Give a real example. ▼
Strong answer A race condition occurs when the program's output depends on the unpredictable timing of thread execution. Classic example: two threads both execute count++ (which is READ, ADD, WRITE — three non-atomic operations). If thread A reads count=5, thread B reads count=5 before A writes, they both compute 6 and write 6 — one increment is lost, count should be 7 but is 6. Real-world example: two users simultaneously clicking "book the last seat" in a ticketing system. Without proper locking, both read "1 seat available," both succeed, now you've sold the same seat twice. Fix: database-level locks or transactions with serializable isolation. Follow-up: "Is JavaScript safe from race conditions?" For CPU-level operations yes — single-threaded, no parallel modification of memory. But async operations (two requests to deduct money from same account) can cause logical race conditions. These must be prevented at the database level with transactions.
What is the difference between a mutex and a semaphore? ▼
Strong answer A mutex is a binary lock with ownership — only the thread that locked it can unlock it. Used for mutual exclusion: one thread in the critical section at a time. A semaphore is an integer counter with no ownership — any thread can signal (increment) it, even if a different thread waited (decremented) on it. Semaphores allow N threads to access a resource simultaneously, where N is the initial count. A binary semaphore (count=1) is similar to a mutex but without ownership, so it can be signaled by any thread — useful for signaling between threads. Use mutex for protecting a critical section. Use semaphore for managing a resource pool (e.g., limit simultaneous DB connections to 10).
What is a monitor? How does Java's synchronized keyword implement it? ▼
Strong answer A monitor is a high-level synchronization construct that combines a mutex with condition variables. Every Java object has an associated monitor (also called intrinsic lock). When you use synchronized(obj), the current thread acquires obj's monitor lock — only one thread can hold a specific object's monitor at a time. Other threads trying to synchronize on the same object block until the lock is released. wait() releases the lock and waits. notify()/notifyAll() signals waiting threads. Java's synchronized keyword is the most common way to use monitors — it handles lock acquisition and release automatically (even on exception, the lock is released when the block exits).

Synchronization — 60-second revision

  • Race condition: outcome depends on thread timing. count++ is not atomic (3 instructions).
  • Critical section: code that accesses shared resources. Only 1 thread at a time.
  • Mutex: binary lock. Only locker can unlock (ownership). Used for mutual exclusion.
  • Semaphore: integer counter. Any thread can signal (no ownership). Used for resource counting.
  • Binary semaphore vs mutex: similar but no ownership in semaphore. Any thread can signal.
  • Java synchronized: implicit monitor lock. Lock acquired on enter, released on exit (even on exception).
  • JS: single-threaded, no CPU race conditions. But async DB operations can have logical races — fix at DB level.
Concept 05 of 07

Deadlock

Four conditions. When all four hold simultaneously, you have deadlock. Break any one condition to prevent it. Real-world examples make this click.
must knowAsked at every product company interview
01What is deadlock?

A deadlock is a situation where two or more threads are each waiting for a resource held by another, and none can proceed. They're all permanently stuck. 

  Thread A                    Thread B
  ─────────────────────       ─────────────────────
  Holds: Lock 1               Holds: Lock 2
  Waiting for: Lock 2         Waiting for: Lock 1

  → Thread A can't proceed (needs Lock 2, B has it)
  → Thread B can't proceed (needs Lock 1, A has it)
  → Neither will ever release what the other needs
  → DEADLOCK — permanent standstill

  Real example: UPI transfer
  Transaction A: locks User X's account → wants User Y's account
  Transaction B: locks User Y's account → wants User X's account
  → Neither transaction can complete → deadlock
02The 4 Coffman Conditions — ALL must hold for deadlock

Deadlock can only occur if all four conditions hold simultaneously. Preventing any one condition prevents deadlock.

#ConditionWhat it meansHow to prevent
1 Mutual Exclusion At least one resource can only be held by one thread at a time (non-shareable) Make resources shareable where possible. Hard to eliminate — some resources genuinely can't be shared.
2 Hold and Wait A thread holds at least one resource while waiting for another Require a thread to request ALL resources it will ever need before starting. (Practical problem: you may not know what you'll need.)
3 No Preemption Resources can't be forcibly taken from a thread — it must release voluntarily Allow OS to preempt resources. If thread can't get a resource, release all it holds and retry.
4 Circular Wait A chain of threads where each waits for a resource held by the next — forming a cycle Most practical fix: impose a total ordering on resources. Always acquire in the same fixed order.
03Prevention — the practical approach

The most practical deadlock prevention strategy is eliminating Circular Wait by imposing a total ordering on resource acquisition. 

// DEADLOCK SCENARIO: Thread A and B acquire locks in different order
// Thread A: lock1 then lock2
// Thread B: lock2 then lock1  ← different order! → circular wait possible

// PREVENTION: Always acquire in the same fixed order (e.g., by lock ID)
// Thread A: lock1(id=1) then lock2(id=2)  ← always lower ID first
// Thread B: lock1(id=1) then lock2(id=2)  ← SAME order
// Thread B will wait for Thread A to release lock1, then acquire it
// No circular wait → no deadlock

// Java example: sort locks by System.identityHashCode before acquiring
void transfer(Account from, Account to, double amount) {
    Account first  = from.id < to.id ? from : to;    // lower ID first
    Account second = from.id < to.id ? to   : from;
    synchronized(first) {
        synchronized(second) {
            from.balance -= amount;
            to.balance   += amount;
        }
    }
}
// Both transfer(A→B) and transfer(B→A) will try to lock lower-ID account first
// No circular wait possible → safe
04Deadlock Detection & Recovery — how databases handle it

Sometimes prevention isn't practical (you don't know the order). Databases use detection and recovery:

  • Detection: The DB monitors a "wait-for" graph. If a cycle exists → deadlock detected.
  • Recovery: Kill one of the transactions (the victim), roll it back. The other transaction proceeds. The killed transaction is retried automatically.
  • Timeout: If a transaction can't acquire a lock within N seconds → assume deadlock → rollback → retry. Simpler than cycle detection.

This is why you sometimes see database errors like "Deadlock detected, transaction rolled back, please retry." The application should handle this by retrying the transaction.

Interview Q&A — Deadlock
What is a deadlock? What are the 4 necessary conditions? ▼
Strong answer Deadlock is when two or more threads are permanently stuck — each waiting for a resource held by another. All 4 Coffman conditions must hold: (1) Mutual Exclusion: at least one resource is non-shareable. (2) Hold and Wait: a thread holds resources while waiting for others. (3) No Preemption: resources can't be forcibly taken — thread must release voluntarily. (4) Circular Wait: a cycle of threads, each waiting for the next's resource. Break ANY one → deadlock impossible. Most practical: break Circular Wait by always acquiring multiple locks in the same fixed order (by resource ID or name).
Give a real deadlock example with a bank transfer and show how to prevent it. ▼
Strong answer PhonePe scenario: Transaction 1 transfers ₹500 from Account A to Account B. It locks Account A first, then needs Account B. Transaction 2 simultaneously transfers ₹200 from Account B to Account A. It locks Account B first, then needs Account A. T1 holds A, waiting for B. T2 holds B, waiting for A. Circular wait — deadlock. Prevention: always lock accounts in ascending order of their ID/account number, regardless of transaction direction. T1 and T2 both try to lock the lower-ID account first. One waits, the other completes and releases, then the waiting one proceeds. No circular wait. This is exactly what database engines implement at a lower level for row-level locking.
What is the difference between deadlock and starvation? ▼
Strong answer Deadlock: threads are permanently blocked — they literally cannot proceed because each holds something the other needs. No amount of waiting will resolve it. Requires external intervention (timeout, rollback, process kill). Starvation: a thread is perpetually denied a resource it needs, but there's no circular dependency — the resource is available, it just keeps getting given to higher-priority threads. Theoretically, if the high-priority threads stop arriving, the starved thread would proceed. Fix: aging (increase priority over wait time). Starvation is unfair scheduling; deadlock is a permanent circular block. Both result in a thread not progressing, but for different reasons with different solutions.

Deadlock — 60-second revision

  • Deadlock: threads permanently blocked, each waiting for resource held by another.
  • 4 Coffman conditions (all must hold): Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait.
  • Prevention: break any one condition. Most practical: break Circular Wait.
  • Fix Circular Wait: always acquire multiple locks in same fixed order (by ID/name).
  • Databases: detect via wait-for graph cycle detection OR timeout + rollback + retry.
  • Deadlock vs Starvation: deadlock = permanent circular block. Starvation = unfair scheduling, can resolve on its own.

02Garbage Collection — how JVM GC works

Garbage Collection automatically frees heap memory that's no longer reachable from the program. The JVM uses generational GC based on the observation: "most objects die young." 

  JVM HEAP STRUCTURE:
  ┌────────────────────────────────────────────────────────┐
  │                    YOUNG GENERATION                    │
  │  ┌─────────┐   ┌────────────┐   ┌───────────────────┐ │
  │  │  Eden   │   │ Survivor S0│   │   Survivor S1     │ │
  │  │(new obj)│   │            │   │                   │ │
  │  └─────────┘   └────────────┘   └───────────────────┘ │
  ├────────────────────────────────────────────────────────┤
  │                    OLD GENERATION                      │
  │         (objects that survived many GC cycles)         │
  └────────────────────────────────────────────────────────┘

  Flow:
  1. New objects → Eden
  2. Eden fills → MINOR GC (fast! most objects die here)
  3. Survivors → Survivor space (S0 or S1)
  4. After several minor GCs → promoted to Old Gen
  5. Old Gen fills → MAJOR GC (slow! stop-the-world)

  Why generational? ~90% of objects die in Young Gen → fast minor GC handles them.

Mark and Sweep: GC traverses all live objects starting from "GC roots" (static fields, local variables in stack frames, active threads) — marks them as live. Everything not marked is garbage. Sweep phase frees the unmarked memory.

04Virtual Memory — concept only

Virtual memory gives each process the illusion that it has a large, contiguous block of memory — much larger than actual physical RAM. The OS maps virtual addresses to physical RAM pages. If a page isn't in RAM, the OS fetches it from disk (a page fault).

Why it matters to you: When you run too many services on a small server, the OS starts swapping memory to disk. This causes frequent page faults, and performance degrades dramatically (disk is 1000x slower than RAM). This is why "swap memory" is a code smell — if your process regularly page-faults, you need more RAM.

Blocking vs Non-Blocking I/O & The Event Loop

The deepest dive into how Node.js actually works. The event loop, libuv, macrotask queue, microtask queue — understand this and you understand async JavaScript completely.
must knowDirectly explains your daily Node.js/React code
01Blocking I/O — the old way

In the traditional blocking I/O model (classic Java servlet, PHP, Python Flask by default): when a request arrives and needs to read from a database or file, the thread blocks — it sits idle, doing nothing, waiting for the I/O to complete. The CPU is wasted.

To handle N concurrent requests, you need N threads. With 1000 concurrent requests, you need 1000 threads. Creating and context-switching 1000 threads is expensive. Most threads spend most time blocked on I/O. 

  Blocking I/O (thread-per-request model):
  Request 1 → Thread 1 →  [====I/O WAIT====] → [process] → response
  Request 2 → Thread 2 →  [====I/O WAIT====] → [process] → response
  Request 3 → Thread 3 →  [====I/O WAIT====] → [process] → response

  1000 concurrent requests = 1000 threads blocking on I/O.
  Most threads sitting idle. Massive memory waste (1 thread ≈ 1MB stack).
02Non-Blocking I/O — Node's approach

In non-blocking I/O: when a request needs I/O, the thread registers a callback and immediately returns to handle more requests. When the I/O completes (handled by the OS or a background thread), the callback is queued for execution. One thread handles many concurrent requests. 

  Non-Blocking I/O (Node.js event loop):

  Single Thread (Event Loop)
  ─────────────────────────────────────────────────────────────
  t=0ms: Request 1 arrives → register DB callback → CONTINUE
  t=0ms: Request 2 arrives → register file callback → CONTINUE
  t=0ms: Request 3 arrives → register API callback → CONTINUE

  [libuv/OS handles I/O in background]

  t=15ms: DB done → callback queued → event loop runs it → send response 1
  t=20ms: File done → callback queued → event loop runs it → send response 2
  t=25ms: API done → callback queued → event loop runs it → send response 3
  ─────────────────────────────────────────────────────────────
  Single thread handled 3 concurrent requests. Never blocked.
03The Event Loop — phases in detail

The event loop runs continuously, processing callbacks in a specific order. Understanding the order explains exactly why your JavaScript code executes in the sequence it does. 

  ┌─────────────────────────────────────────────────────┐
  │                  Event Loop Tick                    │
  │                                                     │
  │  1. timers        — setTimeout / setInterval callbacks │
  │  2. pending I/O   — I/O callbacks deferred from prev │
  │  3. idle, prepare — internal use                    │
  │  4. poll          — retrieve new I/O events           │
  │  5. check         — setImmediate() callbacks           │
  │  6. close callbacks — socket.on('close', ...)       │
  │                                                     │
  │  Between EACH phase:                                │
  │  → Drain the microtask queue                        │
  │    (Promise.then, async/await, process.nextTick)   │
  └─────────────────────────────────────────────────────┘

  MICROTASKS run BEFORE the next phase begins — higher priority
  MACROTASKS (setTimeout callbacks) run in the timers phase

04libuv — the engine behind Node.js I/O

libuv is a C library that handles asynchronous I/O for Node.js. It maintains a thread pool (4 threads by default, configurable via UV_THREADPOOL_SIZE) for I/O operations that don't have native async OS support (like file system operations).

Network I/O (TCP sockets) uses the OS's native async capabilities (epoll on Linux, kqueue on macOS, IOCP on Windows) — these truly don't need extra threads. File I/O uses the libuv thread pool because file operations are less consistently async across OS platforms.

Node.js architecture in one paragraph: Your JavaScript runs on V8 (the JS engine). When your code calls fs.readFile() or https.get(), Node passes the work to libuv. libuv either uses the OS's async I/O (for network) or its thread pool (for file). When the I/O completes, libuv puts the callback in the event queue. The event loop — running in your main JS thread — picks up callbacks from the queue and executes them one at a time. V8 + libuv + event loop = Node.js.
Interview Q&A — I/O and Event Loop
What is the difference between blocking and non-blocking I/O? ▼
Strong answer Blocking I/O: the calling thread suspends execution until the I/O operation completes. The thread is idle during I/O — wasting CPU. To handle N concurrent I/O operations, you need N threads. Traditional Java servlets, PHP, and Python Flask use this model. Non-blocking I/O: the thread initiates the I/O operation, registers a callback, and immediately returns to do other work. The OS notifies when I/O completes, and the callback is queued. One thread can manage many concurrent I/O operations. Node.js uses this model with its event loop. Non-blocking is far more efficient for I/O-bound workloads; blocking is simpler to reason about and better for CPU-bound work.
What is the output of this code? console.log('1'); setTimeout(fn, 0); Promise.resolve().then(fn2); console.log('4'); ▼
Strong answer Output: 1, 4, (fn2 result), (fn result). Execution order: (1) Synchronous code runs first — console.log('1') then console.log('4'). (2) Microtask queue is drained — Promise.then callbacks are microtasks, they run after all synchronous code but before the next event loop phase. fn2 runs here. (3) Macrotask queue — setTimeout callback is a macrotask (in the timers phase). fn runs here. Key rule: synchronous → microtasks (Promises, async/await) → macrotasks (setTimeout, setInterval, I/O callbacks). This ordering explains why Promise-based code executes "before" setTimeout even with 0ms delay.
What is libuv? What role does it play in Node.js? ▼
Strong answer libuv is a cross-platform C library that provides Node.js with asynchronous I/O capabilities and an event loop implementation. When you call fs.readFile() or https.get(), Node.js delegates the actual I/O to libuv. For network I/O, libuv uses the OS's native async mechanisms (epoll/Linux, kqueue/macOS, IOCP/Windows). For file I/O, libuv uses its own thread pool (4 threads by default) because file operations don't have consistent native async support across platforms. When I/O completes, libuv places the callback in the event queue. The Node.js event loop — which libuv also manages — picks up callbacks and gives them to V8 (the JavaScript engine) to execute. Node.js = V8 (JS execution) + libuv (async I/O + event loop).

I/O and Event Loop — 60-second revision

  • Blocking I/O: thread waits idle during I/O. N concurrent requests = N threads needed.
  • Non-blocking I/O: register callback, return immediately. One thread handles many concurrent I/O operations.
  • Event loop phases: timers → poll (I/O) → check (setImmediate) → close callbacks.
  • Microtasks (Promise.then, async/await): run BEFORE next event loop phase. Higher priority than macrotasks.
  • Macrotasks (setTimeout, setInterval, I/O): run in their respective event loop phase.
  • Execution order: synchronous → microtasks → macrotasks.
  • libuv: C library providing async I/O + event loop. Thread pool (4 threads) for file I/O. OS async for network I/O.

All OS Interview Questions

Every OS question that appears in Bangalore product company interviews. Answer out loud without looking, then check. If your answer was weak — study that section again.
Complete OS Q&A bank — 20 questions
1. What is the difference between a process and a thread? ▼
AnswerProcess: independent unit with own memory space (code, data, heap, stack). Isolated — crashes don't affect others. Heavy to create. Thread: lightweight unit within a process, shares heap + data, own stack + registers. Cheap to create. Race condition risk from shared memory. Use processes for isolation (browser tabs, microservices). Use threads for shared-state concurrent work (request handling in Java servers).
2. What is context switching? Why is it expensive? ▼
AnswerOS pauses one process and resumes another: save current process's CPU registers + program counter into its PCB → select next process → load its registers. Expensive because: CPU caches (TLB, instruction cache, data cache) are invalidated — the new process has a different memory map, so cached lookups become misses. Too many threads = too many context switches = performance degradation. Node.js's single-threaded model avoids this overhead for I/O-bound work.
3. What is concurrency? What is parallelism? How does Node.js achieve concurrency? ▼
AnswerConcurrency: multiple tasks make progress via time-slicing on 1 CPU — interleaving, not truly simultaneous. Parallelism: multiple tasks run literally simultaneously on multiple CPU cores. Node.js achieves concurrency through non-blocking I/O + event loop: when I/O is needed, register callback and move on. libuv handles I/O in background. When done, callback queued. Single thread processes one callback at a time — never idles. Efficient for I/O-bound workloads. CPU-bound tasks block the event loop.
4. What is a race condition? How is it caused? ▼
AnswerOutcome depends on unpredictable thread timing. Caused by non-atomic operations on shared data. Example: count++ is READ, ADD, WRITE — three instructions. Thread A reads 5, Thread B reads 5 before A writes, both compute 6, final value is 6 not 7. Real example: two requests to "book last seat" both read "1 available," both succeed → oversold. Fix: synchronize the critical section (mutex/synchronized), or use atomic operations (AtomicInteger), or use database transactions with proper isolation.
5. What is a mutex? What is a semaphore? What is the key difference? ▼
AnswerMutex: binary lock with ownership. Only the thread that locked it can unlock it. Used for mutual exclusion (one thread in critical section). Semaphore: integer counter, no ownership. Any thread can signal (increment) it. Allows up to N threads to access a resource simultaneously. Binary semaphore (count=1) ≈ mutex but without ownership. Key difference: ownership. Mutex owns the lock. Semaphore has no owner — any thread can signal. Use mutex to protect a critical section. Use semaphore to manage a resource pool (connection pool of 10).
6. What is a deadlock? What are the 4 Coffman conditions? ▼
AnswerTwo or more threads permanently blocked — each waiting for a resource held by another. 4 conditions (all must hold): (1) Mutual Exclusion — resource non-shareable. (2) Hold and Wait — holds one resource, waiting for another. (3) No Preemption — resources can't be forcibly taken. (4) Circular Wait — cycle of threads, each waiting for next's resource. Break any one → no deadlock. Most practical: break Circular Wait by always acquiring locks in the same fixed order by resource ID.
7. What is the difference between deadlock and starvation? ▼
AnswerDeadlock: permanent circular block. No thread can proceed. Requires external intervention (kill and restart, timeout + rollback). Starvation: thread perpetually denied CPU time but NOT permanently blocked — high-priority threads keep preempting. If they stop arriving, the starved thread would run. Fix: aging (priority increases with wait time). Deadlock is circular dependency. Starvation is unfair scheduling. Both result in a thread not running, but different causes and fixes.
8. What is stack vs heap memory? What lives where? ▼
AnswerStack: local variables, function call frames, primitives. LIFO — freed automatically when function returns. Thread-specific (no race conditions). Fixed size. Fast. Stack overflow = too deep recursion. Heap: objects (new/malloc), closures, dynamic allocations. GC-managed in Java/JS. Shared across threads (needs synchronization). Variable size. Slower. In Java/JS: the variable name is on the stack, the object it points to is on the heap. When a function exits, its stack frame is popped but heap objects remain until no references point to them (GC eligible).
9. What is garbage collection? How does Java's generational GC work? ▼
AnswerGC automatically frees heap memory that's no longer reachable from the program. Java uses generational GC based on "most objects die young." JVM heap: Young Generation (Eden + Survivor) and Old Generation. New objects in Eden. When Eden fills → fast Minor GC (collects mostly dead young objects). Survivors promoted to Old Gen over multiple GCs. Old Gen fills → slow Major GC (stop-the-world). Mark and Sweep: traverse from GC roots (statics, stack refs, thread objects), mark live objects, sweep unmarked. Efficiency: Minor GC handles 90%+ of garbage, runs fast because Young Gen is small.
10. What causes memory leaks in React? How do you prevent them? ▼
AnswerThree common React memory leaks: (1) setState after unmount — async fetch completes after component unmounts, calls setState. Fix: cancelled flag in useEffect cleanup or AbortController. (2) Forgotten event listeners — addEventListener without removeEventListener in cleanup. DOM element removed but listener persists, holding reference. (3) Forgotten timers — setInterval without clearInterval in cleanup. Pattern: always return cleanup from useEffect: return () => { clearInterval(timer); window.removeEventListener('scroll', handler); }. Detect: Chrome DevTools Memory tab → heap snapshot comparison.
11. What is the Node.js event loop? What is the execution order of sync, microtask, and macrotask? ▼
AnswerThe event loop is Node's mechanism for processing async operations. It continuously loops through phases: timers (setTimeout/setInterval callbacks), I/O callbacks, poll (retrieve I/O events), check (setImmediate), close callbacks. Between each phase, the microtask queue is fully drained. Execution order: (1) All synchronous code executes first. (2) Microtasks run (Promise.then, async/await, process.nextTick — nextTick runs before other microtasks). (3) Macrotasks run in their event loop phase (setTimeout, I/O callbacks). Example: console.log(1); setTimeout(()=>log(2),0); Promise.resolve().then(()=>log(3)); log(4); → output: 1, 4, 3, 2.
12. What is CPU scheduling? What is Round Robin? What is its advantage? ▼
AnswerCPU scheduling determines which ready process runs next. Round Robin: each process gets a fixed time quantum (e.g., 10ms). After quantum expires, it's preempted and put at the back of the ready queue. All processes cycle through equally. Advantages: fair — no process starves; good average response time for interactive systems; preemptive — no convoy effect. Trade-off: time quantum size matters — too small = too many context switches (overhead); too large = behaves like FCFS (long processes block short ones). Most modern OS schedulers use Round Robin with priority queues (multilevel feedback queue).
13. What is virtual memory? Why does swapping hurt performance? ▼
AnswerVirtual memory gives each process the illusion of having a large, contiguous private address space much larger than physical RAM. The OS maps virtual pages to physical RAM frames. When a page isn't in RAM, a page fault occurs — the OS fetches the page from disk (swap space). This is catastrophically slow: disk is ~10,000x slower than RAM. When a system regularly page-faults (called "thrashing"), performance degrades dramatically. Symptom: 100% disk utilization, high swap usage. Fix: add more RAM, reduce memory usage, limit concurrent process count. This is why monitoring memory usage and avoiding memory leaks matters in production services.
14. How does Node.js handle a CPU-heavy task? What's the fix? ▼
AnswerA CPU-heavy synchronous task (image resize, encryption, large sort) blocks the event loop — the single thread is busy, no callbacks can execute, all pending requests time out. Fix options: (1) worker_threads module: create a Worker that runs the heavy computation on a separate OS thread. Main thread + event loop stay free for other requests. (2) cluster module: fork the Node process across all CPU cores. Multiple event loops, a master process distributes requests. (3) Dedicated microservice: move CPU-heavy work to a Python/Go/Rust service, have Node proxy to it via HTTP. (4) Streaming + chunking: if possible, break the work into small async chunks using setImmediate to yield between chunks.
15. What is libuv? Why does Node.js use a thread pool for some operations? ▼
Answerlibuv is a cross-platform C library providing async I/O capabilities to Node.js. It implements the event loop. For network I/O (TCP, UDP), libuv uses the OS's native async APIs (epoll on Linux, kqueue on macOS, IOCP on Windows) — truly non-blocking, no extra threads needed. For file I/O and some other operations, libuv uses its own thread pool (4 threads by default, configurable via UV_THREADPOOL_SIZE) because file operations don't have consistent native async support across all platforms. When I/O completes, libuv places the callback in the event queue for the main thread to pick up and execute.
16. What is the convoy effect? How does Round Robin fix it? ▼
AnswerConvoy effect occurs in FCFS scheduling when a long process (needing 500ms CPU) blocks many short processes (needing 2ms each) waiting behind it. The short processes wait 500ms when they could each complete in 2ms. Average wait time is terrible. Round Robin fixes this by preempting the long process after each time quantum (e.g., 10ms). Short processes get their 2ms of CPU time quickly, without waiting for the long process to finish. The long process gets its total CPU time eventually (in multiple 10ms slices), but short processes aren't blocked.
17. How do databases handle deadlocks? ▼
AnswerDatabases use two approaches: (1) Detection: The DB maintains a "wait-for" graph where nodes are transactions and edges are "A is waiting for a lock held by B." If a cycle exists, deadlock is detected. The DB selects a "victim" transaction (usually the one with fewer locks or less work done), rolls it back, and allows the other to proceed. The rolled-back transaction is typically retried automatically. (2) Timeout: simpler — if a transaction can't acquire a lock within N milliseconds, assume possible deadlock, roll it back, and retry. PostgreSQL uses both. MySQL uses timeout by default. Application code should handle "deadlock detected" errors with retry logic.
18. What is a critical section? What are the three requirements for a correct solution? ▼
AnswerA critical section is code that accesses shared resources and must not execute concurrently. Three requirements: (1) Mutual Exclusion: only one thread in the critical section at a time. (2) Progress: if no thread is in the critical section and some threads want to enter, the selection of which enters next cannot be postponed indefinitely — a thread must eventually enter. (3) Bounded Waiting: after a thread requests to enter the critical section, there's an upper bound on how many times other threads can enter before this thread is allowed. This prevents starvation within the synchronization solution itself.
19. What is the difference between preemptive and non-preemptive scheduling? ▼
AnswerPreemptive scheduling: the OS can interrupt a running process and switch to another, even if the running process hasn't finished its work or yielded voluntarily. Triggered by: timer interrupt (time quantum expired in Round Robin), higher-priority process becomes ready, I/O completion. All modern OS use preemptive scheduling. Non-preemptive (cooperative) scheduling: a process runs until it voluntarily yields the CPU (by doing I/O, calling yield(), or finishing). More predictable but a single misbehaving process can monopolize the CPU. Old Mac OS, early Windows 3.x used cooperative scheduling. Today only used in embedded systems and some game engines.
20. Is JavaScript affected by race conditions? Explain with an example. ▼
AnswerFor CPU-level operations: no. JavaScript is single-threaded — two JS operations cannot execute simultaneously. No two functions race to modify the same variable at the CPU instruction level. However, async operations create logical race conditions. Example: two Express route handlers serve "book last seat." Both read seats = 1 from DB. Both check seats > 0. Both insert a booking. Both decrement seats. Result: seats = -1, two people booked the last seat. Fix: database-level locking (SELECT FOR UPDATE), atomic DB operations, or optimistic locking with version numbers. The race isn't between CPU instructions — it's between async DB operations that need to be atomic at the database level.
