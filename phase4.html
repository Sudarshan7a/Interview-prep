Mock Interviews — Build the Muscle

You can know everything and still fail interviews if you've never practiced performing under pressure. 2 full mock rounds per week minimum. The feedback loop: attempt → get feedback → fix the gap → repeat.

The 3 types of rounds — prepare for all
✓
DSA Round — live coding under pressure
2 problems, 45 minutes total. Explain thinking out loud. Handle edge cases.
must · every company has this
What to do differently in a real interview vs practice
  • Read the problem twice before writing anything. Misunderstanding costs more time than re-reading.
  • Clarify before coding: "Can the array be empty? Can values be negative? Should I handle duplicates?" — shows thoroughness.
  • State your approach first: "I'm going to use a sliding window — expand right, shrink left when condition violated. Time O(n), space O(k). Let me code it." Interviewer can stop you if approach is wrong.
  • Think out loud: don't go silent for 5 minutes. Say what you're considering even if you're not sure. "I'm thinking about using a HashMap here to get O(1) lookup..."
  • Write clean code: meaningful variable names, not i/j for everything. add spaces. Interviewers read your code.
  • Test before declaring done: trace through your code with the given example. Then test an edge case (empty input, single element, all same values).
  • If stuck: start with brute force. Say: "The brute force is O(n²) — let me think about how to optimize." Never sit silent.

CS Fundamentals — 30 Interview Questions

These are the actual questions that get asked at Bangalore product companies in round 2. Read the question, answer in your head or out loud, then reveal the full answer. If your answer missed key points — study that topic again.

OOP — most asked first
What is the difference between abstraction and encapsulation? ▼
Strong answer Encapsulation is the mechanism of hiding internal data and exposing only what's necessary through a controlled interface (private fields + getters/setters). It's about HOW you protect data. Abstraction is about hiding complex implementation details and showing only relevant behavior — it's about WHAT the object exposes. Encapsulation implements abstraction. A car engine is abstracted (you use the accelerator, not the fuel injection system) and encapsulated (engine internals are not directly accessible). In Java: encapsulation = private fields, abstraction = interfaces and abstract classes. Likely follow-up "Can you have one without the other?" — Yes. A class can have private fields (encapsulation) without an abstract interface (abstraction). And you can have a public interface (abstraction) with all public fields (no encapsulation, bad practice).
Explain polymorphism. What's the difference between compile-time and runtime polymorphism? ▼
Strong answer Polymorphism = same interface, different behavior. Compile-time (static): method overloading — same name, different parameters. Resolved at compile time based on argument types. Java supports it, JavaScript does not (last definition wins). Runtime (dynamic): method overriding — child redefines parent's method. Resolved at runtime via dynamic dispatch — Java checks the actual object type, not the reference type. Example: Shape[] shapes = [new Circle(), new Rect()]. Calling shape.area() on each calls the correct overridden version at runtime, even though the reference type is Shape.
Why is the 'this' keyword in JavaScript unpredictable? How do arrow functions fix it? ▼
Strong answer In JavaScript, this is determined at call time (dynamic binding), not where the function is defined. When a method is detached from its object — const fn = obj.method; fn() — this becomes undefined (strict mode) because there's no object before the dot. Arrow functions solve this with lexical binding: they inherit this from the enclosing scope at definition time, not call time. This is why React class component event handlers need binding: this.handleClick.bind(this), or use arrow function class fields which don't have their own this.
What is the Singleton pattern? Why is the basic implementation not thread-safe? ▼
Strong answer Singleton ensures only one instance of a class exists globally. The basic if (instance == null) create is not thread-safe because two threads can simultaneously pass the null check before either creates the instance — resulting in two instances. Fixes: (1) synchronized method — works but slow on every call, (2) double-checked locking with volatile — better, (3) enum singleton — best in Java, JVM guarantees thread-safe enum instantiation. In JavaScript, modules are automatic singletons due to module caching — require('./db') always returns the same connection object.
OS — frequently asked
Node.js is single-threaded. How does it handle 10,000 concurrent requests without blocking? ▼
Strong answer Node.js uses non-blocking I/O with an event loop. When a request needs I/O (database, file, network), instead of blocking the thread, Node registers a callback with libuv's thread pool and immediately moves to the next request. When I/O completes, the callback is queued in the event loop and executed. The single thread is never sitting idle — it's always processing. This is concurrency (not parallelism) — efficient for I/O-bound work. Where it breaks: CPU-heavy tasks (image processing) block the event loop — use worker_threads for those. Connection to your project "In CollabDocs, each Socket.io event handler is processed by this event loop — when a user sends an edit, the Node server receives it, broadcasts to the room, and can handle the next user's edit immediately without waiting."
What is a deadlock? Give a real-world example. How do you prevent it? ▼
Strong answer Deadlock: two or more threads each waiting for a resource held by the other — permanently stuck. All 4 Coffman conditions must hold: mutual exclusion, hold-and-wait, no preemption, circular wait. Real example: A PhonePe transfer — Transaction A locks User X's account and wants User Y's. Transaction B locks User Y's account and wants User X's. Neither can proceed. Prevention: break the circular wait by always acquiring locks in the same fixed order. Databases handle it with timeouts — if a transaction can't acquire a lock in N seconds, it rolls back and retries automatically.
What is the difference between a process and a thread? When use which? ▼
Strong answer Process: independent execution unit with own memory space (code, heap, stack). Isolated — crash doesn't affect others. Heavy to create. Thread: lightweight unit within a process, shares the heap and data segment, only has its own stack. Cheaper to create, risky (shared state → race conditions). Use processes when isolation matters (Chrome tabs, microservices — crash one without killing others). Use threads when shared state and low overhead matter (web server handling multiple requests that share the same application state and DB connection pool).
What causes memory leaks in JavaScript/React? How do you detect and fix them? ▼
Strong answer Common JS memory leaks: (1) Forgotten timers — setInterval keeps closure alive. (2) Event listeners not removed — DOM element removed but listener still references it. (3) Detached DOM nodes — removed from DOM but still referenced in JS variables. (4) React: setState after unmount — async operation completes after component unmounts and calls setState. Fix in React: return cleanup from useEffect — cancel timeouts, abort fetch requests, unsubscribe. Detect: Chrome DevTools → Memory tab → take heap snapshots before/after, compare → look for growing object counts.
DBMS — most asked
Explain ACID properties. Give a real payment example for each. ▼
Strong answer using PhonePe transfer Atomicity: Debit ₹500 from A AND credit to B — both happen or neither. If credit fails, debit is rolled back. Consistency: Total money stays the same. Balance ≥ 0 constraint never violated. DB moves from one valid state to another. Isolation: Two concurrent transfers involving same account don't see each other's intermediate state — T2 sees balance before T1 commits or after, never during. Achieved via locking or MVCC. Durability: Once you see "Transfer Successful" — the transaction is written to disk via WAL. Even if server dies immediately after COMMIT, data is safe.
What is database indexing? What are the trade-offs? When would you NOT add an index? ▼
Strong answer An index is a separate B-Tree data structure that maps column values to row locations — enabling O(log n) lookup instead of O(n) full table scan. Clustered index: rows physically sorted by key — one per table (primary key in InnoDB). Non-clustered: separate structure with pointers — multiple allowed. Trade-off: indexes speed reads but slow every write (INSERT/UPDATE/DELETE must also update all indexes). When NOT to index: low-cardinality columns (gender M/F — index barely helps), frequently updated columns, small tables (full scan is faster than index overhead), columns rarely used in WHERE/JOIN/ORDER BY.
When would you choose NoSQL over SQL? Give a Bangalore product company example. ▼
Strong answer Use SQL for: financial transactions (ACID required — PhonePe payment records), user accounts (strict consistency), anything with complex relationships and joins. Use NoSQL for: flexible/evolving schema (Swiggy restaurant menus — every restaurant has different attributes), horizontal scale (Zepto user activity logs — billions of writes), eventual consistency OK (product catalog, search index). Real example: Swiggy likely uses PostgreSQL for orders/payments (ACID), MongoDB for menu catalog (flexible schema), Redis for cart/sessions (speed), Elasticsearch for restaurant search. CAP theorem: can't have all 3 — pick C+P (MongoDB strong reads) or A+P (Cassandra) in distributed systems.
Walk me through normalizing a table to 3NF. ▼
Strong answer — step by step Starting table: Orders(OrderID, Customer, CustomerCity, Product, Price) with comma-separated products. 1NF: atomic values — split multi-valued Products into separate rows. Primary key: (OrderID, Product). 2NF: remove partial dependencies — Customer and CustomerCity depend only on OrderID, not the full key. Split: Orders(OrderID, CustomerID) and Customers(CustomerID, Name, City). 3NF: remove transitive dependencies — CustomerCity depends on Customer, not OrderID. Already fixed in 2NF by moving to Customers table. Result: 3 tables with no redundancy. If Ravi moves cities, update 1 row in Customers — not every order. Trade-off: more joins → slower reads. Denormalize when reads >> writes.
Networks — full stack specific
What happens when you type a URL in the browser? Full answer. ▼
Strong answer — 7 steps 1. DNS resolution: browser cache → OS cache → ISP resolver → root NS → TLD NS → authoritative NS → IP returned. 2. TCP handshake: SYN → SYN-ACK → ACK. Connection established. 3. TLS handshake (HTTPS): cert verification with CA, asymmetric key exchange → symmetric session key. 4. HTTP GET: browser sends request with headers. 5. Server processes: NGINX receives → Node/Spring handles → DB query → response built. 6. Browser parses HTML: discovers CSS, JS, images → parallel requests for each. 7. Rendering: DOM + CSSOM → render tree → layout → paint → composite. Interviewers can ask follow-ups at any step — know each one.
What is CORS? Why does it exist? How do you configure it in your Express app? ▼
Strong answer CORS (Cross-Origin Resource Sharing) is a browser security policy that prevents JavaScript on one origin (scheme+domain+port) from making requests to a different origin without explicit permission. It exists to prevent malicious sites from making authenticated API calls on behalf of users. Simple requests: browser adds Origin header, server responds with Access-Control-Allow-Origin. Preflight: for non-simple requests (PUT, DELETE, custom headers) browser sends OPTIONS first. Fix in Express: app.use(cors({ origin: 'https://yourfrontend.com', credentials: true })). Critical: CORS is browser-only. Postman and curl bypass it — CORS is NOT API security. A malicious server can still call your API directly.
401 vs 403 status code — when does each apply? ▼
Strong answer 401 Unauthorized: server doesn't know who you are. No token, invalid token, expired token. "Please authenticate." The name is misleading — it's actually about authentication, not authorization. 403 Forbidden: server knows who you are but you don't have permission for this resource. Valid token, but wrong role. "I know who you are — you just can't do this." Real example: 401 when JWT is missing or expired. 403 when a USER role tries to access an ADMIN-only endpoint. This is one of the most common interview gotchas — many developers confuse these.

Behavioral Interview Prep

Behavioral rounds test communication, self-awareness, and how you handle pressure. As a fresher you'll be asked about projects, learning experiences, and collaboration. Use STAR method for every answer.

The STAR method — every behavioral answer uses this
S
Situation: Set the context. What project, what problem. 2-3 sentences. "While building CollabDocs, I ran into a race condition..."
T
Task: What was YOUR responsibility specifically. "My task was to ensure concurrent edits didn't corrupt the document state."
A
Action: What YOU did. Concrete, specific steps. "I first identified the issue using console logs to trace the event sequence, then implemented a last-write-wins strategy with timestamps, and added a debounce to batch rapid edits."
R
Result: What happened. Quantify if possible. "The race condition was eliminated — documents stayed consistent even under rapid concurrent edits. I also learned to always consider concurrency when designing real-time systems."

✓
A technical challenge you faced and overcame
The race condition in CollabDocs, the N+1 problem in Spring Boot, JWT refresh complexity.
asked at every company
How to frame a strong answer
  • Pick a challenge that shows debugging skill — you had to think systematically to find the root cause
  • Be specific: "The issue was that two Socket.io events fired within 10ms and both read the document state before either wrote" — not "there was a bug"
  • Show your process: how you identified it, what you tried, what worked
  • Include what you learned: "This taught me to always think about race conditions in any system where two users can affect the same resource simultaneously"
Example story — CollabDocs race condition
S: While building CollabDocs, I noticed that when two users typed simultaneously, the document would sometimes end up with corrupted content — one user's changes would overwrite the other's even when they were editing different parts.

T: I needed to identify why this was happening and implement a solution that kept documents consistent under concurrent edits.

A: I added timestamps to every edit event and logged them on the server. I discovered both clients were reading the document state, then independently computing the new state, then both writing — the second write would erase the first. I implemented a last-write-wins strategy where each edit includes the timestamp and user ID, and the server serializes them in order. I also added a 500ms debounce to prevent rapid keystrokes from firing 50 separate events.

R: The corruption issue disappeared. The debounce also reduced server load by 80% during typing. The lesson I took from this is to always design concurrent systems assuming multiple actors will modify the same resource simultaneously.

The referral strategy — most underused
✓ Referrals bypass ATS and land you in the interview pile
Most Tier 1 companies give employees referral bonuses. Engineers are happy to refer strong candidates — it's money for them. Find engineers at your target companies on LinkedIn → connect with a personalized note → share your profile + 1 impressive project. Aim for 5 referral asks per week. Success rate is low but the payoff is high — 1 referral is worth 20 cold applications. Template is in the LinkedIn tab.

LinkedIn — Your Inbound Lead Machine

60–70% of Tier 1 Bangalore tech jobs are filled through LinkedIn referrals and recruiter outreach — not Naukri. An optimized profile + weekly posts + targeted outreach = recruiters reaching out to you.

Profile optimization — do these first
📸
Professional photo
Plain background, clear face, professional but not stiff. Profiles with photos get 21x more views. Take one with your phone in natural light.
📝
Headline — not just "Student" or "Fresher"
Write: "Full Stack Developer | React · Node.js · Spring Boot · DSA | Building CollabDocs & ShopFlow | Open to SWE roles in Bangalore". This shows skills and intent — not just a job title.
🗒️
About section — 3 paragraphs
Para 1: Who you are and what you build. Para 2: Your 2 most impressive projects with 1 technical detail each. Para 3: What you're looking for + skills list. End with your email. Keep it specific — not "passionate about technology."
🔗
Featured section — pin your best project
Pin your GitHub + live demo link for CollabDocs. Recruiters who click your profile see this first. Include a 2-sentence description of what it does.
🎓
Open to Work — set it, but choose "recruiters only"
Set "Open to Work" with roles: Software Engineer, Full Stack Engineer, Backend Developer. Choose "Recruiters only" — not the green banner (looks desperate). Target locations: Bengaluru.
Posting strategy — 1 post per week
Why posting works — even with 0 followers
LinkedIn posts reach people beyond your connections. A good technical post can get 5,000-50,000 views even if you have 200 connections. Recruiters actively search for people posting about specific technologies. Every post is an inbound job application you didn't have to write.
Post ideas that perform well
  • Project showcase: "Built a real-time collaborative editor — here's how WebSocket + Redis works together [GIF of feature]"
  • Learning insight: "The N+1 problem in JPA — I hit this in production and here's how I fixed it"
  • Before/after optimization: "My MongoDB query took 2.3 seconds. Added an index. Now it's 12ms. Here's why."
  • Concept explained simply: "The difference between 401 and 403 — most developers I've asked get this wrong"
  • DSA insight: "This is why the sliding window pattern works and when to recognize it"
Post format that works
  • Opening line: Hook in first 2 lines — most people only see this in feed. "I built [thing] and learned [insight]" or "Most people misunderstand [concept]"
  • Body: Short paragraphs or bullet points. No walls of text. Code snippets or screenshots perform well.
  • Closing: What you're working on + tag 2-3 relevant hashtags (#react #fullstackdevelopment #javascript)
  • Length: 150-400 words. Not too short (no substance), not too long (loses engagement)
Referral outreach — the script that works
Hi [Name],

I'm [Your Name], a fresher full stack developer in Bangalore actively exploring SWE roles. I came across your profile while researching [Company] and noticed you work on [team/product area].

I've built a few projects I'm proud of — including a real-time collaborative editor using Socket.io + Redis, and a Spring Boot REST API with JWT auth. I'm a strong MERN stack developer and I'm also working with Java/Spring Boot.

I'd really appreciate it if you could refer me for the [Role] opening at [Company], or even just point me to the right application channel if a referral isn't possible.

Here's my resume and GitHub if it's helpful: [link] | [link]

No pressure at all — thanks for your time.

[Your Name]
⚠️ Rules for outreach
Personalize each message — mention something specific about the company or their work. Don't mass-send the same template. Connect first, send the message 1-2 days later (not in the same connection request). Target engineers who graduated from similar backgrounds or worked at similar types of companies — they're more likely to empathize and respond.

Salary Negotiation

Never accept the first offer. Always negotiate — the worst they can say is no and the offer stands. A 10-minute negotiation conversation can add ₹1–3 LPA to your package. You have nothing to lose.

Before you negotiate — understand what you're looking at
✓
How to read a job offer — CTC vs take-home
CTC includes components you never see in your account. Know what you're actually getting.
must
CTC breakdown — example for ₹12 LPA offer
Base salary₹7.5 LPA
Variable/performance bonus (if targets met)₹1.5 LPA
PF (employer contribution — you never see this cash)₹1.08 LPA
Gratuity, health insurance, other benefits~₹1 LPA
CTC total₹12 LPA
Your actual monthly take-home (after tax ~30%)~₹45,000/month
  • Ask for the breakdown before evaluating. "Can you share the component-wise CTC breakup?"
  • Focus on fixed monthly take-home — variable bonuses often don't materialize, especially in the first year
  • Stock options (ESOPs): for early-stage startups, ESOPs can be significant. For Series B+, understand the vesting schedule (usually 4-year vesting with 1-year cliff)
  • Joining bonus: if offered, understand if it's clawed back if you leave early (common — usually 1 year)
The negotiation — step by step
1
Never give a number first
When they ask "what are your salary expectations?" early in the process: "I'm flexible and open to a fair offer based on the role and responsibilities. Could you share the budget for this position?" If they push: "I'd prefer to evaluate the complete offer — compensation, growth opportunity, and the role itself together."
2
When you get the offer — do not accept on the spot
"Thank you so much for the offer — I'm genuinely excited about this opportunity. Could I have 48-72 hours to review it carefully?" This is standard, expected, and gives you time to evaluate and negotiate. Any company that pressures you to accept immediately is a red flag.
3
Research the market before you counter
Check: levels.fyi for salary data (filter by India, company, role), Glassdoor, LinkedIn Salary, and ask in communities (TeamBlind, relevant Discord/Telegram groups). Know what the range is for this role at this company. Your counter should be backed by data.
4
The counter offer script
"I'm very enthusiastic about joining [Company] and this role. After reviewing the offer, I was hoping we could discuss the base salary. Based on my research and the skills I'm bringing — specifically [mention 1-2 specific skills: Spring Boot + JWT auth system, Docker deployment experience] — I was expecting something closer to [your target]. Is there flexibility there?" — Then stop talking. Don't justify further. Wait for their response.
5
When to negotiate harder — competing offers
If you have multiple offers: "I'm very interested in [Company] as my top choice, but I do have another offer at [X amount]. If you can match or get closer to that, I'd be excited to accept today." This is the most powerful negotiation position. Always try to get at least 2 offers simultaneously — this is why you apply broadly from week 1.
6
What to do if they say the offer is fixed
Try non-salary items: joining bonus, earlier performance review (6 months instead of 12), additional stock options, remote work flexibility, specific team preference. If truly fixed and you want the job: ask "What would I need to achieve in the first 6 months to reach the next compensation level?" — this signals you're thinking long-term and sets expectations for a fast-track raise.
✓ The rule about competing offers
Get an offer from a Tier 3 company first, even if you don't want it. Use it as a floor. When Tier 2 or Tier 1 offers come in, you have leverage. You're not desperate. Desperation is visible in negotiation and weakens your position. An offer in hand = confidence in the negotiation room.

4-Week Plan

Apply from day 1. Don't wait until week 4 to start applying. The earlier you apply, the earlier the offers come, the more time you have to negotiate with multiple options.

Week-by-week
WEEK 1
Resume + LinkedIn + Applications Finalize resume. Optimize LinkedIn profile. Apply to 5-8 Tier 3 companies (TCS Digital, Infosys SP, Wipro Elite). Set up job alerts on LinkedIn + Instahyre + Naukri. Start referral outreach (5 messages to engineers at target companies).
WEEK 2
Mock interviews + Tier 2 applications 2 full mock interview sessions (AI). 1 post on LinkedIn (project showcase). Apply to 5 Tier 2 companies. Prepare STAR stories — write out all 6 behavioral answers. Continue referral outreach.
WEEK 3
Tier 1 applications + real interview experience Apply to 3-5 Tier 1 companies (Swiggy, PhonePe, CRED, Razorpay). By now Tier 3 interviews should be happening — treat them as practice. Post week 2 LinkedIn post. 2 more mock sessions.
WEEK 4+
Keep pushing — don't stop Keep applying 5-7 new companies per week. Keep doing 2 DSA problems per day — don't let it lapse. Analyze every real interview — what questions came up? Update your prep. Negotiate offers carefully. The process takes time — hiring timelines are 3-6 weeks from application to offer.
