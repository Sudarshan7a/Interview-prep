OSI Model — The 7 Layers

You don't need to memorize all 7 layers in detail. You need to understand what layering means, why it exists, and which layers matter for full stack work (Transport, Network, Application).
high valueContext for everything else in networking
01Why layers exist

The OSI model divides network communication into 7 layers, each with a specific responsibility. The purpose: each layer only needs to know how to talk to the layer directly above and below it. HTTP doesn't know or care whether the underlying transport is TCP over WiFi or TCP over Ethernet — that's handled by lower layers.

This separation of concerns means you can change one layer (switch from WiFi to Ethernet) without touching others. A web developer works at the Application layer and lets the OS + hardware handle everything below.

02The layers that matter for interviews

Layer 4 (Transport) — TCP and UDP: TCP provides reliable, ordered delivery. UDP provides fast, connectionless delivery. Your choice of which to use depends on the application. HTTP/HTTPS use TCP. DNS and video streaming often use UDP.

Layer 3 (Network) — IP: Every device on the internet has an IP address. IP handles routing — figuring out how to get a packet from source to destination across many networks. IP doesn't guarantee delivery or order.

Layer 7 (Application) — HTTP: The protocol your Node.js and Spring Boot APIs speak. Defines request/response format, methods (GET, POST), status codes, headers.

The TCP/IP model (4 layers): In practice, you'll hear "TCP/IP model" more than "OSI model." It collapses OSI's 7 layers into 4: Application (OSI 5-7), Transport (OSI 4), Internet (OSI 3), Network Access (OSI 1-2). Same concepts, simpler mental model.

OSI Model — 60-second revision

  • 7 layers: Physical → Data Link → Network → Transport → Session → Presentation → Application.
  • Mnemonic: "Please Do Not Throw Sausage Pizza Away" (bottom to top).
  • Layer 7 (Application): HTTP, WebSocket, DNS, SMTP — what your code uses.
  • Layer 4 (Transport): TCP (reliable, ordered) and UDP (fast, unreliable).
  • Layer 3 (Network): IP addresses, routing between networks.
  • Layering principle: each layer talks only to adjacent layers. Change one without touching others.
Concept 02 of 09

TCP vs UDP + The Three-Way Handshake

TCP is reliable and ordered but slower. UDP is fast but unreliable. The three-way handshake is asked constantly. Know both with real use cases.
must knowThe handshake question comes up in most network rounds
01TCP — Transmission Control Protocol

TCP guarantees: reliable delivery (packets are retransmitted if lost), ordered delivery (data arrives in the correct sequence even if packets arrive out of order), and flow control / congestion control (sender doesn't overwhelm receiver or the network).

The cost: TCP requires a connection setup (the three-way handshake), acknowledgment overhead for every segment, and retransmission delays. It's heavier than UDP but guarantees the data gets there intact.

02The TCP Three-Way Handshake
  CLIENT                              SERVER
  ─────────────────────────────────────────────────────
  
  [CLOSED]                          [LISTEN] — waiting for connections

  Step 1: SYN
  Client: "I want to connect.           →  SYN (seq=100)
          My sequence number starts at 100."

  Step 2: SYN-ACK
  Server: "OK! My seq starts at 300.    ← SYN-ACK (seq=300, ack=101)
          I acknowledge your seq 100."

  Step 3: ACK
  Client: "Got it. I acknowledge        →  ACK (ack=301)
          your seq 300."

  ─────────────────────────────────────────────────────
  [ESTABLISHED]                     [ESTABLISHED]

  Now data can flow in both directions.

  Why 3 steps (not 2)?
  2 steps only confirms server can receive from client.
  3rd step (client ACK) confirms client received server's SYN.
  Both sides must verify they can both SEND and RECEIVE.

  Connection teardown: 4-way handshake (FIN, FIN-ACK, FIN, FIN-ACK)
03UDP — User Datagram Protocol

UDP is connectionless — no handshake, no acknowledgment, no guaranteed delivery. Just fire packets and forget. What you lose in reliability, you gain in speed and simplicity.

TCPUDP

Analogy: TCP = certified mail with tracking and signature confirmation. You know it arrived. UDP = dropping an envelope in a mailbox. Cheap and fast, but you have no idea if it arrived. For important documents (financial transactions, web pages), use TCP. For real-time audio where a slightly garbled frame is better than a pause (VoIP), use UDP.
HTTP/3 uses UDP! HTTP/3 is built on QUIC, which runs on UDP. QUIC re-implements reliability, ordering, and connection establishment in the application layer — but with better performance than TCP for high-latency networks. This is why the "TCP = web, UDP = games" simplification is becoming outdated.
Interview Q&A — TCP/UDP
Explain the TCP three-way handshake. Why three steps and not two? ▼
Strong answerThe three-way handshake establishes a reliable connection: (1) SYN: Client sends a SYN packet with its initial sequence number (ISN). "I want to connect, I'll start my sequence at X." (2) SYN-ACK: Server responds with its own ISN and acknowledges the client's ISN+1. "I acknowledge your sequence X+1, I'll start mine at Y." (3) ACK: Client acknowledges the server's ISN+1. "I acknowledge your Y+1." Why not 2 steps? Two steps only confirms the server can receive from the client and send back. The third step (client's ACK) confirms the CLIENT can also receive from the server. Without it, the server doesn't know if its SYN-ACK reached the client. Both parties must confirm bidirectional communication. Follow-up: "What is a SYN flood attack?" An attacker sends thousands of SYN packets but never sends the final ACK, leaving the server with many half-open connections consuming memory. Fix: SYN cookies — server encodes connection state in the ISN instead of allocating memory until the ACK arrives.
When would you use UDP over TCP? ▼
Strong answerUse UDP when: (1) Speed is more important than reliability — DNS lookups: you want the IP immediately, and if the first UDP packet is lost, it's faster to retry than to set up a TCP connection. (2) Real-time is required — video calls, VoIP, online gaming. A retransmitted audio packet would arrive late and be useless — it's better to skip it and play the next frame. A garbled video frame is better than a freeze. (3) Broadcast/multicast — sending to many recipients simultaneously. TCP is point-to-point; UDP supports one-to-many. (4) Simple request-response with your own reliability — DNS, DHCP. The application layer handles retry logic, which is simpler than full TCP for these simple use cases.

TCP vs UDP — 60-second revision

  • TCP: reliable, ordered, connection-oriented. Three-way handshake (SYN, SYN-ACK, ACK). Retransmits lost packets.
  • UDP: connectionless, unreliable, no ordering. Fast. No handshake overhead.
  • Handshake: SYN (client seq) → SYN-ACK (server seq + ack client) → ACK (ack server). 3 steps to confirm bidirectional communication.
  • TCP use: HTTP, HTTPS, SSH, email, file transfer. Correctness required.
  • UDP use: DNS, video streaming, gaming, VoIP. Speed critical, some loss OK.
  • HTTP/3: built on QUIC (UDP-based). Reimplements reliability in app layer for better performance.

02HTTP Methods — semantics matter
GET
Retrieve resource. No body. Idempotent. Safe. Cacheable. GET /users/123
POST
Create resource. Has body. Not idempotent. Not safe. POST /orders creates new order each time.
PUT
Replace resource entirely. Idempotent. PUT /users/123 replaces the whole user object.
PATCH
Partial update. Only send fields to change. PATCH /users/123 {"phone": "..."}
DELETE
Remove resource. Idempotent (deleting already-deleted returns same outcome). DELETE /orders/456
03Idempotent and Safe — the key properties
PropertyMeaningMethods
SafeDoes not modify server state. Read-only.GET, HEAD, OPTIONS
IdempotentCalling multiple times produces the same result as calling once. DELETE /users/123 once or 10 times — user is deleted either way.GET, PUT, DELETE, HEAD, OPTIONS

PUT vs PATCH confusion: PUT replaces the entire resource — you send all fields, and the server stores exactly what you sent. PATCH is a partial update — you send only the fields that changed. If you PUT {"name": "Ravi"} to a user resource, the phone number would be removed. If you PATCH {"name": "Ravi"}, only the name updates; phone stays untouched.
04HTTP/1.1 vs HTTP/2 vs HTTP/3
VersionKey featureProblem solved
HTTP/1.1Persistent connections (keep-alive). One request per TCP connection at a time (pipelining is broken in practice).Reduced connection overhead vs HTTP/1.0 (new TCP per request)

HTTP/3Built on QUIC (UDP-based). Connection ID instead of IP+port. 0-RTT connection establishment.TCP head-of-line blocking at transport layer. Better for lossy/mobile networks.
05HTTP is stateless — and how sessions work around it

HTTP is stateless: each request is completely independent. The server has no memory of previous requests from the same client. A request for /api/orders has no inherent connection to the previous login request.

How applications add state: Sessions and tokens. The server issues a token (session cookie or JWT) after authentication. The client sends this token on every subsequent request. The server reads the token, identifies the user, and "restores" state. The state is stored server-side (sessions in Redis) or client-side (JWT payload).

Interview Q&A — HTTP
What is the difference between PUT and PATCH? ▼
Strong answerPUT replaces the entire resource. The request body must contain the full resource representation. If you omit a field, it's removed from the resource. PUT is idempotent — calling it multiple times with the same body produces the same result. PATCH applies a partial update — only the fields in the request body are changed, everything else remains. PATCH is used when you want to update one or two fields without sending the entire object. Example: changing a user's phone number. PUT would require sending name, email, address, and phone together. PATCH only needs {"phone": "9876543210"}. In practice, many APIs use POST for everything (not RESTful), but in a proper REST API, the distinction matters.
What is HTTP/2 multiplexing? What problem does it solve? ▼
Strong answerHTTP/1.1 head-of-line blocking: a browser opens one TCP connection per origin (or a few), and each connection can only handle one request at a time. If request A is slow (large image), requests B, C, D queue behind it on that connection. HTTP/2 multiplexing: multiple requests and responses are interleaved on a single TCP connection using a binary framing layer. Requests A, B, C, D are broken into frames and multiplexed — no request blocks another. A slow response for A doesn't block B. Additionally: header compression (HPACK) eliminates repeated headers like User-Agent and Cookie being sent on every request. Result: fewer TCP connections (less overhead), faster page loads, especially for pages with many small resources (JS, CSS, fonts, images).
HTTP is stateless. How does authentication work across requests? ▼
Strong answerHTTP being stateless means the server has no inherent memory of who you are between requests. Authentication adds artificial state via tokens: after login, the server issues a token (session ID or JWT). Client stores it (cookie, localStorage, memory). On every subsequent request, client sends the token (Authorization: Bearer [token] header, or Cookie header). Server verifies the token to identify the user. Two approaches: (1) Server-side sessions: server stores session data (user_id, permissions) in Redis keyed by session_id. Stateful — server must look up session on every request. Scales horizontally if Redis is shared. (2) JWT: all user data encoded in the token itself. Server just verifies the signature — no DB lookup needed. Stateless. Trade-off: JWTs can't be instantly revoked (must wait for expiry).

HTTP — 60-second revision

  • GET: read, no body, safe, idempotent, cacheable. POST: create, has body, not idempotent.
  • PUT: replace entire resource. PATCH: partial update. DELETE: remove, idempotent.
  • Safe: doesn't modify state. Idempotent: multiple calls = same result as one call.
  • HTTP/1.1: persistent connections but head-of-line blocking. HTTP/2: multiplexing (multiple requests on one TCP connection). HTTP/3: QUIC (UDP-based).
  • Stateless: no memory between requests. Work around with JWT or session cookies.

The 401 vs 403 confusion is asked at almost every interview: 401 = "I don't know who you are" (authentication problem). 403 = "I know who you are but you can't do this" (authorization problem). Despite the name "Unauthorized," 401 is about authentication. 403 is about authorization. A logged-in user trying to access another user's data → 403. No login token at all → 401.
Interview Q&A — Status Codes
What is the difference between 401 and 403? ▼
Strong answer401 Unauthorized: the request requires authentication and the client hasn't provided valid credentials. No token sent, expired JWT, invalid signature — the server can't identify who is making the request. Despite the misleading name, 401 is about AUTHENTICATION. The client should log in and try again. 403 Forbidden: the client IS authenticated (server knows who they are) but doesn't have permission to perform this action. A regular user trying to access an admin endpoint — valid JWT, wrong role. This is about AUTHORIZATION. Re-authenticating won't help. Practical in your Spring Boot project: JWT missing or expired → 401. ROLE_USER trying to call an @PreAuthorize("hasRole('ADMIN')") endpoint → 403.
What status code do you return when creating a resource? When deleting? When a validation fails? ▼
Strong answerCreating a resource: 201 Created. Include the newly created resource in the body and optionally a Location header pointing to it: Location: /api/orders/123. Deleting: 204 No Content (success, nothing to return) or 200 OK with a message body if you want to include a deletion confirmation. 204 is the REST standard. Validation failure: 400 Bad Request for malformed input (invalid JSON, missing required field). 422 Unprocessable Entity for semantically invalid input (valid format but business rule violation — like a date range where end is before start). Some teams use 400 for both; pick one and be consistent. The key is: don't return 200 with {"success": false} — that's not RESTful and makes error handling harder for API consumers.
What is 304 Not Modified? When is it used? ▼
Strong answer304 is the caching status code. When a browser fetches a resource with an ETag or Last-Modified timestamp, it stores that value. On subsequent requests, the browser sends an If-None-Match: [etag] or If-Modified-Since: [date] header. The server checks if the resource has changed. If not changed: return 304 with no body — browser uses its cached copy. This saves bandwidth (no body transmitted) and reduces server load. If changed: return 200 with the new resource. Practical: when building an API, use ETags for response caching. When building a CDN or caching layer, 304 is how the CDN validates cached content with the origin server.

Status Codes — 60-second revision

  • 2xx: success. 200 OK, 201 Created (POST), 204 No Content (DELETE).
  • 3xx: redirect. 301 permanent (cached), 302 temporary (not cached), 304 not modified (use cache).
  • 4xx: client error. 400 bad request, 401 not authenticated, 403 not authorized, 404 not found, 429 rate limited.
  • 5xx: server error. 500 generic, 502 bad gateway (upstream failed), 503 unavailable, 504 gateway timeout.
  • 401 vs 403: 401 = no/invalid credentials (WHO are you?). 403 = valid credentials, wrong permissions (you can't do THIS).
  • Use 201 not 200 when creating. Use 204 not 200 when deleting. Use 429 with Retry-After for rate limits.

DNS — Domain Name System

How a domain name becomes an IP address. The resolution hierarchy. Caching. Record types. Why DNS is often the culprit when "the site is down."
must knowThe URL → IP flow is a classic interview question
01The DNS resolution hierarchy

DNS is the internet's phone book — it translates human-readable domain names (api.swiggy.com) into machine-readable IP addresses (52.66.41.78). Without DNS, you'd have to remember IP addresses for every website. 

  You type: https://api.swiggy.com

  Step 1: Browser DNS cache
  → Check: "Do I have api.swiggy.com cached?" → NO (first visit)

  Step 2: OS DNS cache
  → Check /etc/hosts, OS resolver cache → NO

  Step 3: Recursive Resolver (your ISP or 8.8.8.8 / 1.1.1.1)
  → Your first point of contact. Coordinates the rest.
  → Cache hit? → Return cached IP. Cache miss? → Continue.

  Step 4: Root Name Server (13 sets worldwide)
  → Resolver asks: "Who handles .com?"
  → Root returns: "Ask the .com TLD name server at [IP]"

  Step 5: TLD Name Server (.com, .in, .io, .org)
  → Resolver asks: "Who handles swiggy.com?"
  → TLD returns: "Ask Swiggy's authoritative NS at [IP]"

  Step 6: Authoritative Name Server (Swiggy's DNS)
  → Resolver asks: "What is the IP for api.swiggy.com?"
  → Returns: "52.66.41.78"

  Step 7: Resolver returns IP to browser. Caches it (for TTL seconds).
  Step 8: Browser connects to 52.66.41.78

  Total time: typically 20-120ms. Subsequent requests: near-instant (cached).

03TTL — Time to Live and why it matters for deployments

Every DNS record has a TTL (Time to Live) in seconds. This is how long resolvers and browsers cache the record. After TTL expires, they re-query the authoritative server.

Why TTL matters in practice: When you change your server's IP address (migrate to AWS, change load balancer), you need the DNS change to propagate to all clients worldwide. If your TTL is 86400 (24 hours), some clients will still point to the old IP for up to 24 hours. Best practice: lower TTL to 300 seconds before a planned migration, make the change, keep low TTL for a few hours, then restore to normal.

Interview Q&A — DNS
What is DNS and how does it resolve a domain to an IP? ▼
Strong answerDNS is the internet's distributed phonebook — translates human-readable domain names to IP addresses. Resolution hierarchy: (1) Check browser cache (DNS result from recent visits). (2) Check OS resolver cache (/etc/hosts). (3) Query the recursive resolver (ISP's DNS or a public one like 8.8.8.8). (4) If resolver doesn't have it cached: it queries the Root Name Server — one of 13 server clusters worldwide — to find the TLD server (who handles .com). (5) Query the TLD Name Server (.com, .in) for the authoritative name server for swiggy.com. (6) Query Swiggy's authoritative Name Server for the A record (IP) of api.swiggy.com. (7) Return and cache the IP. Each step is fast (~5-20ms). Results cached per TTL. Subsequent requests use cache — near-instant.
What is a CNAME record? When would you use it? ▼
Strong answerA CNAME (Canonical Name) record is an alias — it maps a domain name to another domain name (not an IP). When a DNS lookup hits a CNAME, the resolver follows the chain until it finds an A record with an actual IP. Use cases: (1) www.swiggy.com CNAME swiggy.com — the canonical name is swiggy.com, www just redirects. (2) CDN integration: assets.swiggy.com CNAME swiggy.cdn.cloudflare.com — the CDN's name is the canonical. (3) Load balancer: AWS ELB gives you a hostname (not a static IP), so you CNAME to it. Limitation: you can't use CNAME on a root/apex domain (swiggy.com) because CNAME replaces the entire DNS record set — use ALIAS or ANAME records for apex domains (AWS Route 53 supports this).

DNS — 60-second revision

  • DNS: domain name → IP address. "Internet's phonebook."
  • Resolution order: browser cache → OS cache → recursive resolver → root NS → TLD NS → authoritative NS → return IP.
  • A record: domain → IPv4. AAAA: domain → IPv6. CNAME: domain → another domain (alias). MX: email routing. TXT: verification/security.
  • TTL: how long the result is cached. Lower TTL before migrations so changes propagate faster.
  • Recursive resolver: your ISP's server or 8.8.8.8. Does all the legwork on your behalf.
  • Root name servers: 13 clusters worldwide. Know where .com, .in, etc. live.

What Happens When You Type a URL

The most famous interview question in networking. Combines DNS, TCP, TLS, HTTP, and browser rendering. Walk through all 7 steps without missing any.
must knowClassic question — practiced by every experienced engineer
  URL: https://www.swiggy.com/restaurants?city=bangalore

  ─────────────────────────────────────────────────────────────────
  STEP 1: URL Parsing
  Protocol: https | Host: www.swiggy.com | Path: /restaurants
  Query: city=bangalore | Port: 443 (default for https)

  ─────────────────────────────────────────────────────────────────
  STEP 2: DNS Resolution
  Browser cache → OS cache → Recursive resolver
  → Root NS → TLD NS → Swiggy's authoritative NS
  → Returns: 52.66.41.78

  ─────────────────────────────────────────────────────────────────
  STEP 3: TCP Connection
  Client → Server: SYN (seq=100)
  Server → Client: SYN-ACK (seq=300, ack=101)
  Client → Server: ACK (ack=301)
  Connection established on port 443

  ─────────────────────────────────────────────────────────────────
  STEP 4: TLS Handshake (HTTPS only)
  Client Hello: "I support TLS 1.3, here are my cipher suites"
  Server Hello: "Use TLS 1.3 + AES-256. Here's my certificate."
  Client: Verify certificate with CA. Generate session keys.
  → Symmetric encryption established. All subsequent traffic encrypted.

  ─────────────────────────────────────────────────────────────────
  STEP 5: HTTP Request
  GET /restaurants?city=bangalore HTTP/2
  Host: www.swiggy.com
  Cookie: session=abc123; pref=bangalore
  Accept: text/html

  ─────────────────────────────────────────────────────────────────
  STEP 6: Server Processing
  NGINX receives → Routes to Node.js/Python service
  → Query DB / Redis cache for Bangalore restaurants
  → Build response (HTML or JSON)
  → Return HTTP 200 with body

  ─────────────────────────────────────────────────────────────────
  STEP 7: Browser Rendering
  Parse HTML → Build DOM
  Discover CSS, JS, images → Parallel requests for each
  Parse CSS → Build CSSOM
  DOM + CSSOM → Render tree → Layout → Paint → Composite

  Subsequent resource requests (JS, CSS):
  Check DNS cache → TCP connection may be reused (keep-alive)
  → If cached (304 Not Modified) → Use browser cache
Interview Q&A — URL Flow
What happens when you type a URL in a browser and press Enter? Walk through every step. ▼
Strong answer — walk through all 7 steps1. URL Parsing: browser parses scheme (https), host (swiggy.com), path, query string, port (443 for HTTPS, 80 for HTTP). 2. Interview Q&A — TLS/HTTPS
What does HTTPS provide that HTTP doesn't? ▼
Strong answerHTTPS = HTTP + TLS. TLS adds three guarantees: (1) Confidentiality: all data encrypted — an attacker intercepting traffic sees only ciphertext, not your passwords or tokens. (2) Integrity: HMAC detects any tampering in transit — if an attacker modifies a packet, the hash breaks, receiver detects it. (3) Authentication: the server's certificate proves you're really talking to swiggy.com, not an imposter. The browser verifies the certificate was signed by a trusted CA and issued for this domain. HTTP has none of these — data is plaintext, any network observer can read credentials, and there's no way to verify you're talking to the real server.
Why does TLS use asymmetric crypto for handshake and symmetric for data? ▼
Strong answerAsymmetric crypto (RSA, ECC) is mathematically expensive — 100-1000x slower than symmetric crypto (AES). But asymmetric has a key advantage: you can share the public key openly without security risk. The handshake uses asymmetric crypto (Diffie-Hellman key exchange) to safely establish a shared secret over an untrusted network — without ever transmitting the secret itself. Once both sides have agreed on the session key (symmetric), all actual data transmission uses fast AES encryption. The session key is ephemeral (generated fresh per connection) — this is "Forward Secrecy" — even if the server's private key is later compromised, past sessions can't be decrypted because the session keys were never stored.

  • TLS provides: confidentiality (encryption), integrity (HMAC tamper detection), authentication (certificate verification).

  • Asymmetric (RSA/ECC): for authentication and key exchange only (slow). Symmetric (AES): for actual data (fast).
  • Certificate chain: server cert → intermediate CA → root CA (trusted by browser).
  • Forward secrecy: ephemeral session keys — past sessions can't be decrypted even if private key is compromised.
  • Let's Encrypt: free CA. Use certbot for auto-renewing certificates on your EC2 deployment.

CORS — Cross-Origin Resource Sharing

The most asked networking concept in full stack interviews. Why it exists, what "origin" means, preflight requests, and how to configure it in Express. Every full stack developer has seen CORS errors.
must knowYou've hit CORS errors — now understand why they happen
01What is an "origin"?

An origin = scheme + hostname + port. Two URLs have the same origin ONLY if all three match exactly. 

  Base URL: https://swiggy.com:443/restaurants

  https://swiggy.com/orders       → SAME ORIGIN (same scheme, host, default port)
  http://swiggy.com/              → DIFFERENT (different scheme: http vs https)
  https://api.swiggy.com/         → DIFFERENT (different hostname: api.swiggy.com)
  https://swiggy.com:3000/        → DIFFERENT (different port: 3000 vs 443)
  https://swiggy.com/profile      → SAME ORIGIN (path doesn't matter)
02The Same-Origin Policy — why CORS exists

The Same-Origin Policy (SOP) is a browser security mechanism: JavaScript on page A cannot make requests to a different origin B. Why? Without SOP, malicious.com could load swiggy.com and use your cookies to place orders on your behalf (CSRF).

But legitimate cross-origin requests are needed: your React app on localhost:3000 needs to call your API on localhost:8080. Your frontend on app.mysite.com calls api.mysite.com. CORS is the mechanism that lets servers explicitly allow cross-origin requests from trusted origins.

03How CORS works — simple vs preflight
  SIMPLE REQUEST (GET, HEAD, POST with simple headers):
  ─────────────────────────────────────────────────────
  Browser: GET https://api.swiggy.com/restaurants
  Browser adds: Origin: https://swiggy.com

  Server responds with:
  Access-Control-Allow-Origin: https://swiggy.com  ← "Yes, I allow this origin"

  Browser: "Server said OK → deliver response to JS."

  ─────────────────────────────────────────────────────
  PREFLIGHT REQUEST (PUT, DELETE, or custom headers):
  ─────────────────────────────────────────────────────
  Browser first sends: OPTIONS https://api.swiggy.com/orders
  Origin: https://swiggy.com
  Access-Control-Request-Method: DELETE
  Access-Control-Request-Headers: Authorization, Content-Type

  Server responds (preflight response):
  Access-Control-Allow-Origin: https://swiggy.com
  Access-Control-Allow-Methods: GET, POST, PUT, DELETE
  Access-Control-Allow-Headers: Authorization, Content-Type
  Access-Control-Max-Age: 86400  ← cache preflight for 24 hours

  Browser: "Server approved the request method and headers."
  Browser: Now sends the actual DELETE request.

  Why preflight? Browser asks permission before sending a potentially
  destructive request. Server gets to say "no" before data is sent.
04Configuring CORS in Express (Node.js)
const cors = require('cors');

// Option 1: Allow specific origin (production)
app.use(cors({
    origin: 'https://app.mysite.com',  // ONLY this origin allowed
    methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH'],
    allowedHeaders: ['Content-Type', 'Authorization'],
    credentials: true  // required for cookies/auth headers
}));

// Option 2: Allow multiple origins
const allowedOrigins = [
    'https://app.mysite.com',
    'https://admin.mysite.com',
    'http://localhost:3000'  // dev only
];
app.use(cors({
    origin: (origin, callback) => {
        if (!origin || allowedOrigins.includes(origin)) {
            callback(null, true);  // allow
        } else {
            callback(new Error('Not allowed by CORS'));
        }
    },
    credentials: true
}));

// NEVER do this in production:
app.use(cors({ origin: '*', credentials: true }));
// origin: '*' with credentials: true is a CORS spec violation
// Browser will block it. '*' means "allow anyone" — bad for APIs.
CORS is browser-only — it's NOT server security: CORS only affects browser-based requests. curl, Postman, and server-to-server requests bypass CORS completely. This is a common misconception — "I added CORS so my API is secure." No! CORS prevents your JavaScript from being misused in a browser. A malicious SERVER can still call your API directly without any CORS headers. API security must come from authentication (JWT, API keys), not CORS.
Interview Q&A — CORS
What is CORS? Why does it exist? ▼
Strong answerCORS (Cross-Origin Resource Sharing) is a browser security mechanism built on top of the Same-Origin Policy. The SOP prevents JavaScript from making requests to a different origin (different scheme, hostname, or port) — it protects against CSRF: malicious.com's JavaScript can't use your cookies to make requests to bank.com on your behalf. But legitimate cross-origin requests are needed (React frontend at app.mysite.com calling api.mysite.com). CORS allows servers to explicitly declare which origins they accept. The browser checks the response headers (Access-Control-Allow-Origin) and either delivers the response to JavaScript or blocks it. Key point: CORS is browser-enforced only — curl and Postman bypass it. It's not API security — it's browser-level protection against script misuse.
What is a preflight request? When does the browser send one? ▼
Strong answerA preflight request is an HTTP OPTIONS request the browser sends before a potentially state-modifying cross-origin request. The browser asks permission before sending the actual request. Preflight is triggered by: (1) Methods other than GET, POST, HEAD (e.g., DELETE, PUT). (2) POST with Content-Type other than application/x-www-form-urlencoded, multipart/form-data, or text/plain. (3) Custom headers like Authorization. The preflight OPTIONS request includes Access-Control-Request-Method and Access-Control-Request-Headers. The server must respond with appropriate Access-Control-Allow-* headers. Only if the server approves does the browser send the actual request. Access-Control-Max-Age caches the preflight result so subsequent requests don't need another OPTIONS round trip.
Why does CORS require credentials: true separately from the origin? ▼
Strong answerBy default, cross-origin requests don't include credentials (cookies, Authorization headers). This is the safe default — you don't want every cross-origin fetch to automatically send your authentication credentials. To include credentials in cross-origin requests, you must: (1) Set credentials: 'include' in the fetch options (frontend), and (2) The server must respond with Access-Control-Allow-Credentials: true AND Access-Control-Allow-Origin must be a specific origin, NOT '*'. The reason you can't use '*' with credentials: a wildcard would mean "accept credentials from any website" — any malicious site could make credentialed requests to your API using the victim's cookies. Requiring a specific origin with credentials explicitly whitelists trusted frontends.

  • Origin = scheme + hostname + port. All three must match for same-origin.
  • Same-Origin Policy: browser blocks JS from making cross-origin requests. Prevents CSRF.
  • CORS: server tells browser which origins it allows via Access-Control-Allow-Origin response header.
  • Preflight: browser sends OPTIONS first for non-simple requests (DELETE, PUT, custom headers). Server must respond with allowed methods/headers.
  • Express: cors({ origin: 'https://app.mysite.com', credentials: true }).
  • CORS is BROWSER ONLY. curl/Postman bypass it. CORS is not API security — use authentication for that.
  • origin: '*' + credentials: true = invalid. Specific origin required when using credentials.

WebSocket

Full-duplex persistent connection over a single TCP connection. How the upgrade handshake works. When WebSocket vs HTTP vs Server-Sent Events. Directly connects to your CollabDocs project.
must knowYou used Socket.io in CollabDocs — understand what it uses underneath
01Why WebSocket exists — the problem with HTTP for real-time

HTTP is request-response: client sends request, server sends response, done. To get real-time updates via HTTP, you'd need to poll — repeatedly send "any updates?" requests every second. Wasteful: 99% of polls return "no new data" but each one uses network and server resources.

WebSocket solves this: establish a single persistent TCP connection, then both client and server can send messages to each other at any time without re-establishing the connection. True bidirectional, full-duplex communication.

02The WebSocket Upgrade handshake
  WebSocket starts as HTTP then UPGRADES:

  Client → Server (HTTP Request):
  GET /ws HTTP/1.1
  Host: api.collabdocs.com
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
  Sec-WebSocket-Version: 13

  Server → Client (HTTP 101):
  HTTP/1.1 101 Switching Protocols
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
  ← The accept value is computed from the key (SHA-1 + base64)

  Connection now UPGRADED from HTTP to WebSocket protocol.
  Both sides can now send frames in either direction at any time.
  Connection remains open until explicitly closed.

  Port: same as HTTP/HTTPS. ws:// uses port 80. wss:// uses 443 (TLS).
  NGINX: requires Upgrade + Connection headers to proxy WebSocket correctly
  (This is why your CollabDocs NGINX config has those headers!)

04Socket.io — what it adds on top of WebSocket

Socket.io is not the same as WebSocket. Socket.io uses WebSocket when available, but falls back to HTTP long-polling when WebSocket is blocked by proxies or firewalls. It also adds: rooms (namespaced channels), acknowledgements (message receipts), reconnection logic (auto-reconnects with exponential backoff), and a multiplexing namespace system.

In your CollabDocs project, Socket.io handles: joining document rooms (socket.join(docId)), broadcasting edits to all users in a room (io.to(docId).emit('edit', data)), and reconnecting clients whose connections drop. 

// Socket.io server — CollabDocs pattern
io.on('connection', (socket) => {
    console.log(`User connected: ${socket.id}`);

    socket.on('join-document', (docId) => {
        socket.join(docId);                  // join the document's room
        socket.to(docId).emit('user-joined', socket.id);
    });

    socket.on('document-edit', (data) => {
        // Broadcast to all OTHER users in the same room
        socket.to(data.docId).emit('apply-edit', data);
        // socket.to() excludes the sender — they already applied the edit
    });

    socket.on('disconnect', () => {
        // Socket.io auto-cleans up rooms on disconnect
    });
});

// Socket.io client
const socket = io('https://api.collabdocs.com');
socket.emit('join-document', 'doc_abc');
socket.on('apply-edit', (data) => { applyEditToEditor(data); });
Interview Q&A — WebSocket
What is WebSocket? How does it differ from HTTP? ▼
Strong answerWebSocket is a protocol that enables persistent, bidirectional, full-duplex communication over a single TCP connection. Unlike HTTP (which is request-response — client always initiates, one request per response), WebSocket allows either side to send data at any time without waiting for the other to ask. The connection starts as HTTP, then upgrades: client sends an Upgrade: websocket header, server responds with 101 Switching Protocols, and the connection switches from HTTP to the WebSocket protocol. After that, no HTTP overhead — just lightweight WebSocket frames. Use case: real-time collaborative editing (CollabDocs), chat applications, live dashboards, online gaming. I used it in my CollabDocs project where Socket.io (WebSocket-based) broadcasts document edits to all connected users in a room.
How would you scale a WebSocket server to handle 100,000 concurrent connections? ▼
Strong answerThe challenge: WebSocket connections are stateful — each server maintains open connections. If you have 3 servers and user A is on server 1, user B is on server 2, they can't communicate directly because their WebSockets are on different servers. Solution: Redis Pub/Sub as a message bus between servers. When user A's edit arrives at server 1, server 1 publishes to a Redis channel for that document. All other servers subscribe to that channel and forward the event to their connected users in that room. Socket.io has a built-in Redis adapter (@socket.io/redis-adapter) that does this automatically. Infrastructure: multiple Node instances behind a load balancer with sticky sessions (a user always routes to the same server for their WebSocket connection) OR the Redis pub/sub pattern without sticky sessions. Each Node process can handle tens of thousands of WebSocket connections (Node's event loop is efficient for I/O-bound work).

WebSocket — 60-second revision

  • WebSocket: persistent TCP connection. Full-duplex — both sides send at any time.
  • Upgrade handshake: HTTP request with Upgrade: websocket → server 101 Switching Protocols → protocol switched.
  • WebSocket vs HTTP: HTTP = request-response (client initiates). WebSocket = bidirectional persistent.
  • SSE: server → client only. Simple. Use for news feeds, live scores, one-way push.
  • WebSocket: bidirectional. Use for chat, collaborative editing, gaming.
  • Socket.io: WebSocket + fallback + rooms + reconnection + acknowledgements. Not vanilla WebSocket.
  • Scaling: Redis pub/sub across multiple Node instances. Socket.io Redis adapter handles this.
  • NGINX: needs Upgrade and Connection headers to proxy WebSocket (already in your CollabDocs config).

All Networks Interview Questions

20 questions across all networking topics. Answer out loud without looking first.
Complete Networks Q&A bank — 20 questions
1. What is the OSI model? Which layers does a full stack developer primarily work at? ▼
Answer7 layers: Physical, Data Link, Network, Internet, Transport, Session, Presentation, Application (bottom to top). Full stack developers work primarily at: Layer 7 (Application) — HTTP, WebSocket, REST APIs, your Express/Spring Boot code. Layer 4 (Transport) — TCP vs UDP choice, ports. Layer 3 (Network) — IP addresses, DNS resolution results. The OS and hardware handle layers 1-3 automatically. Knowing what protocol lives at each layer helps you debug: 502 Bad Gateway = layer 7 issue. Packet loss = layer 3/4 issue. SSL certificate error = layer 6 (Presentation).
2. Explain the TCP three-way handshake. Why is it three steps? ▼
AnswerSYN: client sends synchronize packet with its initial sequence number. SYN-ACK: server acknowledges client's ISN+1 and sends its own ISN. ACK: client acknowledges server's ISN+1. Three steps because two-way confirmation is needed: both sides must verify they can both send AND receive. Two steps only confirms client→server direction. The third step (client's ACK) confirms client received server's SYN-ACK, establishing true bidirectional communication. After three steps: connection is ESTABLISHED, data can flow.
3. What is the difference between TCP and UDP? Give a use case for each. ▼
AnswerTCP: reliable, ordered delivery. Three-way handshake. Retransmits lost packets. Slower. Use for: HTTP/HTTPS, SSH, email, file transfer — when data integrity is critical. UDP: connectionless, no guarantee of delivery or order. Minimal overhead. Faster. Use for: DNS (speed matters, simple retry if lost), video streaming (slight frame loss is acceptable, latency is not), VoIP, online gaming (old packet useless by the time retransmitted). HTTP/3 uses QUIC (over UDP) with application-layer reliability — best of both worlds for modern web.
4. What is the difference between GET, POST, PUT, and PATCH? ▼
AnswerGET: retrieve, no body, safe (read-only), idempotent, cacheable. POST: create, has body, not idempotent (each call creates a new resource). PUT: replace entire resource, idempotent (sending same body multiple times = same result). PATCH: partial update, send only changed fields. DELETE: remove resource, idempotent. Idempotent: calling multiple times produces same result. Safe: doesn't modify server state. PUT vs PATCH: PUT replaces entirely (omitted fields removed), PATCH updates only sent fields.
5. What is the difference between 401 and 403? ▼
Answer401 Unauthorized: server cannot identify who you are. No token, expired JWT, invalid signature. Despite the name, it's about AUTHENTICATION. Client should authenticate and retry. 403 Forbidden: server knows who you are but you don't have permission. Valid credentials, wrong role or insufficient privileges. This is about AUTHORIZATION. Re-authenticating won't help — you need different permissions. In Spring Boot: JWT missing/expired → 401 from JWT filter. ROLE_USER hitting ROLE_ADMIN endpoint → 403 from @PreAuthorize.
6. Walk me through what happens when you type a URL and press Enter. ▼
Answer1. URL parsing: scheme, host, path, query string, port. 2. DNS resolution: browser cache → OS cache → recursive resolver → root NS → TLD NS → authoritative NS → returns IP. 3. TCP handshake: SYN → SYN-ACK → ACK on port 443. 4. TLS handshake: cipher negotiation → server cert verification → DH key exchange → symmetric session key. 5. HTTP request: GET with headers (Host, Cookie, Accept). 6. Server processing: NGINX routes to app server → DB/cache query → build response → return 200. 7. Browser renders: HTML → DOM. CSS → CSSOM. Parallel asset fetches. Render tree → layout → paint.
7. What is DNS? Explain the resolution hierarchy. ▼
AnswerDNS translates domain names to IP addresses. Resolution: browser cache → OS cache → recursive resolver (ISP's or 8.8.8.8). If resolver cache miss: queries root name server (who handles .com?) → TLD name server (.com: who handles swiggy.com?) → authoritative name server (Swiggy's DNS: what's the IP for api.swiggy.com?) → returns A record (IP). Recursive resolver returns and caches the result for TTL seconds. DNS record types: A (domain→IPv4), AAAA (IPv6), CNAME (alias to another domain), MX (email), TXT (verification, SPF).
8. What is CORS? Why does it exist? How do you configure it in Express? ▼
AnswerCORS (Cross-Origin Resource Sharing) is a browser mechanism that controls cross-origin requests (different scheme, hostname, or port). Never use origin: '*' with credentials: true (spec violation). Preflight: browser sends OPTIONS first for DELETE/PUT/custom headers. Server must respond with allowed methods/headers. CORS is browser-only — Postman bypasses it. CORS is not security — use JWT for that.
9. What does HTTPS provide that HTTP doesn't? ▼
AnswerHTTPS = HTTP + TLS. TLS provides three guarantees: Confidentiality (AES symmetric encryption — eavesdroppers see ciphertext), Integrity (HMAC detects any in-transit tampering), Authentication (X.509 certificate verified against trusted CAs — proves you're talking to the real server, not an impersonator). HTTP has none: data is plaintext, anyone can intercept passwords/tokens, and there's no verification that the server is who it claims to be. TLS uses asymmetric crypto (RSA/ECC) only for the handshake (key exchange + authentication) because it's expensive. Actual data uses fast symmetric AES with the negotiated session key.
10. What is a WebSocket? How does it differ from regular HTTP? ▼
AnswerWebSocket is a persistent, bidirectional TCP connection. Unlike HTTP (client initiates every exchange, one response per request), WebSocket allows either side to send data at any time. Starts as HTTP then upgrades: client sends Upgrade: websocket header, server responds 101 Switching Protocols, protocol switches. After upgrade: lightweight WebSocket frames instead of HTTP overhead. Use when bidirectional real-time communication is needed: collaborative editing, chat, gaming, live trading. Used Socket.io (WebSocket-based) in my CollabDocs project — when a user edits, the server broadcasts to all other users in the document room immediately via persistent WebSocket connections.
11. What is a preflight request? When does the browser send one? ▼
AnswerA preflight is an HTTP OPTIONS request the browser sends before a potentially state-modifying cross-origin request, to ask permission. Triggered by: non-simple methods (DELETE, PUT, PATCH), POST with non-standard Content-Type, or custom headers (Authorization). Options request includes Access-Control-Request-Method and Access-Control-Request-Headers. Server must respond with Access-Control-Allow-Methods, Access-Control-Allow-Headers, and Access-Control-Allow-Origin. If approved, browser sends the actual request. Access-Control-Max-Age caches the preflight result (avoids sending OPTIONS on every request). If server doesn't include the right CORS headers in its preflight response, the browser blocks the actual request.
12. What is HTTP/2 multiplexing? What problem does it solve? ▼
AnswerHTTP/1.1 head-of-line blocking: browsers open 6 TCP connections per origin, each handling one request at a time. A slow request blocks others on that connection. HTTP/2 multiplexing: multiple requests and responses interleaved on a single TCP connection using binary frames. Request A's slow response doesn't block requests B, C, D. Also: header compression (HPACK) eliminates sending repeated headers like User-Agent on every request. Server push: server can proactively send resources the client will need. Result: fewer TCP connections, better latency for pages with many assets (JS, CSS, fonts, images). HTTP/3 (QUIC) addresses the remaining TCP-level head-of-line blocking.
13. What is the difference between 301 and 302 redirect? ▼
Answer301 Moved Permanently: browser caches this redirect permanently. Future requests go directly to the new URL without checking the old one. Search engines transfer "link juice" to the new URL. Use for: permanently moved content, HTTP → HTTPS redirect, domain changes. 302 Found (Temporary Redirect): browser does NOT cache — always asks the original URL first, then follows the redirect. Use for: login redirect (redirect to login page, then back after auth), maintenance mode (redirect to maintenance page temporarily), A/B testing. Choosing wrong: using 302 when you mean 301 = extra DNS + HTTP roundtrip on every visit. Using 301 when you mean 302 = stuck with the redirect even after you change it back.
14. What is the purpose of the Host header in HTTP? ▼
AnswerThe Host header is mandatory in HTTP/1.1. It tells the server which virtual host (domain) the request is for. One server (one IP) can host multiple websites — NGINX uses the Host header to route to the correct site. Example: IP 52.66.1.1 hosts both swiggy.com and swiggy-business.com. When NGINX receives a request, it checks Host: swiggy.com and routes to Swiggy's frontend, or Host: swiggy-business.com and routes to the business portal. Without the Host header, the server wouldn't know which site to serve. This is called "virtual hosting" and is fundamental to how shared hosting works. NGINX's server_name directive matches against this header.
15. What is a CDN and how does it work? ▼
AnswerCDN (Content Delivery Network): a geographically distributed network of servers (edge nodes) that cache and serve static content (images, CSS, JS) from locations close to users. How it works: User in Mumbai requests swiggy.com/logo.png. Instead of going to Swiggy's origin server (maybe in Bangalore), the request goes to a CDN edge node in Mumbai. If cached: served immediately (~5ms latency). If not cached (cache miss): edge node fetches from origin, caches it, serves it. Next request from Mumbai: cache hit. Benefits: reduced latency (user gets content from nearby server), reduced origin load (origin only serves cache misses), DDoS protection (attack traffic absorbed by CDN), global availability. Cloudflare, AWS CloudFront, Fastly are major CDNs. Static assets should always go through a CDN in production.
16. What is the difference between WebSocket and Server-Sent Events (SSE)? ▼
AnswerSSE (Server-Sent Events): one-directional push from server to client over a persistent HTTP connection. Client can't send messages through the SSE connection. Browser has built-in EventSource API. Auto-reconnects. Works over regular HTTP — no protocol upgrade needed. Use for: live score updates, stock tickers, notifications feed. WebSocket: bidirectional full-duplex. Client can also send messages to server. More complex. Requires protocol upgrade (ws:// or wss://). Use for: chat, collaborative editing, gaming — anything requiring two-way real-time communication. If you only need server-push, SSE is simpler and sufficient. If you need bidirectional communication (like collaborative document editing where user's edits must go to the server), WebSocket is required.
17. What is a TLS certificate? What does the browser verify? ▼
AnswerA TLS (X.509) certificate is a digital document that binds a public key to a domain name. Issued by a Certificate Authority (CA) — the CA's signature on the certificate proves the CA vouches for this domain owning this public key. Browser verification: (1) Is the certificate issued for THIS domain? (CN or SAN field must match the hostname). (2) Is it signed by a CA I trust? (Browser has a built-in list of ~150 root CAs). (3) Is it within its validity period? (Not before, Not after dates). (4) Is it revoked? (OCSP or CRL check). If all pass: padlock icon, secure connection. If any fail: browser shows warning. Let's Encrypt issues free certificates valid for 90 days, auto-renewable via certbot. Used in your EC2 deployment.
18. What is long polling? How does it compare to WebSocket? ▼
AnswerLong polling: client sends a request, server holds it open (doesn't respond immediately) until new data is available or a timeout occurs. When data arrives, server responds, client immediately sends another request. Simulates push using regular HTTP. Advantages: works everywhere (no WebSocket required, works through all proxies). Disadvantages: HTTP overhead for each "push" (headers retransmitted), connection management overhead, latency (new connection setup after each response). WebSocket: persistent connection, minimal frame overhead, true bidirectional. Long polling was the fallback strategy before WebSocket was widely supported — Socket.io still falls back to long polling if WebSocket is blocked. For new applications with modern browser support, use WebSocket (or SSE for one-way push).
19. What is the difference between http:// and https:// in terms of ports? ▼
AnswerHTTP uses port 80 by default. HTTPS uses port 443 by default. These are convention — you can run HTTP on any port. When you see https://swiggy.com (no port specified), the browser connects to port 443. When you see http://localhost:3000, it explicitly specifies port 3000 (non-default). In your projects: Node.js likely runs on port 3000 or 8080, NGINX on port 80/443. NGINX proxies external HTTPS traffic (443) to internal Node HTTP (3000) — this is why you run Node without HTTPS and let NGINX handle TLS termination. WebSocket equivalent: ws:// uses port 80, wss:// uses port 443 (WebSocket over TLS).
20. How do cookies work? What is an HttpOnly cookie? ▼
AnswerCookies are small key-value pairs stored by the browser and automatically sent on every request to the matching domain+path. Server sets them via Set-Cookie response header: Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Max-Age=86400. Browser stores and includes them in all subsequent requests via the Cookie header. HttpOnly: cookie cannot be accessed by JavaScript (document.cookie returns nothing). This is critical for session tokens — prevents XSS attacks from stealing the cookie even if attacker can execute JS on your page. Secure: cookie only sent over HTTPS. SameSite=Strict: cookie only sent on same-site requests — prevents CSRF. In your projects: JWT refresh tokens should be HttpOnly, Secure cookies. Access tokens stored in memory (not localStorage — vulnerable to XSS) or as HttpOnly cookies.
