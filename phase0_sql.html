SQL doesn't execute in the order you write it. This single insight explains most SQL confusion — why you can't use a SELECT alias in WHERE, why you can use it in ORDER BY, why HAVING exists.

02SQL Execution Order — the most important concept

You write SQL in this order: SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT. But SQL executes it in a completely different order. This is why many SQL errors happen.

  • 1
    FROM + JOIN
    First: identify the source tables. Build the combined row set by joining tables together.
  • 2
    WHERE
    Filter rows BEFORE grouping. Cannot use SELECT aliases here (SELECT hasn't run yet!) or aggregate functions (no grouping yet).
  • 3
    GROUP BY
    Collapse rows into groups. Reduces a set of rows to one row per group.
  • 4
    HAVING
    Filter GROUPS after aggregation. CAN use aggregate functions (COUNT, SUM, AVG). This is why HAVING exists — WHERE can't filter on aggregates.
  • 5
    SELECT
    Compute the output columns. Aliases defined here. This is step 5 — so aliases aren't available in WHERE (step 2) or GROUP BY (step 3).
  • 6
    ORDER BY
    Sort the result. CAN use SELECT aliases (SELECT already ran in step 5). PostgreSQL allows this; standard SQL technically doesn't.
  • 7
    LIMIT / OFFSET
    Restrict the number of rows returned. Always last — first sort, then limit.
Why you can't use a SELECT alias in WHERE: SELECT runs at step 5, WHERE at step 2. The alias doesn't exist when WHERE executes. This catches many beginners. Fix: use a subquery or CTE, or repeat the expression in WHERE. PostgreSQL sometimes allows it, but it's not guaranteed behavior.
03Core SELECT — filtering, sorting, limiting
SELECT — the building blocks
-- Basic SELECT with aliases
SELECT
    id,
    name,
    UPPER(city) AS city_upper,
    ROUND(rating, 1) AS avg_rating
FROM restaurants
WHERE city = 'Bangalore'
  AND rating >= 4.0
  AND cuisine IN ('Indian', 'Italian', 'Chinese')
  AND is_active = TRUE
ORDER BY rating DESC, name ASC  -- sort by rating first, then name
LIMIT 10 OFFSET 20;              -- page 3 (0-based, 10 per page)

-- DISTINCT: remove duplicate rows
SELECT DISTINCT city FROM restaurants;

-- LIKE: pattern matching
-- '%text%' = contains. 'text%' = starts with. '%text' = ends with
SELECT * FROM restaurants WHERE name LIKE '%Biryani%';

-- BETWEEN: inclusive range
SELECT * FROM orders
WHERE amount BETWEEN 100 AND 500
  AND placed_at >= '2024-01-01';

-- IS NULL / IS NOT NULL (never use = NULL — it doesn't work)
SELECT * FROM orders WHERE status IS NULL;
-- NULL = NULL → returns NULL (falsy), not TRUE. Always use IS NULL.

-- CASE WHEN: conditional logic in SELECT
SELECT
    id,
    amount,
    CASE
        WHEN amount < 200  THEN 'small'
        WHEN amount < 1000 THEN 'medium'
        ELSE                      'large'
    END AS order_size
FROM orders;

Aggregate functions — operate on groups of rows
-- COUNT, SUM, AVG, MIN, MAX
SELECT

    COUNT(DISTINCT user_id) AS unique_users,

Interview Q&A — SELECT basics
In what order does SQL execute a query? Why does this matter? ▼
Strong answerSQL executes in this order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This matters because: (1) You can't use a SELECT alias in WHERE (SELECT runs later). (2) You can't use aggregate functions in WHERE (no grouping yet). (3) HAVING exists precisely because WHERE can't filter on aggregated values. (4) You CAN use SELECT aliases in ORDER BY because SELECT ran first. Understanding this order explains most SQL errors and helps you write correct queries faster. Example: SELECT city AS c FROM restaurants WHERE c = 'Bangalore' → ERROR because WHERE runs before SELECT creates the alias 'c'. Fix: WHERE city = 'Bangalore'.
What is the difference between WHERE and HAVING? ▼
Strong answerWHERE filters individual rows BEFORE grouping. It cannot use aggregate functions (COUNT, SUM, AVG) because rows haven't been grouped yet. HAVING filters groups AFTER the GROUP BY aggregation. It CAN use aggregate functions because groups already exist. Example: SELECT restaurant_id, COUNT(*) as order_count FROM orders WHERE status = 'delivered' GROUP BY restaurant_id HAVING COUNT(*) > 10 ORDER BY order_count DESC. WHERE filters out non-delivered orders first. HAVING then filters to only restaurants with more than 10 delivered orders. If you try WHERE COUNT(*) > 10 → SQL error: aggregate functions not allowed in WHERE clause. Performance note: WHERE is more efficient — it reduces rows before grouping, so fewer rows need to be aggregated.
Why doesn't `= NULL` work in SQL? What should you use instead? ▼
Strong answerNULL represents an unknown value in SQL. Comparing anything to NULL using = returns NULL (unknown), not TRUE or FALSE. NULL = NULL → NULL. NULL = 5 → NULL. In a WHERE clause, NULL is treated as falsy — the row is filtered out. So WHERE column = NULL never returns any rows. Always use IS NULL or IS NOT NULL. The same applies to != NULL — use IS NOT NULL instead. This is called three-valued logic in SQL: TRUE, FALSE, and UNKNOWN (NULL). It's one of the most common SQL bugs. Even COUNT behaves specially: COUNT(*) counts all rows including NULLs, COUNT(column) only counts non-NULL values in that column.

SELECT basics — 60-second revision

  • Execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
  • Cannot use SELECT aliases in WHERE or GROUP BY (SELECT runs later). Can use in ORDER BY.
  • WHERE: filters rows before grouping. No aggregates. HAVING: filters groups after aggregation. Aggregates OK.
  • NULL: = NULL doesn't work. Use IS NULL and IS NOT NULL. COUNT(*) includes NULLs, COUNT(col) excludes them.
  • LIKE: '%text%' contains, 'text%' starts with, '%text' ends with. Case-sensitive in PostgreSQL.
  • CASE WHEN ... THEN ... ELSE ... END: conditional expression in SELECT (like ternary operator).

JOINs — Combining Tables

INNER, LEFT, RIGHT, FULL OUTER — know what each returns when rows don't match. Self joins, cross joins. Write a JOIN from scratch in an interview without thinking.
must knowJOINs appear in every SQL interview — write them cold
01The four JOIN types — visually
INNER JOIN
🔴⭕🔵 → ⭕
Only rows where the condition matches in BOTH tables. Unmatched rows from either table are dropped.
LEFT JOIN
🔴⭕🔵 → 🔴⭕
All rows from LEFT table + matching rows from RIGHT. Unmatched right-side columns become NULL.
RIGHT JOIN
🔴⭕🔵 → ⭕🔵

02JOIN queries — each type with real examples
INNER JOIN — orders with their user and restaurant details
SELECT
    o.id          AS order_id,
    u.name        AS customer,
    r.name        AS restaurant,
    o.amount,
    o.status,
    o.placed_at
FROM orders o
INNER JOIN users u        ON o.user_id = u.id
INNER JOIN restaurants r ON o.restaurant_id = r.id
WHERE o.status = 'delivered'
ORDER BY o.placed_at DESC
LIMIT 20;
-- Only returns orders where BOTH user AND restaurant exist
-- Orders with NULL user_id or restaurant_id are excluded
LEFT JOIN — all restaurants, including those with no orders
-- "Show me all restaurants and how many orders they've received"
-- Including restaurants that have ZERO orders (new restaurants)
SELECT
    r.id,
    r.name,
    r.city,
    COUNT(o.id) AS order_count,
    COALESCE(SUM(o.amount), 0) AS total_revenue
FROM restaurants r
LEFT JOIN orders o ON r.id = o.restaurant_id
                  AND o.status = 'delivered'  -- condition on the JOIN, not WHERE
GROUP BY r.id, r.name, r.city
ORDER BY total_revenue DESC;

-- IMPORTANT: if you put "AND o.status = 'delivered'" in WHERE instead of ON,
-- it converts the LEFT JOIN to an INNER JOIN for those rows!
-- The WHERE clause filters AFTER joining — restaurants with no orders
-- would have o.status = NULL which doesn't match 'delivered', filtering them out.
-- Putting the condition on JOIN keeps all restaurants, filtering only which
-- orders are matched (not which restaurants are included).
FULL OUTER JOIN + SELF JOIN + CROSS JOIN
-- FULL OUTER JOIN: find users with no orders AND restaurants with no users
SELECT
    u.name AS user_name,
    r.name AS restaurant_name,
    o.amount
FROM users u
FULL OUTER JOIN orders o       ON u.id = o.user_id
FULL OUTER JOIN restaurants r  ON o.restaurant_id = r.id;
-- Rows with NULL on left: user exists but no orders
-- Rows with NULL on right: restaurant exists but no orders

-- SELF JOIN: compare rows within the same table
-- "Find pairs of restaurants in the same city"
SELECT
    a.name AS restaurant_1,
    b.name AS restaurant_2,
    a.city
FROM restaurants a
INNER JOIN restaurants b
    ON a.city = b.city
   AND a.id < b.id  -- avoid duplicates (a,b) and (b,a) and (a,a)
ORDER BY a.city;

-- CROSS JOIN: every combination of rows (cartesian product)
-- Use sparingly — can produce massive results
SELECT u.name, r.name FROM users u CROSS JOIN restaurants r;
-- 100 users × 50 restaurants = 5000 rows

Self JOIN — employees and their managers
-- employees table: id, name, manager_id (FK to same table)
SELECT
    emp.name   AS employee,
    mgr.name   AS manager
FROM employees emp
LEFT JOIN employees mgr ON emp.manager_id = mgr.id;
-- LEFT JOIN: includes CEO who has no manager (manager column = NULL)
-- INNER JOIN would exclude the top-level employee with no manager
Interview Q&A — JOINs
What is the difference between INNER JOIN and LEFT JOIN? ▼
Strong answerINNER JOIN returns only rows where the join condition matches in BOTH tables. If an order has no matching user (user deleted), that order is excluded. LEFT JOIN returns ALL rows from the LEFT table regardless of whether there's a match in the right table. Where there's no match, the right table's columns are NULL. Use LEFT JOIN when you want to include all records from one table even if no related records exist in the other — e.g., all restaurants including those with zero orders. INNER JOIN when you only care about records that have matches in both tables. Never use RIGHT JOIN — flip the tables and use LEFT JOIN instead (clearer to read). Example: LEFT JOIN vs WHERE clause gotcha — putting the filter condition in WHERE instead of ON converts a LEFT JOIN to effectively an INNER JOIN for filtered rows.
Write a query to find all users who have never placed an order. ▼
Strong answer — multiple approachesApproach 1 (LEFT JOIN + NULL check): SELECT u.id, u.name FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.id IS NULL. The LEFT JOIN includes all users. For users with no orders, o.id will be NULL. WHERE o.id IS NULL filters to only those users. Approach 2 (NOT EXISTS — often more readable): SELECT id, name FROM users u WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id). Approach 3 (NOT IN — careful with NULLs): SELECT id, name FROM users WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL). NOT IN with NULLs in the subquery returns no results — always add the IS NOT NULL filter. LEFT JOIN + NULL check or NOT EXISTS are generally preferred in production.
What is a self join? When would you use it? ▼
Strong answerA self join joins a table to itself using two different aliases. Use when data within a table has a relationship to other rows in the same table. Classic cases: (1) Employee-manager hierarchy: employees table has manager_id referencing another row in the same table. JOIN employees emp ON employees mgr ON emp.manager_id = mgr.id — LEFT JOIN to include top-level employees who have no manager. (2) Finding duplicate records: JOIN table a ON a.email = b.email AND a.id != b.id. (3) Finding records that meet some comparative condition relative to other rows: restaurants with a higher rating than some reference restaurant. The key is using two different aliases for the same table so SQL can treat them as separate sources.

JOINs — 60-second revision

  • INNER JOIN: only matching rows in both tables. Non-matching rows dropped.
  • LEFT JOIN: all rows from left table + matching right. Non-matching right → NULL. Most common.
  • RIGHT JOIN: all rows from right table + matching left. Rarely used — flip tables and use LEFT.
  • FULL OUTER JOIN: all rows from both tables. NULLs where no match on either side.
  • Self JOIN: join table to itself with two aliases. Use for hierarchical data (employee-manager).
  • LEFT JOIN + NULL check: find rows in left table with no match in right table (users with no orders).
  • Filter in ON vs WHERE: ON filters during join (LEFT JOIN still keeps all left rows). WHERE filters after (converts LEFT to INNER for filtered rows).
Concept 03 of 07

GROUP BY + Aggregates

The GROUP BY rule every fresher gets wrong. Non-aggregate columns in SELECT must be in GROUP BY. HAVING filters groups. Multiple aggregate functions per query.
must knowGROUP BY errors are the most common SQL mistakes in interviews
01The GROUP BY rule — non-negotiable

The rule: every column in SELECT that is NOT an aggregate function MUST appear in GROUP BY. This is because GROUP BY collapses many rows into one — if you want to show a non-aggregated column, SQL needs to know which value to show (since all rows in a group might have different values for that column).

GROUP BY + HAVING — correct patterns
-- Revenue and order count per restaurant per city
-- All non-aggregate columns (restaurant_id, city, name) must be in GROUP BY
SELECT
    r.id                      AS restaurant_id,   -- in GROUP BY
    r.name                    AS restaurant,      -- in GROUP BY
    r.city,                                         -- in GROUP BY
    COUNT(o.id)               AS total_orders,    -- aggregate ✓
    SUM(o.amount)             AS total_revenue,   -- aggregate ✓
    AVG(o.amount)             AS avg_order_value, -- aggregate ✓
    COUNT(DISTINCT o.user_id) AS unique_customers  -- aggregate ✓
FROM restaurants r
LEFT JOIN orders o
    ON r.id = o.restaurant_id
   AND o.status = 'delivered'
WHERE r.city = 'Bangalore'           -- filter BEFORE grouping
GROUP BY r.id, r.name, r.city        -- all non-aggregates must be here
HAVING COUNT(o.id) > 50              -- filter AFTER grouping
ORDER BY total_revenue DESC;

-- Orders per user per month in 2024
SELECT
    user_id,
    DATE_TRUNC('month', placed_at) AS month,
    COUNT(*) AS orders_this_month,
    SUM(amount) AS monthly_spend
FROM orders
WHERE placed_at >= '2024-01-01'
  AND placed_at < '2025-01-01'
  AND status = 'delivered'
GROUP BY user_id, DATE_TRUNC('month', placed_at)
ORDER BY month, monthly_spend DESC;
GROUP BY with ROLLUP — subtotals and grand totals
-- Revenue by city, with a grand total row
SELECT
    COALESCE(city, 'ALL CITIES') AS city,
    COUNT(*) AS order_count,
    SUM(amount) AS total_revenue
FROM orders o
INNER JOIN restaurants r ON o.restaurant_id = r.id
GROUP BY ROLLUP(city);
-- Result includes: Bangalore row, Mumbai row, and a grand total row
-- Grand total row has NULL for city (use COALESCE to show "ALL CITIES")
Interview Q&A — GROUP BY
Write a query to find the top 5 restaurants by revenue in 2024. ▼
Strong answer SELECT r.id, r.name, SUM(o.amount) AS total_revenue, COUNT(o.id) AS order_count FROM restaurants r INNER JOIN orders o ON r.id = o.restaurant_id WHERE o.status = 'delivered' AND o.placed_at >= '2024-01-01' AND o.placed_at < '2025-01-01' GROUP BY r.id, r.name ORDER BY total_revenue DESC LIMIT 5. Key points: INNER JOIN (only restaurants with orders), WHERE filters before grouping (delivered orders in 2024), GROUP BY on all non-aggregated columns (r.id, r.name), ORDER BY aggregate descending, LIMIT 5. Would mention adding an index on orders(placed_at, status) to optimize the WHERE filter if this is a frequently run report.
What happens if you put a non-aggregate column in SELECT that isn't in GROUP BY? ▼
Strong answerIn strict SQL (PostgreSQL, Oracle): you get an error. "Column must appear in the GROUP BY clause or be used in an aggregate function." MySQL in its default mode allows it and returns an arbitrary value from the group — which is a bug, not a feature. This is why you'll see GROUP BY r.id, r.name even though r.name is functionally determined by r.id (if you know the id, you know the name). The SQL standard requires all non-aggregated SELECT columns to be in GROUP BY. PostgreSQL follows this strictly. Good practice: always include all non-aggregated columns in GROUP BY, even if technically some are functionally dependent — it makes the query portable and intention clear.

GROUP BY — 60-second revision

  • Rule: every non-aggregate SELECT column MUST be in GROUP BY. Aggregate functions (COUNT, SUM, AVG) don't need to be.
  • HAVING: filter groups after aggregation. WHERE: filter rows before. Only HAVING can use aggregate functions in the filter.
  • COUNT(*): all rows including NULLs. COUNT(col): non-NULL values only. COUNT(DISTINCT col): unique non-NULL values.
  • COALESCE(value, default): return first non-NULL value. Use to replace NULL with 0 for SUM of empty groups.
  • DATE_TRUNC('month', timestamp): truncate to month boundary — group by month easily.
Concept 04 of 07

Subqueries + CTEs

Subqueries embed one query inside another. CTEs (WITH clause) give subqueries a name and make complex queries readable. EXISTS vs IN — performance matters.
must knowCTEs are used in almost every real production query
01Subqueries — where they can appear
Subqueries — in WHERE, FROM, SELECT
-- ── Scalar subquery (returns one value) — in SELECT ─────────
SELECT
    r.name,
    r.rating,
    (SELECT AVG(rating) FROM restaurants) AS platform_avg,
    r.rating - (SELECT AVG(rating) FROM restaurants) AS diff_from_avg
FROM restaurants r
ORDER BY diff_from_avg DESC;
-- Runs the subquery once and uses the result in every row

-- ── Subquery in WHERE ─────────────────────────────────────────
-- "Users who spent more than the average order amount"
SELECT DISTINCT user_id
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders WHERE status = 'delivered')
  AND status = 'delivered';

-- IN with subquery
SELECT name FROM users
WHERE id IN (SELECT DISTINCT user_id FROM orders WHERE amount > 1000);

-- ── Derived table (subquery in FROM) ─────────────────────────
-- "Average monthly revenue per restaurant"
SELECT
    restaurant_id,
    AVG(monthly_revenue) AS avg_monthly_revenue
FROM (
    SELECT
        restaurant_id,
        DATE_TRUNC('month', placed_at) AS month,
        SUM(amount) AS monthly_revenue
    FROM orders
    WHERE status = 'delivered'
    GROUP BY restaurant_id, DATE_TRUNC('month', placed_at)
) AS monthly_stats  -- derived tables must have an alias
GROUP BY restaurant_id
ORDER BY avg_monthly_revenue DESC;
02CTEs — WITH clause for readable complex queries
CTEs (Common Table Expressions) — cleaner than nested subqueries
-- Same query as above but with a CTE — much more readable
WITH monthly_revenue AS (
    -- CTE 1: calculate monthly revenue per restaurant
    SELECT
        restaurant_id,
        DATE_TRUNC('month', placed_at) AS month,
        SUM(amount) AS revenue
    FROM orders
    WHERE status = 'delivered'
    GROUP BY restaurant_id, DATE_TRUNC('month', placed_at)
),
restaurant_avg AS (
    -- CTE 2: average over months per restaurant
    SELECT
        restaurant_id,
        AVG(revenue) AS avg_monthly_revenue,
        MAX(revenue) AS best_month_revenue
    FROM monthly_revenue  -- reference the previous CTE!
    GROUP BY restaurant_id
)
-- Final SELECT uses the CTEs like tables
SELECT
    r.name,
    ra.avg_monthly_revenue,
    ra.best_month_revenue
FROM restaurant_avg ra
INNER JOIN restaurants r ON ra.restaurant_id = r.id
ORDER BY ra.avg_monthly_revenue DESC
LIMIT 10;

-- Recursive CTE: walk a hierarchy
WITH RECURSIVE org_tree AS (
    -- Anchor: start with the CEO (no manager)
    SELECT id, name, manager_id, 1 AS level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive: join back to find each person's reports
    SELECT e.id, e.name, e.manager_id, ot.level + 1
    FROM employees e
    INNER JOIN org_tree ot ON e.manager_id = ot.id
)
SELECT * FROM org_tree ORDER BY level, name;
03EXISTS vs IN — when performance matters
EXISTS vs IN — performance difference
-- IN: evaluates the subquery, builds a list, checks membership
SELECT name FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 5000);

-- EXISTS: checks if any row exists. Stops as soon as one is found.
SELECT name FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders WHERE user_id = u.id AND amount > 5000
);
-- EXISTS uses a correlated subquery (references the outer query's 'u.id')
-- SELECT 1 — content doesn't matter, we just check if a row EXISTS

-- When to use which:
-- EXISTS: better when outer table is small, inner is large.
-- EXISTS: better when you just need to know "does at least one row match?"
-- IN: fine for small subquery result sets.
-- NOT IN with NULLs in subquery: NEVER returns rows (NULL comparison issue)
-- Always prefer NOT EXISTS over NOT IN to avoid NULL trap.
Interview Q&A — Subqueries
What is a CTE? How is it different from a subquery? ▼
Strong answerA CTE (Common Table Expression) is a named temporary result set defined with the WITH clause, referenced in the subsequent query. Like a derived table (subquery in FROM), but: (1) defined before the main query, not inline — much more readable for complex logic; (2) can be referenced multiple times in the same query (a subquery in FROM can only be used once); (3) supports recursion (WITH RECURSIVE) for hierarchical data. A subquery is embedded directly within another query — harder to read when nested deeply. Use CTE when: the query needs multiple steps of transformation (CTE 1 → CTE 2 → final SELECT), or when the same intermediate result is needed in multiple places, or when you want self-documenting named steps.
What is the NOT IN NULL trap? How do you avoid it? ▼
Strong answerNOT IN breaks when the subquery returns any NULL values. Example: SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders). If any order has user_id = NULL (orphan record), the entire NOT IN evaluates to UNKNOWN for every row — returns 0 results. This is because NOT IN checks id != NULL for every value in the list, and NULL != anything returns NULL (unknown), which is falsy. Fix: WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL). Better fix: use NOT EXISTS instead — it handles NULLs correctly. NOT EXISTS returns no row if the correlated subquery finds anything (including NULLs treated as existing rows). This is one of the most subtle SQL bugs — worth mentioning in interviews to show SQL depth.

Subqueries + CTEs — 60-second revision

  • Subquery locations: WHERE (filtering), FROM (derived table), SELECT (scalar value per row).
  • CTE (WITH clause): named subquery, referenced in subsequent query. Readable, can be referenced multiple times.
  • Recursive CTE: WITH RECURSIVE. Anchor + recursive step + UNION ALL. Walks hierarchies.
  • EXISTS: correlated subquery, stops on first match. Better for large inner tables.
  • IN: builds result list, checks membership. Fine for small lists.
  • NOT IN + NULL trap: if subquery returns any NULL, NOT IN returns no rows. Use NOT EXISTS or add IS NOT NULL filter.
Concept 05 of 07

Window Functions

Window functions perform calculations across a set of rows related to the current row — without collapsing the result into one row per group (unlike GROUP BY). ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, running totals.
must knowWindow functions separate good SQL writers from the rest — always asked
01The key difference: OVER() — no row collapsing

Regular aggregate functions (SUM, COUNT, AVG) with GROUP BY collapse many rows into one per group. Window functions use OVER() — they calculate across related rows but each row keeps its own line in the output. You can have the aggregate AND the original row detail simultaneously.

OVER() — the syntax and how it works
-- aggregate_function() OVER (PARTITION BY ... ORDER BY ...)

-- PARTITION BY: like GROUP BY for the window — defines the "group" for each calculation
-- ORDER BY: within the partition, how to order rows (for ranking and running calculations)

-- Without PARTITION BY: window is the entire result set
-- With PARTITION BY: window restarts for each unique value of the partition column

SELECT
    id,
    restaurant_id,
    amount,
    placed_at,
    -- Running total of revenue for each restaurant (resets per restaurant)
    SUM(amount) OVER (
        PARTITION BY restaurant_id
        ORDER BY placed_at
    ) AS running_total,
    -- Percentage of restaurant's total for this order
    ROUND(
        amount * 100.0 / SUM(amount) OVER (PARTITION BY restaurant_id),
        2
    ) AS pct_of_restaurant_total,
    -- Total orders for this restaurant (same for every row in partition)
    COUNT(*) OVER (PARTITION BY restaurant_id) AS restaurant_order_count
FROM orders
WHERE status = 'delivered'
ORDER BY restaurant_id, placed_at;
02Ranking functions — ROW_NUMBER, RANK, DENSE_RANK
Ranking — top N per group (the most common window function pattern)
-- "Top 3 highest-value orders per restaurant"
WITH ranked_orders AS (
    SELECT
        id,
        restaurant_id,
        user_id,
        amount,
        ROW_NUMBER() OVER (
            PARTITION BY restaurant_id
            ORDER BY amount DESC
        ) AS row_num
    FROM orders
    WHERE status = 'delivered'
)
SELECT * FROM ranked_orders
WHERE row_num <= 3;  -- can now filter on window function result

-- ROW_NUMBER vs RANK vs DENSE_RANK — the difference:
-- Amounts:  [1000, 1000, 800, 700]
-- ROW_NUMBER:   1, 2, 3, 4      (always unique, arbitrary for ties)
-- RANK:         1, 1, 3, 4      (tied values get same rank, then skip)
-- DENSE_RANK:   1, 1, 2, 3      (tied values get same rank, NO skip)

SELECT
    restaurant_id,
    amount,
    ROW_NUMBER()  OVER (PARTITION BY restaurant_id ORDER BY amount DESC) AS rn,
    RANK()        OVER (PARTITION BY restaurant_id ORDER BY amount DESC) AS rnk,
    DENSE_RANK()  OVER (PARTITION BY restaurant_id ORDER BY amount DESC) AS drnk
FROM orders WHERE status = 'delivered';
03LAG and LEAD — access adjacent rows
LAG / LEAD — compare to previous or next row
-- "For each order, show the previous order amount for that user"
-- LAG: look back at previous row's value
-- LEAD: look forward at next row's value
SELECT
    id,
    user_id,
    amount,
    placed_at,
    LAG(amount, 1, 0) OVER (
        PARTITION BY user_id
        ORDER BY placed_at
    ) AS prev_order_amount,
    -- LAG(column, offset, default_if_no_prev)
    amount - LAG(amount, 1, amount) OVER (
        PARTITION BY user_id
        ORDER BY placed_at
    ) AS change_from_prev
FROM orders
WHERE status = 'delivered'
ORDER BY user_id, placed_at;

-- NTILE: divide into N roughly equal buckets
SELECT
    user_id,
    SUM(amount) AS total_spend,
    NTILE(4) OVER (ORDER BY SUM(amount) DESC) AS quartile
    -- 1 = top 25%, 4 = bottom 25% (quartile based on total spend)
FROM orders
WHERE status = 'delivered'
GROUP BY user_id;
-- Note: NTILE goes OVER grouped result — combine window with GROUP BY
Interview Q&A — Window Functions
What is the difference between window functions and GROUP BY? ▼
Strong answerGROUP BY collapses multiple rows into one row per group — you lose individual row detail. Window functions (using OVER()) perform calculations across related rows but EACH ROW KEEPS ITS OWN LINE in the result. Example: GROUP BY restaurant_id with SUM(amount) gives one revenue total per restaurant. A window function SUM(amount) OVER(PARTITION BY restaurant_id) shows every order with the restaurant's total alongside it. This lets you do things like: "what percentage of this restaurant's total revenue does this single order represent?" — impossible with GROUP BY alone. PARTITION BY in window functions is like GROUP BY — it defines the grouping for the calculation — but doesn't collapse rows. ORDER BY in OVER() enables ordered calculations like running totals, rankings, and LAG/LEAD.
Write a query to find the top 3 customers by spend per city. ▼
Strong answerWITH customer_spend AS (SELECT u.city, u.id AS user_id, u.name, SUM(o.amount) AS total_spend FROM users u INNER JOIN orders o ON u.id = o.user_id WHERE o.status = 'delivered' GROUP BY u.city, u.id, u.name), ranked AS (SELECT city, user_id, name, total_spend, DENSE_RANK() OVER (PARTITION BY city ORDER BY total_spend DESC) AS rank FROM customer_spend) SELECT city, name, total_spend, rank FROM ranked WHERE rank <= 3 ORDER BY city, rank. Key decisions: DENSE_RANK so ties get same rank without skipping numbers; PARTITION BY city so ranking resets per city; CTE for readability (two steps: aggregate then rank); WHERE on the rank in outer query since window functions can't be in WHERE directly.

Window Functions — 60-second revision

  • Window functions: calculate across rows related to current row. No row collapsing. Each row keeps its line.
  • Syntax: function() OVER (PARTITION BY col ORDER BY col). PARTITION BY = "group", ORDER BY = sequence.
  • ROW_NUMBER: unique sequential number. RANK: same rank for ties, skips next. DENSE_RANK: same rank for ties, no skip.
  • Top N per group: ROW_NUMBER() OVER(PARTITION BY group ORDER BY col DESC) in CTE, then WHERE row_num <= N.
  • LAG(col, offset, default): previous row's value. LEAD: next row's value. For comparing adjacent rows.
  • Running total: SUM(amount) OVER(PARTITION BY x ORDER BY date) — accumulates in order.

01Creating and using indexes correctly
Index creation — patterns that work and patterns that don't
-- Single column index: for frequently filtered columns
CREATE INDEX idx_orders_user_id    ON orders(user_id);
CREATE INDEX idx_orders_placed_at  ON orders(placed_at);
CREATE INDEX idx_orders_status     ON orders(status);

-- Composite index: column ORDER matters (leftmost prefix rule)
CREATE INDEX idx_orders_user_date  ON orders(user_id, placed_at);
-- Helps: WHERE user_id = 5                      (prefix: user_id)
-- Helps: WHERE user_id = 5 AND placed_at > '2024-01-01'
-- Does NOT help: WHERE placed_at > '2024-01-01' (not leftmost)
-- Design: most selective column FIRST

-- Partial index: only index a subset of rows
CREATE INDEX idx_active_orders ON orders(placed_at)
WHERE status = 'pending';
-- Smaller index — only pending orders indexed
-- Useful when you almost always filter by status first

-- Functional index: index on an expression
CREATE INDEX idx_lower_email ON users(LOWER(email));
-- Allows: WHERE LOWER(email) = 'ravi@gmail.com' to use the index
-- Without this, LOWER(email) in WHERE → full table scan

-- EXPLAIN ANALYZE: see how a query actually executes
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id = 42 AND status = 'delivered';
-- Look for: "Seq Scan" (bad) vs "Index Scan" or "Bitmap Index Scan" (good)
-- Also: "actual time", "rows", "Execution Time" at the bottom
02When indexes aren't used — the gotchas
Patterns that break index usage
-- GOTCHA 1: Function on the indexed column
-- Index on placed_at (timestamp)
SELECT * FROM orders WHERE DATE_TRUNC('month', placed_at) = '2024-01-01';
-- → Full scan! The function changes the column value, breaking the index.
-- Fix: use range instead
SELECT * FROM orders
WHERE placed_at >= '2024-01-01' AND placed_at < '2024-02-01';
-- → Index scan! Range queries work with B-tree indexes

-- GOTCHA 2: Leading wildcard in LIKE
SELECT * FROM restaurants WHERE name LIKE '%Biryani%';
-- → Full scan! B-tree can't search from unknown start.
-- Fix: use full-text search index, or store name in both directions
SELECT * FROM restaurants WHERE name LIKE 'Biryani%';  -- prefix can use index

-- GOTCHA 3: Type mismatch
SELECT * FROM users WHERE id = '42';  -- id is INT, '42' is varchar
-- PostgreSQL will cast and still use index (sometimes)
-- MySQL may not — always use the correct type

-- GOTCHA 4: OR conditions
SELECT * FROM orders WHERE user_id = 5 OR restaurant_id = 10;
-- May not use indexes efficiently — OR conditions are complex for planners
-- Fix: UNION ALL
SELECT * FROM orders WHERE user_id = 5
UNION ALL
SELECT * FROM orders WHERE restaurant_id = 10 AND user_id != 5;

Indexes — 60-second revision

  • Composite index: leftmost prefix rule. (a, b, c) helps WHERE a, WHERE a+b, WHERE a+b+c. Not WHERE b alone.
  • Partial index: CREATE INDEX ... WHERE condition. Smaller, faster for known filter patterns.
  • Functional index: CREATE INDEX ON (LOWER(email)) — allows LOWER(email) in WHERE to use index.
  • EXPLAIN ANALYZE: check for "Seq Scan" (bad) vs "Index Scan" (good). Also check "actual rows" vs "estimated rows".
  • Index killers: function on column (use range instead), leading LIKE wildcard, type mismatch.

Transactions + Locking in SQL

BEGIN, COMMIT, ROLLBACK. SAVEPOINT. SELECT FOR UPDATE (pessimistic locking). Isolation levels in practice. How to implement a safe bank transfer in SQL.
must knowWrite a safe bank transfer in SQL — asked at every fintech interview
01Transaction syntax and atomicity
Basic transaction — bank transfer
-- Ravi sends ₹500 to Priya
BEGIN;  -- or START TRANSACTION

-- Step 1: Check balance
SELECT balance FROM accounts
WHERE user_id = 'ravi' FOR UPDATE;
-- FOR UPDATE: acquires exclusive row lock
-- Other transactions trying to touch this row → BLOCK until we COMMIT

-- Step 2: Debit Ravi
UPDATE accounts
SET balance = balance - 500
WHERE user_id = 'ravi'
  AND balance >= 500;  -- safe debit: only succeeds if funds available

-- Step 3: Verify the debit happened (1 row affected)
-- In application code: check ROW_COUNT / rowsAffected
-- If 0 rows: insufficient funds → ROLLBACK

-- Step 4: Credit Priya
UPDATE accounts
SET balance = balance + 500
WHERE user_id = 'priya';

-- Step 5: Log the transaction
INSERT INTO transaction_log(from_user, to_user, amount, created_at)
VALUES ('ravi', 'priya', 500, NOW());

COMMIT;  -- All three changes committed atomically
-- If any step fails: ROLLBACK undoes ALL changes since BEGIN
02SAVEPOINT — partial rollback
SAVEPOINT — rollback to a specific point, not all the way to BEGIN
BEGIN;

INSERT INTO orders(user_id, restaurant_id, amount) VALUES (1, 10, 500);

SAVEPOINT after_order;  -- save current state

UPDATE inventory SET stock = stock - 1 WHERE item_id = 42;
-- Suppose this fails: item out of stock

ROLLBACK TO after_order;  -- undo only the inventory update
-- The order INSERT is still there, we're back to after_order state

-- Can try alternative inventory logic here
INSERT INTO backorder(item_id, order_id) VALUES (42, LASTVAL());

COMMIT;  -- commits: the order + the backorder entry
03Setting isolation level + read committed vs repeatable read
Isolation levels in PostgreSQL
-- Set isolation level for the current transaction
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT * FROM accounts WHERE user_id = 'ravi';
-- All reads in this transaction see data as of transaction start
-- Even if another transaction updates ravi's balance and commits,
-- our reads here will still see the old value (snapshot isolation)

COMMIT;

-- Default in PostgreSQL: READ COMMITTED
-- Each statement sees latest committed data
-- Two reads of same row in same transaction CAN give different results

-- SERIALIZABLE: strongest — transactions execute as if serial
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- PostgreSQL uses Serializable Snapshot Isolation (SSI)
-- Detects serialization conflicts and aborts one transaction
-- Application must retry aborted transaction

Interview Q&A — Transactions
Write a safe bank transfer query. What could go wrong and how do you prevent it? ▼
Strong answerBEGIN; SELECT balance FROM accounts WHERE id = ravi_id FOR UPDATE; — the FOR UPDATE acquires an exclusive row lock, preventing concurrent transactions from modifying Ravi's balance. Then UPDATE accounts SET balance = balance - 500 WHERE id = ravi_id AND balance >= 500 — the AND balance >= 500 ensures we don't go negative even if a concurrent transaction snuck through. Check rows affected — if 0, insufficient funds, ROLLBACK. Then UPDATE accounts SET balance = balance + 500 WHERE id = priya_id; COMMIT. What could go wrong: (1) Race condition without FOR UPDATE — two simultaneous transfers both read balance 1000, both subtract, resulting in wrong final balance. (2) Deadlock — if two transfers simultaneously lock accounts in opposite order. Fix: always lock accounts in the same order (by account ID). (3) Crash between debit and credit — solved by the transaction: incomplete transactions are rolled back on recovery.
What is SELECT FOR UPDATE? What is the difference from a regular SELECT? ▼
Strong answerRegular SELECT: acquires a shared (read) lock — multiple transactions can read simultaneously, but none block each other. SELECT FOR UPDATE: acquires an exclusive lock on the selected rows. Other transactions trying to SELECT FOR UPDATE or UPDATE these rows must WAIT until the lock is released (at COMMIT or ROLLBACK). Regular SELECT doesn't block writers in PostgreSQL (MVCC means readers and writers don't block each other for regular reads). SELECT FOR UPDATE is used for read-modify-write patterns where you must guarantee no concurrent modification between your read and write — classic example: check balance, deduct, credit. Without FOR UPDATE, two transactions could both read the balance before either modifies it, causing incorrect double-spending. The lock is held until COMMIT or ROLLBACK.

Transactions — 60-second revision

  • BEGIN / START TRANSACTION → COMMIT (persist) or ROLLBACK (undo all changes).
  • SAVEPOINT name → ROLLBACK TO name: partial rollback, keep earlier changes.
  • SELECT FOR UPDATE: exclusive row lock. Other transactions block until COMMIT. Use for read-modify-write patterns.
  • Safe bank transfer: BEGIN → SELECT FOR UPDATE → UPDATE with balance check → verify rows affected → UPDATE other account → INSERT log → COMMIT.
  • Isolation levels: READ COMMITTED (default PostgreSQL) → REPEATABLE READ (default MySQL) → SERIALIZABLE.
  • Deadlock prevention: always acquire locks in the same fixed order (sort by account ID). DB auto-detects with timeout + rollback.

All SQL Interview Questions

20 questions — from basics to window functions. Answer out loud without looking. Interviewers often give you a schema and ask you to write queries on the spot.
Complete SQL Q&A bank — 20 questions
1. In what order does SQL execute? Why does it matter? ▼
AnswerFROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Matters because: (1) Can't use SELECT aliases in WHERE (SELECT runs later). (2) Can't use aggregates in WHERE (no grouping yet). (3) HAVING exists because WHERE can't filter on aggregated values. (4) Can use SELECT aliases in ORDER BY (SELECT already ran). Understanding this explains most SQL errors and helps you write correct queries without trial and error.
2. What is the difference between WHERE and HAVING? ▼
AnswerWHERE filters individual rows BEFORE grouping — cannot use aggregate functions. HAVING filters groups AFTER GROUP BY — can use aggregate functions. Example: WHERE status = 'delivered' (row-level filter). HAVING COUNT(*) > 100 (group-level filter — only restaurants with more than 100 orders). If you put the aggregate condition in WHERE → SQL error. Performance: WHERE is more efficient — reduces rows before aggregation, less data to process.
3. What is the difference between INNER JOIN and LEFT JOIN? ▼
AnswerINNER JOIN: only rows where the condition matches in BOTH tables. Non-matching rows dropped. LEFT JOIN: all rows from the left table + matching rows from right. Unmatched right columns = NULL. Use LEFT JOIN when you need all records from one table even without matches (all restaurants including those with zero orders). Find non-matching: LEFT JOIN + WHERE right.id IS NULL → rows with no match on right side (users with no orders). Never use RIGHT JOIN — flip tables and use LEFT JOIN instead.
4. Write a query to find users who have never placed an order. ▼
AnswerMethod 1 (LEFT JOIN + IS NULL): SELECT u.id, u.name FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.id IS NULL. Method 2 (NOT EXISTS): SELECT id, name FROM users u WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id). Method 3 (NOT IN — careful): SELECT id, name FROM users WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL). NOT IN requires the IS NOT NULL — if any order has NULL user_id, NOT IN returns zero results (NULL comparison trap). LEFT JOIN + IS NULL or NOT EXISTS are preferred.
5. What is the GROUP BY rule for non-aggregate columns? ▼
AnswerEvery column in SELECT that is NOT an aggregate function MUST appear in GROUP BY. This is because GROUP BY collapses many rows into one per group — if a non-aggregated column could have different values within a group, SQL doesn't know which value to show. PostgreSQL enforces this strictly (error if violated). MySQL's default mode allows it and returns arbitrary values (a bug, not a feature). Practical example: SELECT r.id, r.name, r.city, COUNT(o.id) FROM restaurants r LEFT JOIN orders o ON r.id = o.restaurant_id GROUP BY r.id, r.name, r.city — all three non-aggregated columns in GROUP BY.
6. What is a CTE? How is it different from a subquery? ▼
AnswerCTE (Common Table Expression): named temporary result set defined with WITH clause, referenced in the subsequent query. vs Subquery: subquery is embedded inline; CTE is defined before the main query — more readable. CTE advantages: (1) Named — self-documenting. (2) Can be referenced multiple times in same query. (3) Supports recursion (WITH RECURSIVE) for hierarchical data. Use CTE for: multi-step transformations (CTE1 → CTE2 → final SELECT), when same intermediate result needed multiple places, or when you want clearly labeled steps. Performance: in PostgreSQL, CTEs are "optimization fences" by default — the planner treats them as black boxes. Add MATERIALIZED or NOT MATERIALIZED hint to control this in PG 12+.
7. What is the difference between ROW_NUMBER, RANK, and DENSE_RANK? ▼
AnswerAll are window functions for ranking. Given values [1000, 1000, 800, 700]: ROW_NUMBER: 1, 2, 3, 4 — always unique sequential numbers, arbitrary for ties. RANK: 1, 1, 3, 4 — tied values share the same rank, then the count skips (no rank 2). DENSE_RANK: 1, 1, 2, 3 — tied values share the same rank, next rank is consecutive (no gap). Use ROW_NUMBER for top-N per group (want exactly N results even for ties). Use RANK/DENSE_RANK when ties should be equally ranked (sports leaderboard: two tied for 1st, both get rank 1). DENSE_RANK when you don't want gaps in rankings.
8. Write a query to get the top 3 orders per restaurant. ▼
AnswerWITH ranked AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY restaurant_id ORDER BY amount DESC) AS rn FROM orders WHERE status = 'delivered') SELECT restaurant_id, id, amount, user_id FROM ranked WHERE rn <= 3 ORDER BY restaurant_id, amount DESC. Key points: ROW_NUMBER() because we want exactly 3 per restaurant even for ties; PARTITION BY restaurant_id resets ranking per restaurant; ORDER BY amount DESC ranks by highest first; CTE needed because you can't filter on window function in WHERE directly (window functions run in SELECT phase); final WHERE rn <= 3 in outer query filters to top 3 per restaurant.
9. What is a self JOIN? Give a practical use case. ▼
AnswerA self join joins a table to itself using two different aliases. Used when rows in a table have relationships to other rows in the same table. Classic use case: employee-manager hierarchy. employees table has manager_id referencing another row in the same table. Query: SELECT emp.name AS employee, mgr.name AS manager FROM employees emp LEFT JOIN employees mgr ON emp.manager_id = mgr.id. LEFT JOIN because the top-level employee (CEO) has no manager — INNER JOIN would exclude them. The a.id < b.id trick eliminates duplicate pairs (a,b) and (b,a) when finding pairs within the same table.
10. Why does `NOT IN` with NULLs in the subquery return no rows? ▼
AnswerSQL uses three-valued logic: TRUE, FALSE, and UNKNOWN (for NULL comparisons). NOT IN (a, b, NULL) expands to: id != a AND id != b AND id != NULL. id != NULL evaluates to UNKNOWN (not TRUE). In a WHERE clause, UNKNOWN is treated as FALSE — the row is filtered out. So every row fails the NOT IN check and returns 0 results. This is a silent, dangerous bug. Fix: always add WHERE user_id IS NOT NULL to the subquery. Better: use NOT EXISTS which handles NULLs correctly — it checks for the existence of rows, treating NULLs as existing rows properly.
11. What is SELECT FOR UPDATE? When do you use it? ▼
AnswerSELECT FOR UPDATE acquires an exclusive row lock on the selected rows. Other transactions trying to SELECT FOR UPDATE or UPDATE those rows must wait until the lock is released. Use for read-modify-write patterns where data consistency between the read and the write is critical. Example: bank transfer. Read Ravi's balance (FOR UPDATE locks his row), compute new balance, write it back. Without FOR UPDATE: two concurrent transfers could both read balance=1000 before either writes, both deduct, final balance is wrong. The lock prevents any concurrent modification. Lock is held until COMMIT or ROLLBACK. Note: regular SELECT in PostgreSQL (MVCC) doesn't block writers — only SELECT FOR UPDATE acquires exclusive locks.
12. What is the difference between offset-based and cursor-based pagination? ▼
AnswerOffset-based: LIMIT 20 OFFSET 100. Simple but slow for large offsets — DB scans and discards the first 100 rows on every page request. At page 500 of 20 items, it scans 10,000 rows to discard them. Also inconsistent with inserts/deletes (items can shift pages). Cursor-based (keyset pagination): WHERE placed_at < last_seen_value ORDER BY placed_at DESC LIMIT 20. Always fast regardless of page depth — uses an index on placed_at, no rows scanned and discarded. Consistent — new items don't shift existing items. Limitation: can only paginate in one direction (forward or backward, not jump to arbitrary page). Use keyset for large datasets, infinite scroll. Use offset for small datasets or when jumping to arbitrary pages is needed.
13. What is a running total? How do you write it using window functions? ▼
AnswerA running total accumulates a value across rows in order. Using window function: SUM(amount) OVER (PARTITION BY user_id ORDER BY placed_at). PARTITION BY resets the total per user. ORDER BY placed_at defines the order of accumulation — each row's running total includes its own amount plus all previous rows for that user. By default, the window frame is "ROWS UNBOUNDED PRECEDING TO CURRENT ROW" — accumulates up to and including the current row. Without ORDER BY: SUM calculates the total of the entire partition (all rows), not a running total. With ORDER BY: running accumulation. This is the most common window function pattern for analytics (cumulative revenue, running balance).
14. What is a FULL OUTER JOIN? When would you use it? ▼
AnswerFULL OUTER JOIN returns all rows from both tables. Where there's no match on either side, the other table's columns are NULL. It's the union of LEFT JOIN and RIGHT JOIN. Use when you need to find rows that exist in either table with or without a match in the other. Example: reconciliation report — find transactions that exist in your internal DB but not in the bank's records (and vice versa). Or: compare two sets of data to find what's unique to each. In practice, less common than INNER or LEFT JOIN — most queries have a clear "primary" table you want all rows from (use LEFT JOIN). FULL OUTER JOIN is for when both directions matter equally.
15. What is the difference between UNION and UNION ALL? ▼
AnswerUNION: combines results of two queries and removes duplicates. Equivalent to UNION ALL + DISTINCT. Slower because it must sort or hash results to identify and remove duplicates. UNION ALL: combines results without removing duplicates. Faster — no deduplication step. Use UNION when you genuinely need distinct rows and the same row might appear in both queries. Use UNION ALL when: you know there are no duplicates (the queries are on different data), or you want all rows including duplicates, or performance matters. In practice, UNION ALL is usually correct and faster — UNION is rarely needed if your queries are well-designed. Requirements: same number of columns, compatible data types in each position.
16. How would you calculate the percentage of total in SQL? ▼
AnswerUsing a window function: amount * 100.0 / SUM(amount) OVER (PARTITION BY restaurant_id) AS pct_of_restaurant_total. OVER(PARTITION BY restaurant_id) computes the total for each restaurant while keeping all individual rows. Each row then has both its individual amount and the total to compute percentage. Alternative with subquery or CTE: compute the total separately, then join and divide. Window function is cleaner. The 100.0 (not 100) is important — integer division in SQL truncates. 500 / 2500 = 0. 500 * 100.0 / 2500 = 20.0. Use ROUND(pct, 2) for cleaner output.
17. What is the purpose of COALESCE? ▼
AnswerCOALESCE(v1, v2, ..., vn) returns the first non-NULL value in its argument list. Use cases: (1) Replace NULL with a default: COALESCE(SUM(amount), 0) — LEFT JOIN might produce NULL for restaurants with no orders; COALESCE converts to 0. (2) Fallback values: COALESCE(preferred_name, nickname, first_name, 'Unknown'). (3) ROLLUP grand total label: COALESCE(city, 'ALL CITIES') — ROLLUP produces NULL for the totals row. vs NULLIF(value, other): returns NULL if value = other, else returns value. Useful for avoiding division by zero: amount / NULLIF(quantity, 0) — returns NULL instead of error when quantity is 0. ISNULL and IFNULL are MySQL-specific equivalents — COALESCE is standard SQL.
18. What is the difference between TRUNCATE and DELETE? ▼
AnswerDELETE: removes rows one at a time. Can have a WHERE clause to remove specific rows. Writes to transaction log for every deleted row — can be rolled back. Slow for large tables. Fires DELETE triggers. TRUNCATE: removes all rows at once by deallocating the data pages. Much faster — doesn't log individual row deletions. Cannot have a WHERE clause. In PostgreSQL: TRUNCATE can be rolled back (it's within a transaction). In MySQL: TRUNCATE is DDL and cannot be rolled back. Resets SERIAL/AUTO_INCREMENT counters (DELETE doesn't). Doesn't fire row-level triggers. Use DELETE when: you need a WHERE clause, you need row-level logging, or you need triggers to fire. Use TRUNCATE when: clearing a whole table and speed matters.
19. Write a query to find the second-highest salary in a table. ▼
AnswerMethod 1 (DENSE_RANK — handles ties correctly): WITH ranked AS (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees) SELECT DISTINCT salary FROM ranked WHERE rnk = 2. Method 2 (subquery): SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees). Method 3 (LIMIT/OFFSET): SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1. DENSE_RANK is the most robust — handles the case where multiple employees share the highest salary. The DISTINCT in method 1 handles multiple employees at the second-highest level. Method 2 fails if there's only one distinct salary. LIMIT/OFFSET approach is simple but doesn't handle ties correctly if multiple people share the 2nd highest salary.
20. How do you detect and remove duplicate rows? ▼
AnswerFind duplicates: SELECT email, COUNT(*) as cnt FROM users GROUP BY email HAVING COUNT(*) > 1. This shows which emails appear more than once. Find the full duplicate rows: SELECT * FROM users WHERE email IN (SELECT email FROM users GROUP BY email HAVING COUNT(*) > 1) ORDER BY email. Delete keeping one (keep lowest id): DELETE FROM users WHERE id NOT IN (SELECT MIN(id) FROM users GROUP BY email). Or using CTE with ROW_NUMBER: WITH ranked AS (SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM users) DELETE FROM users WHERE id IN (SELECT id FROM ranked WHERE rn > 1). The ROW_NUMBER approach is safer — you explicitly define which duplicate to keep (by ordering within the partition).
